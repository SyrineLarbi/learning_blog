Kubernetes manifests in practice

The five objects that run a service, and the fields that matter
DEPLOYMENT   the desired state: which image, how many replicas,
             and how to replace them.
  ⭐ THE FIELDS PEOPLE OMIT AND THEN REGRET:
    · RESOURCE REQUESTS AND LIMITS. Requests decide where the
      pod is scheduled; limits decide when it is throttled or
      killed. ⚠ NO REQUESTS MEANS THE SCHEDULER IS GUESSING,
      and one noisy pod starves its neighbours.
    · LIVENESS vs READINESS PROBES — two different questions.
      Liveness: "restart me." Readiness: "stop sending me
      traffic." ⭐ CONFLATING THEM PRODUCES A RESTART LOOP: an
      app that is alive but not yet connected to the database
      gets killed before it can become ready.
    · a rolling-update strategy with maxUnavailable/maxSurge
    · TERMINATION GRACE and a preStop hook, or in-flight
      requests die on every deploy

SERVICE      a stable name and virtual IP in front of the pods.
             ClusterIP for internal, and that is what you want
             for the backend and AI service.

CONFIGMAP    non-secret configuration.
SECRET       ⚠ base64, NOT encryption. It is access-controlled,
             not encrypted at rest by default — treat it as
             "not in the repo" rather than "safe".

INGRESS      how traffic from outside reaches a service —
             hostname and path routing, and TLS. See topic 28.

HPA — HORIZONTAL POD AUTOSCALER, at zero prior coverage
  scales replicas on a metric, usually CPU.
  ⚠ AND THE THREE REASONS IT DISAPPOINTS:
    ① ⭐ CPU IS THE WRONG SIGNAL FOR AN I/O-BOUND WEB SERVICE.
      A Node API waiting on the database is not CPU-busy, so it
      never scales — while being slow.
    ② SCALING UP MULTIPLIES DATABASE CONNECTIONS. Ten replicas
      with a pool of ten is a hundred connections, which
      Postgres will refuse long before CPU is interesting.
    ③ WITHOUT RESOURCE REQUESTS, HPA HAS NO BASELINE and does
      nothing useful.
  ⇒ SO: request-rate or queue-depth metrics, a pooler in front
    of the database, and sensible min/max replicas.

⭐ AND THE HONEST JUDGEMENT: THREE SERVICES DO NOT JUSTIFY
  KUBERNETES. It is a platform you operate, not a tool you use,
  and its real cost is ongoing expertise. Knowing the manifests
  matters because enterprises run it — being able to say "we
  did not need this" matters more.
Topic 28 · two prior sentences

Traefik and ingress routing

The layer this adds

A reverse proxy is described as "it routes traffic". The layer underneath is what it terminates, what it rewrites, and what it must preserve — because most proxy bugs are one of those three.

The mechanism
  • It terminates TLS. Certificates live at the proxy, renewed automatically; traffic behind it is usually plain HTTP inside the network. So certificate expiry — the entirely preventable 3 a.m. outage — is a proxy concern, and monitoring it is not optional.
  • Routing rules match on host, path prefix and headers, then forward to a service. Traefik's distinguishing trait is dynamic configuration: it discovers services from labels or CRDs rather than from a static file, so adding a service does not mean editing the proxy.
  • Middleware chains do the cross-cutting work: redirect HTTP to HTTPS, strip a path prefix, add security headers, rate-limit, basic auth, compress.
  • What it must preserve: the original client IP and protocol, via the forwarded headers. Without them your logs record the proxy's IP and your app thinks every request is HTTP — which breaks rate limiting, audit logs and any redirect logic.
  • Sticky sessions, which is the setting that makes Socket.io's polling fallback work behind multiple replicas — the missing piece from Volume 03.
  • WebSocket upgrades need to be allowed through, and long-lived connections need a timeout longer than the default, or your realtime connection drops every sixty seconds.
Where it goes wrong
  • Path-prefix stripping mismatches — the app receives /api/api/employees or loses the prefix entirely. The most common ingress bug.
  • Trusting forwarded headers from an untrusted source, which lets a client spoof its own IP. Only trust them from your own proxy.
  • Certificate renewal that was never tested, discovered on expiry day.
  • A timeout shorter than a legitimate long request — a report download that dies at thirty seconds with no error anywhere.
  • No health check at the proxy, so it routes to a starting or broken instance.
The question you must be able to answer

"Your WebSocket connects and then drops after a minute, only in production." — a proxy idle-timeout on the upgraded connection, or a missing upgrade allowance. Naming the proxy as the suspect rather than the application is the answer.

Topic 29 · ~60 concept lines prior

Turborepo and monorepo engineering

The layer this adds

The idea is usually described as "shared code in one repo". The engineering underneath is a task graph with a content-addressed cache — and everything useful or frustrating about it follows from that.

The mechanism
  • Tasks form a dependency graph. You declare that build depends on the build of upstream packages, and the runner orders and parallelises accordingly. That ordering is the actual product.
  • The cache is keyed by a hash of inputs — source files, dependencies, environment variables, the task definition. Same inputs, cached output, restored instantly instead of rebuilt. A remote cache shares that between CI runs and machines, which is where the large wins are.
  • Only what changed rebuilds. Change the frontend and the backend's build is a cache hit — which is what makes a monorepo CI tolerable.
  • Shared internal packages — types, a validation schema, an API client — are the reason to do this at all: one Zod schema shared by the frontend and the backend means the contract cannot drift.
  • Task outputs must be declared, or the cache restores nothing and silently does no work.
Where it goes wrong
  • Undeclared inputs. A task reads an environment variable or a file that is not in its hash inputs, so a stale cached result is restored and you get a "works locally, wrong in CI" mystery. This is the defining Turborepo bug.
  • Undeclared outputs, so caching appears configured and achieves nothing.
  • A circular package dependency, which the graph refuses — usually a sign a third shared package is missing.
  • Everything in one shared package, so touching anything invalidates everything and the cache stops helping.
  • Version drift between apps in the same repo, which is one of the problems a monorepo was supposed to remove.
The question you must be able to answer

"Your build passes locally and fails in CI with the same commit. Where do you look?" — an undeclared cache input, or an environment variable present in one place and not the other. And the general form: a cache is only correct if its key includes everything the task reads.

Vercel and deployment topology

What is running where, and the constraints that follow
THE TOPOLOGY OF THIS PROJECT, SAID PRECISELY
  frontend   Next.js — static assets on a CDN, server
             components and route handlers as serverless
             functions
  backend    NestJS — a long-running container. ⚠ NOT
             serverless-friendly: it holds connections, has
             startup cost, and expects to stay alive
  AI service FastAPI — a container, and the model must load
             ONCE at startup rather than per request
  database   managed Postgres with a POOLER in front

⭐ THE CONSTRAINT THAT DECIDES THE SHAPE: SERVERLESS FUNCTIONS
  AND A RELATIONAL DATABASE FIGHT EACH OTHER.
  a hundred concurrent function instances each open their own
  connections and exhaust Postgres while using almost no CPU.
  ⇒ SO: a pooled connection string, and prefer containers for
    anything holding state or connections.

THE OTHER VERCEL-SPECIFIC FACTS WORTH KNOWING
  · PREVIEW DEPLOYMENTS PER PULL REQUEST — ⭐ genuinely
    valuable: a reviewer clicks the change instead of imagining
    it, which catches a class of problem no test does
  · ENVIRONMENT VARIABLES ARE PER-ENVIRONMENT, and anything
    prefixed for the browser is EMBEDDED AT BUILD TIME — so it
    is published, and changing it needs a rebuild
  · EDGE vs NODE RUNTIME: the edge runtime is fast to start and
    lacks Node APIs. ⚠ A library that needs `fs` or a native
    module will not run there.
  · COLD STARTS on infrequently-hit functions
  · REGION CHOICE: ⭐ put the functions in the same region as
    the database, or every query pays a cross-ocean round trip
    and edge compute makes it worse rather than better

⚠ AND THE ONE THAT CATCHES TEAMS: A FUNCTION TIMEOUT SHORTER
  THAN A LEGITIMATE OPERATION. Report generation and model calls
  do not belong in a function with a short ceiling — which is
  the platform-level version of "unbounded work does not belong
  in a request".

Topic 31

Playwright

The layer this adds

The layer underneath "we have E2E tests" is why Playwright is less flaky than what came before — auto-waiting on actionability — and how to keep it that way, because a flaky E2E suite is worse than none.

The mechanism
  • Auto-waiting is the core feature. An action waits for the element to be attached, visible, stable and enabled before acting. Which means an explicit sleep is almost always a bug — it either wastes time or hides a race.
  • Locators are lazy and re-resolved on each use, so they survive re-renders. Prefer role- and text-based locators: they are the accessibility tree, so they double as an accessibility check and they do not break on a class rename.
  • Web-first assertions retry. expect(locator).toBeVisible() polls until the timeout rather than asserting once — which is what removes most timing flakiness.
  • Network interception lets you stub a third party, force an error path, or make a non-deterministic dependency deterministic — which is how you test what happens when the LLM provider is down, an otherwise untestable path.
  • Storage state reuse — log in once, save the session, reuse it across tests. The single biggest speed win in an authenticated suite.
  • Trace on retry gives you a timeline, DOM snapshots and network for a failure that will not reproduce locally. This is the feature that makes CI failures diagnosable.
Where it goes wrong
  • Hard-coded waits, which is where flakiness is deliberately reintroduced.
  • CSS-selector locators tied to implementation details, so a restyle breaks the suite.
  • Tests that share state or depend on order — fine locally, broken when the runner parallelises.
  • Testing everything through the UI. Set up state through the API and assert through the UI; using the UI to create fixtures is slow and brittle.
  • Asserting on exact markup rather than on behaviour.
The question you must be able to answer

"Your E2E suite is flaky. What do you do?" — treat it as a bug with a deadline, because once failures are assumed to be noise the suite has stopped catching anything. Then the usual five causes: shared state, ordering, real clocks, unmocked network, a database not reset.

Topic 32 · zero prior coverage

Cucumber and BDD done right

The layer this adds

Cucumber, Gherkin and BDD were at literal zero. And the layer that matters is not the syntax — it is the reason BDD usually fails, which is that teams adopt the file format without the conversation the format exists to record.

The mechanism, and the point
  • Gherkin is Given / When / Then — a precondition, one action, an observable outcome. Plain language, in a .feature file, mapped to step definitions in code.
  • The value is the shared vocabulary. A scenario a non-engineer can read and correct is a specification that has been checked by the person who wanted it — which catches the most expensive defect there is, a correct solution to the wrong problem.
  • Write scenarios in the domain's language, not the UI's. "Given an employee with no completed reviews" is durable; "Given I click the third row" breaks on every redesign and teaches nobody anything.
  • One When per scenario. Several actions means several scenarios, and a failure then tells you which behaviour broke.
  • Scenario outlines for the same behaviour across a table of cases — which is where the format genuinely earns its keep, because the table is readable by the stakeholder.
  • Step definitions should be thin, delegating to page objects or API helpers. Logic in a step definition is untestable and unreusable.
Why it usually fails
  • Nobody outside the team ever reads the features. Then it is an E2E suite with a slower syntax and an extra indirection layer — and you should say so and use Playwright directly.
  • Scenarios written after the code, describing the implementation rather than the requirement.
  • UI-coupled steps, which makes every redesign a test rewrite.
  • Shared state between scenarios, producing order dependence.
  • Hundreds of scenarios nobody can run quickly, so they stop being run.
The question you must be able to answer

"Why Cucumber rather than just Playwright?" — the only defensible answer is that a non-engineer reads and corrects the scenarios. If that is not true on your team, the honest answer is that it is not buying you anything, and being able to say that is a stronger signal than defending it.

Topic 33

Test data and flakiness engineering

The five causes, and the fix for each
①  SHARED STATE
   two tests touching the same rows; one passes only because
   the other ran first.
   ⇒ ⭐ RESET PER TEST, or wrap each test in a transaction that
     rolls back. And BUILD DATA WITH A FACTORY that takes
     overrides, so each test states only what it cares about.
   ⚠ A SHARED SEED FILE EVERY TEST DEPENDS ON BECOMES
     UNTOUCHABLE WITHIN A MONTH — nobody can change a row
     without breaking something unrelated.

②  ORDERING AND PARALLELISM
   passes serially, fails when the runner parallelises.
   ⇒ isolate by data: per-test tenant, per-test user, unique
     identifiers. Not by forcing serial execution, which just
     hides it.

③  TIME
   ⭐ FREEZE THE CLOCK. Otherwise a test fails at midnight, on
     the 29th of February, at a month boundary, or in another
     timezone — and it will be dismissed as flaky rather than
     recognised as a genuine timezone bug.
   ⇒ and seed any randomness.

④  UNMOCKED NETWORK
   a third party that is slow, rate-limited or down.
   ⇒ intercept it. ⭐ AND MAKE THE MOCK MISBEHAVE THE WAY THE
     REAL THING CAN — timeout, 429, malformed body — or you
     have only tested the happy path of your error handling.

⑤  ASSERTING ON NON-DETERMINISTIC OUTPUT
   the AI feature. Equality fails randomly, gets marked flaky,
   and is deleted.
   ⇒ assert the STRUCTURE (schema-valid, enum in range), the
     PROPERTIES (length bounds, only cites chunks that were in
     the context), and the SURROUNDING BEHAVIOUR (timeout
     handled, page renders when the provider is down).

⭐ THE CULTURAL POINT, WHICH MATTERS MORE THAN ANY TECHNIQUE:
  A FLAKY SUITE DESTROYS THE PIPELINE'S VALUE. Once the team
  re-runs instead of reading, every failure is assumed to be
  noise — including the real one. So a flake is a bug with a
  deadline; quarantine it if you must, but track it.
  ⚠ "JUST HIT RE-RUN" IS HOW A REAL REGRESSION REACHES
    PRODUCTION.
