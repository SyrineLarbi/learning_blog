The shared foundation

Both tracks reduce to four primitives — compute, storage, network, identity — and every provider sells the same four under different names. Learn the primitives and any provider's documentation becomes navigable; learn one provider's product names and you have learned something that expires.

Part I is those primitives. It is worth reading whichever track you are on.

How to choose, honestly

Mostly you do not. The decision is usually made by existing contracts, the team's experience, or where your data already is — and those are legitimate reasons.

Where there is a genuine preference: GCP's Cloud Run and BigQuery are unusually pleasant for exactly this project's shape (containers you do not want to orchestrate, and analytical SQL); AWS has the widest service catalogue and the most hiring-market recognition; Azure wins when the organisation already runs Microsoft identity. All three are adequate for anything in this handbook — the difference in your day is far smaller than the difference between managed and self-managed.

Cloud 04 · the one that causes incidents

Identity and access

Every cloud permission model is the same four ideas
WHO (principal) may do WHAT (action) to WHICH (resource),
UNDER WHAT CONDITIONS.

  principal   a user · a service · a workload
  action      read an object · write a row · start an instance
  resource    ⭐ SPECIFIC, not "all of them"
  condition   from this network · with MFA · during these hours

⭐ THE SINGLE MOST IMPORTANT PRACTICE: A ROLE PER WORKLOAD,
  NOT A SHARED KEY.
  the platform issues and rotates short-lived credentials to
  the running workload, so there is no long-lived secret to
  commit, log or paste. ⚠ A STATIC ACCESS KEY IN AN ENVIRONMENT
  VARIABLE IS A CREDENTIAL WAITING FOR AN ACCIDENT.

⭐ AND THE ANTI-PATTERN THAT IS ALMOST UNIVERSAL:
  grant broad permissions "to get it working", intend to narrow
  them later, never narrow them.
  ⇒ THE FIX IS PROCEDURAL, NOT TECHNICAL: start from nothing,
    add the specific permission the error names, and keep going
    until it works. It takes twenty minutes longer once, and it
    is the difference between a compromised component reaching
    one bucket and reaching everything.

FOR THIS PROJECT, CONCRETELY
  · the AI service needs to READ the model artefact from object
    storage. Nothing else. Not write, not delete, and no access
    to the employee database at all.
  · the backend needs read/write on its own database and
    permission to call the AI service. Not permission to change
    infrastructure.
  · CI needs to push an image and trigger a deploy. ⚠ NOT
    production database credentials.

⭐ THE REVIEW QUESTION WORTH ASKING OF ANY CLOUD SETUP: "IF THIS
  ONE COMPONENT WERE COMPROMISED, WHAT COULD THE ATTACKER
  REACH?" If the answer is "everything", the permissions are
  the vulnerability, whatever else is in place.

Cloud 06

Databases in the cloud

What "managed" actually gets you, and what it does not
✅ WHAT THE PROVIDER DOES
  · provisioning and patching
  · automated backups and point-in-time recovery
  · replication and failover to a standby
  · monitoring and metrics
  · encryption at rest and in transit

⚠ WHAT REMAINS ENTIRELY YOURS
  · ⭐ SCHEMA DESIGN AND INDEXES. No provider fixes a missing
    index or a fan-out join.
  · query performance — Volume IV, Part V
  · connection management (see below)
  · ⭐ AND TESTING THE RESTORE. Backups existing is not the same
    as backups working, and the difference is discovered at the
    worst moment.

⭐ CONNECTION POOLING — THE ONE THAT ACTUALLY BITES
  Postgres handles hundreds of connections, not thousands, and
  each one costs memory. Autoscaled containers or functions each
  open their own pool.
  ⇒ SO YOU CAN EXHAUST CONNECTIONS AT LOW CPU AND LOW TRAFFIC,
    which looks like a mysterious total outage.
  ⇒ USE A POOLER — PgBouncer, or the provider's built-in
    pooling. ⚠ AND KNOW WHICH MODE: transaction-mode pooling
    does not support session-level features such as prepared
    statements or advisory locks, which is a real constraint on
    what your ORM may do.

SERVERLESS POSTGRES (Neon, Aurora Serverless)
  ✅ scales to zero, branches like Git, cheap when idle — ⭐ and
     database branching per pull request is genuinely
     transformative for review environments.
  ⚠ cold starts after idle, and a pricing model based on
     compute-time that rewards short connections.
  ⇒ THIS IS WHAT THIS PROJECT USES, and the pooled connection
    string is not optional.

READ REPLICAS
  for read-heavy load — ⚠ accepting replication lag, and
  needing read-your-writes for a user's own changes (Volume II).
Cloud 07

Object storage and CDN

Cheap, durable, and the source of most cloud data breaches
OBJECT STORAGE is not a filesystem. Flat keys, whole-object
writes, HTTP access, effectively unlimited, extremely durable.
⇒ for uploads, exports, model artefacts, backups, static assets.

⭐ THE THREE RULES THAT MATTER MORE THAN EVERYTHING ELSE

  ① DEFAULT TO PRIVATE, AND VERIFY.
    ⚠ A PUBLIC BUCKET IS THE SINGLE MOST COMMON CLOUD DATA
      BREACH. Providers now default to private and warn loudly;
      people still make them public to fix a broken link.

  ② SERVE PRIVATE FILES WITH PRE-SIGNED URLs.
    a time-limited, unguessable URL generated by your backend
    after it has checked permissions.
    ⭐ AND THE POINT FROM THE INTERVIEW PLAYBOOK, WHICH APPLIES
      HERE LITERALLY: A LINK IS A CREDENTIAL. Whoever holds the
      string holds the file, so keep the expiry short, make the
      key unguessable, and prefer serving through an
      authenticated endpoint for anything as sensitive as an HR
      record.

  ③ SET A LIFECYCLE POLICY.
    generated exports, old backups and temporary artefacts get
    deleted automatically. ⚠ A BUCKET OF HR PDFs WITH NO EXPIRY
      IS A BREACH WAITING FOR AN AUDIT — and it is also a
      growing bill.

STORAGE CLASSES
  hot · infrequent · archive. Cheaper per gigabyte, more
  expensive and slower to retrieve. ⇒ right for backups, wrong
  for anything a user might click.

CDN — ⭐ AND THE POINT PEOPLE MISS
  a CDN caches at the edge, close to users. It is for static and
  cacheable content.
  ⚠ IT DOES NOTHING FOR AUTHENTICATED, PERSONALISED RESPONSES —
    which is most of an internal HR dashboard. So a CDN is the
    right answer for your JavaScript bundle and the wrong answer
    for your API.
Cloud 08

Queues and events

The managed versions of Volume II's patterns
QUEUE (SQS, Cloud Tasks, Service Bus)
  one producer, one consumer group, work distributed.
  ⇒ for report generation, bulk imports, model inference over
    many records — anything that must not sit in a request.

PUB/SUB (SNS, Pub/Sub, Event Grid)
  one publisher, many independent subscribers.
  ⇒ "employee.updated" reaching audit, notifications and a
    search re-index without the producer knowing about any of
    them.

⭐ THE MANAGED VERSION GIVES YOU DURABILITY, RETRIES AND A
  DEAD-LETTER QUEUE WITHOUT WRITING THEM. What it does NOT give
  you is the thing that actually matters:

  ⚠ YOUR CONSUMER MUST STILL BE IDEMPOTENT. Every one of these
    services is at-least-once. A message will be delivered
    twice, and a consumer that charges a card or sends an email
    on each delivery will do it twice.
  ⚠ AND ORDER IS NOT GUARANTEED unless you explicitly choose an
    ordered variant — which limits parallelism, so it is a
    trade rather than a free upgrade.

THE OPERATIONAL DETAILS THAT DECIDE WHETHER IT WORKS
  · VISIBILITY TIMEOUT — how long a message is hidden while
    being processed. ⭐ SET IT LONGER THAN YOUR SLOWEST
    LEGITIMATE RUN, or the message reappears and is processed
    twice while the first attempt is still going.
  · A DEAD-LETTER QUEUE, and ⭐ AN ALERT ON ITS DEPTH. A DLQ
    nobody watches is a silent data-loss mechanism.
  · a concurrency cap on the consumer, so draining a backlog
    does not overwhelm the database or a metered API.
Cloud 09

Caching

LayerCachesWatch out for
CDN / edgeStatic assets, public pagesNothing personalised. And invalidation is your problem on every deploy.
Application (Redis)Query results, computed aggregates, sessions, rate-limit countersThe most useful layer. Needs an eviction policy and a memory limit, or it becomes an outage.
In-processAnything tiny and hotEach instance has its own copy, so they disagree — and it does not survive a restart.
Database-levelMaterialised views, aggregate tablesRefresh cost and staleness, but it keeps the data in one place with one access model.
The three failure modes worth knowing by name

Stampede. A popular key expires and a thousand requests all miss and all recompute simultaneously. Fix: a lock so one request refreshes, or staggered expiries.

Everything expiring at once. A fixed TTL set at deploy time means every key expires together. Fix: add jitter — the same idea as retry jitter.

Caching a permission-filtered result under a shared key. The dangerous one. One user's filtered data served to another. Any cache key for per-user data must include the user or the scope — and in an HR system that is the difference between a cache and an incident.

Cloud 10

Microservices on cloud infrastructure

What the cloud makes easy, and what it cannot make easy
✅ THE CLOUD GENUINELY SOLVES: service discovery, load
balancing, TLS termination, autoscaling, rolling deploys,
health checking. All configuration rather than code.

⚠ WHAT IT DOES NOT SOLVE, AND CANNOT
  · ⭐ DATA CONSISTENCY ACROSS SERVICES. There is no distributed
    transaction. Two services with two databases means eventual
    consistency and compensating actions, and that is a design
    problem no platform removes.
  · debugging across services — you still need correlation ids
    and traces
  · the deployment coupling: service A's new field must be
    compatible with service B's old code, in both directions
    during a rollout
  · the organisational cost — every boundary needs an owner

⭐ THE PATTERN WORTH KNOWING FOR CROSS-SERVICE WORK: THE SAGA.
  a multi-step operation across services, where each step has a
  COMPENSATING ACTION instead of a rollback.
    reserve → charge → confirm
    if charge fails ⇒ release the reservation
  ⚠ AND COMPENSATION IS NOT THE SAME AS ROLLBACK: the
    intermediate state was visible to someone, and the
    compensation can itself fail. This is genuine complexity,
    and it is the real price of splitting a transaction across
    services.

⭐ THE JUDGEMENT, UNCHANGED FROM VOLUME II: SPLIT ON A BOUNDED
  CONTEXT AND FOR A REASON YOU CAN STATE IN ONE SENTENCE. This
  project's split — Python has the ML ecosystem — is such a
  reason. "Microservices are modern" is not.
Cloud 11

Security in depth

Layers, so one mistake is not fatal
THE LAYERS, OUTSIDE IN
  ① EDGE          a WAF and rate limiting in front of the app
  ② NETWORK       private subnets; security groups that name
                  the source, not the world
  ③ IDENTITY      ⭐ a role per workload, least privilege
                  (reflex 04) — the layer that most often fails
  ④ APPLICATION   authn, authz, validation — Volume III
  ⑤ DATA          encryption at rest, field-level for the most
                  sensitive columns, and ⭐ AUDIT LOGGING OF
                  ACCESS, which for HR data is a requirement
                  rather than a nice-to-have

SECRETS, PROPERLY
  a managed secret store with versioning, rotation and access
  audit — injected at runtime, never baked into an image
  (Volume V, reflex 08) and never in a build log.
  ⭐ AND THE TEST: CAN YOU ROTATE THE DATABASE PASSWORD ON A
    TUESDAY AFTERNOON WITHOUT DOWNTIME? If not, that is a
    finding, and it is discovered during an incident otherwise.

COMPLIANCE, FOR AN HR SYSTEM SPECIFICALLY
  · ⭐ DATA RESIDENCY — EU employee data has location
    obligations, and the region you choose in a console is
    where that obligation is implemented. It is very expensive
    to change later.
  · RETENTION AND ERASURE — a legal erasure request is not the
    same as a delete button, and it must reach backups, logs,
    exports and analytics copies.
  · ACCESS AUDIT — who viewed whose record, retained.
  · ⚠ AND THE ONE PEOPLE GET WRONG: PRODUCTION DATA MUST NOT BE
    COPIED TO LOWER ENVIRONMENTS. Anonymise or generate.

⭐ THE MINDSET: ASSUME ONE LAYER WILL FAIL. The question is not
  "is it secure" but "what happens when this specific control
  is bypassed" — and if the answer is "everything is reachable",
  you have one layer, not five.
Cloud 12

Cost optimisation

In order of money recovered per hour spent
①  TURN OFF WHAT NOBODY USES — ⭐ ALWAYS THE BIGGEST WIN
   idle staging environments, oversized instances left from a
   load test, unattached disks, old snapshots, a forgotten
   experiment. ⇒ and schedule non-production environments to
   stop overnight and at weekends: roughly a 70% saving on
   them, for one configuration change.

②  RIGHT-SIZE
   most instances are provisioned for an imagined peak. Look at
   actual utilisation over a month and resize.

③  COMMIT TO WHAT YOU KNOW YOU WILL USE
   reserved capacity or committed-use discounts are 30–70% off
   for a one-year commitment. ⚠ only for genuinely steady
   baseline load.

④  SPOT / PREEMPTIBLE CAPACITY
   heavily discounted, and it can be taken away with little
   notice. ⭐ PERFECT FOR BATCH AND TRAINING JOBS THAT
   CHECKPOINT; unusable for a user-facing API.

⑤  STORAGE LIFECYCLE
   move old data to colder classes automatically, and delete
   what has no reason to exist.

⑥  FIX THE ARCHITECTURE
   ⭐ THE LARGEST STRUCTURAL SAVINGS ARE USUALLY ENGINEERING
     PROBLEMS, NOT PROCUREMENT ONES: an N+1 that triples
     database load, a missing cache on a hot read, a log level
     writing terabytes, a cross-zone chat pattern, a metered API
     called in a loop.

⭐ THE TWO HABITS THAT MAKE ANY OF THIS POSSIBLE
  · TAG EVERYTHING BY ENVIRONMENT, SERVICE AND OWNER. Untagged
    spend cannot be attributed, and therefore cannot be
    questioned.
  · A BUDGET ALERT FROM DAY ONE — ⭐ AS A SECURITY CONTROL AS
    MUCH AS A FINANCIAL ONE. A leaked credential shows up as a
    compute bill within hours.
Cloud 13

Multi-cloud, honestly

The uncomfortable version

Deliberate multi-cloud is almost always a mistake for a small team. You pay twice the operational surface, forgo every managed service that would actually help, and end up building on the lowest common denominator — which is usually just virtual machines.

The stated motive is avoiding lock-in. The realistic outcome is being locked into your own abstraction layer, maintained by nobody, instead of a provider's well-documented service.

What to do instead
⭐ MANAGE PORTABILITY WHERE IT IS CHEAP, AND ACCEPT LOCK-IN
  WHERE IT PAYS.

  CHEAP PORTABILITY — take it
    · containers rather than a proprietary runtime
    · standard Postgres rather than a proprietary dialect
    · your business logic free of provider SDKs, behind an
      adapter (Volume II) — ⭐ this is the highest-value one,
      and it is a design habit rather than an infrastructure
      project
    · infrastructure as code, so recreating is describable

  WORTH THE LOCK-IN — usually
    · managed Postgres, object storage, a queue: the concepts
      are portable even though the API is not, and migrating is
      weeks rather than years
    · a warehouse such as BigQuery, where the capability is the
      point

  ⚠ EXPENSIVE LOCK-IN — think first
    · a proprietary orchestration or workflow engine your whole
      business logic lives inside
    · a provider-specific event and function fabric with
      hundreds of small pieces

LEGITIMATE MULTI-CLOUD REASONS — they do exist
  · a regulatory requirement
  · a customer contract demanding a specific provider
  · one specialised capability available only in one place —
    ⭐ WHICH IS THE COMMON REAL CASE TODAY: an application on
    one provider and a particular AI or ML capability on
    another. That is not multi-cloud strategy; it is using the
    right service.

Part IV · Track B

Cloud for data science

Cloud 15

Why a data scientist needs the cloud

Four specific limits of a laptop
①  THE DATA DOES NOT FIT.
   ⭐ AND THE RULE FROM VOLUME IV: A DATAFRAME IS SEVERAL TIMES
     THE SIZE OF THE FILE. A 20 GB export is not a 20 GB
     DataFrame, and 16 GB of RAM is not 16 GB of headroom.

②  TRAINING TAKES TOO LONG.
   a GPU is 10–100× a CPU for the shape of work deep learning
   does. Renting one for two hours costs a few dollars; owning
   one costs thousands and is idle most of the time.

③  ⭐ NOBODY CAN REPRODUCE YOUR RESULT.
   a notebook on your machine with a local CSV, a package set
   nobody recorded, and cells run out of order is not a result
   — it is an anecdote. THIS IS THE MOST COMMON AND LEAST
   DISCUSSED PROBLEM IN APPLIED DATA SCIENCE.

④  IT CANNOT BE SCHEDULED OR SERVED.
   a model on a laptop cannot retrain nightly or answer an API
   call. Getting from notebook to endpoint is the whole gap
   between an experiment and a feature.

⭐ THE HONEST SCOPING NOTE FOR THIS PROJECT: attrition
  prediction over a few thousand employee records with XGBoost
  trains in seconds on a laptop and needs none of this. ⇒ THE
  REASON TO KNOW IT IS ③ AND ④ — reproducibility and serving —
  not scale. Those two apply at every size, and they are what
  turn a model into a product.
Cloud 16

Compute for ML

ShapeForCost note
A notebook instanceExploration, feature workThe classic waste. Left running overnight while nobody uses it. Set an idle-shutdown policy on day one.
A training jobOne run, then the machine goes awayThe right default. You pay for the run, not the day, and the job definition is reproducible.
Spot / preemptibleLong training that checkpoints60–90 % cheaper, and it can be reclaimed. Checkpoint, or a four-hour run becomes nothing.
GPU instancesDeep learning, large modelsExpensive per hour. Pointless for gradient boosting on tabular data — the money buys nothing there.
Distributed trainingData or a model too large for one machineReal complexity, and it is only worth it when a single large machine genuinely will not do.
The habit that saves the most money here

Explore on a small sample locally; train on the cloud as a job. Interactive compute is billed by the hour whether or not you are typing, and it is where ML budgets quietly go.

The corollary is a discipline worth building: if a run takes more than a few minutes, it should be a job definition rather than a cell in a notebook — reproducible, schedulable, and it releases the machine when it finishes.

Cloud 17

Storage for data

The lake, and the file format that matters
OBJECT STORAGE IS THE DATA LAKE. Cheap, durable, effectively
unlimited, and every tool reads from it.

⭐ ORGANISE IT DELIBERATELY OR IT BECOMES A SWAMP
  raw/        exactly as received, never modified — ⭐ SO YOU
              CAN ALWAYS REBUILD
  staged/     cleaned, typed, deduplicated
  curated/    modelled, ready for analysis and features
  ⇒ the same layering as any pipeline, and each layer has one
    job.

PARTITION BY WHAT YOU FILTER ON
  raw/events/year=2026/month=09/day=07/…
  ⭐ THEN A QUERY FOR SEPTEMBER READS SEPTEMBER'S FILES AND
    NOTHING ELSE. On a query engine billed per byte scanned,
    this is the difference between cents and hundreds of
    dollars for the same answer.

⭐ USE PARQUET, NOT CSV — and this is the single highest-value
  technical choice in this section.
    · COLUMNAR: reading three columns of forty reads three
      columns of data, not the whole row
    · compressed — typically 5–10× smaller than CSV
    · TYPED — ⭐ no more "was that column a string or a number
      today", which is the source of a whole class of pipeline
      bug
    · splittable, so engines can parallelise
  ⚠ CSV keeps its place for interchange with humans and
    spreadsheets. It is a terrible storage format.

VERSIONING THE DATA
  ⭐ A MODEL IS ONLY REPRODUCIBLE IF THE DATASET IT TRAINED ON
    IS. Snapshot the exact training set — a versioned path, a
    table snapshot, or a data-versioning tool — and record its
    identifier alongside the model. Without it, "why did the
    metrics change?" is unanswerable.
Cloud 18

Managed notebooks

Convenient, and the source of the reproducibility problem
✅ WHAT THEY GIVE YOU: a preconfigured environment, direct
access to cloud data and credentials, a GPU when you need one,
and no local setup.

⚠ WHAT THEY DO NOT FIX — the notebook's own failure modes
  · ⭐ HIDDEN STATE. Cells run out of order produce results
    that cannot be reproduced by running the notebook top to
    bottom. ⇒ RESTART AND RUN ALL BEFORE BELIEVING ANY RESULT.
    This one habit prevents most false findings.
  · they diff terribly in Git, so review is nearly impossible
  · ⚠ OUTPUTS ARE SAVED IN THE FILE — including, routinely,
    real employee data in a rendered table. Committing that
    notebook commits the data. ⇒ STRIP OUTPUTS BEFORE
    COMMITTING, and treat a notebook as a data-bearing
    artefact.
  · they encourage code that lives nowhere reusable

⭐ THE WORKFLOW THAT ACTUALLY WORKS
  EXPLORE in the notebook · then MOVE THE LOGIC INTO MODULES ·
  and have the notebook import and call them.
  ⇒ the exploration stays readable, and the code becomes
    testable, reviewable and runnable as a scheduled job. The
    notebook becomes a narrative, not the implementation.

⚠ AND THE COST AND ACCESS NOTES, BOTH OF WHICH BITE
  · idle-shutdown, always — an unattended notebook instance is
    a bill with no output
  · a notebook runs with real credentials against real data.
    ⭐ THAT IS AN ACCESS PATH THAT NEEDS THE SAME SCRUTINY AS AN
      API ENDPOINT, and in an HR context it needs to be audited.
Cloud 19

Warehouse SQL at scale

Why analytical databases are a different thing
OLTP (Postgres)          OLAP (BigQuery, Redshift, Snowflake)
  row-oriented             ⭐ COLUMN-ORIENTED
  many small reads/writes  few enormous scans
  indexes                  partitioning + clustering
  transactions             append-mostly
  ⇒ ⭐ THE SAME QUERY CAN BE A THOUSAND TIMES FASTER ON THE
    RIGHT ONE, because summing one column out of fifty reads
    one column rather than every row.

⭐ THE PRICING MODEL CHANGES HOW YOU WRITE SQL — and this is
  the part that surprises people
  many warehouses bill PER BYTE SCANNED. So:
    ⚠ `SELECT *` IS EXPENSIVE, LITERALLY. It scans every
      column, and you wanted four.
    ⚠ NO PARTITION FILTER MEANS SCANNING EVERYTHING. A missing
      `WHERE date >= …` can be a hundred-dollar query.
    ⭐ AND A `LIMIT` DOES NOT REDUCE THE SCAN — it reduces the
      rows returned after the scan has already been paid for.
      This is the single most expensive misconception in cloud
      analytics.
  ⇒ SO: select the columns you need, always filter the
    partition, and preview with a sampled table rather than a
    LIMIT on the full one.

WHEN TO USE ONE AT ALL
  ✅ analytics over tens of millions of rows and up · joining
     several sources · anything a BI tool queries
  ⚠ NOT for application queries — latency is seconds, not
    milliseconds, and there are no useful transactions.

⭐ FOR THIS PROJECT, THE HONEST ANSWER: a few thousand employees
  and their history fits comfortably in Postgres, and a
  warehouse would add cost and a synchronisation problem for no
  benefit. ⇒ THE TIME TO ADOPT ONE IS WHEN ANALYTICAL QUERIES
  START HURTING THE APPLICATION DATABASE — that is the specific
  limit worth waiting for.

Cloud 20

What they are actually for

Five problems, and they are not "training"
TRAINING A MODEL IS THE EASY PART AND IT IS NOT WHY THESE
PLATFORMS EXIST. They exist for:

  ①  REPRODUCIBILITY — this model came from this code, this
     data version, these hyperparameters, at this time.
     ⭐ THE MOST VALUABLE THING THEY PROVIDE, and the thing
     hardest to build yourself.
  ②  EXPERIMENT TRACKING — 200 runs, comparable, searchable,
     instead of a spreadsheet and some filenames.
  ③  A MODEL REGISTRY — versioned artefacts with stages
     (staging, production) and a promotion path.
  ④  SERVING — an endpoint, with autoscaling and versioning,
     without you building a service.
  ⑤  PIPELINES — the whole flow as a scheduled, monitored DAG:
     ingest → features → train → evaluate → register → deploy.

⚠ WHAT THEY DO NOT DO
  · pick the right problem, or tell you the framing is wrong
  · fix leakage — ⭐ A PLATFORM WILL HAPPILY TRACK 200 RUNS OF A
    LEAKING MODEL and report excellent metrics for all of them
  · make a bad dataset good
  · remove the need to understand evaluation

⭐ AND THE HONEST ENTRY POINT: START WITH EXPERIMENT TRACKING
  ONLY. It is a few lines in your training script and it solves
  the most painful problem — "which run produced this?" — with
  almost no commitment. Adopt the registry when you have a
  model in production, and pipelines when retraining is
  regular. Adopting the whole platform on day one is how teams
  end up with elaborate infrastructure around one model.

How to choose

Use whichever provider your data already lives in. Moving large datasets between clouds costs money and time, and every one of these platforms is adequate.

Cloud 22

Training and experiment tracking

What to record, so a result means something later
EVERY RUN SHOULD RECORD
  □  the CODE VERSION — a commit SHA, not "the current script"
  □  the DATA VERSION — ⭐ a snapshot identifier, not "the
     employees table". Without this nothing is reproducible.
  □  the HYPERPARAMETERS
  □  the ENVIRONMENT — library versions ⭐ (a different XGBoost
     version can change results)
  □  the METRICS, on a named split
  □  the ARTEFACT — the fitted PIPELINE, not just the model
  □  who ran it, and when

⭐ THE PAYOFF IS NOT TIDINESS. It is being able to answer, six
  months later: "why is the model in production better than the
  one I just trained?" Without these records that question is
  unanswerable, and people re-run experiments they have already
  done.

HYPERPARAMETER TUNING, MANAGED
  grid · random · Bayesian — the platform runs many trials in
  parallel and keeps the best.
  ⚠ AND THE WARNING THAT MATTERS MORE THAN THE METHOD: TUNING
    IS THE EASIEST WAY TO OVERFIT YOUR VALIDATION SET. Two
    hundred trials selected on one split will find the
    configuration that suits that split. ⭐ SO KEEP A TEST SET
    THE TUNING NEVER TOUCHED, and treat the tuned score as
    optimistic until the test set agrees.

⭐ AND THE DISCIPLINE POINT: A PLATFORM MAKES IT EASY TO RUN 200
  EXPERIMENTS AND EASY TO AVOID THINKING ABOUT ANY OF THEM. The
  judgement in Volume VII — baselines, leakage, the right
  metric for the base rate — is what makes the runs worth
  anything.
Cloud 23

Serving a model

ModeShapeRight when
Real-time endpointAn HTTP call, milliseconds to a secondA prediction is needed while someone waits. Costs money continuously, whether or not it is called.
Serverless inferenceScales to zeroInfrequent traffic. Cold start on the first call, which is worse the larger the model.
Batch transformScore a whole file, write the resultsUsually the right answer — and the one people skip. Nightly scoring of every employee is cheaper and simpler than an endpoint nobody calls interactively.
Embedded in your serviceLoad the model in the FastAPI processWhat this project does. Simplest possible operationally, for a small model: no extra service, no extra network hop.
The framing worth carrying

Ask whether the prediction is needed at the moment of the request. An attrition risk score changes slowly — monthly at most. Computing it nightly in a batch and reading the stored value is faster, cheaper, more reliable and easier to audit than an endpoint.

A real-time endpoint is for predictions that depend on the request itself. Building one for a slowly-changing score is a common and expensive default.

LLMs in the cloud

Three ways to access one, and the choice is mostly about data
①  A PROVIDER API — ⭐ WHAT THIS PROJECT USES
   the best models, no infrastructure, per-token pricing.
   ⚠ your text leaves your boundary ⇒ so the questions are
     contractual and legal: what is retained, where, for how
     long, and is it used for training. ⭐ FOR HR DATA THOSE
     ANSWERS MATTER AND SHOULD BE ON RECORD.

②  A MANAGED MODEL GARDEN IN YOUR CLOUD
   models hosted inside your provider's boundary, under your

   expect, and a much simpler compliance conversation.

   full control, nothing leaves. ⚠ AND THE COST IS THE PART

     almost never cheaper for the intermittent workload of an
     internal tool.

⭐ THE DECISION PROCEDURE
  · sensitive data with strict residency ⇒ ② or ③
  · best quality with least effort ⇒ ①

    idle time and the engineer's salary
  · ⚠ AND WHATEVER YOU CHOOSE: PUT AN ADAPTER BETWEEN YOUR

Cloud 25

ML cost control

Where ML budgets actually go
⭐ THE FOUR, IN ORDER OF HOW MUCH MONEY THEY WASTE

  ①  IDLE NOTEBOOK AND ENDPOINT INSTANCES.
     ⭐ ALWAYS THE LARGEST. A GPU notebook left running over a
       weekend costs more than the experiment it was for. An
       endpoint deployed for a demo and never deleted bills
       forever. ⇒ IDLE SHUTDOWN, AND AN OWNER FOR EVERY
       ENDPOINT.

  ②  TRAINING ON THE WRONG HARDWARE.
     a GPU for gradient boosting on tabular data buys nothing.
     ⇒ match the hardware to the algorithm.

  ③  RE-SCANNING THE SAME DATA.
     in a per-byte-scanned warehouse, an unfiltered exploratory
     query run twenty times is twenty full scans. ⇒ materialise
     a sampled table for exploration.

  ④  METERED API CALLS IN A LOOP.
     an LLM over 10,000 records has a price. ⭐ ESTIMATE IT
       BEFORE RUNNING IT, and show the cost in the confirmation
       when a human triggers it.

THE HABITS
  · SPOT CAPACITY FOR TRAINING, with checkpoints
  · BATCH RATHER THAN REAL-TIME wherever the prediction is not
    needed instantly (reflex 23)
  · CACHE what does not change — embeddings of unchanged
    documents, predictions for unchanged records
  · SMALLER MODELS WHERE THEY SUFFICE ⭐ — and measure the
    quality difference rather than assuming it
  · TAG EVERY ML RESOURCE with an owner and an experiment

⭐ AND THE SENTENCE THAT MAKES YOU CREDIBLE: "This costs $0.004
  per prediction, $240 a month at current volume, and here are
  the three levers if that needs to come down." Almost nobody
  brings that number, and it is what turns a model into a
  business decision.

Term bank

Volume VI · cloud vocabulary
region / zone
A geography, and an isolated datacentre within it. A latency and compliance choice.
VPC
Your private network inside a provider.
security group
A firewall attached to a resource. Name the source, never 0.0.0.0/0 on a database.
NAT gateway
Outbound access for private resources. Surprisingly expensive.
workload identity
A rotated, short-lived credential issued to a running service instead of a static key.
least privilege
The narrowest permissions that work. Widened to fix an error and never narrowed.
pre-signed URL
A time-limited link to a private object. A link is a credential.
lifecycle policy
Automatic transition or deletion of stored objects by age.
visibility timeout
How long a queue message is hidden while processed. Too short means double processing.
cache stampede
Many requests missing the same expired key at once.
saga
A multi-service operation with compensating actions instead of a rollback.
strangler fig
Replacing a live system by routing one path at a time.
spot / preemptible
Cheap capacity that can be reclaimed. Requires checkpointing.
committed use
A discount for a usage commitment. Only for steady baseline load.
Parquet
Columnar, compressed, typed storage. The default for analytical data.
partition pruning
Filtering on the partition column so the engine reads only relevant files.
bytes scanned
The warehouse billing unit. LIMIT does not reduce it.
data version
An identifier for the exact training snapshot. Without it, nothing is reproducible.
model registry
Versioned model artefacts with promotion stages.
batch transform
Scoring a whole dataset offline. Usually cheaper and simpler than an endpoint.
model garden
Provider-hosted models inside your own cloud boundary and data agreements.
