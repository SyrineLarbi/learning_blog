Part I

MLOps

Everything between "the model works in a notebook" and "the model works in production and we would notice if it stopped".

Data/AI 01

What MLOps actually is

Why an ML system is harder to operate than a normal one
ORDINARY SOFTWARE          AN ML SYSTEM
  behaviour comes from       behaviour comes from CODE *AND*
  code                       DATA — ⭐ so it can break without
                             anyone changing anything
  correct or broken          ⭐ DEGRADES GRADUALLY AND SILENTLY
  a test asserts equality    a metric moves on a distribution
  deploy = ship code         deploy = ship code + weights +
                             the preprocessing that made them
  reproducible from git      reproducible only if the DATA
                             VERSION was recorded

⭐ THE CONSEQUENCE THAT DEFINES THE DISCIPLINE: AN ML SYSTEM CAN
  FAIL WITHOUT FAILING. Nothing errors, latency is fine, the
  dashboard is green — and the predictions have quietly become
  worthless because the world moved. No ordinary monitoring
  catches that.

SO MLOps IS FOUR THINGS
  ①  VERSION EVERYTHING — code, data, parameters, environment,
     artefact. ⭐ THE MINIMUM VIABLE PRACTICE, and the one that
     pays back immediately.
  ②  AUTOMATE THE PATH from data to a deployed model, so it is
     repeatable rather than remembered.
  ③  MONITOR THE INPUTS AND THE OUTPUTS, not just the service.
  ④  BE ABLE TO ROLL BACK to a previous model as easily as to
     previous code.

⭐ AND THE HONEST STARTING POINT: FOR ONE MODEL, ①  ALONE IS
  MOST OF THE VALUE. A tracked run and a versioned artefact
  turn "which model is this?" from unanswerable into trivial.
  Build the rest when retraining becomes regular.
Data/AI 02

Tracking and the registry

RecordWhy, concretely
Code versionA commit SHA. "The script as it was that day" is not a version.
Data versionThe one most often missing. A snapshot identifier. Without it the model is not reproducible at any price, and "why did the metrics change?" is unanswerable.
HyperparametersSo the run can be repeated and compared.
EnvironmentLibrary versions — a different XGBoost version can change results, and a pickle loaded under a different version can predict differently or refuse to load.
Metrics, per named splitTrain, validation and test separately. One number with no split is not a result.
The artefactThe whole fitted pipeline, not the estimator — the preprocessing is part of the model.
Who and whenAccountability, and it is what makes an audit answerable.
What a registry adds

A registry gives a model a name, a version and a stage — staging, production, archived. Which turns two otherwise painful questions into lookups: which model is serving right now, and what do I roll back to.

And it gives you the promotion gate: a model moves to production because it beat the incumbent on a held-out set, not because someone copied a file.

Data/AI 03

CI/CD for models

Three pipelines, not one
①  CODE PIPELINE — ordinary CI on the training and serving code.
   lint, types, unit tests. Nothing special.

②  TRAINING PIPELINE — triggered by new data, a schedule, or a
   code change.
     ingest → validate → features → train → evaluate → register
   ⭐ WITH AN AUTOMATIC GATE: DO NOT REGISTER A MODEL THAT DOES
     NOT BEAT THE INCUMBENT ON THE HELD-OUT SET. That single
     rule prevents the most common regression — shipping a
     worse model because the run completed.

③  DEPLOYMENT PIPELINE — promote a registered model to serving.
   ⭐ AND IT MUST BE SEPARATE FROM ②. Training and deploying are
     different decisions with different risk; a model that
     trains well may still need a human before it affects
     anyone.

⭐ THE VALIDATION STEP PEOPLE OMIT: VALIDATE THE DATA BEFORE
  TRAINING.
  schema unchanged? row count within expected bounds? no column
  suddenly 90% null? distributions roughly where they were?
  ⚠ WITHOUT THIS, A BROKEN UPSTREAM LOAD SILENTLY PRODUCES A
    MODEL TRAINED ON GARBAGE, and the pipeline reports success
    at every step.

DEPLOYING SAFELY — the same strategies as any service
  · SHADOW MODE: the new model predicts, its output is logged
    and not used. ⭐ THE SAFEST AND MOST UNDER-USED OPTION —
    real traffic, zero risk.
  · CANARY: a small share of traffic, watched.
  · ⚠ AND ALWAYS KEEP THE PREVIOUS VERSION DEPLOYABLE. Rolling
    back a model must be as fast as rolling back code.
Data/AI 04

Monitoring, and the two drifts

The part that distinguishes a deployed model from a maintained one
FOUR LAYERS, AND MOST TEAMS MONITOR ONLY THE FIRST

  ①  THE SERVICE — latency, error rate, throughput. Ordinary.

  ②  THE INPUTS — ⭐ DATA DRIFT
     the distribution of incoming features moves away from the
     training distribution.
     ⇒ a reorganisation changes every department code; a new
       office changes the tenure mix; an upstream system starts
       sending nulls.
     ⭐ THIS IS DETECTABLE IMMEDIATELY AND WITHOUT LABELS, which
       makes it the most valuable monitor you can add.

  ③  THE OUTPUTS — prediction drift
     the distribution of predictions shifts. Suddenly 40% of
     employees are high risk where it was 8%.
     ⇒ also label-free, and it usually means ② happened.

  ④  THE OUTCOMES — ⚠ CONCEPT DRIFT
     the relationship itself changed — the same features now
     imply a different outcome.
     ⭐ AND THE HONEST PROBLEM: YOU LEARN THE TRUE OUTCOME
       MONTHS LATER. Attrition is only confirmed when someone
       leaves. So accuracy is always measured in arrears, and
       ② and ③ are your only early warning.

⭐ AND THE ONE UNIQUE TO THIS DOMAIN, WHICH IS EASY TO MISS:
  A RETENTION MODEL CHANGES BEHAVIOUR. Managers act on the
  flags, so future data is shaped by the model's own
  predictions. ⇒ YOUR NEXT TRAINING SET IS NO LONGER A CLEAN
  OBSERVATION OF REALITY, and naive retraining on it slowly
  degrades into modelling your own interventions. Plan for it:
  keep a holdout that is not acted on, or record which
  predictions were acted upon.
Data/AI 05

Feature stores

One real problem, and whether you have it
THE PROBLEM THEY SOLVE — ⭐ TRAINING/SERVING SKEW
  the feature "team average satisfaction over the last 90 days"
  is computed one way in a training notebook and another way in
  the serving code. They differ subtly. ⇒ THE MODEL PERFORMS
  WORSE IN PRODUCTION THAN IN VALIDATION, FOR NO VISIBLE
  REASON, and it is very hard to diagnose.

WHAT A FEATURE STORE PROVIDES
  · ONE DEFINITION of each feature, used by both training and
    serving
  · an offline store for training and an online store for
    low-latency lookup
  · ⭐ POINT-IN-TIME CORRECTNESS: "what was this feature's value
    at the moment of the event?" ⇒ THIS IS LEAKAGE PREVENTION
    AS INFRASTRUCTURE, and it is the genuinely hard part it
    solves
  · reuse across models, and documentation of what exists

⚠ WHETHER YOU NEED ONE
  ✅ several models sharing features · features computed from
     streams · a team large enough that people duplicate
     definitions
  ❌ one model, batch scoring, a handful of features
  ⇒ ⭐ FOR THIS PROJECT: NO. A feature store for one attrition
    model is infrastructure without a problem.

⭐ BUT TAKE THE IDEA WITHOUT THE PLATFORM: WRITE THE FEATURE
  LOGIC ONCE, IN ONE MODULE, AND CALL IT FROM BOTH TRAINING AND
  SERVING. That is 95% of the benefit for none of the cost —
  and it is the same "one definition, derived everywhere"
  principle as everywhere else in this handbook.
Part II

Data/AI 06

ETL versus ELT

What actually changed, and when each is right
ETL  extract → TRANSFORM → load
     transform before landing it. Made sense when storage and
     compute were expensive and the warehouse was precious.

ELT  extract → LOAD → transform
     ⭐ land the raw data first, transform inside the warehouse.
     WHY IT WON: storage became cheap and warehouse compute
     became elastic. And the decisive advantage —

  ⭐ YOU KEEP THE RAW DATA. So when a transformation turns out
    to be wrong — and one will — you can rebuild from source
    rather than re-extracting from a system that may no longer
    have the history. WITH ETL, A BAD TRANSFORM DESTROYS
    INFORMATION YOU CANNOT RECOVER.

WHEN ETL IS STILL RIGHT
  · the data must be masked or filtered BEFORE it lands, for
    legal reasons ⭐ — which is a real consideration for HR
    data crossing a boundary
  · the volume is enormous and most of it is discarded
  · the destination cannot transform

⭐ THE RULE THAT MATTERS MORE THAN THE ACRONYM: NEVER MODIFY THE
  RAW LAYER. It is append-only and immutable. Every
  transformation writes somewhere new. That single discipline is
  what makes a pipeline debuggable and rebuildable.
Data/AI 07

Pipeline layers

SOURCES ──► RAW ──► STAGING ──► INTERMEDIATE ──► MARTS │ │ │ │ exactly as typed, joined, shaped for received renamed, business one audience immutable cleaned logic applied ⭐ EACH LAYER HAS EXACTLY ONE JOB. That is the whole discipline, and the reason it works. RAW land it unchanged. Never edit. ⇒ you can always rebuild everything downstream. STAGING one model per source table. Rename, cast, clean, deduplicate. ⭐ NO JOINS HERE — joining early destroys reusability, because the next use needs a different join. INTERMEDIATE the joins and the business logic. Where "regretted attrition" gets its definition, once. MARTS the tables people query. One per audience or question, wide and denormalised on purpose. ⭐ THE PROPERTY THAT MAKES A PIPELINE OPERABLE: IDEMPOTENCY. Running any step twice produces the same result as running it once. ⇒ then a failed run can simply be re-run, and a backfill is not a special procedure requiring courage. ⚠ AN APPEND-ONLY STEP WITH NO DEDUPLICATION IS NOT IDEMPOTENT — re-running it doubles the data, and this is the most common pipeline bug there is. AND THE DEFINITION LIVES IN EXACTLY ONE PLACE ⚠ if "active employee" is defined in four marts, it will eventually be defined four different ways, and two dashboards will disagree in a meeting. ⭐ DEFINE IT ONCE IN THE INTERMEDIATE LAYER AND BUILD EVERYTHING FROM IT.
Data/AI 08

Incremental loads

Full reload is simple; incremental is fast and subtly wrong
FULL SNAPSHOT — reload everything each run.
  ✅ simple, self-correcting, and idempotent by construction.
  ⭐ USE IT UNTIL IT HURTS. For a few million rows it is fine,
    and it eliminates every problem below.

INCREMENTAL — load only what changed since last time.
  ✅ fast and cheap.
  ⚠ AND HERE ARE THE FOUR WAYS IT LOSES DATA:

  ① THE BOUNDARY. `WHERE updated_at > last_run` — a row
    written at exactly that timestamp is either processed twice
    or missed. ⇒ use an inclusive lower bound plus
    deduplication, or an exclusive upper bound.
  ② CLOCK SKEW. The source's clock and yours differ, so rows
    appear "before" your watermark and are never collected.
    ⇒ take the watermark from the SOURCE's own timestamps.
  ③ ⭐ UPDATES WITH AN UNCHANGED TIMESTAMP. Some systems modify
    a row without touching `updated_at`. That change is
    invisible to you forever.
  ④ ⭐ DELETES — THE ONE EVERYONE MISSES. A deleted row does not
    appear in "rows changed since". So incremental pipelines
    silently accumulate records that no longer exist upstream,
    and your headcount slowly drifts upward.
    ⇒ the fixes: soft deletes at the source, change data
      capture, or a periodic full reconciliation.

⭐ THE PRACTICAL PATTERN: INCREMENTAL DAILY, FULL RELOAD WEEKLY.
  You get the speed and a self-correcting mechanism that
  repairs whatever the increments missed. It is unglamorous and
  it is what keeps numbers trustworthy.
Data/AI 09

Batch versus stream

BatchStream
ShapeScheduled runs over a window of dataContinuous processing per event
FreshnessMinutes to a daySeconds
ComplexityLow. Re-runnable, debuggable, easy to reason aboutHigh. Late-arriving events, windowing, exactly-once semantics, state management
FailureRe-run the batchReplay from an offset, and hope your state was checkpointed
Right forAlmost everything in a business context — reporting, nightly scoring, reconciliationFraud detection, live dashboards, anything where seconds change a decision
The question that settles it

What decision changes if this is one hour fresher? If the answer is "none", batch is correct and streaming is a large amount of complexity bought for nothing.

For HR analytics the answer is almost always none — attrition risk does not change between 9am and 10am. "Real-time" is frequently a stated requirement that nobody can attach a decision to, and asking this question directly is one of the more valuable things you can do in a requirements conversation.

Data/AI 10

Data quality

Tests in the pipeline, not hope
⭐ THE FOUR KINDS OF TEST WORTH HAVING, AND THEY ARE CHEAP

  ①  SCHEMA — the columns and types are what we expect.
     Catches an upstream change before it corrupts anything
     downstream.
  ②  VOLUME — the row count is within expected bounds.
     ⭐ CATCHES THE PARTIAL LOAD, which is the most damaging
       silent failure: a run that succeeded with 12% of the
       data, so every number is quietly wrong.
  ③  UNIQUENESS AND REFERENTIAL INTEGRITY — one row per grain,
     no orphan foreign keys.
  ④  DISTRIBUTION — nulls, ranges and category sets roughly
     where they were. Catches "the satisfaction column is
     suddenly all zeros".

WHERE THEY GO
  ⭐ AS A GATE BETWEEN LAYERS, NOT AS A REPORT AFTERWARDS.
    A failing test should STOP the pipeline, not annotate it.
    ⚠ A data-quality dashboard nobody looks at is documentation
      of your problems, not prevention of them.

AND THE TWO HABITS FROM THE ANALYTICS SIDE THAT MATTER MOST
  · ⭐ QUANTIFY EVERY FINDING TWICE — BY ROW COUNT AND BY VALUE.
    "3% of rows are affected" and "those rows are 40% of total
    salary" are both true and lead to opposite decisions.
  · ⭐ RECONCILE TO A SOURCE NOBODY IN THE ARGUMENT CONTROLS.
    If your headcount matches the payroll system's, the number
    is defensible. If it only matches your own pipeline, it is
    not evidence.

⚠ AND THE FAILURE THAT DEFINES THIS SECTION: A PIPELINE THAT
  REPORTS SUCCESS AT EVERY STEP AND PRODUCED WRONG NUMBERS.
  Every test above exists to convert that into a loud failure.
Data/AI 11

Orchestration

Dependencies, not schedules
⚠ THE NAIVE APPROACH: schedule the extract at 01:00, the
  transform at 02:00, the report at 03:00, and hope each
  finishes in an hour.
  ⇒ THE DAY THE EXTRACT TAKES 70 MINUTES, THE TRANSFORM RUNS ON
    YESTERDAY'S DATA AND REPORTS SUCCESS. Nothing errors, and
    the numbers are wrong.

⭐ AN ORCHESTRATOR EXPRESSES DEPENDENCIES: the transform runs
  WHEN the extract succeeds. Time-based chaining is the bug;
  dependency-based execution is the fix.

WHAT AN ORCHESTRATOR GIVES YOU
  · a DAG with retries and failure handling per task
  · ⭐ BACKFILLS — re-running a date range as a first-class
    operation rather than an act of courage
  · visibility: what ran, when, how long, and what failed
  · ⭐ SLAs — an alert when a task has not completed by the time
    someone needs it, which is a different and more useful
    alarm than "it failed"

⭐ BACKFILLS ARE THE HARDEST ROUTINE OPERATION IN DATA, so the
  checklist matters:
  □ is the step IDEMPOTENT? ⇒ if not, stop; fix that first
  □ what is the date range, exactly?
  □ will it overwrite corrected values downstream?
  □ what will it cost — compute and metered API calls?
  □ ⭐ WILL IT RESTATE PUBLISHED NUMBERS? If last month's report
    changes, somebody must be told BEFORE they notice.
  □ can it run in chunks, so a failure is partial?

⭐ AND THE PART THAT KEEPS TRUST: WHEN A NUMBER CHANGES
  RETROSPECTIVELY, SAY SO. "As at" dating and a note beats a
  stakeholder discovering that last quarter moved.
Data/AI 12

Governance

Lineage

Which sources produced this number, through which steps. The first question asked when a figure is disputed, and unanswerable without it.

Ownership

Every dataset has a named owner. Unowned data rots, and nobody can approve access to it.

A catalogue

What exists, what it means, what the grain is. Prevents the same table being rebuilt three times under different names.

Classification

Which columns are sensitive — salary, health, disciplinary. This drives access control and masking, and in an HR system it is the foundation of everything else.

Retention

How long each dataset is kept, and what erasure requires. A legal commitment, not a storage preference.

Minimum cell size

An aggregate over three people identifies three people. Aggregation is not anonymisation, and filter combinations are a re-identification tool.

Data/AI 13

Should this use AI at all?

The first question, and it is asked far too rarely
⭐ USE RULES WHEN A RULE WORKS.
  "flag anyone with satisfaction below 0.3 and no promotion in
  three years" is auditable, instant, free, explainable, and
  often nearly as accurate.
  ⇒ AND IT CAN BE DEFENDED IN A ROOM. A rule you can state is
    worth a great deal in a domain where decisions affect
    people's jobs.

USE CLASSICAL ML WHEN
  · you have labelled historical outcomes
  · the data is tabular
  · you need the same answer twice for the same input
  ⭐ ⇒ THIS IS THE ATTRITION MODEL, AND GRADIENT BOOSTING WINS
    HERE. Not deep learning, and not an LLM.

USE AN LLM WHEN
  · the input is unstructured language
  · the task is generation, summarisation, extraction or
    classification with fuzzy categories
  · ⭐ AND AN OCCASIONAL WRONG ANSWER IS TOLERABLE, because it
    will happen

⚠ DO NOT USE AN LLM FOR
  · arithmetic or anything auditable ⇒ ⭐ THE DETERMINISTIC
    SYSTEM COMPUTES, THE MODEL NARRATES
  · tabular prediction with labels — boosting is better, cheaper
    and explainable
  · a decision that must be reproducible and defensible

⭐ THE TEST THAT SETTLES MOST DEBATES: WHAT IS THE COST OF BEING
  WRONG, AND WHO PAYS IT?
    a clumsy sentence in a summary ⇒ fine
    a wrong number in a board pack ⇒ not fine
    a person not shortlisted for a job ⇒ ⭐ AN ENTIRELY
      DIFFERENT BAR — fairness, explainability, records, and an
      appeal path.
Data/AI 14

Success metrics

Three layers, and only the third matters to the business
①  MODEL METRICS — precision, recall, PR-AUC, calibration.
   necessary, and ⚠ INVISIBLE TO STAKEHOLDERS. "PR-AUC improved
   to 0.71" answers no business question.

②  PRODUCT METRICS — is the feature being used, and does it
   work in situ?
   · what proportion of flagged employees get a conversation?
   · how often does a user override the suggestion?
     ⭐ THE OVERRIDE RATE IS THE BEST SINGLE SIGNAL YOU WILL
       GET. High and consistent overrides mean the model is
       wrong, or the interface is not trusted — and either way
       nobody told you in a survey.
   · time saved per task

③  BUSINESS METRICS — did the thing we care about change?
   · regretted attrition among flagged-and-contacted employees
     versus a comparable group
   ⭐ AND THE HARD PART: ATTRIBUTION. Attrition falls; was it
     the model, the pay review, or the labour market? ⇒ THIS IS
     WHY A HOLDOUT GROUP MATTERS EVEN WHEN IT FEELS
     UNNECESSARY. Without one you cannot claim the effect, and
     someone will eventually ask you to.

⚠ AND THE THREE TRAPS
  · CELEBRATING ①  ALONE. A better model nobody acts on has
    changed nothing.
  · GOODHART. Target "number of flags actioned" and you get
    box-ticking conversations.
  · ⭐ IGNORING THE FEEDBACK LOOP: acting on predictions changes
    the outcomes you later measure, so the model appears to
    become less accurate precisely when it is working. Say this
    out loud before anyone concludes it is broken.
Data/AI 15

Designing the interface

The UX decides whether the model is used or ignored
⭐ THE FIRST DESIGN DECISION, BEFORE ANY SCREEN: IS THIS
  ADVISING A HUMAN, OR ACTING?
  ADVISING  a display problem — show the evidence, make it
            checkable, let a person decide
  ACTING    an authorisation problem — permission checks in
            code, a record of what was done and why, and a way
            to undo it
  ⚠ MOST TEAMS BUILD THE SECOND WHILE THINKING ABOUT THE FIRST.

THE FIVE RULES THAT DECIDE ADOPTION

  ①  SHOW THE EVIDENCE, NOT JUST THE SCORE.
     "0.73" is unusable. "Low satisfaction, no promotion in
     four years, manager changed twice" is actionable — and it
     lets the reader disagree, which is what builds trust.

  ②  ⭐ FRAME IT AS A PROMPT, NOT A VERDICT.
     "worth a conversation this month" — not "will leave".
     ⇒ AND THE BASE-RATE ARITHMETIC REQUIRES THIS: with a 5%
       base rate, a good model's flags are majority
       false-positive. The framing must be honest about that or
       the feature will lose its credibility on first contact.

  ③  MAKE DISAGREEING EASY AND RECORDED.
     an override button that captures a reason. ⭐ IT IS YOUR
     BEST EVALUATION DATA AND YOUR BEST TRUST-BUILDING DEVICE,
     simultaneously.

  ④  BE HONEST ABOUT UNCERTAINTY.
     ranges, confidence bands, "not enough data for this
     employee". ⚠ A CONFIDENT WRONG ANSWER COSTS MORE TRUST
     THAN AN UNCERTAIN RIGHT ONE EARNS.

  ⑤  SET EXPECTATIONS BEFORE FIRST USE.
     what it does, what it does not do, how often it is wrong.
     ⭐ USERS FORGIVE A DISCLOSED LIMITATION AND DO NOT FORGIVE
       A DISCOVERED ONE.

⚠ AND FOR THIS DOMAIN SPECIFICALLY: THE EMPLOYEE IS A
  STAKEHOLDER TOO. Who can see that someone was flagged?
  What happens if they see it? That is a design question, and
  in some jurisdictions a legal one.
Data/AI 16

Cost-benefit

The arithmetic almost nobody brings
THE COSTS, ALL OF THEM
  BUILD        engineering weeks — including evaluation, which
               is usually underestimated by half
  RUN          ⭐ per-request, at realistic volume. Tokens, GPU
               hours, storage, the warehouse scans.
  MAINTAIN     ⭐ THE ONE ALWAYS OMITTED: monitoring, drift
               investigation, retraining, prompt updates when
               the provider changes a model. An AI feature has
               a permanent maintenance cost that ordinary code
               does not.
  RISK         a wrong answer's consequence, times its rate.
               In this domain: a discrimination exposure, and
               the reputational cost of a bad flag.

THE BENEFITS, HONESTLY
  time saved × people × frequency × loaded hourly cost
  ⚠ AND DISCOUNT IT: a feature used by four people twice a
    month saves less than the meeting that specified it cost.

⭐ THE SENTENCE TO BE ABLE TO SAY: "It costs about $0.004 per
  request, roughly $240 a month at current volume, and it saves
  each of eleven managers about two hours a month. Here are the
  three levers if we need the cost down."
  ⇒ ALMOST NOBODY BRINGS THAT NUMBER, and it is what turns an
    engineering proposal into a business decision.

⚠ AND THE CHEAPEST ALTERNATIVE, ALWAYS ON THE LIST: DO NOTHING,
  or a rule, or a better report. ⭐ SOMETIMES THE HONEST ANSWER
  IS THAT A FILTERED VIEW SOLVES 80% OF THIS FOR A DAY OF WORK
  AND NO ONGOING COST — and saying so is a senior act, not a
  defeat.
Data/AI 17

Common mistakes

The demo that cannot become a product

Impressive on five curated examples, unevaluated on the distribution of real inputs. The gap is the entire project.

No baseline

Nobody measured the rule, the spreadsheet, or the status quo. So "the model is good" has no reference point and cannot be defended.

Solving the interesting problem

Prediction is interesting; the actual bottleneck was that nobody can find last year's reviews. Ask what the person does all day.

Automating a broken process

An AI layer over a process nobody trusts produces faster distrust. Fix the process first.

Shipping without an eval set

Then nobody dares change the prompt, and a superstition stays frozen in production for a year.

Ignoring the maintenance

Launched, celebrated, unowned. Six months later it is quietly wrong and still running.

Data/AI 18

Where bias enters

Five entry points, and none of them are the algorithm
①  HISTORICAL BIAS — ⭐ THE DEEPEST AND LEAST FIXABLE
   the training data records past decisions, including
   discriminatory ones. A model that predicts who was promoted
   learns who WAS promoted, faithfully.
   ⇒ AND ACCURACY MAKES IT WORSE, NOT BETTER: a model that
     perfectly reproduces a biased history is a machine for
     perpetuating it at scale and with an appearance of
     objectivity.

②  REPRESENTATION BIAS
   a group is thinly represented, so the model is simply worse
   for them — and the aggregate metric hides it.
   ⇒ ⭐ ALWAYS EVALUATE PER SUBGROUP. An overall PR-AUC of 0.72
     can be 0.75 for one group and 0.51 for another, and the
     single number will never tell you.

③  MEASUREMENT BIAS
   the label is a proxy for what you actually care about, and
   the proxy is unequal. "Performance rating" measures a
   manager's judgement, and manager judgement varies
   systematically.

④  PROXY VARIABLES — ⭐ THE ONE PEOPLE THINK THEY HAVE SOLVED
   you removed gender and ethnicity. But postcode, school,
   name, working pattern, part-time status and career gaps all
   correlate with protected characteristics.
   ⇒ REMOVING THE OBVIOUS COLUMN IS NOT SUFFICIENT, and a model
     can be indirectly discriminatory with no protected
     attribute anywhere in its inputs.

⑤  FEEDBACK LOOPS
   flagged employees get attention, which changes their
   outcomes, which becomes training data. The model's beliefs
   become self-fulfilling.

⭐ THE ENGINEERING CONSEQUENCE: BIAS IS A DATA AND DESIGN
  PROBLEM, NOT A MODEL PROBLEM. Switching algorithms changes
  nothing on this list.
Data/AI 19

Fairness metrics — and why they conflict

DefinitionRequiresThe problem with it
Demographic parityThe same flag rate across groupsIgnores genuine differences in the outcome, and can require flagging people you have no reason to flag.
Equal opportunityThe same recall across groupsOften the most defensible for a beneficial intervention: everyone who needs help is equally likely to be found.
Equalised oddsThe same recall and false-positive rateStricter, and harder to satisfy without sacrificing accuracy.
Calibration within groupsA predicted 0.7 means 70 % in every groupReasonable, and mathematically incompatible with equalised odds when base rates differ between groups.
The result that matters, and it is not optional knowledge

These definitions are mutually incompatible. When base rates differ between groups, it is mathematically impossible to satisfy calibration and equalised odds simultaneously. This is proven, not a limitation of current technique.

So "is the model fair?" has no technical answer. Someone must decide which definition applies to this decision, and that is a policy choice belonging to the business, HR and legal — not to the engineer. Your job is to surface the trade-off, measure whichever definition is chosen, and document the choice. Choosing silently is the failure.

Data/AI 20

Explainability

Three levels, and only the third satisfies a person
①  GLOBAL — which features matter overall?
   feature importances. Useful for validation and for spotting
   leakage ⭐ (one feature dominating absurdly is usually a leak,
   not a discovery). ⚠ Says nothing about an individual.

②  LOCAL — why this prediction, for this person?
   per-prediction attributions. ⭐ THIS IS WHAT A MANAGER
   ACTUALLY NEEDS, and what makes the output checkable.

③  ACTIONABLE — what would change it?
   "if this person had been promoted in the last two years, the
   score would be materially lower."
   ⭐ THE ONLY LEVEL THAT ANSWERS THE QUESTION A PERSON ASKS,
     which is not "why" but "what now".

⚠ THE HONEST CAVEATS
  · ⭐ AN EXPLANATION IS NOT A CAUSE. Attributions describe the
    model's behaviour, not the world. "Tenure drove this score"
    does not mean changing tenure changes the outcome.
  · a plausible explanation increases trust whether or not it
    is correct ⇒ WHICH IS A RISK, not a benefit. Convincing
    explanations of a bad model are worse than none.
  · ⚠ NEVER LET AN LLM INVENT THE EXPLANATION. It will produce
    fluent, confident reasoning unrelated to the model's actual
    computation. ⭐ COMPUTE THE ATTRIBUTIONS, THEN LET THE MODEL
    PHRASE THEM — the same "compute, then narrate" rule.

⭐ AND FOR THIS DOMAIN: IF A DECISION AFFECTS SOMEONE'S
  EMPLOYMENT, AN EXPLANATION IS OFTEN A LEGAL REQUIREMENT AND
  ALWAYS AN ETHICAL ONE. ⇒ this is a real argument for a
  simpler model: a logistic regression whose coefficients you
  can state may be the correct engineering choice even at
  slightly lower accuracy.
Data/AI 21

HR-specific duties

What makes people data different
⭐ ONE FACT SETS THE BAR: THIS SYSTEM MAKES INFERENCES ABOUT
  IDENTIFIABLE PEOPLE'S LIVELIHOODS. Nearly every regulatory
  framework treats employment decisions as high-risk, and
  several treat them explicitly.

THE OBLIGATIONS THAT BECOME ENGINEERING REQUIREMENTS
  □  PURPOSE LIMITATION — data collected for payroll may not
     silently become model features. ⭐ THIS IS A DESIGN
     CONSTRAINT, and it is routinely violated by accident.
  □  DATA MINIMISATION — collect and retain what the purpose
     needs. "It might be a useful feature" is not a purpose.
  □  MEANINGFUL HUMAN REVIEW — a person who can actually
     override, with the information to do so. ⚠ A HUMAN WHO
     RUBBER-STAMPS IS NOT HUMAN REVIEW, and regulators say so.
  □  EXPLANATION — reflex 20.
  □  ACCESS AND CORRECTION — an employee can ask what is held
     and challenge it.
  □  ERASURE — ⭐ WHICH MUST REACH BACKUPS, LOGS, EXPORTS,
     ANALYTICS COPIES AND TRAINING SETS. A delete button on one
     table is not erasure, and this is the requirement most
     systems cannot actually satisfy.
  □  ⭐ RETRAINING AFTER ERASURE is an open, genuinely hard
     problem. Design so that removing an individual is
     tractable — which argues for retraining from a versioned
     dataset rather than incrementally.
  □  ACCESS AUDIT — who viewed whose record, retained.
  □  MINIMUM CELL SIZE on every aggregate. "Engagement in the
     Lisbon team" where the team is three people identifies
     three people.

⚠ AND THE ONE THAT IS PURELY A PROCESS FAILURE: PRODUCTION HR
  DATA IN STAGING. Salaries, reviews and health information in
  a lower environment with weaker access control. ⭐ ANONYMISE
  OR GENERATE — and "we only copied it once for testing" is
  exactly how these incidents are described afterwards.

The checklist

Before an AI feature affecting people goes live
PURPOSE
  □  can we state the decision this changes, in one sentence?
  □  is a rule sufficient? ⭐ was that seriously considered?
  □  is it advisory or decisive, and does the design match?

DATA
  □  are protected attributes and their PROXIES excluded, and
     is that documented?
  □  is the training data representative of everyone it will
     be applied to?
  □  is the dataset versioned, and does erasure reach it?

MODEL
  □  is it evaluated PER SUBGROUP, not only in aggregate?
  □  which fairness definition did we choose, and WHO chose it?
  □  is it calibrated, if a probability is shown to a human?
  □  is it better than the baseline, on a held-out set?

INTERFACE
  □  is the evidence shown alongside the score?
  □  is the framing honest about the false-positive rate?
  □  can a human override, and is the reason recorded?
  □  does the employee have any visibility or recourse?

OPERATIONS
  □  is drift monitored — inputs and outputs?
  □  is there an owner, and a review date?
  □  can we roll back to the previous model quickly?
  □  is access to predictions audited?
  □  ⭐ CAN WE TURN IT OFF WITHOUT A DEPLOY?

⭐ AND THE LAST QUESTION, WHICH IS THE MOST IMPORTANT ONE ON THE
  PAGE: WOULD WE BE COMFORTABLE EXPLAINING THIS SYSTEM, IN
  DETAIL, TO THE EMPLOYEES IT SCORES?

Agents in production

Data/AI 23

Demo to production

The escalation, and where to stop
   ONE CALL         you write the prompt. Deterministic path,
      │             cheapest, easiest to evaluate.
      ▼
   CHAINED CALLS    you write the sequence. Each step
      │             separately evaluable. ⭐ MOST PRODUCTION
      │             VALUE LIVES HERE, and it is unglamorous.
      ▼
   ROUTED           a classifier picks a branch. Still bounded.
      ▼
   AGENT            ⭐ THE MODEL chooses the sequence. Unbounded
                    paths, unbounded cost, every run different —
                    which is exactly what makes evaluation hard.

⭐ THE TEST: CAN YOU ENUMERATE THE STEPS IN ADVANCE?
  yes → build a pipeline, and get determinism, per-step evals
        and lower cost for free.
  genuinely no → an agent, with caps.

⚠ AGENTS ARE THE MOST OVER-APPLIED PATTERN IN THE FIELD. Most
  tasks people build agents for CAN be enumerated — which makes
  them pipelines wearing a costume, with worse economics and
  worse debuggability.

WHY THE DEMO-TO-PRODUCTION GAP IS SO LARGE
  a demo runs one happy path once, watched by its author.
  production means: ⚠ every path · hostile inputs · a tool
  that times out · a loop that will not terminate · a metered
  bill · and a user who is not you.
  ⭐ THE GAP IS NOT MODEL QUALITY. It is ordinary engineering
    discipline applied to a non-deterministic component.
Data/AI 24

Tool design

The tools are the agent — more than the prompt is
THE MECHANISM: you describe functions the model may call. It
does not execute them — it REQUESTS a call, YOUR CODE runs it,
and you return the result.
⭐ THE MODEL NEVER RUNS ANYTHING. It asks. Your code decides
  whether to comply, and that gap is where all your security
  lives.

⭐ THE TOOL DESCRIPTION IS A PROMPT. It is how the model decides
  whether and how to call it. ⇒ A VAGUE DESCRIPTION CAUSES WRONG
  TOOL CHOICE, AND THAT IS A DOCUMENTATION BUG, NOT A MODEL
  FAILURE.

THE RULES
  □  FEW, WELL-NAMED TOOLS beat many overlapping ones. Twenty
     similar tools produce confident wrong selections.
  □  ⭐ SCOPE EVERY TOOL TO THE CALLER, BUILT FROM THE VERIFIED
     SESSION. `get_employee(id)` must enforce the same
     ownership check as the endpoint — ⚠ NOT accept whatever id
     the model produced.
  □  SEPARATE READ FROM WRITE, and require confirmation for
     anything destructive or outward-facing.
  □  RETURN ERRORS AS DATA, not exceptions. "No employee with
     that id" lets the model recover; a crash ends the run.
  □  ⭐ KEEP RESULTS SMALL. Tool output accumulates in the
     context, and a tool returning 500 rows will exhaust the
     window and the budget within a few turns.
  □  MAKE WRITES IDEMPOTENT — the loop may retry.

⚠ AND THE SPECIFIC HAZARD: PROMPT INJECTION THROUGH TOOL
  RESULTS. A retrieved document, a CV or a ticket becomes part
  of the context, and its author is now instructing your model.
  ⭐ THE ONLY REAL DEFENCE IS THE TRUST BOUNDARY ABOVE: actions
    run with the session user's permissions, enforced in code.
    Then an injection that fully succeeds achieves nothing the
    user could not already do.
Data/AI 25

Guardrails

GuardrailWhy it is not optional
Iteration capAn unbounded loop is an unbounded bill. A confused agent will happily call the same tool forty times.
Token / cost budgetPer run and per user. Enforced in code, not hoped for.
Wall-clock timeoutA run that has taken four minutes is not going to finish well.
Tool allow-list per contextThe agent handling a public query does not get the tool that writes to the employee table.
Human confirmation for side effectsAnything that sends, deletes, pays or publishes. The last line before an irreversible action.
Output validationModel output is an input. Validate it against a schema before it reaches a database, a shell or an email.
A full traceEvery call, argument and result, stored. Without it an agent failure is unexplainable — and you will be asked to explain one.
A kill switchDisable the feature without a deploy. The first thing you want during an incident.
Data/AI 26

Evaluating agents

Harder than evaluating one call, and the shape is different
⚠ WHY IT IS HARDER: the path differs every run, so there is no
  single correct output to compare against. Two runs can both
  be right by different routes.

⭐ SO EVALUATE AT THREE LEVELS

  ①  THE OUTCOME — did it achieve the goal? A programmatic
     check where possible: was the record updated correctly, is
     the answer factually right against a known case.
  ②  THE TRAJECTORY — did it take a sensible path? Count the
     steps, the tool calls, the retries and the cost.
     ⭐ AN AGENT THAT SUCCEEDS IN FOURTEEN STEPS WHERE THREE
       WOULD DO IS A COST AND LATENCY PROBLEM THAT WILL BECOME
       A CORRECTNESS PROBLEM — long trajectories drift.
  ③  THE FAILURE MODE — when it fails, does it fail SAFELY?
     Does it stop and say so, or does it invent a result and
     proceed?

WHAT A USABLE EVAL SET LOOKS LIKE
  20–50 scenarios, each with a goal, a fixed starting state and
  a programmatic success check. ⭐ INCLUDING FAILURE SCENARIOS:
  a tool that errors, a missing record, a hostile document,
  an ambiguous request.
  ⇒ run it on every prompt, model or tool change, and record
    success rate, mean steps and mean cost together. All three
    move, and they trade against each other.

⚠ AND THE LLM-AS-JUDGE CAVEAT: using a model to grade output
  is useful and it is NOT free of error. ⭐ VALIDATE THE JUDGE
  AGAINST HUMAN LABELS ON A SAMPLE before trusting its scores —
  otherwise you have automated a bias and called it a metric.
Data/AI 27

MCP and the ecosystem

What the moving parts are, without the hype
MODEL CONTEXT PROTOCOL (MCP)
  a standard way to expose tools, data and prompts to a model
  host. ⭐ THE POINT: WRITE AN INTEGRATION ONCE AND ANY
  COMPATIBLE CLIENT CAN USE IT, instead of re-implementing
  per assistant.
  ⇒ so "an MCP server for our HR API" would let several tools
    query it with one integration.
  ⚠ AND THE SECURITY POINT THAT MATTERS: CONNECTING AN MCP
    SERVER GRANTS CAPABILITY. A server's description and tool
    names are text written by whoever wrote it — treat them as
    untrusted, and scope what it can reach.

AGENT FRAMEWORKS
  they supply a loop, tool plumbing, memory and often a graph
  abstraction.
  ⭐ THE HONEST GUIDANCE: BUILD THE LOOP DIRECTLY FIRST. It is
    perhaps fifty lines, and having written it you will
    understand what a framework does — and often find you do
    not need one. Frameworks hide exactly the mechanics you
    most need to control: context growth, retries, and where
    the authorisation check lives.

AUTONOMOUS CODING TOOLS
  agents that read a repository, edit many files and run
  commands.
  ⭐ THE DISCIPLINE THAT MAKES THEM SAFE IS FROM VOLUME I:
    commit first, keep their changes in their own commits, and
    review the diff rather than the result.

⭐ AND THE STRATEGIC READ FOR THIS WHOLE PART: THE FRAMEWORKS
  WILL CHANGE. What will not change is the evaluation set, the
  trust boundary, the cost model and the trace. Invest in those
  four; rent the rest.
Data/AI 28

Production failure modes

The infinite loop

Two tools that undo each other, or a retry with no cap. Caught by an iteration cap; found in the trace.

Context exhaustion

Tool results accumulate until the window fills and the earliest instructions fall out. Summarise, or return less.

Confident fabrication

A tool failed; the agent invented a plausible result and continued. Return errors as data and validate outputs.

The bill

One user, one bad Tuesday, thousands of calls. Budgets per run and per user, enforced in code.

Injection via content

A CV instructing the agent. Defended by the trust boundary, never by a prompt instruction.

Silent quality decay

The provider updated the default model; nothing errored and everything got slightly worse. Pin versions, and run the eval set.

Data/AI 29

Privacy-preserving AI

TechniqueIdeaRealistic use here
Federated learningTrain where the data lives; share model updates, not dataFor multiple entities that cannot pool data — separate legal entities, or on-device. Overkill for one HR database.
Differential privacyAdd calibrated noise so no individual is identifiable from an outputGenuinely useful for publishing aggregate statistics — engagement by team, pay-gap figures. The formal version of the minimum-cell-size rule. Costs accuracy, deliberately.

What to actually do

Two of these five pay off immediately in a project like this: synthetic data for lower environments, and differential-privacy thinking — or at minimum enforced minimum cell sizes — on any published aggregate.

The other three are worth being able to discuss and are not worth building. Knowing which is which is the skill.

Data/AI 30

Quantum awareness

One concrete implication, and it is not "quantum computers will break everything"
WHAT IS ACTUALLY AT RISK
  ⚠ ASYMMETRIC CRYPTOGRAPHY — RSA and elliptic curve. These
    underpin TLS key exchange and digital signatures.
  ✅ SYMMETRIC ENCRYPTION (AES) AND HASHES are largely fine;
    doubling key sizes is sufficient.
  ⇒ SO IT IS NOT "ALL ENCRYPTION BREAKS". It is specifically
    key exchange and signatures.

⭐ THE ONE IMPLICATION THAT MATTERS TODAY: HARVEST NOW, DECRYPT
  LATER.
  an adversary can record encrypted traffic today and decrypt
  it once capable hardware exists.
  ⇒ WHICH MEANS THE RELEVANT QUESTION IS: DOES ANY OF OUR DATA
    NEED TO STAY CONFIDENTIAL FOR TEN OR TWENTY YEARS?
    ⭐ FOR HR DATA — health information, disciplinary records,
      salary history — THE HONEST ANSWER IS YES. That is the
      one place this topic touches this project.

POST-QUANTUM CRYPTOGRAPHY
  standardised algorithms now exist and are being adopted in
  TLS libraries and cloud services.

⭐ WHAT TO ACTUALLY DO — AND IT IS SHORT
  □  know where you use TLS and what versions
  □  ⭐ PREFER MANAGED TLS from your cloud or CDN, so the
     migration happens to you rather than by you
  □  keep an inventory of long-lived encrypted data
  □  ⭐ CRYPTOGRAPHIC AGILITY IS THE REAL LESSON: can you change
     algorithm without rewriting the application? That property
     is worth having regardless of quantum computing, and it is
     the transferable takeaway.
  ⚠ DO NOT implement post-quantum cryptography yourself. Use
    the library.
Data/AI 31

WebAssembly and the edge

Two related ideas, and what each is genuinely for
WEBASSEMBLY — a portable binary format that runs in a
sandboxed VM at near-native speed.
  IN THE BROWSER: run compiled code — image processing, video
  editing, a CAD kernel, a database engine.
  ⭐ OUTSIDE THE BROWSER (WASI): a sandbox that starts in
    microseconds, which is why it is interesting for
    serverless and for plugins.
  ⇒ THE GENUINELY USEFUL PROPERTY: SAFE EXECUTION OF UNTRUSTED
    CODE. Stronger isolation than a container, far lighter than
    a VM. If you ever need to run a customer's script, this is
    the mechanism.

EDGE COMPUTING — run code in many locations near users.
  ✅ good for: latency-sensitive transforms, auth checks at the
     edge, personalisation of cached content, geo-routing, A/B
     assignment.
  ⚠ AND THE CONSTRAINTS ARE REAL: limited runtimes, tight CPU
    and memory limits, ⭐ AND YOUR DATABASE IS STILL IN ONE
    REGION. Edge compute plus a single-region database means
    every data-dependent request crosses the ocean anyway —
    which is the trap people fall into.

⭐ THE HONEST ASSESSMENT FOR THIS PROJECT: an internal HR
  dashboard used by staff in a few offices does not need edge
  compute. The frontend on a CDN is the useful 90% of the
  benefit.
  ⇒ TRACK IT; DO NOT ADOPT IT WITHOUT A LATENCY PROBLEM YOU
    HAVE MEASURED.
Data/AI 32

Workflow automation platforms

n8n and its relatives — when a visual workflow beats code
WHAT THEY ARE: a node-based editor where a trigger starts a
flow through connected steps — HTTP calls, transforms,
conditionals, and hundreds of prebuilt service integrations.

⭐ WHERE THEY GENUINELY WIN
  · GLUE BETWEEN SAAS PRODUCTS you would otherwise write and
    maintain integrations for
  · ⭐ WORKFLOWS A NON-ENGINEER SHOULD OWN AND EDIT — an HR
    onboarding checklist, an approval chain. That is the real
    argument: the person who owns the process owns the
    automation.
  · rapid prototyping of a process before committing code
  · scheduled internal jobs with visible run history

⚠ WHERE THEY LOSE, AND IT IS WORTH SAYING PLAINLY
  · ⭐ VERSION CONTROL AND REVIEW ARE WEAK. A visual workflow
    diffs badly, and a critical business process with no
    reviewable history is a liability.
  · testing is limited; complex logic becomes an unreadable
    graph
  · debugging a long flow is harder than debugging code
  · ⚠ THEY HOLD CREDENTIALS TO EVERYTHING THEY TOUCH, which
    makes the instance a high-value target. Self-hosted means
    you own that security.

⭐ THE DIVIDING LINE: USE A WORKFLOW TOOL FOR PROCESS
  AUTOMATION AT THE EDGE OF THE SYSTEM — notifications,
  approvals, syncing between tools. KEEP CORE BUSINESS LOGIC IN
  THE APPLICATION, where it is versioned, tested and reviewed.
  ⚠ THE FAILURE MODE IS DRIFT: the critical calculation ends up
    in a workflow nobody can review, owned by someone who has
    left.
Data/AI 33

Evaluating any new tool

The meta-skill, because the list above will be out of date
⭐ THE SIX QUESTIONS

  ①  WHAT SPECIFIC PROBLEM OF OURS DOES THIS SOLVE?
     if you cannot name it, stop. ⚠ "It's the future" and "a
     competitor uses it" are not problems.
  ②  WHAT IS THE ALTERNATIVE, INCLUDING DOING NOTHING?
     ⭐ AND HOW GOOD IS THE BORING OPTION? Frequently good
       enough, and it is the baseline this must beat.
  ③  WHAT DOES ADOPTION COST — REALLY?
     licence, plus learning, plus migration, plus the
     maintenance nobody budgets, plus the hiring implication.
  ④  WHAT IS THE EXIT?
     if this is wrong in a year, how hard is it to leave? ⭐ A
     TOOL THAT HOLDS YOUR DATA OR YOUR BUSINESS LOGIC IS A
     MUCH BIGGER COMMITMENT than one that processes it.
  ⑤  WHO OWNS IT AFTERWARDS?
     an unowned tool becomes an unmaintained dependency and
     then a risk.
  ⑥  HOW WILL WE KNOW IF IT WORKED?
     ⭐ DECIDE THE SUCCESS CRITERION BEFORE THE TRIAL, not
       after — otherwise the trial concludes whatever the
       person who wanted it already believed.

THE PROOF OF CONCEPT THAT IS ACTUALLY USEFUL
  □  timeboxed — two weeks, not "when we get to it"
  □  on a REAL problem with REAL data, not the vendor's demo
  □  with the success criterion written down in advance
  □  ⭐ INCLUDING THE HARD PART, not the easy path. Vendors
     demo the easy path; your adoption will live or die on the
     awkward integration.
  □  a written recommendation, either way — ⭐ AND "NO" IS A
     SUCCESSFUL POC. Two weeks spent avoiding a two-year
     mistake is an excellent trade.

data drift
Incoming feature distributions moving away from training. Detectable without labels.
concept drift
The relationship itself changing. Only detectable once outcomes arrive.
training/serving skew
A feature computed differently in training and in production. What feature stores exist to prevent.
point-in-time correctness
Using a feature's value as at the event, not as at now. Leakage prevention as infrastructure.
shadow mode
A new model predicting on real traffic with its output logged and unused.

Acting on predictions changes the outcomes you later train on.

Load raw, transform in place. Keeps the raw layer so you can rebuild.
watermark
The high-water mark an incremental load resumes from. Four ways to lose data.
idempotent step
Re-running produces the same result. What makes backfills safe.
backfill
Re-running a pipeline over past dates. The hardest routine data operation.
restatement
A published number changing retrospectively. Requires telling people.
lineage
Which sources and steps produced a number. The first thing asked in a dispute.

The floor below which an aggregate identifies individuals.

How often a human rejects the suggestion. The best trust signal you have.
proxy variable
A feature correlating with a protected attribute. Removing the obvious column is not enough.
demographic parity
Equal flag rates across groups. One of several incompatible fairness definitions.
equal opportunity
Equal recall across groups. Often the defensible choice for a beneficial intervention.

A person who can actually override, with the information to do so. Not a rubber stamp.

Model-requested actions run with the session user's permissions, enforced in code.
trajectory
The path an agent took. Evaluated alongside the outcome.

Using a model to grade output. Validate it against human labels first.

A standard for exposing tools and data to model hosts. Connecting one grants capability.

Calibrated noise making individuals unidentifiable in an output.
