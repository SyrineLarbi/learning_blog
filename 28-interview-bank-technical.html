How to use it

The grading format

Read the answers second

Answer out loud first, then read. The gap between what you said and the strong answer is the actual study material — and reading answers without attempting them produces recognition, not recall.

Each question has five parts: what it is really testing · a weak answer · a strong answer · the follow-up that arrives when your first answer is good · and the red flag that costs you the round.

On scope, stated honestly

The source bank holds roughly 1,030 questions across fourteen files. This edition covers every topic area with representative graded questions rather than reproducing all of them — the patterns transfer, and a bank you can finish beats one you can only skim. Where you want more questions on one area, the source file is named in each section.

Foundations

Prep file 01 — runtimes, types, async, HTTP, databases, the ORM.

Topic 01

Runtimes and environments

Junior · testing whether you know where code runs

What is the difference between Node.js and the browser as a JavaScript runtime?

Weak

"Node runs on the server and the browser runs on the client."

True, and it says nothing about what changes as a result.

Strong

"Both execute JavaScript, but they expose different capabilities. The browser gives you the DOM, window, fetch and storage — and it is a hostile environment, because the user can read and modify anything you send. Node gives you the filesystem, processes, environment variables and network sockets, and it is trusted. So the same language, but where a rule can actually be enforced is only Node."

Follow-up

"Where does TypeScript run?" — Nowhere. It is compiled to JavaScript first and the types are deleted. Which is why an annotation on an API response is a hope, not a check.

Red flag

Saying the browser is secure because the code is minified, or that a NEXT_PUBLIC_ variable is hidden from users.

Mid · testing reproducibility instincts

Why does a lock file matter, and should it be committed?

Strong

"package.json records what we asked for — often a range like ^11.0.0. The lock file records what we actually got, including every transitive dependency. Commit it: without it, two installs a month apart resolve differently, and you get a bug that appears on one machine and not another with no explanation. It is also a security property — it is what stops a fresh install pulling a newly compromised version."

Follow-up

"What is the difference between dependencies and devDependencies?" — runtime versus build-and-test, and the second is not shipped.

Red flag

"We delete the lock file when there's a conflict." That resolves the conflict by discarding reproducibility.

Topic 02

Types and TypeScript

Mid · the single most revealing TypeScript question

You type an API response as Employee and the code crashes at runtime. Why?

Weak

"The API returned the wrong shape, so the type was wrong."

Close, and it misses the mechanism.

Strong

"Because types are erased at compile time — nothing checked the response. Telling TypeScript the body is an Employee is an assertion, not a validation. A date field arrives as a string over JSON, so hiredAt.getFullYear() fails even though the compiler was satisfied. The fix is to validate at the boundary — a schema with Zod or class-validator — and let the type describe what the validator guarantees."

Follow-up

"So what should the type be before validation?" — unknown. You cannot use it until you narrow it, which is exactly the behaviour you want at a boundary.

Red flag

Reaching for as or ! as the fix. Both silence the compiler and keep the bug.

Senior · testing whether you design with the type system

How would you make it impossible to pass a user id where an organisation id is expected?

Strong

"Both being string is the problem — the compiler cannot tell them apart, so the wrong argument order compiles. I would give them distinct types, either branded types or small wrapper types, so the mistake becomes unrepresentable rather than merely unlikely. It is the same principle as a database constraint: prefer a mechanism that holds for every caller over a convention that holds for the ones who remembered."

Follow-up

"Where else does that principle apply?" — Omit<Employee,'salary'> as a public response type, and a literal union instead of a bare string for a role.

Topic 03

Async

Mid · asked in almost every screen

This endpoint fetches teams then employees, one after the other, and it is slow. What do you change?

Strong

"If they do not depend on each other, awaiting them sequentially doubles the latency for no reason — Promise.all runs them concurrently. But before that I would check whether there is a loop with an await inside it, because that is the more common and more damaging version: one query per item, so 200 employees means 201 round trips. The fix there is one query with an in filter and grouping in memory, or an include on the first call."

Follow-up

"How would you have found it?" — a trace, not a guess. And note it is invisible in development with four rows.

Red flag

"I'd add a cache." A cache in front of an N+1 hides the defect until it misses, and then you own two problems.

Junior · testing whether you understand the event loop

Does await block the server?

Strong

"No. It pauses that function, and the runtime carries on serving other requests. That is the whole point — JavaScript is single-threaded, so if a database call blocked, nothing else could happen. What does block is CPU-bound work: a heavy synchronous computation stalls every request, and that is a real trap when people put model inference inside an async handler."

Topic 04

HTTP and APIs

Mid · the question that separates readers from users

What is the difference between 401 and 403, and when would you return 404 instead?

Strong

"401 means unauthenticated — I do not know who you are; no token, a bad token, or an expired one. 403 means I know exactly who you are and you may not do this. And for a record that exists but is not yours, 404 is often the better answer, because a 403 confirms the record exists — which is itself a small leak."

Follow-up

"Which of those is a client bug and which is yours?" — both are 4xx, so neither should be retried; retrying a caller's-fault error can never succeed.

Red flag

Returning 200 with an error in the body. Every retry policy, monitor and load balancer trusts the status code, so your failures become invisible to all of them.

Senior · the most important API design question there is

A client calls your "create report" endpoint twice with the same payload. What happens?

Strong

"By default two reports, which is a real bug rather than a hypothetical — users double-click, phones re-send, and every network layer retries. The fix is a caller-supplied idempotency key that we store: the second request with the same key returns the first result instead of doing the work again. It matters most for anything that moves money, sends a message or starts a job. And it is the precondition for retries generally — you cannot safely retry an operation that is not idempotent."

Follow-up

"Which HTTP methods are naturally safe to repeat?" — GET, PUT and DELETE by definition; POST is not, which is why it needs the key.

Topic 05

Databases and SQL

Mid · a favourite because it catches confident wrong answers

Your total is three times too high after adding a join. Why?

Strong

"Fan-out. Joining to a table with several matching rows multiplies the rows on the left, so summing a salary after joining to three skills counts that salary three times. It is the most common source of inflated figures in reporting, and it produces a number that is wrong but plausible — nothing errors. I would aggregate the many-side first in a subquery or CTE, then join the single row."

Follow-up

"What else silently changes a count?" — an inner join dropping rows with no match, which makes orphans invisible; and COUNT(column) ignoring nulls where COUNT(*) would not.

Senior · testing whether you have read a plan

You have an index on the column and the query is still slow. Give me three reasons.

Strong

"One — a composite index only serves a prefix: an index on (team_id, hired_at) cannot serve a filter on hired_at alone. Two — a function on the column defeats it; LOWER(email) = … cannot use an index on email. Three — a leading wildcard, LIKE '%ch%', is a scan by definition. And I would confirm rather than guess: EXPLAIN ANALYZE, and specifically the estimated-versus-actual row counts, because a large gap means the planner chose a strategy for the wrong problem."

Topic 06

The ORM

Mid · testing whether you know what the tool hides

What does an ORM cost you?

Strong

"Visibility. You get generated types, parameterised queries and reviewable migrations — genuinely valuable — but you no longer see the SQL, so an inefficient query is invisible until it is slow. The N+1 is one line away and reads perfectly. So I turn query logging on early, and I use select rather than include for anything user-facing, which is both faster and the mechanism that keeps a salary out of a payload."

Follow-up

"When do you drop to raw SQL?" — window functions, recursive queries, multi-level aggregation. And parameterise it: a template literal in a raw query is the one place injection re-enters.

Red flag

Creating a new client per request, or per service. Providers are singletons for a reason — otherwise you have twenty connection pools.

Topic 07

React state

Junior · and a surprising number of people get it wrong

You push to an array in state and the UI does not update. Why?

Strong

"React decides whether to re-render by comparing references. Mutating the array leaves the reference identical, so React concludes nothing changed. You have to create a new array — spread it and add the item — and call the setter. The same applies to objects, and it is shallow: nested objects are still shared with the original."

Follow-up

"Two consecutive setCount(count + 1) calls — what happens?" — both read the same value, so it increments once. The function form setCount(c => c + 1) fixes it.

Senior · testing information architecture, not React trivia

Where should the state for a filtered, paginated table live?

Strong

"The filters, the sort and the page number belong in the URL — then the view can be shared, bookmarked, and reached with the back button, and the server can render it. The rows themselves are server data, cached and revalidated, never copied into local state so we can edit it, because the copy goes stale and the save overwrites someone else's change. Purely visual state — an open menu — stays local. And anything derivable, like a total, is computed at render rather than stored, or it drifts out of step with the rows it sums."

Red flag

Putting everything in a global store because it is "easier to reach", then wondering why every keystroke re-renders the page.

Topic 08

Rendering and effects

Mid · the bug that looks like a haunting

A checked checkbox jumps to the wrong row after you delete an item. What did you do?

Strong

"Used the array index as the key. Delete the first of five and every remaining index shifts, so React thinks item 0's content changed rather than that item 0 was removed. It keeps the DOM node and swaps the data — and any state inside that node, like a checkbox or half-typed text, stays where it was. The key has to be stable and unique: the database id, essentially always."

Follow-up

"When is an index acceptable?" — a list that never reorders, never filters and never loses items. Rare enough to treat as never.

Mid · testing whether you understand what effects are for

When should you use useEffect?

Strong

"For synchronising with something outside React — a subscription, a socket, a browser API, a timer. Not for deriving values from props, which causes a second render and can loop; and not for responding to a user action, which belongs in the handler. And every effect that opens something must close it in its cleanup, or navigating twenty times leaves twenty live sockets."

Red flag

An effect with no dependency array "so it stays up to date". That runs after every render, and often forever.

Topic 09

Next.js

Senior · the question with a security answer

What are the risks of the App Router's server components and server actions?

Strong

"Two that matter. First, 'use client' applies to everything a component imports, so one careless directive high in the tree drags the whole subtree into the browser bundle — including code you thought was server-only. Second, and more serious: a server action is a public endpoint. It is reachable by anyone who can craft the request, so 'it is only called from that form' is not a control — it needs its own authentication and ownership checks in its body, exactly like a REST route."

Follow-up

"And caching?" — rendering mode is inferred, not declared, so an authenticated page can silently stay static and serve one user's data to another. Be explicit about no-cache for per-user data.

Mid · everyone hits this error eventually

"Text content did not match server-rendered HTML." What causes it?

Strong

"The server rendered one thing and the browser's first render produced another. Almost always new Date() or Math.random() in render, reading localStorage or window — which do not exist on the server — or a timezone difference. The fix is to make the first render identical on both sides and move the browser-only value into an effect. Not to suppress the warning."

Topic 10

Performance in the browser

Mid · testing whether you measure

The dashboard feels slow. Walk me through diagnosing it.

Strong

"First: slow at what — first load, or interaction? They have different causes. Slow first load is usually bundle size, and I would look at what is actually in the bundle rather than guess; it is normally one heavy dependency. Slow interaction is usually re-render scope — state lifted too high, so every keystroke re-renders a large subtree. Slow data is a waterfall of sequential requests, which a server component removes entirely. And I would check the percentiles rather than the average, because the average is dominated by the fast cases."

Red flag

Wrapping everything in useMemo before measuring. Memoisation has its own cost, and it is not free.

Topic 11

Complexity

Junior · asked to check you can reason, not recite

What does O(n log n) mean, and why does it matter?

Strong

"It describes how the work grows with the input, ignoring constants. It is the practical floor for comparison sorting, which is why the built-in sort is fine and I would not write my own. What matters day to day is the shape: for a million items, O(log n) is about 20 operations, O(n) is a million, and O(n²) is a trillion — so the only distinction I check most days is whether something is nested over the same collection."

Follow-up

"Where do hidden nested loops appear?" — includes inside map, and a database query inside a loop. Both look like one call.

Red flag

Quoting complexity while ignoring constants that dominate in practice: an O(n) algorithm with a network call per item is far worse than an O(n²) one over 100 in-memory items.

Topic 12

Structures

Mid · the highest-value structure question

You need to attach each employee to their team. Both are arrays. How?

Strong

"Build a Map from team id to team once, then look each one up in constant time — O(n + m) instead of O(n × m). Searching a list inside a loop over another list is the most common accidental quadratic in application code, and this is a one-line fix. It is the same idea as a database index: spend memory to buy time."

Follow-up

"Object or Map?" — Map. Object keys are coerced to strings, so obj[1] and obj["1"] collide, and an object cannot key on an object.

Senior · testing whether you push work to the right layer

You need the ten highest-risk employees out of fifty thousand.

Strong

"Conceptually that is a top-k problem — a heap of size ten gives O(n log k) time and O(k) space rather than sorting everything. But in this system the right answer is ORDER BY risk DESC LIMIT 10 with an index on risk: the database does exactly that, reads ten rows, and never sends fifty thousand over the wire. The point of knowing the structure is recognising that fetching everything to sort in Node is the wrong shape of solution."

Topic 13

Algorithms in real work

Senior · a question about judgement disguised as trivia

Name an algorithm you have actually used at work.

Strong

"Binary search — as a debugging technique rather than in code. git bisect to find the commit that introduced a bug, and halving an import file to find the record that breaks it. Any time you can ask a yes/no question that eliminates half the possibilities, you have turned a linear hunt into a logarithmic one. The other one is a topological sort, which is what a migration runner and a CI pipeline both do — and it is how a circular dependency gets detected."

Red flag

Reciting sorting algorithms from memory. Nobody is hiring for that, and it signals puzzle practice rather than experience.

Topic 14

The request journey

Mid–senior · a standard opener, and a good one

Walk me through what happens when a user opens your dashboard.

Strong

"DNS resolves the host — cached at several levels, which is why the first request is slower. Then a TCP handshake, one round trip, then TLS, another one or two. So there is roughly three to four round trips of setup before my request is even sent, which is why connection reuse matters so much. Then the request hits a load balancer, my app, the guards, validation, the service, the database. The HTML comes back, the browser requests the sub-resources, builds the DOM and CSSOM, lays out, paints, and hydrates. Naming the step is most of the diagnosis when someone says it is slow."

Follow-up

"Which step would you suspect first if it is slow only for one office?" — DNS or geography; and if it is slow for everyone after a deploy, my code.

Topic 15

CORS and browser rules

Mid · the most misunderstood error in web development

The console shows a CORS error but the server log shows a clean 200. Explain.

Strong

"CORS is a browser rule, not a server error. The request was sent and answered — the browser is refusing to hand the response to my JavaScript because the server did not say that origin is allowed. That contradiction is the whole confusion. And an origin is scheme plus host plus port, so localhost:3001 and localhost:3010 are different origins, which is why we meet this in development. The fix is on the server, naming the allowed origins."

Follow-up

"Why does my POST not appear in the logs at all?" — the preflight OPTIONS request failed, so the POST was never sent. Your route must handle OPTIONS.

Red flag

"I fixed it with origin: '*'." That is a development shortcut, it cannot be combined with credentials, and shipped to production it lets any site call your API with a user's browser. And CORS is not access control — it protects the user, not your server.

Topic 16

Advanced SQL

Senior · separates people who use SQL from people who know it

You need each employee plus their department's average salary, in one query.

Strong

"A window function: AVG(salary) OVER (PARTITION BY department). GROUP BY collapses the rows and I need to keep them. The alternative — a subquery per row, or fetching everything and computing in application code — is an N+1 in disguise. Same tool solves 'rank within team' with ROW_NUMBER() and month-over-month change with LAG(), which otherwise needs a self-join."

Follow-up

"Can you filter on the window result in the same WHERE?" — No: window functions run after WHERE. Wrap it in a CTE and filter outside. That catches everyone once.

Topic 17

Transactions

Senior · the concurrency question that matters

Two requests both decrement a balance of 100 by 80, inside transactions. What happens?

Strong

"Under Postgres's default isolation, read committed, both read 100, both compute 20, both write 20 — and one withdrawal has vanished. A transaction alone does not prevent that; it is a lost update. The best fix is to let the database do the arithmetic: SET balance = balance - 80 is atomic, needs no read, and removes the race. Otherwise optimistic locking with a version column, or SELECT … FOR UPDATE held briefly."

Follow-up

"What is the rule for transaction scope?" — keep it short and never make a network call inside one. Holding locks and a pooled connection while waiting on another service is how one slow dependency becomes a database-wide outage.

Reference

The red flags, collected

Silencing the compiler

as, ! or any offered as a fix. All three keep the bug and remove the warning.

Security by obscurity

Minified code, a hidden button or a NEXT_PUBLIC_ variable described as protection.

Caching over a defect

A cache proposed before the query has been read. It hides the problem until it misses.

200 with an error body

Makes every failure invisible to retries, monitoring and load balancers.

Disabling browser security

A wildcard CORS origin, or a disabled certificate check, described as the fix.

Optimising without measuring

Any performance answer with no trace, profile or percentile in it.

Index-as-key

Offered as normal practice rather than as a narrow exception.

Reciting over reasoning

Complexity classes or sorting algorithms quoted with no connection to a decision.
