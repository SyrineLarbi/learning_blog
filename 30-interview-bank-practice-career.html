What changes in this bank

In Banks I and II a strong answer is largely a correct one. Here, almost every strong answer contains a trade-off and a consequence — "I chose X over Y because Z, and it costs me W." An answer with no cost in it reads as inexperience even when the content is right.

Part I

AI-era development

Prep file 06 — and increasingly asked in every round.

Topic 01

Working with the tools

Mid–senior · now a standard question, and answered badly

How do you use AI coding assistants in your work?

Weak

"All the time, it makes me much faster." — or the reverse, "I don't, I prefer to write my own code." Both read as unconsidered.

Strong

"For boilerplate that matches an existing pattern, translation between formats, explaining unfamiliar code, and a first draft to react to. Not for anything security-critical, and not for decisions that depend on context it cannot see. I keep a project instruction file with the stack and versions, because version drift is the most common failure — it will confidently write the pre-7 Prisma client constructor. And I review everything against a fixed pass: does it do what I asked, is everything it references real, are the edge cases handled, is authorisation there, does it fit our patterns, is it more complicated than necessary."

Follow-up

"What has it got wrong for you?" — have a real example. Invented method names, a missing ownership check, an N+1 in a loop. The specificity is the credibility.

Red flag

Not being able to name a failure mode. It signals you have not been reviewing the output.

Topic 02

Evaluating output

Senior · the question that actually differentiates now

A colleague opens a 600-line generated PR. How do you review it?

Strong

"First I would push back on the size, because a 600-line diff gets reviewed at roughly the same quality as any 600-line diff — which is to say poorly — and that is upstream of anything I can do as a reviewer. Then I ask the author to describe what it does in their own words, not as a challenge but because if they cannot, it is not ready. Then I read the diff rather than the new file, and I search it mechanically: every catch block for a swallowed error, every loop for a query inside it, every raw query for interpolation, every new dependency, every changed default. And I do not trust generated tests for generated code — both encode the same guess."

Follow-up

"What is different about generated code in review?" — it is uniformly well-formatted and idiomatic, so every surface cue you normally use to sense something is off has been removed. It never looks suspicious.

Topic 03

The honest position

Senior · a strategy question wearing a tools question's clothes

Does AI make engineers less valuable?

Strong

"It made producing code much cheaper, which moved the bottleneck rather than removing it. What got more valuable is judging whether output is correct, deciding what should be built, and owning the outcome — and the volume of code nobody fully read is now growing, which makes review, evaluation and debugging worth more, not less. What did depreciate is routine implementation as a differentiator. Those were always the senior skills; the change is that they are now the main skills rather than the ones you grow into."

Red flag

Either extreme — dismissing the tools, or claiming they have replaced the need for understanding. Both suggest you have not used them seriously.

Part II

Engineering excellence

Prep file 07 — review, debugging, testing, security, performance.

Topic 04

Code review

Mid–senior · asked of anyone senior-titled

What do you look for in a code review, in order?

Strong

"Does it do the right thing — I read the description then the code and check they match, because the most expensive defect is a correct solution to the wrong problem. Then authorisation: every id from outside checked against the caller on this path. Then the edge cases. Then what else does this change, which is the question juniors skip and which is only visible in the diff — a changed default, a changed error case, a removed field. Then migrations, which get disproportionate attention because they have no undo. Complexity and names last. And I do not spend review on formatting; that is automated."

Follow-up

"How do you phrase a blocking comment?" — the failure, the consequence, then a suggestion. And label severity: blocking, suggestion, question, nit. Without labels, twelve nits read as a rejection.

Red flag

Describing review as gatekeeping, or as mainly catching bugs. Its biggest output is that two people now understand the change.

Topic 05

Debugging

Senior · your best story, and prepare it

Tell me about the hardest bug you have fixed.

Strong

"Structure it in six beats: the symptom, why the obvious theory was wrong, how I narrowed it, the moment it clicked, the fix — and then what I changed so the class cannot recur. That last beat is the scoring one: a constraint added, a type tightened, a check moved to a path every caller traverses. Without it the story ends at 'I fixed it', which is a junior ending. I would also name a wrong turn — two hours on the cache before checking whether the data was already wrong upstream — because honesty about a wrong turn reads as confidence."

Follow-up

"How do you approach an intermittent bug?" — almost always one of five things: a race, a retry, a cache, a clock, or one bad instance in a pool. Find which instance served the failure.

Red flag

A story that ends with "it went away" or with a patch and no mechanism. And picking a bug whose cause you cannot explain.

Topic 06

Testing

Mid–senior · testing whether you have opinions

What is your testing strategy, and what do you not test?

Strong

"Weighted toward integration tests, because in a web application most defects live in the seams — a missing permission check, a wrong join, a validation that did not fire — and a unit test of a mocked service cannot see any of them. My highest-value test is one per endpoint asserting four things: the happy path, 401 unauthenticated, 403 wrong owner, 400 invalid input. What I do not test: framework behaviour, getters, exact markup, and implementation details — a test that must be rewritten every time I tidy the code is a tax on improvement."

Follow-up

"Coverage target?" — coverage measures execution, not assertion, so it is a useful map of what is untested and a terrible target. If the risk engine is at 20% and the mappers at 100%, the number is fine and the situation is not.

Red flag

Mocking your own database. Then the tests assert that you called it the way you thought you should — a test of your assumptions, not of the query.

Topic 07

Security

Senior · and the answer people get wrong

What is the most likely vulnerability in an application like ours?

Strong

"Broken access control — not injection. A correctly formed request from a logged-in user carrying someone else's id, which the code serves because it authenticated the caller and never asked whether this caller may see this record. A role check does not cover it: 'managers may view employees' is true, but this manager may only view their team. And in an HR system it compounds, because permissions are per-field: salary, sickness and a disciplinary note have completely different audiences, so one endpoint returning 'the employee' returns all of it regardless of what the UI shows."

Follow-up

"Where does the check go?" — one path every caller must traverse. A check repeated in forty handlers will be missing from the forty-first, written on a Friday.

Red flag

Treating the UI as a boundary — hidden buttons or disabled fields offered as protection. And describing a wildcard CORS origin as a fix.

Topic 08

Performance

Mid–senior · a scenario, and they want your process

An endpoint that was fine last month now takes eight seconds. Go.

Strong

"'Was fine last month' is the most informative part — a nonlinear change means a threshold was crossed rather than gradual load. Usually a query that lost its index as the table grew, a saturated connection pool, or a queue whose arrival rate passed its service rate. So: get one real trace before touching anything, look at the p95 rather than the average, and find where the time actually goes. Four candidates in order of likelihood: too many round trips, one bad query, per-row work that should be done once, or waiting on another service. And I would ask whether the work is necessary at all — the fastest query is the one you do not run."

Follow-up

"When would you add a cache?" — after fixing the query, adding the index and removing the round trips. Caching first buys speed and keeps the defect, and hides it until the cache misses.

Red flag

Any answer with no measurement in it. And optimising against development data, where four rows conceal every N+1.

Topic 09

Git and branching

Mid · a competence check with one right instinct

Merge or rebase?

Strong

"Rebase my own unpushed work to keep history linear; merge anything shared, because rebasing rewrites commits and anyone who has pulled them now has a diverging history that is genuinely painful to reconcile. So: rebase before you push, merge after. And what matters more than the choice is that the team makes one and configures it — half rebasing and half merging produces a history nobody can read."

Follow-up

"How do you undo something already deployed?" — revert, which adds a commit and is safe on a shared branch. Not reset, which rewrites history.

Bonus

Mentioning reflog unprompted is a strong signal — it is the undo button for almost everything and very few people know it.

Topic 10

Containers

Mid · testing whether you understand the model

Your Docker build takes six minutes every time. Why, and what do you change?

Strong

"Almost certainly instruction order. Each instruction is a cached layer, so COPY . . before npm ci means any source edit invalidates the copy layer and dependencies reinstall on every build. Copy the manifest, install, then copy the source — dependencies stay cached until the manifest changes. I would also use a multi-stage build so the shipped image has no compilers or dev dependencies, and a .dockerignore, which is not just tidiness: it is what stops you baking a .env into the image."

Follow-up

"Why can't your app be reached inside a container?" — it bound to 127.0.0.1. Bind to 0.0.0.0. And inside Compose, services reach each other by service name, not localhost.

Red flag

Believing a deleted file is gone from the image. Layers are additive — a secret copied in and then removed is still extractable.

Topic 11

CI/CD and deploys

Senior · the deployment question that matters most

You need to rename a database column. Walk me through shipping that safely.

Strong

"Not in one deploy, because during a rolling deploy two versions of the code are running against one database — so a rename breaks whichever instances have not been replaced yet. Three deploys: add the new column and write to both; migrate reads over and backfill; then drop the old column once nothing references it. Expand, migrate, contract. And separately: tag images with the commit SHA rather than latest, or 'which code is in production' and 'what do I roll back to' have no answer — which is exactly what you need during an incident."

Follow-up

"What makes a pipeline trustworthy?" — it is the only route to production, it builds once and promotes the same artefact, and it has no flaky tests. Once failures are assumed to be noise, it has stopped catching anything.

Topic 12

Observability

Mid–senior · a cheap question with a revealing answer

A request is slow and three services were involved. How do you find where?

Strong

"With a correlation id — generated at the edge, passed in a header to every downstream call, logged on every line. Then one grep reconstructs the whole request across all three services. That is about twenty lines of middleware and it is the difference between debugging a distributed system and guessing at one. Beyond that: metrics tell me something is wrong, traces tell me where, logs tell me why — and a team with only logs finds out late and greps blindly."

Follow-up

"What do you alert on?" — user-visible symptoms, not causes. High CPU with fine latency is a machine doing its job; an alert that fires and is ignored trains everyone to ignore the channel.

Red flag

Logging personal data or tokens. Logs are readable by more people and retained longer than your database.

Topic 13

Incidents

Senior · they are listening for one specific instinct

Production is down and you have a theory. What do you do first?

Strong

"Mitigate, not diagnose. Roll back, disable the flag, fail over, shed load — while users are affected, 'let me just find out why' is the wrong instinct, and a rollback I can explain later beats a root cause found while the site is down. Then the first four questions: what is the impact, when did it start, what changed, can we undo it. One person coordinates and communicates while everyone else investigates, and I write a timeline as I go because I will not remember it. And before restarting anything I capture the logs and state, because a restart that 'fixes' it also removes the only chance to learn why."

Follow-up

"And afterwards?" — the question is what made this possible, never who did it. Three outputs: what stops the class, what detects it sooner, what makes it smaller. "We'll be more careful" is a wish, not an action item.

Part IV

Cloud

Prep file 10 — compute choices, identity, cost.

Topic 14

Where code runs

Mid–senior · testing proportion, not knowledge

How would you deploy our three services?

Strong

"Containers on a managed container platform. We keep the reproducibility and portability of an image and hand off scaling, restarts, TLS and rolling deploys. Not Kubernetes — three containers do not justify a platform you have to operate, and the real cost there is ongoing expertise. Not functions for the API or the model service, because of cold starts and, more importantly, connection exhaustion: a hundred concurrent instances each opening database connections will exhaust Postgres at almost no CPU, which is why a pooler is mandatory with serverless."

Follow-up

"Why managed Postgres rather than self-hosted?" — every layer you manage is a layer you patch, monitor, scale and get woken by. A small team running its own cluster has spent its scarcest resource on something a provider does better.

Red flag

Proposing Kubernetes or microservices by default. It reads as inexperience rather than ambition.

Topic 15

Identity and access

Senior · the cloud question that causes real incidents

How do you scope permissions for the AI service?

Strong

"Least privilege, actually applied: it needs to read the model artefact from object storage and nothing else — no write, no delete, and no access to the employee database at all. A role attached to the workload rather than a static key, so the platform rotates it and there is no long-lived secret to commit or paste. And the review question I would ask of any setup: if this one component were compromised, what could the attacker reach? If the answer is 'everything', the permissions are the vulnerability whatever else is in place."

Follow-up

"What are the misconfigurations that actually cause breaches?" — a public object store bucket, a database reachable from the internet, an over-permissive security group or CORS, and secrets visible in a console or a build log. None of them are clever attacks.

Topic 16

Cost

Senior · very few candidates can answer this well

How would you reduce our cloud bill?

Strong

"In order of money recovered per hour spent. First, turn off what nobody uses — idle staging environments, oversized instances left from a load test, unattached disks, forgotten experiments; and schedule non-production to stop overnight, which is roughly a 70% saving on it for one configuration change. Then right-size against a month of actual utilisation. Then commit to steady baseline load for a discount. And the largest structural savings are usually engineering problems rather than procurement ones: an N+1 tripling database load, a missing cache on a hot read, a log level writing terabytes, or a metered API called in a loop."

Follow-up

"What is the habit?" — tag everything by environment, service and owner, because untagged spend cannot be attributed or questioned; and a budget alert on day one, which is a security control as much as a financial one, since a leaked credential shows up as a bill within hours.

Career and culture

Topic 17

Decisions and trade-offs

Senior · the single most repeated senior question

Tell me about a technical decision you made and would make differently.

Strong

"The structure that works: the constraint, the options, why I chose one, what it cost, and what I know now. The cost clause is the part that matters — a decision without a stated cost is a default wearing a decision's clothes. And 'would make differently' should be a genuine change of judgement, not a humblebrag: something where the trade-off turned out worse than I priced it, and where I can say which signal I should have weighted more."

Follow-up

"How do you decide how much time to spend deciding?" — classify it. Reversible and cheap: just decide. Irreversible — data models, public APIs, a vendor holding your data: slow down. Most engineering decisions are far more reversible than they feel.

Red flag

Naming no cost at all, or describing a decision with no alternative considered.

Topic 18

Estimation

Mid–senior · a trust question, not a maths question

How do you estimate, and what do you do when you are wrong?

Strong

"Decompose until each piece is a day or less, because estimation error compounds with size — a 'two week' task is a guess and ten one-day tasks is an estimate. Then give a range with the condition attached: 'three to eight days; eight if the legacy export format is undocumented.' The condition is the useful part, because it tells everyone what to resolve to narrow it. And anything genuinely unknown becomes a timeboxed spike before I estimate it, because estimating something I do not understand is fiction with a number attached."

Follow-up

"And when it slips?" — tell people early. A revised date is a manageable problem; a missed date discovered on the day is a trust problem, and trust is what seniority is made of.

Red flag

Confident single numbers with no conditions, or silence until the deadline.

Topic 19

Saying no

Senior · testing whether you can be trusted with priorities

A stakeholder asks for something you think is a bad idea. What do you do?

Strong

"Use the trade-off sentence rather than a refusal: 'I can do that — it means X slips by two weeks. Is that the right priority?' That accepts the work, surfaces the real cost, and puts the prioritisation where it belongs. If the problem is the approach rather than the priority, the stronger form is 'not this, but here is what solves the problem' — which requires having asked what they will actually do with it. And I would say what I recommend, because presenting options with no recommendation is abdication dressed as neutrality."

Follow-up

"Is there anything you would refuse outright?" — yes, and it is worth having the list: shipping a known data-leak, removing a permission check to hit a date, or an AI feature making employment decisions with no human review. Those are not prioritisation conversations; you state the reason in writing and escalate.

Topic 20

Behavioural questions

The structure, and where people lose the answer
THE FRAME: SITUATION · TASK · ACTION · RESULT
  ⭐ AND THE FIFTH BEAT THAT MOST PEOPLE OMIT: WHAT YOU CHANGED
    AFTERWARDS. A story that ends at the result is a story about
    one event; a story that ends with a structural change is a
    story about how you work.

⚠ WHERE ANSWERS GO WRONG
  · "WE" WITH NO "I". The interviewer cannot score a team. Say
    what you personally decided and did.
  · NO NUMBERS. "Much faster" versus "50 seconds to 6" — one is
    a claim, the other is evidence.
  · NO CONFLICT. A story with no disagreement, constraint or
    wrong turn in it reads as sanitised.
  · TOO LONG. Two minutes. If they want depth they will ask —
    and the follow-up is where the real scoring happens.

⭐ PREPARE FIVE STORIES, NOT TWENTY. They recombine:
  ①  a hard technical problem you diagnosed
  ②  a disagreement you handled well
  ③  something you shipped that was wrong, and what you did
  ④  a time you changed someone's mind with evidence
  ⑤  a time you said no, or cut scope, and were right

⭐ THE ONE ABOUT FAILURE IS THE MOST IMPORTANT. A real failure,
  owned without excuses, with the specific change it caused, is
  the strongest answer available in a behavioural round — and a
  deflected one ("my weakness is caring too much") is the
  weakest.
Topic 21

Business acumen

Senior · rare, and it separates candidates instantly

How would you justify spending a week on technical debt?

Strong

"By quantifying the interest rather than describing the mess. 'The code is messy' funds nothing. 'Every change to reporting takes three days instead of one because the logic is duplicated in four places, and we make about two changes a month' is a cost that can be prioritised against features. Same translation everywhere: not 'this reduces risk' but 'this removes a failure mode that caused two incidents this quarter, each costing about four hours of eleven people's time.'"

Follow-up

"Where does cloud spend sit in the accounts?" — usually cost of sales, which makes infrastructure efficiency a gross-margin conversation rather than only an engineering one. Knowing that changes who listens.

Topic 22

Growth

Any tier · the closing question you will definitely get

How do you keep learning?

Weak

"I read newsletters and follow people on social media." — unfalsifiable and forgettable.

Strong

"Mostly from the problem in front of me, because depth acquired while solving something real sticks and depth from a tutorial for a problem I do not have evaporates. Concretely: I read one system's design a month and work out why it is shaped that way, because architecture intuition is pattern exposure. I write things down — explaining something exposes every gap instantly. And I filter deliberately: fundamentals deeply, tools on demand, news skimmed, because the field emits more than anyone can absorb and feeling behind is what that stream is designed to produce."

Follow-up

"What are you learning now?" — have a real, specific answer with something you have built or read, however small. Vagueness here undoes the previous paragraph.

Reference

The red flags, collected

No cost named

A decision described with no trade-off. The single most common senior-round failure.

"We" with no "I"

The interviewer cannot score a team's contribution.

No numbers

"Much faster", "a lot of users". Evidence beats adjectives.

A deflected failure question

A non-failure offered as a failure. It reads as either dishonesty or inexperience.

Blaming a previous team

Even when justified. Describe the constraint, not the people.

Over-engineering by default

Kubernetes, microservices or a distributed system proposed with no estimate behind it.

No measurement

Any performance or reliability answer with no trace, metric or percentile in it.

Defending a wrong answer

Being challenged and digging in. Hearing it, checking, and adjusting is a strong positive.

Nothing to ask them

"No questions" closes the interview on a flat note and suggests you are not evaluating them.
