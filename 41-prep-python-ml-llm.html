Topic 34

FastAPI production-grade

The layer this adds

The onboarding handbook covers routes, Pydantic and dependency injection. The production layer is the async/sync decision, lifecycle management, and the fact that this service holds a loaded model — which changes almost everything about how it should be written.

The mechanism
  • The async/sync decision is the one that decides whether the service survives. async def for work that waits; a plain def for work that computes, which FastAPI runs in a thread pool. Model inference inside an async def blocks the entire event loop — every other request waits, and the service appears to hang under any concurrency at all.
  • Load the model once, at startup, via the lifespan handler — not per request, and not at import time where it breaks testing. And release it on shutdown.
  • Pydantic validates at runtime, which is the real reason to choose FastAPI for a service whose input arrives over a network: a TypeScript interface is a compile-time hope, a Pydantic model actually inspects the data.
  • Bounded concurrency for inference. The thread pool is not infinite, and a burst of predictions will queue. Cap it deliberately rather than discovering the ceiling.
  • Workers versus threads. Multiple worker processes each load their own copy of the model — which multiplies memory. That is a capacity calculation, not a default.
  • Health endpoints that mean something: readiness should confirm the model is loaded, because a service that is alive but modelless will accept traffic and fail every request.
Where it goes wrong
  • Inference in an async handler. The defining mistake in this file.
  • Loading the model per request, so every prediction pays the load cost.
  • allow_origins=["*"] shipped — and in this topology the frontend does not call this service at all, so its CORS list should be narrow or empty.
  • Returning a stack trace on error, and no request id in the logs to correlate with the backend's.
  • No timeout on the caller's side, so the backend waits indefinitely when this service is slow.
The question you must be able to answer

"Why is your prediction endpoint a plain def and not async?" — because inference is CPU-bound, and putting it in an async handler blocks the event loop for every other request. That single answer demonstrates you have run this under load.

Topic 35

XGBoost library mastery

Beyond "we used XGBoost"
WHY IT WINS ON TABULAR DATA
  boosting builds trees SEQUENTIALLY, each fitting the residual
  errors of the ensemble so far. ⇒ it reduces BIAS, where a
  random forest's averaging reduces VARIANCE. That distinction
  is the answer to "why not a forest?"

THE PARAMETERS THAT ACTUALLY MATTER, AND WHAT EACH TRADES
  n_estimators      how many trees. ⭐ USE EARLY STOPPING
                    RATHER THAN GUESSING — it is the simplest
                    and most effective anti-overfitting control.
  learning_rate     how much each tree contributes. Lower needs
                    more trees; the two trade directly.
  max_depth         complexity per tree. ⚠ THE FASTEST WAY TO
                    OVERFIT is a deep tree on a small dataset.
  min_child_weight  minimum evidence required to split — a
                    strong regulariser on small data.
  subsample /       row and column sampling per tree. Adds
  colsample_bytree  randomness, reduces overfitting.
  reg_lambda /      L2 and L1 penalties.
  reg_alpha
  scale_pos_weight  ⭐ FOR IMBALANCED DATA — and for attrition
                    at a 5% base rate this is the parameter
                    people forget exists.

⭐ WHAT IT DOES *NOT* NEED — and knowing this is a real signal
  · NO FEATURE SCALING. Trees split on thresholds; the units
    are irrelevant. So the absence of a scaler in the pipeline
    is correct, not an oversight.
  · IT HANDLES MISSING VALUES NATIVELY, learning a default
    direction per split. ⚠ WHICH DOES NOT MEAN YOU SHOULD
    IGNORE MISSINGNESS: if it is MNAR, the model learns the
    bias faithfully. Keep the `was_missing` flag.

INTERPRETABILITY — and the caveat
  built-in importance comes in several kinds (gain, weight,
  cover) and they disagree, which is why quoting "the most
  important feature" without saying which measure is weak.
  ⭐ FOR A PER-PREDICTION EXPLANATION you need attributions,
    not global importance — a manager needs to know why THIS
    person was flagged.
  ⚠ AND AN ATTRIBUTION DESCRIBES THE MODEL, NOT THE WORLD. It
    is not a cause, and saying so unprompted is the senior half
    of this answer.

⚠ AND THE LEAKAGE CHECK THAT USES THIS TOOL: IF ONE FEATURE
  DOMINATES IMPORTANCE ABSURDLY, IT IS PROBABLY A LEAK RATHER
  THAN A DISCOVERY.
Topic 36

Attrition modelling and serving

What this topic is for

This is the project's core model, and the questions it invites are not about XGBoost. They are about the base rate, the leakage, the threshold and the ethics — and all four are answerable or the feature should not ship.

The four things to have straight
  • It is a ranking problem, not a classification. The deliverable is five people worth a conversation this month, not a label per employee. That reframing sets the metric to precision at k, where k is what a manager can actually act on.
  • The base rate governs the framing. At 5% attrition, a model catching 90% of leavers while wrongly flagging 10% of stayers is right about 32% of the people it flags — 45 true out of 140 flagged. So a flag must be presented as a prompt, never as a verdict, and accuracy is a meaningless metric here.
  • The leakage list is specific and known: exit interview completed, handover uploaded, access revoked, last day. All perfect predictors, all known after the decision. Plus aggregates computed over a window that includes the row being predicted.
  • Batch, not real-time. An attrition risk changes monthly at most, so nightly scoring into a table is cheaper, simpler, easier to audit and easier to explain than an endpoint. Building a real-time endpoint for a slowly-changing score is a common and expensive default.
Where it goes wrong
  • Evaluating only in aggregate. An overall score can be good for one group and poor for another, and in an employment context that is a legal exposure rather than a modelling detail.
  • Proxies left in — postcode, school, working pattern, career gaps. Removing the obvious protected column is not sufficient.
  • Uncalibrated probabilities shown to humans as though 0.7 means 70%.
  • No feedback-loop plan. Managers act on flags, so future data reflects the interventions — and the model appears to get worse precisely when it is working.
  • No holdout that was never acted on, so the effect can never be claimed.
The question you must be able to answer

"Your model flags an employee. What does their manager see, and what does the employee see?" — the strong answer covers the contributing factors shown alongside the score, the override that records a reason, and the audit entry. And it ends with the governing question: would you be comfortable explaining this system to the employees it scores?

Topic 37 · zero prior coverage

Claude API engineering

The SDK details that were at literal zero
THE SHAPE
  a Messages API call: a system prompt, a list of messages, and
  a max token limit. Stateless — ⭐ THE MODEL REMEMBERS NOTHING
  BETWEEN CALLS. A "conversation" is your code resending the
  whole history every turn, and paying for all of it every
  turn, which is why cost grows quadratically in a long chat.

⭐ PROMPT CACHING — THE COST LEVER THAT MATTERS MOST HERE
  a stable prefix — the system prompt, the tool definitions,
  a long reference document — can be cached and reused across
  requests at a fraction of the input price.
  ⇒ THE MECHANICS THAT DECIDE WHETHER IT WORKS:
    · it is a PREFIX match, so anything that changes early
      invalidates everything after it
    · ⚠ SO KEEP THE SYSTEM PROMPT FROZEN. No dates, no user
      names, no per-request values. Put those at the END, in
      the messages.
    · a write costs more than a normal input token; a read
      costs far less — so it pays off from a small number of
      requests onward
    · ⭐ VERIFY IT IS WORKING by reading the cache-read token
      count in the response usage, not by assuming
  ⇒ FOR THIS PROJECT: the report-generation system prompt and
    the metric definitions are the same on every call. That is
    exactly the case caching exists for.

STREAMING
  the model generates one token at a time, so OUTPUT LENGTH
  DOMINATES LATENCY. Streaming gets the first words on screen
  immediately instead of waiting for the whole response — and
  it prevents request timeouts on long outputs.
  ⭐ AND "ANSWER IN ONE SENTENCE" IS A GENUINE PERFORMANCE AND
    COST CONTROL, because output tokens cost several times
    input tokens.

STRUCTURED OUTPUT AND TOOLS
  · a schema constrains the response, which removes a class of
    hallucination rather than reducing it — an enum of seven
    values cannot become an eighth
  · a tool call is a REQUEST: the model asks, YOUR CODE decides
    whether to comply. ⭐ THAT GAP IS WHERE ALL YOUR SECURITY
    LIVES.

⚠ AND THE DRIFT TO BE AWARE OF: this API has changed. Several
  parameters that older tutorials use are now rejected outright,
  and defaults have moved. ⭐ CHECK THE CURRENT REFERENCE RATHER
  THAN RECALLING A PATTERN — and deliberately trigger one
  rejection in development so the drift becomes muscle memory.

THE FOUR THINGS TO LOG, ALWAYS
  the prompt version · the token counts (including cache reads)
  · the stop reason · the latency.
  ⇒ ⭐ WITHOUT THOSE FOUR, A QUALITY REGRESSION IS
    UNEXPLAINABLE.
Topic 38

LLM reporting patterns

The layer this adds

The report generator is the CV claim, and the architectural principle underneath it is the one worth being able to state: the deterministic system computes; the model narrates.

The pattern
  • Every number is computed in SQL or by the model service — reproducible, auditable, testable. The LLM receives those numbers and writes the sentences around them. So the worst possible hallucination is a clumsy sentence, never a wrong figure in an HR review.
  • The prompt carries data, not instructions to calculate. If the model is being asked to work out a percentage, the design is wrong.
  • Constrained output where the result is consumed by code — a schema for sections and headings — and free text only where a human reads it directly.
  • Long generation belongs in a job. A multi-section report is unbounded work, so accept, enqueue, stream progress, notify — which connects directly to Volume 03's pipeline.
  • Headless PDF rendering — at zero prior coverage — is the delivery half: render HTML in a headless browser, stream the output rather than buffering it, and remember that the resulting file is a document containing employee data. Which makes it a Volume 06 problem: a lifetime, an audit entry, and no guessable URL.
  • Templates plus generation, not generation alone. The structure is fixed and deterministic; only the prose varies. That makes the output reviewable and the diffs meaningful.
Where it goes wrong
  • Letting the model produce or restate a figure, which it will sometimes do slightly wrong and always do confidently.
  • A provider call inside a request, so the page waits seconds and times out on the largest records.
  • No fallback when the provider is down. The report should fail as a report — a clear failure state — not blank a page.
  • Buffering a PDF in memory for a twenty-year record with attachments.
  • Sending more employee data into the prompt than the report needs. Minimisation applies to prompts too.
The question you must be able to answer

"How do you know the numbers in a generated report are right?" — because the model never produced them. That is the whole answer, and it is only available if the architecture was built that way.

Topic 39

Evals and multi-provider architecture

The layer this adds

Two things that turn an LLM feature from a demo into a maintained system: a graded example set, and an adapter. Neither is difficult; both are usually absent.

The mechanism
  • An eval set is twenty to fifty cases with programmatic checks where possible, run on every prompt, model or retrieval change, producing a score. Without it nobody dares touch the prompt — which is how a nine-month-old prompt with a superstition in it stays frozen in production.
  • Grade what can be graded deterministically first: does it validate against the schema, is the enum in range, does it cite only chunk ids that were in the context, is it within length bounds. Only then reach for subjective grading.
  • An LLM judge is useful and not free of error. Validate the judge against human labels on a sample before trusting its scores — otherwise you have automated a bias and called it a metric.
  • The adapter is one interface with one implementation per provider. Your business logic depends on the interface. This field moves fast enough that switching is a matter of when, not if — and with an adapter it is one file.
  • Pin the model version. A provider updating a default is a silent quality change: nothing errors and everything gets slightly different. Pinning plus the eval set is what turns that from a mystery into a detected event.
  • Fallback and circuit breaking. A timeout, a retry policy, a secondary provider or a degraded path — because it is an external dependency with a bad day like any other.
Where it goes wrong
  • Verifying generated output with generated tests. Both encode the same guess and agree with each other.
  • An eval set that only contains happy cases, so a regression on the awkward inputs is invisible.
  • Multi-provider abstraction built before it is needed, at the cost of using neither provider's distinctive features — the opposite failure, and also real.
  • No cost ceiling per run or per user, so one bad Tuesday is an invoice.
The question you must be able to answer

"How would you know if the provider silently changed the model and your reports got worse?" — a pinned version, a logged prompt version, and an eval set in CI. If the honest answer is "we would not", say so; it is a real gap and naming it is better than inventing a process.
