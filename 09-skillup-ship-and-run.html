Part I

Version control

Most Git confusion comes from memorising commands without the model. Learn the model and the commands become obvious.

Ops 01

The model underneath

Four ideas, and everything else follows
①  A COMMIT IS A SNAPSHOT, NOT A DIFF.
   it records the whole tree, plus a pointer to its parent.
   ⇒ diffs are COMPUTED between snapshots when you ask for one.
   ⭐ THIS EXPLAINS WHY BRANCHING IS CHEAP: a branch is not a
     copy of anything.

②  A BRANCH IS A MOVEABLE POINTER TO ONE COMMIT.
   that is the entire implementation — a file containing a
   commit id. ⇒ creating one is instant, deleting one deletes
   nothing but a label, and "where did my work go?" is almost
   always "which pointer am I looking at?"

③  HEAD IS WHERE YOU ARE.
   usually pointing at a branch, which points at a commit.
   ⚠ "detached HEAD" simply means HEAD points straight at a
     commit with no branch — your commits there have no label,
     which is why they seem to vanish.

④  THERE ARE THREE PLACES A CHANGE CAN LIVE.
     working directory  → your edits
     staging area       → what the next commit will contain
     repository         → committed history
   ⭐ THE STAGING AREA IS THE PART PEOPLE SKIP, and it is what
     lets you commit half of your changes deliberately — which
     is how you produce a reviewable commit instead of a dump.

⭐ THE CONSEQUENCE THAT MATTERS MOST: COMMITTED WORK IS VERY
  HARD TO LOSE. Almost every "I destroyed my work" is
  recoverable if it was committed — see reflex 05. Uncommitted
  work is genuinely fragile.
  ⇒ SO COMMIT EARLY AND OFTEN, especially before anything
    large, generated, or experimental.
Ops 02

Branching strategies

StrategyHowSuits
Trunk-basedShort-lived branches off main, merged within a day or two, features hidden behind flagsMost teams, most of the time. Minimises merge pain because branches never diverge far.
GitHub flowA branch per change, PR, review, merge, deployTrunk-based with a review gate. What this project's workflow resembles.
Git flowdevelop, release branches, hotfix branches, mainSoftware with versioned releases and multiple supported versions. Overhead for a continuously deployed web app.
Release branchesA branch per version, fixes cherry-picked backWhen you must support customers on old versions.
The principle behind the choice

The longer a branch lives, the more it costs to merge — and the cost is not linear. A branch open for three weeks accumulates conflicts, and worse, it accumulates semantic divergence that no tool detects: your code and main both work, and together they do not.

So the useful instinct is not "which strategy" but "how do I get this merged this week?" — usually by splitting the work, or hiding an incomplete feature behind a flag rather than behind a branch.

Ops 03

Merge versus rebase

MERGE — creates a commit with two parents main A───B───────M ╲ ╱ feature C───D ✅ preserves exactly what happened, and it is SAFE on shared branches because it changes no existing commit. ⚠ history becomes a braid; many small merge commits add noise. REBASE — replays your commits on top of the new base main A───B───C'───D' (C and D are NEW commits, rewritten) ✅ linear, readable history — `git log` reads as a story. ⚠ ⭐ IT REWRITES HISTORY. The commits have new ids. ⇒ NEVER REBASE A BRANCH SOMEONE ELSE HAS PULLED. Their history and yours have diverged in a way that produces genuinely confusing conflicts, and fixing it requires someone to discard work. ⭐ THE RULE THAT COVERS EVERY CASE REBASE YOUR OWN UNPUSHED WORK · MERGE ANYTHING SHARED. ⇒ "rebase before you push, merge after." SQUASH MERGE — the common team default, and a good one the whole branch becomes one commit on main. ✅ main reads as one clean change per feature, and reverting a feature is one revert. ⚠ the individual commits are gone, so a granular bisect inside that feature is no longer possible. ⭐ WHAT MATTERS MORE THAN THE CHOICE: THAT THE TEAM MAKES ONE AND CONFIGURES IT. Half the team rebasing and half merging produces a history nobody can read and conflicts nobody expects.
Ops 04

Conflicts

What a conflict is, and the one people do not notice
A CONFLICT IS GIT SAYING "TWO PEOPLE CHANGED THE SAME LINES AND
I WILL NOT GUESS." It is not an error and not a failure — it is
a request for a decision.

RESOLVING ONE
  1  ⭐ UNDERSTAND BOTH SIDES BEFORE EDITING. Read what each
     change was trying to achieve. `git log --merge` shows the
     commits involved.
  2  the answer is often BOTH changes, not one of them. Picking
     a side because it is quicker silently discards someone's
     work.
  3  after resolving, ⭐ RUN THE TESTS. A syntactically clean
     resolution can be semantically wrong.

⭐ THE CONFLICT GIT CANNOT DETECT — AND IT IS THE DANGEROUS ONE:
  A SEMANTIC CONFLICT. You renamed a function; a colleague added
  a new call to the old name in a different file. No textual
  overlap, so no conflict — and it merges cleanly and breaks.
  ⇒ THIS IS WHY CI MUST RUN ON THE MERGE RESULT, not only on
    your branch. A green branch plus a green main does not
    imply a green merge.

REDUCING THEM STRUCTURALLY
  · short-lived branches (reflex 02)
  · pull from main frequently, so you resolve small conflicts
    early rather than one enormous one at the end
  · ⭐ AGREE ON FORMATTING AND AUTOMATE IT — a formatter
    eliminates the entire category of whitespace conflict
  · small, focused files: a 2,000-line file everyone edits is a
    conflict generator, and that is a design smell as much as a
    Git one

⚠ AND ONE SPECIFIC TO THIS PROJECT SHAPE: lock files
  (package-lock.json) conflict constantly and must NOT be
  hand-edited. Take one side, then re-run the install to
  regenerate it.
Ops 05

The rescue commands

Worth knowing before you need them
⭐ git reflog — THE UNDO BUTTON FOR EVERYTHING
  a log of everywhere HEAD has been, including states no branch
  points at any more. Bad rebase, deleted branch, hard reset —
  ⇒ find the commit id here and check it out. THIS IS THE SINGLE
    MOST VALUABLE GIT COMMAND AND ALMOST NOBODY KNOWS IT.

git stash            park uncommitted work · `stash pop` to
                     restore. ⚠ easy to forget you have several.
git cherry-pick <c>  apply one specific commit here — how a
                     hotfix reaches a release branch.
git revert <c>       ⭐ a NEW commit that undoes an old one.
                     SAFE ON SHARED BRANCHES. This is how you
                     undo something already deployed.
git reset --soft     move the branch pointer, keep changes
                     staged ⇒ how you rewrite your last commit.
git reset --hard     ⚠ DISCARDS uncommitted work permanently.
                     The one command that genuinely loses data.
git bisect           ⭐ binary search over history to find the
                     commit that introduced a bug. Turns a
                     linear hunt through 200 commits into eight
                     checks — Volume IV's binary search, applied.
git blame            who last changed this line, and in which
                     commit. ⭐ USE IT TO FIND THE *REASON* — the
                     commit message and PR — not the person.

⭐ REVERT vs RESET, and it is the distinction that matters:
  RESET rewrites history — fine on your own unpushed work,
  destructive on anything shared. REVERT adds history — always
  safe. ⇒ ON A SHARED BRANCH, ALWAYS REVERT.
Ops 06

Commits and hooks

Write why, not what

The diff shows what changed. Only the message can say why — and it is the note your future self reads while debugging.

One logical change per commit

So it can be reviewed, reverted and bisected independently. A commit mixing a refactor with a fix is neither reviewable nor revertable.

Generated changes get their own commit

Reviewable in isolation, revertable in one command. Mixed with hand edits it becomes archaeology.

Hooks: fast checks only

Format and lint on commit; tests in CI. A slow pre-commit hook gets bypassed with --no-verify, and then it protects nothing.

Part II

Containers

Ops 07

Why they exist

The problem they actually solved
"IT WORKS ON MY MACHINE" — because your machine has a different
Node version, a different OpenSSL, a different locale, a
different timezone, and a Python package someone installed
globally in 2024.

A CONTAINER SHIPS THE APPLICATION *AND ITS ENVIRONMENT* AS ONE
ARTEFACT. Same image on your laptop, in CI, and in production.

⭐ WHAT IT IS NOT: A VIRTUAL MACHINE.
  a VM virtualises hardware and runs a whole guest OS —
  gigabytes, and tens of seconds to boot.
  a container shares the HOST KERNEL and isolates only the
  process, its filesystem view and its network — megabytes,
  and milliseconds to start.
  ⇒ THIS IS WHY CONTAINERS CHANGED DEPLOYMENT: something you
    can start in 200 ms and run 50 of on one machine enables
    orchestration, autoscaling and per-request isolation. A VM
    does not.

⚠ AND THE CONSEQUENCE OF SHARING THE KERNEL: containers are
  ISOLATION, NOT A SECURITY BOUNDARY as strong as a VM. A
  kernel vulnerability crosses it. For untrusted code — running
  someone else's submitted script — you want stronger isolation
  than a container alone.

⭐ AND THE PART PEOPLE UNDER-VALUE: A CONTAINER IS A
  SPECIFICATION OF THE ENVIRONMENT, WRITTEN DOWN. The
  Dockerfile documents every dependency and version that the
  application actually needs — which is documentation that
  cannot drift, because if it were wrong the image would not
  work.
Ops 08

Images and layers

IMAGE = a stacked, read-only filesystem. CONTAINER = a running instance of an image, plus one writable layer on top. ┌─────────────────────────┐ ← writable layer (the container) ├─────────────────────────┤ ← COPY . . (your code) ├─────────────────────────┤ ← RUN npm ci (deps) ├─────────────────────────┤ ← COPY package*.json └─────────────────────────┘ ← FROM node:20-alpine (base) ⭐ EACH INSTRUCTION IS A LAYER, AND LAYERS ARE CACHED. If a layer's inputs have not changed, it is reused. ⇒ WHICH DICTATES THE ONE RULE OF DOCKERFILE WRITING: ORDER FROM LEAST TO MOST FREQUENTLY CHANGING. ⚠ COPY . . then RUN npm ci ⇒ any source edit invalidates the copy layer, so dependencies reinstall on EVERY build. Minutes, every time. ✅ COPY package*.json . RUN npm ci COPY . . ⇒ dependencies are cached until package.json changes. Seconds. ⭐ AND THE FACT WITH SECURITY CONSEQUENCES: LAYERS ARE ADDITIVE, SO DELETING A FILE IN A LATER LAYER DOES NOT REMOVE IT FROM THE IMAGE. A secret copied in and then removed is still there and still extractable. ⇒ never copy a secret into an image at all. Use build arguments carefully, or better, inject at runtime. THE WRITABLE LAYER IS EPHEMERAL ⚠ anything written inside a running container is GONE when it stops. That is not a bug — it is the model, and it is why persistent data needs a volume or a managed service (reflex 11).
Ops 09

Writing a Dockerfile that is not embarrassing

Five things, in order of impact
①  MULTI-STAGE BUILDS — ⭐ the biggest single win
   build in one stage with the full toolchain; copy only the
   output into a slim runtime stage.
     FROM node:20 AS build
     … install dev dependencies, compile TypeScript …
     FROM node:20-alpine
     COPY --from=build /app/dist ./dist
   ⇒ the shipped image contains no compilers, no dev
     dependencies and no source — often ten times smaller, and
     a much smaller attack surface.

②  PIN THE BASE IMAGE
   `node:20-alpine` rather than `node:latest`.
   ⚠ `latest` means your build is not reproducible and can
     break overnight without any change from you.

③  DON'T RUN AS ROOT
   the default is root. Create a user and switch to it — one
   line, and it limits what a compromised process can do.

④  .dockerignore — ⭐ and this is not just tidiness
   exclude node_modules, .git, .env, local build output.
   ⇒ faster builds, smaller images, AND ⚠ IT IS WHAT STOPS YOU
     ACCIDENTALLY BAKING A .env FILE INTO THE IMAGE.

⑤  ONE PROCESS PER CONTAINER
   the orchestrator restarts a failed container. If your
   container runs three processes, it cannot tell which one
   died, and the model breaks down.

⚠ AND THE ALPINE CAVEAT WORTH KNOWING: Alpine uses musl rather
  than glibc. Most things work; some native modules — and some
  Python scientific packages — build slowly or misbehave. ⭐ FOR
  A PYTHON ML SERVICE, A SLIM DEBIAN BASE IS OFTEN THE LESS
  PAINFUL CHOICE than chasing musl build failures.
Ops 10

Compose

The multi-service local environment, in one file
ONE FILE DESCRIBING SEVERAL SERVICES, A NETWORK AND SOME
VOLUMES — and `docker compose up` starts all of them.

⭐ FOR THIS PROJECT THAT IS EXACTLY THE RIGHT TOOL: backend,
  frontend, AI service and a local Postgres, started with one
  command. A new joiner goes from clone to running application
  without a page of setup instructions — which is the real
  payoff.

THE THINGS THAT MATTER
  · SERVICES REACH EACH OTHER BY SERVICE NAME, not localhost.
    ⚠ `http://localhost:8000` from inside a container means
      "this container", so it fails. It is `http://ai-service:8000`.
      ⭐ THIS IS THE #1 COMPOSE CONFUSION, and it is why an app
      that works locally breaks the moment it is containerised.
  · `depends_on` WAITS FOR START, NOT FOR READY. A database
    container is "up" seconds before it accepts connections.
    ⇒ you need a health check, or retry logic in the app —
      which you want anyway.
  · BIND-MOUNT SOURCE IN DEVELOPMENT for hot reload; do not in
    production.
  · env vars from a `.env` file, which is never committed.

⚠ AND THE HONEST SCOPE: COMPOSE IS FOR DEVELOPMENT AND SMALL
  DEPLOYMENTS. It has no rolling updates, no autoscaling and no
  scheduling across machines. For production at scale that is
  what an orchestrator or a managed platform does — but reaching
  for Kubernetes to run three containers is a much more common
  mistake than outgrowing Compose.
Ops 11

Volumes and networking

ConceptWhat to know
The writable layerEphemeral. Everything written inside a container is lost when it stops. By design.
Named volumeDocker-managed persistent storage. The right choice for a local database's data directory.
Bind mountA host directory mapped in. For source code in development — and the cause of most "permissions denied" confusion, because file ownership crosses the boundary.
Port mapping3010:3010 is host:container. They need not match, and the container port is what the app binds to.
Binding to localhostThe classic mistake. An app bound to 127.0.0.1 inside a container is unreachable from outside it. Bind to 0.0.0.0.
Service discoveryWithin a Compose network, the service name resolves. Across machines, that is the orchestrator's or the cloud's job.
Ops 12

When not to containerise

Honest limits

A managed platform may already do this for you. If your host builds from a repository and runs it, adding a Dockerfile can be work with no benefit — and one more thing to keep current.

Stateful data services are usually better managed. Running Postgres in a container locally is excellent; running your production database in one means owning backups, failover, upgrades and disk. Neon does that better than you will.

And the honest one: the value is reproducibility. If your team is on one platform with one runtime version and deploys to a managed service, the reproducibility problem may already be solved — in which case a container is optional rather than obviously right.

Part III

CI/CD

Ops 13

The mental model

Two different things with one abbreviation
CONTINUOUS INTEGRATION — every change is automatically built
and tested, on merge to a shared branch.
  ⭐ THE POINT IS NOT AUTOMATION. It is that integration
    problems are found in minutes rather than at the end of a
    three-week branch, when they are entangled.

CONTINUOUS DELIVERY — every passing change is automatically
deployable. A human decides when.
CONTINUOUS DEPLOYMENT — every passing change deploys itself.

⚠ THE DIFFERENCE IS WHO PRESSES THE BUTTON, and choosing
  requires honesty about your test suite: continuous deployment
  is only responsible if your pipeline genuinely catches
  regressions.

⭐ THE PROPERTY THAT MAKES ALL OF IT WORK: THE PIPELINE IS THE
  ONLY WAY CODE REACHES PRODUCTION. The moment someone can
  deploy from their laptop, the pipeline stops being a
  guarantee and becomes a suggestion — and the state of
  production becomes unknowable.

AND THE SECOND PROPERTY: THE SAME ARTEFACT IS PROMOTED.
  build once, then deploy that exact image to staging and then
  to production. ⚠ REBUILDING PER ENVIRONMENT MEANS YOU TESTED
  SOMETHING YOU DID NOT SHIP — dependencies can resolve
  differently between two builds minutes apart.
Ops 14

Pipeline stages

① CHECKOUT seconds ② RESTORE CACHE dependencies, build output ③ INSTALL ⭐ from the LOCK FILE — a reproducible install, not a fresh resolve ④ FAST CHECKS ─┐ lint · format · type-check ⑤ UNIT TESTS ├─ run in parallel where possible ⑥ BUILD ─┘ ⑦ INTEGRATION TESTS against a real test database ⑧ SECURITY SCAN dependencies, secrets in the diff ⑨ BUILD THE IMAGE tag it with the commit SHA ⭐ ⑩ DEPLOY TO STAGING and run smoke tests ⑪ DEPLOY TO PRODUCTION manual gate, or automatic ⑫ VERIFY health checks, error rate, ⭐ and roll back if they fail ⭐ ORDER BY SPEED, NOT BY IMPORTANCE. A type error should fail in 40 seconds, not after an eight-minute test suite. The purpose of a pipeline is fast feedback, and cheap checks first is what produces it. ⭐ TAG THE IMAGE WITH THE COMMIT SHA, NOT `latest`. then "which code is in production?" has an exact answer, and rolling back is deploying a previous, known tag. ⚠ with `latest` you cannot answer either question, and that is precisely what you need during an incident. ⚠ AND THE STEP TEAMS SKIP: ⑫. A deploy that completes is not a deploy that worked. Check the error rate for a few minutes afterwards — automatically, so nobody has to remember.
Ops 15

Making it fast, and keeping it trusted

A slow or flaky pipeline stops being used
⭐ THE TARGET: UNDER TEN MINUTES TO A MERGE DECISION. Past
  that, people context-switch, stop waiting, and start merging
  on hope.

HOW
  · CACHE dependencies and build output, keyed on the lock file
  · RUN INDEPENDENT JOBS IN PARALLEL — lint, types and unit
    tests have no reason to be sequential
  · only run what changed, in a monorepo
  · put the slowest suite behind the merge, not in front of it,
    if it genuinely takes too long

⭐ AND THE ONE THAT MATTERS MORE THAN SPEED: FLAKY TESTS DESTROY
  A PIPELINE'S VALUE.
  once a suite fails randomly, the team learns to re-run it
  instead of reading it — and at that moment the pipeline has
  stopped catching anything, because every failure is assumed
  to be noise.
  ⇒ TREAT A FLAKY TEST AS A BUG WITH A DEADLINE. Quarantine it
    if you must, but track it. ⚠ "Just hit re-run" is how a
    real regression reaches production.

  THE USUAL CAUSES: shared state between tests · reliance on
  execution order · real timers or real clocks · unmocked
  network · a database not reset between runs · an assertion on
  a non-deterministic output.

⭐ AND KEEP THE PIPELINE'S OWN CONFIGURATION IN THE REPOSITORY,
  REVIEWED LIKE CODE. A pipeline edited through a web console
  is infrastructure nobody can review, diff, or roll back.
Ops 16

Deployment strategies

StrategyHowTrade-off
RecreateStop the old, start the newSimple, and there is downtime. Fine for internal tools with a maintenance window.
RollingReplace instances a few at a timeThe common default. No downtime — but both versions run simultaneously, so the API and the database must be compatible with both.
Blue-greenTwo full environments; switch trafficInstant rollback by switching back. Costs double the infrastructure during the switch.
Canary5 % of traffic to the new version, watch, then widenBest risk control — real traffic finds what staging cannot. Needs traffic splitting and good metrics to be meaningful.
Feature flagsDeploy the code disabled; enable separatelySeparates deploy from release, which is the most useful idea here. Costs you flag cleanup, and flags left forever become permanent branching.
The constraint every strategy shares

During any zero-downtime deploy, two versions of your code are running against one database. So every migration must be compatible with the version that is still running.

Which forces the three-step shape for any destructive schema change: add the new column → deploy code that writes both and reads the new → drop the old column in a later deploy. A migration that renames or drops in one step will break the instances that have not been replaced yet — and it is the most common self-inflicted deployment outage there is.

Ops 17

Environments

What each is for, and the two rules
LOCAL       fast iteration. Compose, seeded data.
CI          ephemeral, created and destroyed per run.
STAGING     ⭐ AS CLOSE TO PRODUCTION AS YOU CAN AFFORD. Its
            value is entirely proportional to how similar it
            is; a staging environment with 200 rows and a
            different config tells you almost nothing.
PRODUCTION  the only one that matters.

⭐ RULE ONE: SEPARATE CREDENTIALS PER ENVIRONMENT.
  a shared secret means staging can read and write production
  data — and someone will eventually run a test script against
  the wrong one.

⭐ RULE TWO: CONFIGURATION COMES FROM THE ENVIRONMENT, NOT FROM
  A BRANCH.
  the same artefact runs everywhere, configured by variables.
  ⚠ a `if (env === 'production')` branch in application code is
    a code path you never test until it is live.

⚠ AND THE PRODUCTION-DATA QUESTION, WHICH IS NOT OPTIONAL HERE:
  DO NOT COPY PRODUCTION HR DATA INTO STAGING. Salaries,
  reviews and health information in a lower environment with
  weaker access control is a breach waiting to be discovered.
  ⇒ ANONYMISE OR GENERATE. And "we only copied it once for
    testing" is exactly how these incidents are described
    afterwards.

⭐ THE UNDERRATED ONE: A PREVIEW ENVIRONMENT PER PULL REQUEST.
  a reviewer can click the change instead of imagining it, and
  a product decision gets made against something real. It
  catches a class of problem no test does.
Ops 18

Pitfalls

Secrets in the pipeline log

An echoed variable, a verbose flag, a printed environment. Logs are widely readable and retained. Mask them, and rotate anything that appeared.

Tests that need the previous test

Order dependence works locally and fails when the runner parallelises. Each test sets up its own state.

Deploying on Friday afternoon

Not superstition — the fix window matters as much as the deploy. Deploy when the people who can roll it back are available.

A pipeline nobody owns

It rots, gets bypassed, and then production and the pipeline disagree. It is code, and it needs a maintainer.

Part IV

Cloud fundamentals

What you are actually renting, and the two things that surprise teams: the bill and the permissions model.

Ops 19

What you rent

ModelYou manageSuits
IaaSThe OS, the runtime, the app, patching, scalingMaximum control, maximum work. A virtual machine.
PaaSJust the appWhere most small teams should live. Push code, it runs. Less control, far less operational burden.
ServerlessJust the functionSpiky or infrequent workloads. Scales to zero and to very high, with real constraints — reflex 21.

The judgement that saves the most time

Every layer you manage is a layer you must patch, monitor, scale and be woken up by. A small team running its own database cluster has chosen to spend its scarcest resource — attention — on something a provider does better and cheaper.

Which is exactly why this project uses Neon rather than a self-hosted Postgres. That is not laziness; it is allocating engineering effort to the part that is actually yours.

The core services, by category

Every provider has these under different names
COMPUTE        VMs · containers · functions
STORAGE        object storage (files, cheap, durable) · block
               storage (disks attached to a VM)
DATABASE       managed relational · managed key-value · managed
               analytical

IDENTITY       ⭐ who may do what — see reflex 23, and it is the
               part that causes the most incidents

⭐ LEARN THE CATEGORIES, NOT THE PRODUCT NAMES. Every provider
  has an object store, a queue and a managed Postgres; the names
  differ and the concepts do not. Knowing the categories makes
  any provider's documentation navigable, and it is what
  survives a change of employer.

THE TWO PIECES OF VOCABULARY WORTH KNOWING PRECISELY
  REGION            a geographic location. ⭐ CHOOSING ONE IS A
                    LATENCY AND A COMPLIANCE DECISION — EU
                    employee data has residency implications,
                    which is not a detail in an HR system.
  AVAILABILITY ZONE an isolated datacentre within a region.
                    ⇒ spreading across zones survives one
                      datacentre failing; spreading across
                      regions survives more and costs latency
                      and complexity.
Ops 21

Serverless, with its real constraints

Genuinely useful, and not free of trade-offs
✅ WHAT IT BUYS
  · scales to zero — you pay nothing when idle
  · scales up without capacity planning
  · no servers to patch

⚠ WHAT IT COSTS, AND EACH ONE IS A DESIGN CONSTRAINT
  · COLD STARTS. An idle function must be initialised. Tens of
    milliseconds to seconds — ⭐ AND HEAVY DEPENDENCIES MAKE IT
    WORSE, which is why loading a large ML model per invocation
    is the wrong shape.
  · A TIME LIMIT. Long jobs do not fit; you need a queue and
    chunking.
  · STATELESSNESS. Nothing persists between invocations.
  · ⭐ CONNECTION EXHAUSTION — THE ONE THAT BITES THIS STACK.
    a hundred concurrent function instances each opening
    database connections will exhaust Postgres while using
    almost no CPU. ⇒ THIS IS WHY A CONNECTION POOLER IS
    MANDATORY, not optional, with serverless plus Postgres.
  · harder local reproduction and harder debugging.

⭐ WHERE IT FITS WELL: webhook handlers · scheduled jobs ·
  image processing · spiky low-volume endpoints · glue between
  services.
⚠ WHERE IT FITS BADLY: a long-lived WebSocket server · anything
  needing a warm in-memory model · steady high-volume traffic,
  where a container is cheaper and more predictable.

⇒ FOR THIS PROJECT: the NestJS API and the FastAPI service are
  better as containers — the AI service in particular, because
  the model should be loaded once at startup rather than per
  request.
Ops 22

Cost awareness

Where cloud bills actually come from
⭐ THE THINGS THAT SURPRISE PEOPLE, IN ORDER

  ① EGRESS. Data leaving the provider costs money; data going
    in is usually free. ⇒ a chatty integration, or serving
    large files without a CDN, is a line item.
  ② CROSS-ZONE AND CROSS-REGION TRAFFIC. Internal traffic is
    not always free.
  ③ IDLE RESOURCES. ⭐ THE BIGGEST REAL WASTE: a staging
    environment running 24/7 for a team that works 40 hours a
    week, an oversized instance from a load test, an unattached
    disk, an old snapshot. All quietly billing.
  ④ LOGS AND METRICS. Verbose logging at volume with long
    retention is a genuine cost centre, and it grows silently.
  ⑤ MANAGED SERVICE PREMIUMS. Worth it — but know the number.
  ⑥ ⭐ METERED APIS. An LLM provider is per-token. A loop over
    10,000 records has a price, and it belongs in the design
    review rather than the invoice.

THE THREE HABITS
  · ⭐ TAG EVERYTHING BY ENVIRONMENT AND OWNER. Without tags you
    cannot answer "what is this $400 for?", and you will be
    asked.
  · SET A BUDGET ALERT ON DAY ONE. Not to control spend — to
    detect a mistake. A runaway loop or a leaked key shows up
    as a bill before it shows up anywhere else.
  · ESTIMATE THE MONTHLY COST AT DESIGN TIME, at 10× current
    volume. ⭐ "IT COSTS $0.004 PER REQUEST, $240/MONTH AT
    CURRENT VOLUME" IS REAL ENGINEERING and it is rare.

⚠ AND THE ONE PEOPLE LEARN THE HARD WAY: A LEAKED CREDENTIAL
  BECOMES A COMPUTE BILL WITHIN HOURS. Budget alerts are a
  security control as much as a financial one.
Ops 23

Cloud security basics

The permission model is the part that causes incidents
⭐ LEAST PRIVILEGE, ACTUALLY APPLIED
  every service gets the narrowest permissions that work.
  ⚠ the anti-pattern is universal: grant broad access "to get
    it working", intend to narrow it later, never narrow it.
    ⇒ so a compromised component can reach everything.

USE ROLES, NOT LONG-LIVED KEYS
  a workload identity that the platform rotates beats a static
  access key in an environment variable. ⭐ A LONG-LIVED KEY IS
  A CREDENTIAL WAITING TO BE COMMITTED, LOGGED OR PASTED.

⭐ THE FOUR MISCONFIGURATIONS THAT CAUSE REAL BREACHES — and
  none of them are clever attacks:
  ① A PUBLIC OBJECT STORE BUCKET. ⚠ The single most common
    cloud data breach in existence. Default to private, and
    verify.
  ② A DATABASE REACHABLE FROM THE INTERNET. It should be on a
    private network, reachable only by your services.
  ③ OVER-PERMISSIVE CORS OR SECURITY GROUPS — `0.0.0.0/0` or
    `origin: '*'` shipped from development.
  ④ SECRETS IN ENVIRONMENT VARIABLES VISIBLE IN A CONSOLE, or
    in a build log.

AND THE OPERATIONAL MINIMUM
  □ ENCRYPTION AT REST AND IN TRANSIT — usually a checkbox,
    and it is the answer to a question auditors will ask
  □ AUDIT LOGGING ON, and retained
  □ BACKUPS — ⭐ AND A RESTORE THAT HAS ACTUALLY BEEN TESTED.
    An untested backup is a hope, not a backup, and people
    discover this at the worst possible moment.
  □ MFA on the accounts that can change infrastructure

⚠ AND THE SPECIFIC POINT FOR AN HR SYSTEM: data residency and
  retention are not IT details. Where employee data is stored,
  and for how long, are legal commitments — and the region you
  pick in a console is where that commitment is implemented.

Ops 24

The three pillars

LOGS discrete events. "What happened, exactly?" ⇒ high detail, high volume, expensive at scale. Best for investigating one known problem. METRICS numbers over time. "Is anything wrong right now?" ⇒ cheap, aggregatable, and what you alert on. ⚠ cannot tell you WHY. TRACES one request across services. "Where did the time go?" ⇒ ⭐ the only pillar that answers that question in a multi-service system, and the one most teams skip. ⭐ THE DIVISION OF LABOUR, WHICH IS THE USEFUL PART: METRICS TELL YOU SOMETHING IS WRONG. TRACES TELL YOU WHERE. LOGS TELL YOU WHY. ⇒ a team with only logs finds out late and greps blindly; a team with only metrics knows it is broken and not where. THE MINIMUM THAT IS WORTH HAVING, AND IT IS SMALL □ STRUCTURED LOGS with a correlation id on every line □ FOUR METRICS PER SERVICE — reflex 25 □ THE CORRELATION ID PASSED BETWEEN SERVICES □ ⭐ AN ALERT ON USER-VISIBLE FAILURE, not on CPU □ AN UPTIME CHECK FROM OUTSIDE your infrastructure ⭐ THE POINT ABOUT OBSERVABILITY THAT MATTERS MOST: YOU CANNOT ADD IT DURING AN INCIDENT. The question "what happened at 02:14?" is answerable only if the answer was being recorded at 02:14. Everything on that list is cheaper to add now than to wish for later.

MetricWatch forWhy

Latency percentilesp50, p95, p99 — never the averageThe average is dominated by the many fast requests. p99 is where the pain lives, and it moves first.

Ops 26

Alerting

The hardest part, and it is a discipline problem
⭐ THE ONE RULE: ALERT ON SYMPTOMS THE USER FEELS, NOT ON
  CAUSES.
  ✅ "the error rate exceeded 2% for five minutes"
  ✅ "the p95 exceeded two seconds"
  ✅ "no reports have been generated in an hour"
  ⚠ "CPU is above 80%" ⇒ so what? If nobody noticed, it is not
    an incident. High CPU with fine latency is a machine doing
    its job.

⭐ AND THE FAILURE MODE THAT MAKES MONITORING WORTHLESS: ALERT
  FATIGUE.
  an alert that fires and is ignored is worse than no alert,
  because it trains everyone to ignore the channel — and then
  the real one arrives and is also ignored.
  ⇒ EVERY ALERT MUST BE ACTIONABLE AND URGENT. If the answer is
    "we'll look at it tomorrow", it is a dashboard item or a
    ticket, not an alert.

THE THREE PROPERTIES OF AN ALERT WORTH KEEPING
  · it says WHAT IS AFFECTED FROM THE USER'S POINT OF VIEW
  · it links to the DASHBOARD and the RUNBOOK (reflex 29)
  · it has a THRESHOLD AND A DURATION, so a two-second blip
    does not page anyone

⭐ AND THE HYGIENE THAT KEEPS IT HONEST: REVIEW YOUR ALERTS
  PERIODICALLY. Delete the ones that never fire, and fix the
  ones that fire constantly. An alert list nobody has pruned in
  a year is a list nobody reads.

⚠ ONE MORE: MONITOR FROM OUTSIDE YOUR OWN INFRASTRUCTURE. If
  monitoring runs inside the thing that is down, it cannot tell
  you. An external uptime check is a few minutes to set up and
  it is the one that catches total failure.
Ops 27

Health checks

Two different questions, and conflating them causes outages
LIVENESS   "is this process alive?" ⇒ if not, RESTART it.
READINESS  "can this process serve traffic right now?" ⇒ if
           not, STOP SENDING IT TRAFFIC — but do not restart.

⭐ WHY THE DISTINCTION MATTERS, CONCRETELY: at startup your app
  is alive but not ready (still connecting to the database). If
  your only check is liveness, the load balancer sends traffic
  immediately and those requests fail. If readiness is wired to
  liveness, a temporarily unready app gets restarted in a loop
  and never becomes ready at all.

WHAT A CHECK SHOULD ACTUALLY VERIFY
  ⚠ AN ENDPOINT THAT RETURNS 200 UNCONDITIONALLY IS WORSE THAN
    NO CHECK. It hides the failure from the load balancer, which
    keeps routing to a broken instance forever.
  ⇒ readiness should verify what the service genuinely needs:
    can it reach the database? is the model loaded?

⚠ BUT DO NOT CASCADE. A health check that fails because a
  NON-ESSENTIAL dependency is down takes your service out of
  rotation for no reason — ⭐ and if every service checks every
  dependency, one small outage removes everything from
  rotation simultaneously. Check what you need to serve, not
  everything you can reach.

⭐ FOR THIS PROJECT, CONCRETELY: the backend's readiness should
  check the database (it cannot serve without it) and NOT the
  AI service (report generation fails, everything else works).
  That single distinction is the difference between a degraded
  feature and a total outage.
Ops 28

Infrastructure as code

Because a console click is a fact that exists on nobody's machine
THE PROBLEM WITH MANUAL SETUP
  · nobody knows what the current configuration IS
  · nobody can recreate it — ⭐ INCLUDING AFTER AN OUTAGE
  · staging and production drift apart silently
  · a change cannot be reviewed, diffed, or rolled back
  · the knowledge lives with one person

⭐ IaC MAKES INFRASTRUCTURE A REVIEWABLE, VERSIONED ARTEFACT.
  the repository becomes the answer to "what is deployed?", and
  a change to infrastructure goes through the same review as a
  change to code.

THE CONCEPTS THAT TRANSFER ACROSS TOOLS
  DECLARATIVE       you describe the desired end state; the
                    tool works out the steps. ⇒ running it
                    twice changes nothing the second time.
  STATE             ⭐ the tool's record of what it created and
                    manages. Treat it as precious: it is shared,
                    it must be locked during changes, and it can
                    contain secrets.
  PLAN THEN APPLY   ⭐ ALWAYS READ THE PLAN. It is the diff, and
                    it is where you notice that a change
                    replaces a database rather than modifying
                    it.
  MODULES           reusable parameterised pieces, so staging
                    and production are the same definition with
                    different variables.
  DRIFT             ⚠ someone changed something by hand and the
                    real world no longer matches the code. ⭐ THE
                    RULE THAT PREVENTS IT: ONCE IT IS IN CODE,
                    NOBODY TOUCHES THE CONSOLE.

⭐ AND THE PRAGMATIC ENTRY POINT: YOU DO NOT NEED TERRAFORM TO
  START. A committed Compose file, a documented list of managed
  services with their settings, and scripted database
  migrations already give you most of the benefit. IaC is a
  direction, and partial adoption is genuinely useful.
Ops 29

Runbooks

Written calmly, for someone who is not calm
A RUNBOOK IS THE PROCEDURE FOR ONE KNOWN SITUATION, written
before it happens and linked from the alert.

  TITLE      "Database migration failed during deploy"
  SYMPTOMS   what you will see, and where
  IMPACT     who is affected and how badly
  FIRST STEP ⭐ THE MITIGATION, NOT THE DIAGNOSIS. "Roll back
             to the previous image tag."
  THEN       the diagnostic steps, in order
  ESCALATE   who to wake, and when
  AFTER      what to record, and what to verify

⭐ WHY THIS FORMAT: AT 3 A.M. NOBODY IMPROVISES WELL, INCLUDING
  THE PERSON WHO BUILT THE SYSTEM. A runbook converts a
  stressful judgement call into a checklist, and it lets someone
  who is not the author handle it — which is the actual point.

WHICH ONES TO WRITE
  ⭐ WRITE THE RUNBOOK AFTER THE FIRST TIME IT HAPPENS. Post-
    mortems are the natural source: every incident that could
    recur deserves one, written while the details are fresh.
  the usual first four for a stack like this:
    · a failed deploy or migration
    · the database is unreachable or out of connections
    · a dependency (the AI service, the LLM provider) is down
    · certificates or credentials expired

⚠ AND KEEP THEM WITH THE CODE, NOT IN A WIKI NOBODY OPENS. A
  runbook that is wrong is worse than none — it sends a tired
  person down a path that no longer exists. ⭐ SO REVIEW THEM
  WHEN THE SYSTEM CHANGES, and delete the ones for systems you
  no longer run.

Term bank

Volume V · operations vocabulary
reflog
Git's log of everywhere HEAD has been. The undo button for almost everything.
rebase
Replaying commits onto a new base. Rewrites history — never on shared branches.
revert
A new commit that undoes an old one. Always safe on shared branches.
semantic conflict
Two changes that merge cleanly and break together. Why CI must test the merge result.
bisect
Binary search over history to find the commit that introduced a bug.
layer cache
Docker reusing unchanged build steps. Why instruction order decides build time.
multi-stage build
Building in one image and shipping only the output. Smaller image, smaller attack surface.
ephemeral filesystem
A container's writes are lost on stop. By design.
0.0.0.0
What a containerised app must bind to. Binding to localhost makes it unreachable.
artefact promotion
Building once and deploying that same image to each environment.
flaky test
Intermittent failure. Destroys trust in the pipeline faster than anything else.
rolling deploy
Replacing instances gradually — so two versions run at once against one database.
canary
Sending a small share of real traffic to a new version and watching.
feature flag
Separating deploy from release. Needs cleanup discipline.
expand-migrate-contract
The three-deploy shape for a destructive schema change.
cold start
The initialisation delay of an idle serverless function.
egress
Data leaving the provider. Usually the surprising line on a cloud bill.
least privilege
The narrowest permissions that work. Widened "temporarily" and never narrowed.
liveness vs readiness
"Restart me" versus "don't send me traffic". Conflating them causes restart loops.
saturation
How full a resource is. The leading indicator — it rises before latency.
alert fatigue
Alerts that fire and are ignored, training everyone to ignore the channel.
drift
Real infrastructure no longer matching its code, because someone used the console.
runbook
The procedure for one known failure, mitigation first, linked from the alert.
