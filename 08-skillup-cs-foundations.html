Part I

Complexity

Foundations 01

Big-O, demystified

One question: as the input grows, how does the work grow?
⭐ THAT IS THE WHOLE IDEA. Not "how fast is it" — how does it
  SCALE. Constants and hardware are deliberately ignored,
  because they do not change the shape.

  O(1)        constant     a hash lookup, array index
  O(log n)    logarithmic  binary search, a B-tree index probe
  O(n)        linear       one pass over a list
  O(n log n)  linearithmic ⭐ a good sort. The practical floor
                           for comparison sorting.
  O(n²)       quadratic    nested loops over the same data
  O(2ⁿ)       exponential  ⚠ unusable beyond tiny inputs

WHAT THE DIFFERENCE ACTUALLY MEANS — n = 1,000,000

  O(1)         1 operation
  O(log n)     20
  O(n)         1,000,000
  O(n log n)   20,000,000
  O(n²)        1,000,000,000,000   ⚠ this is the cliff

⭐ THE ONLY DISTINCTION THAT MATTERS MOST DAYS: IS IT NESTED?
  A loop inside a loop over the same collection is O(n²), and
  that is the difference between "fine" and "the page times
  out" as data grows. Everything else is nuance.

THE RULES FOR READING IT
  · drop constants: O(2n) is O(n). Two passes still scale
    linearly.
  · drop lower terms: O(n² + n) is O(n²).
  · nesting multiplies; sequence adds.
  · ⭐ WATCH FOR HIDDEN LOOPS: `.includes()` inside a `.map()`
    is a nested loop wearing a method call. So is a database
    query inside a loop — the N+1, which is O(n) round trips
    and is what actually hurts.

⚠ AND THE HONEST CAVEAT: BIG-O IGNORES CONSTANTS, AND CONSTANTS
  ARE WHY YOUR CODE IS SLOW. An O(n) algorithm with a network
  call per item is far worse than an O(n²) one over an in-memory
  array of 100 items. ⭐ MEASURE; USE BIG-O TO PREDICT WHAT WILL
  BREAK LATER.
Foundations 02

Space complexity

The one people forget, and it causes the worse outage
SAME QUESTION, ABOUT MEMORY: how does memory grow with input?

  O(1) space   a few variables, whatever n is
  O(n) space   a copy of the input, a lookup map
  O(n²) space  a matrix

⭐ THE CLASSIC TRADE, AND IT IS THE MOST USEFUL ONE TO KNOW:
  SPEND MEMORY TO BUY TIME.
    · a hash map turns an O(n) scan into an O(1) lookup, at
      O(n) space
    · an index turns a table scan into a tree probe, at the
      cost of storage and slower writes
    · a cache turns a computation into a lookup, at the cost of
      memory and staleness
  ⇒ these are the same decision at three altitudes, and
    recognising that is worth more than either concept alone.

⚠ WHY SPACE FAILS WORSE THAN TIME
  slow code is annoying. ⭐ OUT-OF-MEMORY KILLS THE PROCESS —
  every in-flight request dies, not just the expensive one. And
  it usually happens at the worst moment, because that is when
  volume is highest.

THE PRACTICAL VERSIONS IN THIS STACK
  · loading every row to count them, instead of COUNT in SQL
  · building an array of all records to sum it, instead of
    aggregating in the database
  · a Map used as a cache with no eviction and no bound
  · reading an entire file into memory rather than streaming
  ⭐ ALL FOUR ARE O(n) SPACE WHERE O(1) WAS AVAILABLE, and all
    four are invisible until the data grows.

Discussing it without sounding like a puzzle site

"This is O(n²), that's bad.""It's nested over the same list — fine at 200 employees, and it becomes the bottleneck around a few thousand. Worth fixing now if we expect growth, otherwise noting."

The pattern in the right column

Every senior version connects the concept to a decision, and to a number. The vocabulary is used to explain a choice rather than to demonstrate that it is known — which is, generally, the difference the whole handbook is about.

Part II

Data structures

Six of them cover almost everything you will ever need. What matters is which operations each makes cheap.

Foundations 04

Arrays and lists

The default, and what it is bad at
ARRAY (JavaScript array, Python list) — contiguous, indexed
  read by index        O(1)   ⭐ the superpower
  append at the end    O(1)   amortised
  insert/remove front  O(n)   ⚠ everything shifts
  search by value      O(n)
  ⇒ ⭐ USE IT UNLESS YOU HAVE A REASON NOT TO. Contiguous memory
    is also cache-friendly, which makes it faster in practice
    than the theory suggests.

  ⚠ THE HIDDEN COST PEOPLE MISS: `array.includes(x)` inside a
    loop over the same array is O(n²). It looks like one method
    call. This is the single most common accidental quadratic in
    application code.

LINKED LIST — nodes pointing to nodes
  insert/remove at a known position   O(1)
  read by index                       O(n)   ⚠ must walk
  ⇒ ⭐ YOU WILL ALMOST NEVER CHOOSE ONE. Worth knowing because
    it explains queues, and because "O(1) insertion" sounds
    attractive until you notice you must first find the
    position, which is O(n).

WHERE THIS MATTERS IN REAL CODE
  · building a result set: append, don't insert at the front
  · deduplicating: ⭐ a Set, not `includes` in a loop —
    O(n) instead of O(n²), and it is a one-line change
  · "does this list contain x" repeatedly: build a Set once
Foundations 05

Hash maps

The most useful structure in application code
A HASH MAP (object, Map, dict) gives you O(1) lookup by key.
  insert · lookup · delete   all O(1) average
  ⚠ O(n) worst case, when many keys collide — theoretically
    interesting, practically irrelevant with a decent hash.
  ⚠ NO ORDER GUARANTEE by design (though JS objects and modern
    Python dicts preserve insertion order — do not rely on it
    across languages).

⭐ THE PATTERN THAT SOLVES MOST PERFORMANCE PROBLEMS IN
  APPLICATION CODE: BUILD A LOOKUP, THEN JOIN IN MEMORY.

    ⚠ for each employee: find their team in the teams array
      ⇒ O(n × m)

    ✅ build Map(teamId → team) once      O(m)
       then each lookup is O(1)            ⇒ O(n + m)

  this is exactly how you fix an N+1 after fetching both sets
  in two queries — and it is the same idea as a database index.

WHEN A SET INSTEAD
  a Set is a hash map with no values. Use it for membership
  ("have I seen this id?") and deduplication. ⭐ SEEING A `Set`
  IN A DIFF IS USUALLY A SIGN SOMEONE AVOIDED AN O(n²).

⚠ THE GOTCHA IN JAVASCRIPT: OBJECT KEYS ARE STRINGS.
  `obj[1]` and `obj["1"]` are the same key, and an object key
  cannot be an object. `Map` allows any key type and preserves
  it — which is why `Map` is the right default for anything
  non-trivial.
Foundations 06

Stacks and queues

STACK — last in, first out (LIFO) push and pop at the same end. Both O(1). ⭐ WHERE YOU ALREADY MEET IT · THE CALL STACK — which is why deep recursion overflows, and why a stack trace is called that · undo history · depth-first traversal · matching brackets, parsing nested structures QUEUE — first in, first out (FIFO) enqueue at one end, dequeue at the other. Both O(1) with the right implementation. ⚠ `array.shift()` IS O(n) — it shifts every element. A "queue" built on shift in a hot loop is a quadratic algorithm hiding in plain sight. ⭐ WHERE YOU ALREADY MEET IT · a job queue — the whole of Volume II's async work · breadth-first traversal · rate limiting and buffering · the event loop itself PRIORITY QUEUE — highest priority out first, not oldest ⇒ "process the highest-risk employees first", scheduling, and the internals of shortest-path algorithms. implemented with a heap — reflex 08. ⭐ WHY KNOWING THESE THREE PAYS OFF: they are the vocabulary of asynchronous systems. "Back-pressure on the queue", "the stack unwinds", "a priority queue for the retry schedule" — these describe designs, and without the words you cannot participate in the design conversation.
Foundations 07

Trees

Hierarchies, and the structure inside your database
A TREE is nodes with children and no cycles. Depth d, and
operations are usually O(d) — which is O(log n) if the tree is
BALANCED and O(n) if it has degenerated into a list.
⭐ "BALANCED" IS THE WHOLE GAME. An unbalanced binary tree is a
  linked list with extra steps.

THE ONES THAT MATTER TO YOU

  BINARY SEARCH TREE — left is smaller, right is larger
    lookup, insert, delete: O(log n) when balanced
    ⇒ the idea behind sorted-order lookup.

  B-TREE / B+TREE — ⭐ WHAT YOUR DATABASE INDEX ACTUALLY IS
    wide, shallow, and designed so each level is one disk page
    read. A billion rows is ~4 levels deep.
    ⇒ THIS IS WHY AN INDEXED LOOKUP IS FAST AND A SCAN IS NOT,
      and why index order matters (reflex 23). Knowing this one
      structure changes how you read a query plan.

  TRIE — a tree of characters
    ⇒ prefix search, autocomplete. "All employees whose name
      starts with 'Ch'" is a prefix query, which is also why a
      B-tree index can serve `LIKE 'Ch%'` and cannot serve
      `LIKE '%ch%'`.

  HEAP — reflex 08.

TREES IN YOUR DATA MODEL
  an org chart, a category hierarchy, a comment thread.
  ⚠ AND THE PRACTICAL PROBLEM: SQL is bad at arbitrary-depth
    trees. `manager_id` self-references are easy to store and
    awkward to query — "everyone under this manager, at any
    depth" needs a RECURSIVE CTE (reflex 25), or a different
    model such as a materialised path.
  ⭐ THIS IS A REAL DESIGN DECISION IN AN HR APPLICATION, and it
    is the kind of thing worth deciding deliberately rather
    than discovering.
Foundations 08

Heaps

One job, done extremely well
A HEAP keeps the smallest (or largest) element instantly
available, without keeping everything sorted.
  peek the min/max     O(1)
  insert               O(log n)
  remove the min/max   O(log n)
  ⚠ finding an arbitrary element   O(n) — it is not a search
    structure

⭐ THE PATTERN WORTH KNOWING: "TOP K OF N".
  you need the 10 highest-risk employees out of 50,000.
    ⚠ sort everything and take 10   → O(n log n)
    ✅ keep a heap of size 10        → O(n log k)
  ⇒ with k = 10 and n = 50,000 that is a large difference, and
    more importantly it is O(k) SPACE rather than O(n) — you
    never hold all 50,000 in memory.

  ⇒ AND THE DATABASE EQUIVALENT, WHICH IS THE ONE YOU WILL
    ACTUALLY USE: `ORDER BY risk DESC LIMIT 10` with an index on
    risk. The database does exactly this. ⭐ THE POINT OF
    KNOWING THE STRUCTURE IS RECOGNISING THAT FETCHING 50,000
    ROWS TO SORT IN NODE IS THE WRONG SHAPE OF SOLUTION.

WHERE ELSE
  · scheduling the next job by due time
  · a retry queue ordered by next-attempt time
  · inside Dijkstra's shortest-path algorithm
Foundations 09

Graphs

Anything with relationships that are not a hierarchy
NODES AND EDGES. Directed or undirected; weighted or not.
⭐ YOU ALREADY HAVE GRAPHS: the org chart with dotted-line
  reporting, "employees who worked on projects together",
  service dependencies, module import graphs, a CI pipeline's
  stages.

TWO TRAVERSALS, AND THE DIFFERENCE MATTERS
  BFS — breadth first, uses a QUEUE
    explores level by level. ⭐ FINDS THE SHORTEST PATH in an
    unweighted graph. "Degrees of separation", "who is within
    two reporting levels".
  DFS — depth first, uses a STACK (or recursion)
    goes deep first. ⭐ RIGHT FOR CYCLE DETECTION, topological
    sort, and exploring every path.

THE TWO ALGORITHMS WORTH RECOGNISING BY NAME
  TOPOLOGICAL SORT — order things so dependencies come first.
    ⇒ ⭐ THIS IS WHAT A BUILD SYSTEM, A MIGRATION RUNNER AND A
      CI PIPELINE ALL DO. And it FAILS IF THERE IS A CYCLE —
      which is precisely how a circular-dependency error is
      detected.
  DIJKSTRA — cheapest path with weighted edges.
    ⇒ routing, cost optimisation. Uses a priority queue.

⚠ THE TRAP IN A DATABASE: a graph query in SQL is a recursive
  CTE, and it is easy to write one that never terminates when
  the data contains a cycle. ⭐ ALWAYS BOUND THE DEPTH. Real HR
  data does contain reporting cycles, usually by mistake, and
  the query is where you find out.

⭐ AND THE HONEST SCOPE: you will not implement Dijkstra. You
  will recognise "this is a graph problem, not a table problem",
  which prevents a genuinely bad schema decision.
Foundations 10

Choosing one

You need to…Use
Keep an ordered collection and read by positionArray. The default; do not overthink it.
Look something up by id, repeatedlyMap / dict. The single highest-value swap in slow application code.
Ask "have I seen this?" or deduplicateSet. Replaces the accidental O(n²).
Process in arrival orderQueue. And do not build it on shift().
Process most important firstPriority queue — or ORDER BY … LIMIT in the database, which is usually the real answer.
Track nesting or reverse somethingStack.
Represent a hierarchyTree — and decide deliberately how you will query it at depth.
Represent arbitrary relationshipsGraph. Recognising this early prevents a bad schema.
Find the top or bottom few of manyHeap conceptually; an indexed ORDER BY … LIMIT in practice.
The honest summary of Part II

In application code you will use arrays, maps and sets for 95 % of everything — and knowing when a map replaces a nested loop is worth more than every other structure on this page combined.

The rest earns its place as recognition: seeing that a problem is a graph, a top-k, or a hierarchy tells you what to reach for and, more often, tells you the database should be doing it.

Algorithms

Foundations 11

Searching

Two, and the second one explains your database
LINEAR SEARCH — check each item. O(n).
  no preparation needed, works on anything, and it is the right
  answer for small collections.

BINARY SEARCH — halve the search space each step. O(log n).
  ⚠ REQUIRES SORTED DATA. That precondition is the whole cost.
  ⭐ 1,000,000 items in 20 steps. This is why sorted order and
    indexes matter so much.

⭐ AND THE GENERALISATION THAT IS ACTUALLY USEFUL DAILY:
  BINARY SEARCH IS A DEBUGGING TECHNIQUE.
    · `git bisect` over commits to find where a bug entered
    · commenting out half the code to isolate a failure
    · halving the input to find which record breaks the import
  ⇒ any time you can ask a yes/no question that eliminates half
    the possibilities, you have turned a linear hunt into a
    logarithmic one. That is the same idea as Volume III's
    bisect-in-time, and it is the most transferable algorithm
    on this page.
Foundations 12

Sorting

You will not implement one. Here is what to know anyway.
THE FLOOR: comparison sorting cannot beat O(n log n). Your
language's built-in sort achieves it and is written by people
who cared a great deal. ⭐ USE IT.

WHAT IS WORTH KNOWING
  · MERGE SORT   O(n log n) always, and STABLE. Needs O(n)
                 extra space.
  · QUICKSORT    O(n log n) typical, O(n²) worst case on bad
                 input. In-place, and usually fastest in
                 practice.
  · TIMSORT      what Python and JavaScript actually use — a
                 hybrid tuned for partly-sorted real data,
                 which most real data is.

⭐ THE ONE PROPERTY THAT AFFECTS YOUR CODE: STABILITY.
  a stable sort preserves the original order of equal elements.
  ⇒ so you can sort by name, then sort by department, and get
    departments containing alphabetised names. With an unstable
    sort, the second sort scrambles the first.
  ⚠ AND THE RELATED BUG: an unstable or ambiguous ORDER BY in
    SQL means paginated results can repeat or skip rows between
    pages, because the database is free to return ties in any
    order. ⭐ ALWAYS ADD A UNIQUE TIE-BREAKER — `ORDER BY risk
    DESC, id` — and this single line prevents a class of
    pagination bug that is very confusing to diagnose.

⭐ AND THE BIGGER POINT: SORT IN THE DATABASE, NOT IN NODE.
  `ORDER BY … LIMIT 20` with an index reads 20 rows. Fetching
  50,000 rows to sort and slice in application code is the same
  answer with a thousand times the cost — and it is a common
  pattern in ORM code.

Foundations 14

Recursion

Power, and the two ways it goes wrong
A FUNCTION THAT CALLS ITSELF, with:
  · a BASE CASE that stops it
  · a step that moves toward the base case
⚠ MISS EITHER AND YOU GET A STACK OVERFLOW.

WHERE IT IS GENUINELY THE RIGHT TOOL
  · walking a tree of unknown depth — an org chart, a folder
    structure, a nested comment thread
  · parsing nested structures — JSON, expressions
  · divide and conquer

⚠ THE TWO FAILURES
  ① NO BASE CASE, OR DATA WITH A CYCLE.
    ⭐ REAL ORG DATA CONTAINS REPORTING CYCLES, usually by
      mistake. A recursive walk over it never terminates. ⇒
      TRACK VISITED NODES AND BOUND THE DEPTH — always, not
      only when you suspect a problem.
  ② REDUNDANT WORK.
    naive recursion can recompute the same subproblem
    exponentially many times. ⇒ memoise, and it collapses to
    linear. That is all dynamic programming is.

⭐ THE PRACTICAL PREFERENCE: FOR DEEP OR UNBOUNDED STRUCTURES,
  AN EXPLICIT STACK BEATS RECURSION. Same algorithm, and the
  depth limit becomes your memory rather than the runtime's
  call stack — which in JavaScript is only a few thousand
  frames deep and gives you no useful error when it runs out.
Foundations 15

Where this shows up in daily work

The nested loop in a list render

For each row, searching another array. Build a Map once. The most common accidental quadratic in frontend code.

The unbounded fetch

Loading everything to count, sum or take the top ten. Aggregate and limit in the database — O(1) memory instead of O(n).

The recursive org walk

Works in dev, hangs on real data with a reporting cycle. Track visited, bound the depth.

The unstable pagination

ORDER BY on a non-unique column, so rows repeat or vanish between pages. Add a unique tie-breaker.

The retry storm

A queue drained without bounded concurrency. This is back-pressure, and it is a queue problem with a queue solution.

The import that dies at 400k

Whole file in memory. Stream it, batch the writes. O(n) space where O(1) was available.

Foundations 16

One request, fully

you type https://app.example.com/employees ① URL PARSED scheme · host · port · path · query ② DNS RESOLUTION host → IP address (reflex 17) ③ TCP CONNECTION three-way handshake (reflex 18) ④ TLS HANDSHAKE certificate, keys (reflex 18) ⑤ HTTP REQUEST SENT method, path, headers, body ⑥ SERVER ROUTES IT load balancer → app → your handler ⑦ APP DOES ITS WORK guards → validation → service → DB ⑧ RESPONSE RETURNS status, headers, body ⑨ BROWSER PARSES HTML builds the DOM (reflex 20) ⑩ SUB-RESOURCES FETCHED CSS, JS, fonts, images — ⭐ each one potentially repeating ②–⑧ ⑪ RENDER style → layout → paint → composite ⑫ JS HYDRATES the page becomes interactive ⭐ WHY TRACING THIS ONCE IS WORTH IT: every "the site is slow" and every "it works for me" lives at one of these twelve steps, and naming the step is most of the diagnosis. · slow at ② → DNS or a cold cache · slow at ③④ → connection setup, geography, no keep-alive · slow at ⑦ → your code. ⭐ THE ONLY STEP MOST ENGINEERS LOOK AT, and often not where the time is. · slow at ⑩ → too many resources, or too large · slow at ⑪⑫ → bundle size, or main-thread work · ⚠ AND THE ONE THAT CONFUSES EVERYONE: a failure between ⑤ and ⑧ that the browser hides from your JavaScript is CORS (reflex 21) — the request succeeded and you are not allowed to read the answer.
Foundations 17

DNS

Names to addresses, with caching at every level
THE LOOKUP CHAIN
  browser cache → OS cache → your router → your ISP's resolver
  → root servers → the .com servers → the domain's own
  nameservers
  ⇒ any level may answer from cache, which is why the first
    request to a new host is slower than the rest.

THE RECORD TYPES WORTH KNOWING
  A       name → IPv4 address
  AAAA    name → IPv6
  CNAME   name → another name  ⚠ cannot exist at the apex of a
          domain, which is why `example.com` and
          `www.example.com` are configured differently
  MX      mail
  TXT     verification, SPF/DKIM — ⭐ where "prove you own this
          domain" lives

⭐ TTL IS THE ONLY DNS CONCEPT THAT WILL AFFECT YOUR DAY.
  it says how long resolvers may cache an answer. So a DNS
  change is NOT instant — it propagates over the TTL, and
  during that window some users reach the old address and some
  the new one.
  ⇒ ⚠ BEFORE A PLANNED CUTOVER, LOWER THE TTL FIRST — a day or
    two in advance. Otherwise your rollback also takes hours to
    take effect, which is the worst possible time to discover
    this.

⭐ AND THE DEBUGGING VALUE: "is it DNS?" is a real first
  question. A service that is unreachable by name and reachable
  by IP has a DNS problem, and you have just eliminated your
  entire application from the investigation.
Foundations 18

TCP and TLS

Why the first request to a host is expensive
TCP — a reliable ordered stream over an unreliable network
  THE THREE-WAY HANDSHAKE: SYN → SYN-ACK → ACK.
  ⭐ ONE FULL ROUND TRIP BEFORE ANY DATA MOVES. Across a
    continent that is ~80 ms of nothing happening.
  it then guarantees delivery and order by retransmitting lost
  packets — ⚠ which is why a lossy network shows up as latency
  rather than as errors.

TLS — encryption and identity on top
  another 1–2 round trips (1 with TLS 1.3): agree a cipher,
  present the CERTIFICATE, derive session keys.
  ⭐ WHAT THE CERTIFICATE ACTUALLY PROVES: that a certificate
    authority vouches this host is who it claims. It says
    nothing about the site being trustworthy — a phishing site
    with valid HTTPS is completely normal.

⇒ SO A COLD CONNECTION COSTS: DNS + TCP + TLS ≈ 3–4 round trips
  BEFORE your request is even sent. ⭐ THIS IS WHY CONNECTION
  REUSE (keep-alive) AND CONNECTION POOLS MATTER SO MUCH — and
  why a service that opens a new connection per request is slow
  for reasons that never appear in your application profile.

⚠ THE CERTIFICATE FAILURES YOU WILL MEET
  · EXPIRED — and it takes the whole site down, at 3 a.m., on a
    holiday. ⭐ MONITOR EXPIRY DATES; this is an entirely
    preventable outage that keeps happening.
  · wrong hostname; a missing intermediate certificate that
    works in a browser and fails in curl or a server-side
    client
  · ⚠ and the anti-pattern: disabling verification to make an
    error go away. That removes the only protection TLS
    provides, and it ships.
Foundations 19

HTTP versions

VersionChangedWhy you care
HTTP/1.1Text protocol, one request at a time per connectionHead-of-line blocking — browsers opened ~6 connections per host to work around it, which is where "bundle your assets" and "domain sharding" came from.
HTTP/2Binary, multiplexed — many requests in parallel on one connection; header compression; server pushMakes many small files viable, so aggressive bundling matters less than it did. Still TCP, so packet loss stalls all streams.
HTTP/3Runs on QUIC over UDP; TLS built inRemoves TCP's head-of-line blocking and cuts handshake round trips. Noticeably better on mobile and lossy networks.
The practical takeaway

You do not configure this — your host or CDN does. What matters is knowing that advice written for HTTP/1.1 is often now wrong: concatenating everything into one giant bundle was a workaround for a limit that no longer exists, and it costs you cache granularity.

Foundations 20

How a page renders

HTML ──parse──► DOM ─┐ ├──► RENDER TREE ──► LAYOUT ──► PAINT CSS ──parse──► CSSOM ┘ │ ▼ COMPOSITE ⭐ THE FACTS THAT EXPLAIN FRONTEND PERFORMANCE ① CSS IN THE HEAD IS RENDER-BLOCKING. Nothing paints until it is parsed — deliberately, to avoid a flash of unstyled content. ② A CLASSIC SCRIPT TAG IS PARSER-BLOCKING. The HTML parser stops. ⇒ `defer` (run after parsing, in order) or `async` (run whenever) exists for this reason. ③ LAYOUT IS EXPENSIVE, AND SOME PROPERTIES FORCE IT. changing width, height, top or margin triggers layout for a subtree. ⭐ CHANGING `transform` OR `opacity` DOES NOT — they are composited. THIS IS WHY SMOOTH ANIMATIONS USE TRANSFORM AND NOT `left`. ④ READING A LAYOUT PROPERTY MID-CHANGE FORCES A SYNCHRONOUS RECALCULATION. A loop that writes a style then reads `offsetHeight` is layout thrashing — the single worst frontend performance pattern, and it looks innocent. ⑤ FONTS CAUSE A VISIBLE JUMP unless you plan for it — `font-display: swap` and a real fallback stack. ⭐ AND THE ONE THAT EXPLAINS THE ERROR YOU WILL ACTUALLY SEE: HYDRATION. The server sent HTML; the browser then runs the same components and expects to produce identical markup. A mismatch — `new Date()`, `Math.random()`, `localStorage`, a timezone difference — is what produces "text content did not match server-rendered HTML". ⇒ THE FIX IS TO MAKE THE FIRST RENDER IDENTICAL ON BOTH SIDES, not to suppress the warning.
Foundations 21

CORS, properly understood

The most misunderstood error in web development
⭐ WHAT IT IS: A BROWSER RULE, NOT A SERVER ERROR.
  by default, JavaScript on origin A may not READ a response
  from origin B. The request is usually SENT and ANSWERED — the
  browser refuses to hand the answer to your code.

  ⇒ SO THE SERVER LOG SHOWS A CLEAN 200 AND THE CONSOLE SHOWS A
    FAILURE. That contradiction is the whole confusion, and
    recognising it saves hours.

AN ORIGIN IS scheme + host + PORT.
  ⚠ localhost:3001 and localhost:3010 ARE DIFFERENT ORIGINS.
    Which is exactly why this project meets CORS in development.

THE PREFLIGHT — the part people miss
  for anything beyond a simple request (a custom header such as
  Authorization, or a JSON content type), the browser first
  sends an OPTIONS request asking what is allowed.
  ⇒ ⭐ SO YOUR SERVER MUST HANDLE OPTIONS. A route that only
    handles POST will fail CORS with a confusing error, and the
    POST never appears in your logs at all.

  the response must say: allowed origin · allowed methods ·
  allowed headers · and, for cookies, allow-credentials.
  ⚠ AND YOU CANNOT COMBINE `Allow-Origin: *` WITH CREDENTIALS.
    The browser rejects it. With cookies you must name the exact
    origin.

⭐ WHERE THE FIX GOES: ALWAYS ON THE SERVER. Naming the allowed
  origins.
  ⚠ NOT by disabling browser security, not with a browser
    extension, and ⚠ NOT with `origin: '*'` shipped to
    production — a development shortcut that keeps reaching
    production and quietly permits any site to call your API
    with a user's browser.

⭐ AND THE BOUNDARY OF THE CONCEPT: CORS PROTECTS THE USER, NOT
  YOUR SERVER. A script, a curl command or another backend
  ignores it entirely. It is not access control — your auth
  checks are. Confusing the two is how people conclude an
  endpoint is "protected" because a browser could not read it.

Foundations 22

Reading a query plan

The single most valuable database skill
`EXPLAIN ANALYZE <query>` shows what the database ACTUALLY DID —
not what you assume it did. ⭐ EVERY DATABASE PERFORMANCE
CONVERSATION SHOULD START HERE, and most start with a guess
instead.

WHAT TO LOOK FOR, IN ORDER

  ① SEQ SCAN ON A LARGE TABLE
    it read every row. Fine on 500 rows, fatal on 5,000,000.
    ⇒ a missing index, or a query the index cannot serve.

  ② ROWS ESTIMATED vs ROWS ACTUAL
    ⭐ THE MOST INFORMATIVE LINE IN THE PLAN. If the planner
      expected 10 rows and got 400,000, it chose a strategy for
      the wrong problem — and everything above that node is
      consequently wrong. ⇒ usually stale statistics, or a
      correlation the planner cannot see.

  ③ THE JOIN STRATEGY
    NESTED LOOP  good for few rows; ⚠ catastrophic for many
    HASH JOIN    good for large unsorted sets, needs memory
    MERGE JOIN   good when both sides are already sorted
    ⇒ you rarely override this. You use it to understand WHY it
      was slow.

  ④ SORT — and whether it spilled to disk
    "external merge Disk: 52MB" means the sort exceeded working
    memory. ⇒ add an index that provides the order, or reduce
    the rows first.

  ⑤ FILTER APPLIED AFTER A SCAN, and how many rows it removed
    reading a million rows to keep four is an index that does
    not exist yet.

⭐ THE MENTAL MODEL: PLANS ARE TREES, READ FROM THE INSIDE OUT.
  the deepest nodes run first; each parent consumes its
  children's rows. And ⭐ THE EXPENSIVE NODE IS USUALLY ONE
  NODE — find it and you have found the work.
Foundations 23

Indexes, deeply

What an index is, and the rules that follow from it
AN INDEX IS A SORTED STRUCTURE (a B-tree, reflex 07) mapping
column values to row locations. So a lookup becomes a tree
probe — a handful of page reads instead of a full scan.

⭐ THE RULES THAT FOLLOW, AND THEY ALL FOLLOW FROM "SORTED"

  ① COMPOSITE INDEX ORDER MATTERS — LEFT TO RIGHT.
    an index on (team_id, hired_at) serves:
      WHERE team_id = 5                       ✅
      WHERE team_id = 5 AND hired_at > '…'    ✅
      WHERE hired_at > '…'                    ⚠ NOT SERVED
    ⇒ think of a phone book sorted by surname then first name:
      you cannot use it to find everyone called "Alice".
    ⭐ THIS IS THE MOST USEFUL INDEXING FACT THERE IS, and it is
      the reason "we have an index on that column" is not
      always the same as "the index helps".

  ② A FUNCTION ON THE COLUMN DEFEATS THE INDEX.
    WHERE LOWER(email) = '…'  ⚠ cannot use an index on email.
    ⇒ index the expression instead, or store it normalised.

  ③ LEADING WILDCARDS CANNOT BE SERVED.
    LIKE 'Ch%'   ✅ a prefix — it is a range in sorted order
    LIKE '%ch%'  ⚠ full scan. ⇒ that is what a text-search
                 index is for.

  ④ AN INDEX HELPS ORDER BY TOO.
    `ORDER BY hired_at LIMIT 20` with a matching index reads 20
    rows instead of sorting the table.

  ⑤ COVERING INDEX — if the index contains every column the
    query needs, the table is never touched at all.

⚠ WHAT INDEXES COST
  · every write must update every index on that table
  · storage
  · ⭐ AND UNUSED INDEXES ARE PURE COST. Check which are
    actually used before adding a sixth.

⭐ THE RULE OF THUMB: INDEX WHAT YOU FILTER, JOIN AND ORDER BY.
  Foreign keys almost always deserve one — ⚠ and Postgres does
  NOT create one automatically for a foreign key, which
  surprises people and is a common cause of slow joins.
Foundations 24

Window functions

Aggregate without collapsing rows — the feature that replaces application loops
THE PROBLEM THEY SOLVE: GROUP BY collapses rows. Sometimes you
want each row PLUS something computed across its group.

  "each employee, with their department's average salary"
  "each employee's rank within their team by risk"
  "the change from the previous month, per row"

⭐ ALL THREE ARE ONE QUERY WITH A WINDOW FUNCTION, AND ALL THREE
  ARE OTHERWISE A LOOP IN APPLICATION CODE — usually an N+1.

THE SHAPE
  <function>() OVER (PARTITION BY <group> ORDER BY <sort>)
                     └─ which rows ─┘   └─ in what order ─┘

THE ONES THAT EARN THEIR KEEP
  ROW_NUMBER()   1,2,3 — no ties. ⭐ THE STANDARD WAY TO PICK
                 "the latest row per group": number them and
                 keep number 1. This replaces a very common
                 and very slow correlated subquery.
  RANK()         ties share a rank and leave gaps
  DENSE_RANK()   ties share, no gaps
  LAG() / LEAD() the previous or next row's value ⇒ ⭐ month-
                 over-month change without a self-join
  SUM() OVER     running totals
  AVG() OVER     the group average, on every row

⚠ WHAT TO WATCH
  · ⭐ THEY RUN AFTER WHERE. You cannot filter on a window
    result in the same WHERE clause — wrap it in a CTE or
    subquery and filter outside. This catches everyone once.
  · they need an ORDER BY to be deterministic; without one,
    ties resolve arbitrarily
  · a window over a large unindexed set is a sort, and the plan
    will tell you if it spilled to disk
Foundations 25

CTEs, including recursive ones

Naming the steps of a query
WITH active AS (
  SELECT * FROM employees WHERE left_at IS NULL
), scored AS (
  SELECT e.*, r.risk FROM active e JOIN risks r ON …
)
SELECT * FROM scored WHERE risk > 0.7;

⭐ WHY THEY MATTER: READABILITY. A nested-subquery query is
  written inside-out and read inside-out. A CTE chain is a
  pipeline with named steps, and reviewable one step at a time.

⚠ THE PERFORMANCE NOTE PEOPLE GET WRONG: in older Postgres a
  CTE was an OPTIMISATION FENCE — always materialised, so it
  could be slower than the equivalent subquery. Modern versions
  inline them when it is safe. ⭐ SO CHECK THE PLAN RATHER THAN
  RELYING ON EITHER PIECE OF FOLKLORE.

RECURSIVE CTEs — ⭐ THE TOOL FOR HIERARCHIES
  WITH RECURSIVE chain AS (
    SELECT id, manager_id, 1 AS depth
      FROM employees WHERE id = 42        -- the anchor
    UNION ALL
    SELECT e.id, e.manager_id, c.depth + 1
      FROM employees e JOIN chain c ON e.manager_id = c.id
     WHERE c.depth < 10                   -- ⭐ THE BOUND
  )
  SELECT * FROM chain;

  ⇒ "everyone under this manager, at any depth" — the org-chart
    query, and the reason reflex 07 said SQL and trees need
    thought.
  ⚠ THE DEPTH BOUND IS NOT OPTIONAL. Real reporting data
    contains cycles, and without a bound the query runs until
    something dies.
Foundations 26

Normalisation, and when to stop

FormRuleIn practice
1NFAtomic values; no lists in a columnA comma-separated skills column is unqueryable and unjoinable. This one is not optional.
2NFNo partial dependency on a composite keyRarely a live issue with surrogate integer keys.
3NFNo column depends on another non-key columnThe practical target. Storing department_name on the employee row alongside department_id is the violation you will actually meet.
DenormalisedDeliberately duplicatedFor read performance, or to freeze a historical fact — which is a different and better reason.
The denormalisation that is always right

Store the value that was true at the time, when the historical record must not change. An invoice keeps the price as charged; a report keeps the department as it was.

That is not a performance shortcut — it is correct modelling. Joining to the current department means last quarter's report silently rewrites itself after a reorganisation, which is a data-integrity failure that looks like a reporting bug. The question from the onboarding handbook applies: do we need to know what was true then?

Foundations 27

Transactions and isolation

ACID, then the levels — and what each one still permits
ATOMIC      all or nothing
CONSISTENT  constraints hold before and after
ISOLATED    concurrent transactions do not corrupt each other
DURABLE     committed means survived a crash

⭐ THE ONLY ISOLATION FACTS THAT AFFECT YOUR CODE:

  READ COMMITTED — Postgres's default
    you never read uncommitted data. ⚠ BUT two reads in the same
    transaction can return different values, because someone
    else committed in between.
    ⇒ SO THIS IS UNSAFE:
        read balance → decide → write balance
      two transactions both read 100, both subtract 80, both
      write 20. One withdrawal has vanished. ⭐ A TRANSACTION
      ALONE DOES NOT PREVENT THIS.

  REPEATABLE READ
    the same read returns the same value throughout. Prevents
    the above, at the cost of possible serialisation failures
    you must retry.

  SERIALIZABLE
    as if transactions ran one at a time. Safest, slowest, and
    ⚠ it will abort transactions that conflict — so your code
    MUST handle a retry.

⭐ THE PRACTICAL ANSWERS TO READ-MODIFY-WRITE, IN ORDER
  ① LET THE DATABASE DO THE ARITHMETIC:
    `UPDATE accounts SET balance = balance - 80 WHERE …`
    ⇒ atomic, no read, no race. THE BEST ANSWER, and the one
      people skip because the ORM encourages fetch-then-save.
  ② A UNIQUE CONSTRAINT, so the duplicate is impossible rather
    than unlikely.
  ③ OPTIMISTIC LOCKING — a version column, and the update
    fails if the version changed.
  ④ `SELECT … FOR UPDATE` — pessimistic lock. Works, and it
    serialises access, so hold it briefly.

⚠ AND THE RULE FOR EVERY TRANSACTION: KEEP IT SHORT, AND NEVER
  MAKE A NETWORK CALL INSIDE ONE. A transaction held open while
  waiting on the AI service holds locks and a pooled connection
  for seconds — and that is how one slow dependency becomes a
  database-wide outage.
Foundations 28

Scaling, and NoSQL in one page

The order to try things, and what the alternatives actually offer
THE SCALING LADDER — ⭐ IN THIS ORDER, NOT THE REVERSE
  1  FIX THE QUERY. Read the plan.
  2  ADD THE INDEX.
  3  REMOVE THE ROUND TRIPS (the N+1).
  4  CACHE the hot reads, accepting staleness.
  5  A BIGGER MACHINE. ⭐ Boring, immediate, and it takes you
     further than most people assume.
  6  READ REPLICAS for read-heavy load ⚠ accepting replication
     lag, and needing read-your-writes for the user's own
     changes.
  7  PARTITION a huge table by time or tenant.
  8  SHARD. ⚠ Enormous complexity: cross-shard queries, hot
     shards, rebalancing, no easy transactions. ⭐ ALMOST NEVER
     THE ANSWER, and proposing it before step 1 is a tell.

CONNECTION POOLING — the one that bites in serverless
  each connection costs the database memory. ⚠ Postgres handles
  hundreds, not thousands.
  ⭐ SO A SERVERLESS OR AUTOSCALED APP CAN EXHAUST CONNECTIONS
    WHILE BARELY USING CPU — every instance opens its own pool.
    ⇒ this is exactly why a pooler (PgBouncer, or Neon's
      built-in pooling) exists, and why the connection string
      matters.

NOSQL, HONESTLY — what each family trades away
  DOCUMENT (Mongo)   flexible schema, denormalised documents.
                     ⚠ you now own consistency and shape, and
                     "schemaless" means the schema lives in
                     your code, unenforced.
  KEY-VALUE (Redis)  ⭐ genuinely useful alongside Postgres:
                     caching, sessions, rate limit counters,
                     queues. Not a system of record.
  WIDE-COLUMN        enormous write throughput, query patterns
                     fixed at design time.
  GRAPH              relationship traversal as a first-class
                     operation. For genuine graph workloads.

⭐ THE JUDGEMENT: A RELATIONAL DATABASE WITH GOOD INDEXES AND
  JSONB COLUMNS FOR THE GENUINELY UNSTRUCTURED PARTS COVERS THE
  LARGE MAJORITY OF APPLICATIONS — including this one. Adopt
  another store when you can name the specific limit you hit,
  not because of the category.
