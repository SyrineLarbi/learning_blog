Part I

How code runs

Four ideas — runtime, package manager, port, environment variable. Every command you will type in your first week is one of these four wearing a costume.

Foundation 01

Runtimes

Source code is text. Text does nothing. A runtime is the program that reads your text and makes the machine act on it.

RuntimeRunsIn this project
The browser (V8 in Chrome)JavaScriptEverything the user sees. The frontend, once it has been downloaded.
Node.jsJavaScript / TypeScriptThe NestJS backend, and Next.js while it renders on the server.
CPythonPythonThe FastAPI AI service and everything with a model in it.
Interpreted, compiled, and the confusing middle
COMPILED       source ──► machine code ──► run
               (C, Rust, Go) a separate build step produces a
               binary. Fast to run, slow to iterate.

INTERPRETED    source ──► runtime reads and executes line by line
               (Python) no build step. Start fast, run slower.

THE MIDDLE     JavaScript is interpreted, but modern engines
               compile hot code to machine code WHILE RUNNING
               (just-in-time). You get most of both.

⭐ WHERE TYPESCRIPT SITS — AND WHY IT MATTERS TO YOU
  TypeScript is NOT a runtime. Nothing runs TypeScript. It is
  compiled ("transpiled") to plain JavaScript first, and the
  types are DELETED in that step.

    employee.ts  ──tsc──►  employee.js  ──node──►  runs

  ⇒ so types catch mistakes BEFORE the program runs, and are
    completely absent AT runtime. A value that arrives from an
    API as a string does not become a number because you typed
    it as one. This single fact explains most TypeScript
    surprises — see reflex 16.
Foundation 02

Package managers

Nobody writes a web framework from scratch. A package manager downloads code other people wrote, records exactly which versions you used, and makes the same set reproducible on someone else's machine.

LanguageToolDeclaresLocks
JavaScriptnpmpackage.jsonpackage-lock.json
Pythonpiprequirements.txtthe same file, when versions are pinned
The two files, and why the second one exists
package.json      WHAT YOU ASKED FOR
                  "@nestjs/common": "^11.0.0"
                  the ^ means "11.anything, as long as it is not 12".

package-lock.json WHAT YOU ACTUALLY GOT
                  "@nestjs/common": "11.0.4", plus the exact
                  version of every dependency of every dependency.

⭐ COMMIT THE LOCK FILE. Without it, two developers running the
  same install command a month apart get different code, and the
  bug that appears on one machine and not the other is
  unexplainable. With it, installs are reproducible.

DEPENDENCIES vs DEV DEPENDENCIES
  dependencies      needed to RUN            (nestjs, prisma, react)
  devDependencies   needed to BUILD or TEST  (typescript, jest,
                    eslint) — not shipped to production.

THE COMMANDS THAT MATTER
  npm install              install everything in package.json
  npm install <pkg>        add one, and record it
  npm run <script>         run a script defined in package.json
  ⚠ npm run dev / start:dev — this project's services each have
    their own; you will run three terminals.

Part II

Databases

Where the data actually lives, and the smallest amount of SQL that lets you read what the ORM generates.

Foundation 04

Tables, rows, keys

A relational database stores data in tables. A table is a grid: columns define what a record can hold, and each row is one record.

One table, and the four ideas in it
employees
┌────┬─────────────┬──────────────┬────────┬─────────────┐
│ id │ name        │ department   │ salary │ hired_at    │
├────┼─────────────┼──────────────┼────────┼─────────────┤
│  1 │ A. Chen     │ Engineering  │  62000 │ 2021-03-01  │
│  2 │ B. Osei     │ Engineering  │  58000 │ 2023-09-15  │
│  3 │ C. Rossi    │ Sales        │  51000 │ 2019-01-07  │
└────┴─────────────┴──────────────┴────────┴─────────────┘

①  SCHEMA — the shape is declared and enforced. A column typed
    as a date rejects "next Tuesday". The database refuses bad
    data rather than storing it, which is the entire reason to
    prefer one over a spreadsheet.

②  PRIMARY KEY — `id`. Unique, never reused, never meaningful.
    ⚠ never key on something real (email, employee number) —
    real things change, and a key that changes breaks everything
    pointing at it.

③  NOT NULL vs NULL — is this value REQUIRED, or may it be
    absent? "absent" and "zero" and "empty string" are three
    different things, and treating them alike is a classic bug.

④  INDEX — a lookup structure. Without one, finding a row means
    reading every row. With one, it is near-instant.
    ⇒ the trade: indexes make reads fast and writes slightly
      slower, and they take space. Add them for columns you
      filter or join on, not for everything.
Foundation 05

Relationships

ONE-TO-MANY — one team has many employees teams employees ┌────┬────────────┐ ┌────┬──────────┬─────────┐ │ id │ name │ │ id │ name │ team_id │ ├────┼────────────┤ ├────┼──────────┼─────────┤ │ 5 │ Platform │◄──────┤ 1 │ A. Chen │ 5 │ │ 6 │ Growth │ │ 2 │ B. Osei │ 5 │ └────┴────────────┘ │ 3 │ C. Rossi │ 6 │ └────┴──────────┴─────────┘ └─ FOREIGN KEY ⭐ THE CHILD HOLDS THE LINK. The employee row knows its team; the team row does not list its employees. The "many" side always carries the foreign key. ⭐ AND THE FOREIGN KEY IS A GUARANTEE, not a convention: the database will REFUSE an employee whose team_id does not exist. That is a whole class of bug the database removes for you, on every path, forever. MANY-TO-MANY — an employee has many skills; a skill has many employees. Neither side can hold the link, so a third table does: employees employee_skills skills ┌────┐ ┌─────────────┬────────┐ ┌────┬─────────┐ │ 1 │◄────────┤ employee_id │ skill_id├─┤ 9 │ Python │ └────┘ │ 1 │ 9 │ │ 10 │ SQL │ │ 1 │ 10 │ └────┴─────────┘ └─────────────┴─────────┘ called a JOIN TABLE (or junction, or pivot). Recognising when you need one is a real modelling skill — the moment you find yourself wanting a list inside a column, this is the answer. ON DELETE — the question people forget delete a team with employees in it. What happens? CASCADE delete the employees too ⚠ rarely right RESTRICT refuse the delete ← usually right SET NULL employees keep existing, teamless ⇒ the database makes you choose. Choose deliberately.
Foundation 06

Enough SQL to read

You will write queries through Prisma, not by hand. But you must be able to read the SQL it generates when something is slow or wrong.

The clauses, in the order the database applies them
SELECT   name, department, salary      -- ⑤ which columns
FROM     employees                     -- ① which table
JOIN     teams ON teams.id = employees.team_id   -- ② stitch
WHERE    salary > 55000                -- ③ filter ROWS
GROUP BY department                    -- ④ collapse into groups
HAVING   COUNT(*) > 3                  -- ④b filter GROUPS
ORDER BY salary DESC                   -- ⑥ sort
LIMIT    10;                           -- ⑦ cut

⭐ THE NUMBERS ARE THE EXECUTION ORDER, AND IT IS NOT THE WRITING
  ORDER. FROM first, SELECT almost last. This explains the error
  every beginner hits: you cannot use a name you invented in
  SELECT inside WHERE, because WHERE ran first.

WHERE vs HAVING — the distinction that produces wrong numbers
  WHERE  filters rows BEFORE grouping
  HAVING filters groups AFTER
  ⚠ putting a row condition in HAVING (or an aggregate in WHERE)
    gives a number that is wrong but plausible — the most
    expensive kind of bug.

JOIN TYPES
  INNER JOIN   only rows that match on BOTH sides
               ⚠ silently DROPS employees with no team. If a
                 count is lower than expected, suspect this first.
  LEFT JOIN    all rows from the left, NULLs where no match
               ⇒ what you usually want for "list everyone, with
                 their team if they have one".

⚠ AND THE ONE THAT PRODUCES WRONG TOTALS: joining a table that
  has MANY matching rows multiplies your rows. Sum a salary after
  joining to three skills and you have counted the salary three
  times. This is called fan-out, and it is the most common source
  of inflated figures in reporting.

AGGREGATES
  COUNT(*)  rows        COUNT(col)  non-null values in col
  SUM AVG MIN MAX
  ⚠ COUNT(*) and COUNT(column) differ whenever the column has
    nulls, and AVG silently ignores nulls rather than treating
    them as zero.

APIs

How two programs on different machines — or on the same machine in different languages — agree to talk.

Foundation 07

What HTTP is

THE RESTAURANT, AND WHY THE ANALOGY IS ACTUALLY USEFUL you (the frontend) ──order──► waiter (the API) ──► kitchen ◄──plate── ◄── (backend + DB) you never enter the kitchen. You do not know whether the soup was made fresh or reheated. You know the MENU — the contract — and nothing else. ⭐ THAT IGNORANCE IS THE POINT. The kitchen can be rebuilt in a different language and your order still works, as long as the menu is unchanged. This is the whole value of an API, and it is why "what can never change?" is the key API design question. ONE REQUEST, ONE RESPONSE REQUEST RESPONSE ┌──────────────────────────┐ ┌──────────────────────────┐ │ POST /api/reports │ │ 201 Created │ │ Host: localhost:3010 │ │ Content-Type: application│ │ Authorization: Bearer … │ │ /json│ │ Content-Type: application│ │ │ │ /json │ │ { "id": 42, │ │ │ │ "status": "PENDING" } │ │ { "teamId": 5 } │ │ │ └──────────────────────────┘ └──────────────────────────┘ method · path · headers status · headers · body · body ⭐ HTTP IS STATELESS. The server remembers nothing between requests. Every single request must carry its own proof of identity — which is exactly why a token is attached to all of them, and why "logged in" is not a state the server holds.

Methods and URLs

MethodMeansSafe to repeat?Notes
GETRead somethingYesMust not change anything. A GET that deletes is a genuine bug — browsers and proxies pre-fetch GETs.
POSTCreate somethingNoTwo POSTs make two things. This is why double-clicks create duplicates, and why an idempotency key exists.

DELETERemoveYesDeleting twice should not be an error the second time — it is already gone, which is the requested state.
Where data can travel in a request — and the security consequence
PATH PARAMETER      /api/employees/42
                    identifies WHICH resource.
                    ⭐ every id in a path is a CLAIM, not a fact.
                      "42" being well-formed says nothing about
                      whether this caller may see employee 42.

QUERY STRING        /api/employees?department=Sales&page=2
                    filters, sorting, pagination — things that
                    modify a read.
                    ⚠ appears in server logs and browser history.
                      Never put a token or a password here.

HEADERS             Authorization: Bearer <token>
                    identity, content type, caching. Metadata
                    about the request rather than the subject
                    of it.

BODY                { "teamId": 5 }
                    the payload for POST / PUT / PATCH.
                    GET requests do not have one.
Foundation 09

Status codes

The families, then the ones you will actually meet
2xx  it worked
3xx  look somewhere else
4xx  ⭐ YOU sent something wrong      ← do not retry, fix the call
5xx  ⭐ THE SERVER broke              ← retrying may help

THE ONES THAT MATTER

200 OK                  read succeeded
201 Created             ⇒ and return the thing you created, or
                          at least where to find it
204 No Content          succeeded, nothing to say (a delete)

400 Bad Request         malformed or invalid input
401 Unauthorized        ⭐ MISNAMED — it means UNAUTHENTICATED.
                          "I do not know who you are." No token,
                          bad token, or expired token.
403 Forbidden           "I know exactly who you are, and you may
                          not do this." ⇒ 401 vs 403 is the
                          authentication/authorisation distinction
                          made visible, and getting it backwards
                          in your own API confuses every client.
404 Not Found           no such thing
                        ⚠ ALSO the right answer for "exists, but
                          not yours" — a 403 confirms the record
                          exists, which is itself a leak.
409 Conflict            it clashes with current state (duplicate
                          email, already approved)
422 Unprocessable       well-formed but semantically invalid
429 Too Many Requests   rate limited ⇒ back off, don't hammer

500 Internal Error      an unhandled bug on the server
502 / 503 / 504         a service behind this one is broken,
                          unavailable, or too slow

⚠ THE ANTI-PATTERN: returning 200 with {"error": "..."} in the
  body. Every generic client — retry logic, monitoring, load
  balancers — believes the status code. Lying in it means your
  failures are invisible to all of them.
Foundation 10

REST conventions

ConventionWhy it exists
Nouns, not verbs
/api/employees, not /api/getEmployees		The method is already the verb. GET /employees and POST /employees are two operations on one noun, and a new reader can guess both.
Plural collections
/employees and /employees/42		Consistency beats grammar. Pick plural everywhere and never think about it again.
Nesting shows ownership
/teams/5/employees		Reads as "the employees of team 5". Stop at one level of nesting — deeper than that becomes unreadable and inflexible.
Filters go in the query string
?department=Sales&page=2		The path identifies what; the query modifies which ones. Filters in the path multiply endpoints forever.
Every list is paginatedAn unpaginated list endpoint is a future incident. And the response shape is a contract — adding a wrapper later breaks every caller, so decide now.
Errors have a shapeA code a machine can branch on, a message a human can read, and which field was wrong. Otherwise every integration becomes a support conversation.
In this project

The NestJS backend exposes /api/auth, /api/users, /api/teams, /api/employees, /api/analytics and /api/reports — one module per noun, which is exactly the NestJS structure covered in Volume III. Swagger generates browsable documentation from the code, so the contract is never a separate document that drifts.

Part IV

JSON

Foundation 11

The format

JSON is how all three services talk to each other despite two of them being TypeScript and one being Python. It is text — which is precisely why every language can read it.

Six types, and that is the entire specification
{
  "employeeId": 42,                    ← number  (no quotes)
  "name": "Alice Chen",                ← string  (double quotes ONLY)
  "isActive": true,                    ← boolean (lowercase)
  "managerId": null,                   ← null
  "skills": ["Python", "SQL"],         ← array
  "risk": { "score": 0.73,             ← object  (nested freely)
            "level": "high" }
}

THE RULES THAT TRIP PEOPLE
  ⚠ DOUBLE QUOTES ONLY — on values AND on keys. 'single' is
    invalid JSON, even though it is valid JavaScript.
  ⚠ NO TRAILING COMMA after the last item. Valid in JS, invalid
    in JSON, and the error message is unhelpful.
  ⚠ NO COMMENTS. There is no way to write one.
  ⚠ NO DATE TYPE. A date is a string, by convention ISO 8601:
    "2026-03-01T09:00:00Z" — and the Z matters. A timestamp with
    no timezone is the single most common data bug in reporting.
  ⚠ NO undefined. Only null.

JSON vs A JAVASCRIPT OBJECT — they are not the same thing
  a JS object is a live thing in memory with methods and
  references. JSON is a string. Converting loses everything that
  is not one of the six types above:

    JSON.stringify({ when: new Date(), fn: () => {} })
    ⇒ the Date becomes a string; the function VANISHES silently.

  ⭐ so a value that is a Date on the server is a STRING by the
    time the browser has it, even if TypeScript says otherwise.
    See reflex 16: types are erased, and the network does not
    read your interfaces.
Foundation 12

Where it bites

Numbers lose precision

JSON numbers are doubles. A 19-digit database id survives the trip only as a string — as a number it silently rounds, and the record you fetch is not the one you asked for.

Key order is not guaranteed

Never rely on it, and never hash a serialised object to compare two payloads.

Empty vs missing vs null

"", absent, and null are three different states. Decide which one your API means, then be consistent — the frontend has to branch on it.

Snake case meets camel case

Python writes risk_score; TypeScript expects riskScore. Convert at exactly one boundary, deliberately, or you will convert in five places and miss one.

Foundation 13

The language, in one pass

What you need before reading any React or NestJS file
VARIABLES
  const  cannot be reassigned          ← use this by default
  let    can be reassigned             ← when it must change
  var    ⚠ legacy, function-scoped, avoid
  ⭐ const on an object still lets you change what is INSIDE it.
    It freezes the binding, not the contents.

FUNCTIONS — and the one difference that matters
  function classic(a) { return a * 2; }
  const arrow = (a) => a * 2;          ← implicit return
  ⭐ ARROW FUNCTIONS INHERIT `this`. That is why every React
    handler and every class method callback is an arrow — a
    classic function loses `this` and you get "cannot read
    property of undefined" at runtime.

DESTRUCTURING — everywhere in modern code
  const { name, department } = employee;
  const [first, ...rest] = list;
  function f({ id, name }) { … }       ← props, in one line

SPREAD — copy and merge
  const updated = { ...employee, salary: 65000 };
  ⭐ THE MOST IMPORTANT PATTERN IN REACT: build a NEW object
    rather than mutating the old one, because React decides
    whether to re-render by comparing references.
  ⚠ IT IS SHALLOW. Nested objects are still shared with the
    original, so mutating one mutates both.

THE ARRAY METHODS YOU WILL READ CONSTANTLY
  .map()     transform each → new array of the same length
  .filter()  keep some      → new, shorter array
  .find()    first match    → one item, or undefined
  .reduce()  collapse to one value (a sum, a lookup object)
  .some() / .every()   → boolean
  ⭐ all of these RETURN A NEW ARRAY and leave the original
    alone. That is exactly why they suit React.

TRUTHINESS — the source of real bugs
  falsy: false · 0 · "" · null · undefined · NaN
  ⚠ if (count) is FALSE when count is 0. So a genuine zero is
    treated as "missing" — the same 0-versus-null confusion as
    in the database, now in the UI.
  ⭐ ?? vs || : `a ?? b` falls back only on null/undefined;
    `a || b` falls back on any falsy value, including 0 and "".
    Use ?? for numbers, always.
  ⭐ ?. safely reads through a possibly-absent object:
    employee?.team?.name
Foundation 14

Async, properly

Anything that touches a network or a disk is asynchronous. Getting this wrong is the most common source of "it works sometimes".

WHY IT EXISTS JavaScript runs on ONE thread. If a database call blocked it, nothing else could happen — no other request, no click, no render. So slow work is handed off and the thread carries on. THE THREE GENERATIONS callbacks → nesting that becomes unreadable promises → .then().catch() chains async/await → ⭐ what all modern code uses THE SHAPE async function load(id) { const employee = await prisma.employee.findUnique({ … }); return employee; } · `await` pauses THIS function until the promise settles. It does not block the thread. · an `async` function ALWAYS returns a promise — so its caller must await it too, all the way up. ⭐ THE FOUR MISTAKES, IN ORDER OF HOW OFTEN THEY HAPPEN ① FORGETTING await const e = getEmployee(); // a Promise, not a value console.log(e.name); // undefined ⇒ if a value is mysteriously undefined or "[object Promise]", this is the first thing to check. ② SEQUENTIAL WHEN IT COULD BE PARALLEL const a = await getTeams(); // 200ms const b = await getEmployees(); // 200ms → 400ms total vs const [a, b] = await Promise.all([getTeams(), getEmployees()]); // → 200ms total ⭐ these do NOT depend on each other, so waiting for the first before starting the second is pure waste. This is the single easiest performance win in most codebases. ③ await INSIDE A LOOP for (const id of ids) { await fetchOne(id); } 200 ids × 50ms = 10 seconds, one at a time. This is the N+1 problem in its most literal form. Fetch them together, or in bounded batches. ④ AN UNHANDLED REJECTION a promise that rejects with nobody awaiting it does not stop your code — it becomes a warning in a log nobody reads, and the operation silently did not happen. ⇒ every await belongs inside a try/catch, or under a framework that catches for you (NestJS does).

What TypeScript adds

The annotations you will meet on day one
PRIMITIVES        string · number · boolean · null · undefined

                    id: number;

                  }

⭐ THE ONE-SENTENCE VALUE: TypeScript turns a class of bug you
  would have found in production into a red squiggle you find
  while typing. That is all it does, and it is enormous.
Part VI

TypeScript, deeper

The follow-on that makes NestJS and Next.js code readable rather than mysterious. Six ideas, and the last one is a skill nobody teaches.

Foundation 16

How TypeScript thinks

Two facts that explain almost every surprise
①  TYPES ARE ERASED. They exist at compile time and are GONE at
   runtime. Nothing is checked when the program runs.

   ⚠ SO THIS COMPILES AND IS STILL WRONG:
       const res = await axios.get<Employee>('/api/employees/42');
       res.data.hiredAt.getFullYear();   // 💥 at runtime

     you TOLD TypeScript the response is an Employee. Nobody
     verified it. The API sent a JSON string for the date, and a
     string has no getFullYear.

   ⭐ THE RULE THAT FOLLOWS: at every boundary where data enters
     your program — an HTTP response, a request body, a queue
     message, a parsed file — a type annotation is a HOPE.
     Validate the shape at runtime (class-validator in NestJS,
     Pydantic in FastAPI, Zod in the frontend) and let the type
     describe what the validator guarantees.

②  TYPING IS STRUCTURAL, NOT BY NAME. If the shape fits, it fits.

     interface Point { x: number; y: number }
     const p = { x: 1, y: 2, label: 'a' };
     const q: Point = p;        // ✅ fine — extra keys allowed
                                //    when assigning a variable
     ⚠ but an OBJECT LITERAL assigned directly is checked for
       excess properties, so the same shape written inline
       errors. That inconsistency is a real rule, and it is why
       "object literal may only specify known properties"
       appears when a spread of the same object would not.

   ⭐ AND INFERENCE IS USUALLY BETTER THAN YOU
     const names = employees.map(e => e.name);   // string[]
     let count = 0;                              // number
     ⇒ annotate FUNCTION SIGNATURES (the contract) and let
       inference handle the inside. Over-annotating adds noise
       and, worse, can hide a genuine mismatch.
Foundation 17

Unions and narrowing

A UNION IS "ONE OF THESE" type Result = | { status: 'ok'; data: Employee } | { status: 'error'; message: string } ⭐ THIS IS A DISCRIMINATED UNION and it is the most useful pattern in applied TypeScript. The shared literal field (`status`) tells the compiler which branch you are in. NARROWING — proving to the compiler which one it is if (result.status === 'ok') { result.data // ✅ known to exist here } else { result.message // ✅ known here, and .data is an error } ⭐ INSIDE THE BRANCH, THE TYPE IS NARROWER. You do not need a cast, and reaching for `as` here means you have skipped the check rather than done it. THE WAYS TO NARROW typeof v === 'string' primitives Array.isArray(v) arrays v instanceof Date classes 'salary' in v property presence v.kind === 'manager' a literal discriminant ← best v !== null && v !== undefined the null guard OPTIONAL VS undefined VS null — three different statements managerId?: number the key may be ABSENT managerId: number | undefined the key EXISTS, value may be undefined managerId: number | null explicitly "no manager" ⭐ pick one meaning per field and write it down. Mixing them across a codebase produces checks that pass in one place and fail in another for the same data. EXHAUSTIVENESS — the trick worth stealing when you handle every branch of a union in a switch, add a default that assigns the value to `never`. If someone later adds a fourth role, every switch that forgot it becomes a COMPILE ERROR rather than a silent fall-through. ⇒ this is "make it hard to do wrong", in the type system.
Foundation 18

any · unknown · never

TypeMeansWhen
any"Stop checking this."Almost never. It disables checking for everything it touches downstream — one any quietly removes safety from a whole call chain. It is not a type; it is an opt-out.
unknown"A value, and I do not know what."The right choice for anything arriving from outside. You cannot use it until you narrow it, which is exactly the behaviour you want at a boundary.
never"This cannot happen."The return type of a function that always throws, and the exhaustiveness trick above. If a variable is never and you did not intend it, your narrowing eliminated every case — usually a real logic error.
void"Returns nothing useful."Callbacks and handlers. Different from undefined: void is about intent, not value.
The habit that undoes TypeScript

as is not a check — it is you overruling the compiler. value as Employee performs no verification whatsoever; it only silences the error. Used at a data boundary, it converts a compile-time question into a runtime crash somewhere far away.

The two legitimate uses: narrowing a genuinely-known literal (as const), and the rare case where you know something the compiler structurally cannot. Everything else wants a type guard or a validator.

Foundation 19

Generics

A type you fill in later
WITHOUT — you lose the type
  function first(list: any[]): any { return list[0]; }
  const e = first(employees);      // any. Nothing is checked.

WITH — the type flows through
  function first<T>(list: T[]): T | undefined { return list[0]; }
  const e = first(employees);      // Employee | undefined ✅

⭐ READ <T> AS "WHATEVER TYPE THE CALLER USED". The function does
  not care what T is; it promises to give back the same thing it
  received.

CONSTRAINTS — "any type, as long as it has this"
  function byId<T extends { id: number }>(items: T[], id: number)
  ⇒ now T could be Employee, Team or Report — but not a number,
    and inside the function `item.id` is known to exist.

WHERE YOU MEET THEM IN THIS PROJECT
  Promise<Employee>            an async result
  Array<string> / string[]     the same thing, two spellings
  Repository<Employee>         a typed data accessor
  Partial<CreateEmployeeDto>   an update DTO — see 20
  useState<Employee | null>    React state that starts empty

⚠ WHEN NOT TO: if a generic parameter appears exactly once in a
  signature, it is doing nothing. Generics earn their complexity
  by LINKING two positions — an input to an output.
Foundation 20

Utility types and type operators

WrittenGives you
keyof EmployeeA union of its key names — 'id' | 'name' | …. Lets a function accept "any field of this thing" safely, so a sort helper cannot be passed a column that does not exist.
typeof configThe type of an existing value. Useful for deriving a type from a constant instead of writing it twice and letting the two drift.
Employee['name']The type of one property. Reuse it rather than re-declaring string in ten places.
Partial<T>All fields optional. Exactly what an update DTO is — which is why NestJS ships PartialType().
Required<T> · Readonly<T>The inverses: everything mandatory, everything frozen.
Pick<T, K> · Omit<T, K>A subset, or everything except. Omit<Employee, 'salary'> is a public-facing employee — the type system expressing a permission boundary.
Record<K, V>A dictionary — Record<Role, string[]> maps every role to a permission list, and the compiler notices when a new role is unhandled.
ReturnType<typeof f>Whatever that function returns. Handy when a service method's shape is the truth and you do not want to duplicate it.
The principle underneath all of them

Derive types, do not duplicate them. Every type written twice is a promise to update both, and that promise is always broken eventually. Partial, Omit, keyof and ReturnType all exist so that one definition stays the single source of truth — the same principle as one source of truth in data, applied to types.

Foundation 21 · the skill nobody teaches

Reading a TypeScript error

Long errors are not hard errors
THE METHOD
  1  READ THE FIRST LINE AND THE LAST LINE. The middle is the
     compiler showing its work as it walks nested types.
  2  FIND THE PHRASE "Type 'X' is not assignable to type 'Y'".
     ⭐ X IS WHAT YOU HAVE. Y IS WHAT IS WANTED. Almost every
       error reduces to that one sentence.
  3  LOOK FOR THE SMALLEST DIFFERENCE. Usually one field, one
     `undefined`, or one string where a literal union was wanted.

THE FIVE YOU WILL ACTUALLY SEE

  "Object is possibly 'undefined'"
    ⇒ you have not handled the absent case. This is the compiler
      finding a real crash before your users do — do not silence
      it with `!`, handle it.

  "Property 'x' does not exist on type 'y'"
    ⇒ a typo, or the type is narrower than you think. Hover it.

  "Type 'string' is not assignable to type '"admin" | "manager"'"
    ⇒ a literal union wants an exact value. `as const` on the
      source, or narrow it properly.

  "Argument of type 'X' is not assignable to parameter of type 'Y'.
   Types of property 'z' are incompatible."
    ⇒ ⭐ the last clause is the answer. Skip to it: property `z`
      is the mismatch, and everything above is the path to it.

  "Type 'undefined' is not assignable to type 'string'"
    ⇒ an optional field meeting a required one. Either the field
      should be optional downstream too, or you need a default.

⚠ THE ANTI-PATTERNS — both make the message go away and the bug
  stay: casting with `as`, and asserting non-null with `!`.
  ⭐ THE ERROR IS USUALLY RIGHT. When the compiler and your
    instinct disagree, the compiler has read more of the codebase
    than you have.

Classes, just enough

You will read more classes than you write
class RiskModel:
    def __init__(self, path: str):        ← the constructor
        self.model = joblib.load(path)    ← self is EXPLICIT

    def score(self, features: list[float]) -> float:
        return float(self.model.predict_proba([features])[0][1])

⭐ `self` IS THE ONE THING TO REMEMBER. Python passes the
  instance in as the first parameter, explicitly, on every
  method. Forgetting it in a definition is the most common
  beginner error, and the message is confusing.

WHERE THIS APPEARS IN FASTAPI CODE
  · Pydantic models — a class per request and response shape,
    which is how FastAPI validates and documents automatically
  · a model wrapper loaded once at startup rather than per
    request, because loading is slow and the object is reusable
  · scikit-learn estimators — every one of them is a class with
    .fit() and .predict()

  @app.post("/predict")
  def predict(body: PredictRequest) -> PredictResponse: …

  a decorator wraps the function in another function. Here it
  registers the route. In NestJS you will see the same idea with

  the two languages, which is why FastAPI feels familiar after

Foundation 24

Virtual environments

THE PROBLEM project A needs pandas 1.5. Project B needs pandas 2.2. Python installs packages globally by default, so the second install breaks the first project. Silently. THE FIX — one isolated package folder per project python -m venv venv create it source venv/bin/activate use it (prompt changes) pip install -r requirements.txt deactivate leave it ⭐ ACTIVATION IS PER TERMINAL. A new tab is not activated, and "ModuleNotFoundError" for something you definitely installed is almost always this — you are in a different shell. ⚠ venv/ IS NEVER COMMITTED. requirements.txt is. The folder can be hundreds of megabytes and is machine-specific. THE NODE EQUIVALENT, AND THE DIFFERENCE node_modules/ is already per-project, so npm needs no activation step. Same isolation, achieved by default rather than by ceremony — which is why this trips up people coming from JavaScript.

Volume I · the words that will be used without explanation later
runtime
The program that executes your code — Node.js, CPython, or the browser.
transpile
Convert source to other source (TypeScript → JavaScript), as opposed to compiling to machine code.
port
A number identifying which program on a machine should receive a connection.
env var
Configuration supplied from outside the code, so secrets and per-machine values stay out of the repository.
schema
The declared shape of data — of a database table, or of a request body.
primary key
The column that uniquely identifies a row. Meaningless by design.
foreign key
A column pointing at another table's primary key, enforced by the database.
join
Combining rows from two tables on a matching column.
fan-out
A join to a many-side that multiplies rows, inflating any sum computed afterwards.
index
A structure that makes lookups fast at the cost of slightly slower writes.
idempotent
Safe to repeat: doing it twice has the same effect as doing it once.
stateless
The server keeps nothing between requests, so each one must carry its own identity.

"I don't know who you are" versus "I know, and you may not".
promise
A value that will exist later. await waits for it without blocking the thread.
destructuring
Pulling fields out of an object or array into named variables in one expression.
spread
{ ...obj } — a shallow copy, used to create new objects instead of mutating.
truthy / falsy
Which values count as true in a condition. 0 and "" are false, which causes real bugs.

Proving to the compiler which member of a union a value currently is.
structural typing
Compatibility decided by shape rather than by declared name.
comprehension
Python's [f(x) for x in xs] — the equivalent of .map().
venv
A per-project Python package folder that must be activated in each terminal.
