Topic 04

TypeScript beyond the deep dive

The layer this adds

The onboarding handbook covers narrowing, generics and utility types. What sits underneath is using the type system to make wrong states unrepresentable — moving errors from runtime to compile time by construction rather than by discipline.

The mechanism
  • Branded types. UserId and OrgId both being string means the compiler cannot catch a swapped argument. A brand — an intersection with a phantom property — makes them distinct without any runtime cost.
  • Discriminated unions for state. A loading state modelled as { loading: boolean; data?: T; error?: E } permits four impossible combinations. Modelled as a union on a status field, the impossible ones cannot be written.
  • Exhaustiveness via never. Assign the value to never in the default branch, and adding a fifth role turns every switch that forgot it into a compile error. That is "make the mistake impossible" implemented in the type system.
  • satisfies rather than a type annotation when you want the literal types preserved and checked against a shape.
  • Derive, never duplicate. Omit<Employee,'salary'> as the public response type; ReturnType<typeof f> where the function is the truth.
Where it goes wrong
  • as and ! used as fixes. Both silence the compiler and keep the defect — and at a data boundary they convert a compile-time question into a runtime crash somewhere distant.
  • Trusting an annotation on anything that arrived over a network. Types are erased; validate with a schema and let the type describe what the validator guarantees.
  • Over-annotating internals, which adds noise and can hide a genuine mismatch. Annotate signatures; let inference handle the inside.
  • Reaching for conditional and mapped types where a plain union would do — clever types are read far more often than written.
The question you must be able to answer

"How would you make it impossible to pass a user id where an org id is expected?" — and the strong answer connects it to the general principle: prefer a mechanism that holds for every caller over a convention that holds for the ones who remembered.

Node runtime internals

But any SYNCHRONOUS work blocks everything: every other request, every timer, every socket. ⇒ SO CPU-BOUND WORK IS THE ONE THING YOU MUST MOVE OFF THE LOOP. JSON.parse of a 50 MB payload, a synchronous crypto call, a tight loop over a million rows. ② PROMISES RESOLVE BEFORE TIMERS. Microtasks drain completely between phases, so an await-heavy chain runs ahead of a `setTimeout(…, 0)`. This is why ordering surprises happen and why `setImmediate` exists. ③ THE THREAD POOL IS SMALL AND SHARED. File I/O, DNS lookups and some crypto go to a pool of four by default. ⚠ SO A BURST OF FILE READS OR DNS CALLS CAN QUEUE BEHIND EACH OTHER while the CPU is idle — a latency mystery with no visible cause in your code. BACKPRESSURE AND STREAMS writing faster than the consumer can read buffers in memory. ⭐ A STREAM'S RETURN VALUE TELLS YOU TO STOP — ignoring it is how a PDF generator or a CSV export becomes an out-of-memory crash under load. ⇒ AND FOR THIS PROJECT'S EXPORT PATH THAT IS THE ACTUAL RISK: a twenty-year employee record streamed correctly is fine; the same record buffered is not. ⚠ WORKER THREADS vs CLUSTER — know the difference CLUSTER several processes, one per core, sharing a port. For throughput on a multi-core box. WORKER threads inside one process, for CPU-bound work THREADS without blocking the loop. ⇒ AND NEITHER IS A FIX FOR A SLOW QUERY.
Topic 06

NestJS advanced composition

The layer this adds

The onboarding handbook covers modules, controllers, services and the lifecycle order. The layer below is the injector itself — custom providers, scopes, dynamic modules — and it is what lets you build the reusable pieces rather than only consume them.

The mechanism
  • Provider forms. A class is only the common case. useValue for a constant or a test double, useFactory when construction needs configuration or async work, useExisting for an alias. Injection tokens — a string or symbol — are how you inject an interface, which TypeScript cannot do alone because interfaces do not exist at runtime.
  • Scopes. Default is singleton. REQUEST scope creates an instance per request — useful for a per-request context, and expensive: it makes every consumer request-scoped too, up the whole chain. TRANSIENT gives each consumer its own copy.
  • Dynamic modules. forRoot and forRootAsync are how a module takes configuration — the pattern behind every configurable Nest library, and the thing to build when you want one shared, configured concern.
  • Where each cross-cutting concern belongs: a guard for "may I proceed", an interceptor for wrapping and shaping, a pipe for transforming and validating arguments, a filter for turning a throw into a response. The lifecycle order is fixed, so the placement decision is answerable rather than a matter of taste.
  • OnModuleInit and OnApplicationShutdown — where you open a connection or load a model once, and where you drain it. Graceful shutdown is the one people skip, and it is why in-flight requests die during a deploy.
Where it goes wrong
  • Circular dependencies "fixed" with forwardRef rather than by noticing that two modules want to be one, or that a third concept is missing.
  • @Global() used to avoid thinking about imports, which hides the dependency graph.
  • Request scope applied casually, then a performance mystery as the whole chain becomes per-request.
  • Business logic in an interceptor, which makes it invisible to anyone reading the service.
The question you must be able to answer

"Nest can't resolve dependencies of X (?)" — what does that mean and how do you fix it? Two causes only: the provider was not exported, or this module did not import that module. And the ? marks which constructor position failed.

Topic 07

NestJS testing

The three levels, and what each is actually worth
①  UNIT — the service, with fakes in the constructor
   ⭐ THIS IS WHERE DEPENDENCY INJECTION PAYS FOR ITSELF: a
     service that asks for its dependencies can be tested with
     no framework, no database and no HTTP, in milliseconds.
   ⇒ worth it for genuine business rules — the risk
     calculation, eligibility, the ownership rule.

②  MODULE / INTEGRATION — `Test.createTestingModule`
   builds a real injector, so guards, pipes, interceptors and
   filters actually run.
   ⭐ THIS IS THE HIGHEST-VALUE LEVEL IN A NEST APPLICATION,
     because most defects live in the seams: a guard that did
     not fire, a pipe that did not validate, a filter that
     changed the status code.
   ⇒ `overrideProvider` to swap the AI client for a fake, while
     keeping a REAL test database.

③  E2E — the HTTP surface, via supertest
   the four assertions per endpoint that are worth more than
   anything else:
     · happy path returns the expected shape
     · no token → 401
     · ⭐ VALID TOKEN, SOMEONE ELSE'S RESOURCE → 403
     · invalid body → 400
   ⇒ THAT THIRD ONE IS THE TEST ALMOST NOBODY WRITES, and it is
     the vulnerability most likely to ship.

⚠ WHAT NOT TO DO
  · MOCK PRISMA. Then the test asserts you called Prisma the
    way you thought you should — a test of your assumptions,
    not of the query. Wrong joins and constraint violations are
    exactly what it cannot see.
  · assert on the response of a mocked service and call it an
    integration test
  · share database state between tests — ⭐ reset per test, or
    wrap each in a transaction that rolls back

⭐ AND THE FIXTURE DISCIPLINE THAT PREVENTS FLAKES: build test
  data with a factory function that takes overrides, so each
  test states only what it cares about. A shared seed file that
  every test depends on becomes untouchable within a month.
Topic 08 · zero prior coverage

Passport strategies and the token lifecycle

The layer this adds

The existing docs mention Passport in two sentences. What is underneath: a strategy is just a class with a validate method, and what it returns becomes request.user. Once that is clear, the whole library stops being magic.

The mechanism
  • The local strategy runs once, at login: it receives the credentials, verifies the password hash, and returns the user. Its validate return value is what gets signed into the token.
  • The JWT strategy runs on every request: the library verifies the signature and expiry before calling your validate, which receives the decoded payload. So your validate is the place to check the user still exists and is still active — which is the only defence against a valid token for a disabled account.
  • The guard is what invokes the strategy. AuthGuard('jwt') triggers it; a global guard plus a @Public() decorator is the pattern that makes "authenticated by default" the rule rather than the exception.
  • The refresh flow. A short-lived access token plus a long-lived refresh token that is stored and therefore revocable. Rotation on use — issue a new refresh token each time and invalidate the old one — gives you detection: if an old one is presented, it has been stolen.
Where it goes wrong
  • Believing logout invalidates a JWT. The server stores nothing; the token remains valid until it expires. Logout clears the client's copy and nothing more.
  • The role is baked in at login. Promote or demote someone and their existing token still says what it said — which is a real design consideration, not a curiosity.
  • A refresh token stored with the same exposure as the access token, which removes the point of separating them.
  • Putting anything private in the payload. It is base64, not encryption — readable by anyone holding the token.
  • No revocation path at all, so a compromised account cannot be shut out until expiry.
The question you must be able to answer

"A user is fired at 14:00 and their token expires at 14:12. What can they do in those twelve minutes?" — the honest answer is "everything their role allowed, unless we check status in validate or maintain a denylist", and naming that trade-off is the whole point of the question.
