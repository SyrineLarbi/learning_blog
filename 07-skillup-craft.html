Part I

Code review

Craft 01

What review is actually for

People think it's forIt's mostly for
Catching bugsCatching the bugs a machine can't — wrong business logic, a missing permission check, a behaviour change nobody noticed. Formatting and style belong to the linter.
Gatekeeping qualitySpreading knowledge. After review, two people understand the change. That is the single highest-value output, and it is why the bus factor of a reviewed codebase is different.
Enforcing preferencesMaintaining coherence — that the codebase still looks like one team wrote it, so the next person can predict where things go.
ApprovingAsking the question the author was too close to ask. "What happens if this list is empty?" is worth more than any number of approvals.
Why it matters more now

When a large share of code arrives generated, review stops being a quality ritual and becomes the primary control. It is the only place where a human decides whether plausible code is correct code.

Which means a team that reviews shallowly has, in effect, no control at all — and the faster the generation, the faster that gap compounds.

Craft 02 · print this

What to look for, in order

Ordered by what actually costs money when missed
①  DOES IT DO THE RIGHT THING?
   read the description, then the code, and ask whether they
   match. ⭐ THE MOST EXPENSIVE DEFECT IS A CORRECT SOLUTION TO
   THE WRONG PROBLEM, and it is invisible if you only assess
   code quality.

②  AUTHORISATION
   every id from outside — is it checked against the caller, on
   this path? does the response include a field this caller may
   not see?
   ⭐ HIGHEST SEVERITY ON THE LIST. A missing ownership check
     looks exactly like working code.

③  THE EDGE CASES
   zero · one · many · null · twice · order · race · lie ·
   halfway. ⇒ ask about the two most likely, by name.

④  WHAT ELSE DOES THIS CHANGE?
   ⭐ THE QUESTION SENIOR REVIEWERS ASK AND JUNIORS DO NOT.
     A changed default, a changed error case, a changed response
     shape, a removed field. ⚠ READ THE DIFF, NOT THE NEW FILE —
     the diff is where the silent behaviour change is visible.

⑤  FAILURE PATHS
   what happens if this throws halfway? is there a swallowed
   error? does a retry duplicate anything?

⑥  DATA AND MIGRATIONS
   is this migration reversible? does it lock a large table? is
   it deployed before the code that needs it?
   ⭐ MIGRATIONS DESERVE DISPROPORTIONATE REVIEW ATTENTION —
     they are the part with no undo.

⑦  COMPLEXITY
   is there an abstraction with one caller? config nobody will
   set? a clever line a tired person would misread?

⑧  NAMES AND CLARITY
   would someone with no context understand WHY? ⇒ suggesting a
   rename is the highest-value-per-second comment available.

⚠ WHAT NOT TO SPEND REVIEW ON: formatting, import order, quote
  style, tabs. If it can be automated, automate it — every
  comment spent there is attention taken from ① to ④.
Craft 03

Giving feedback people can act on

Same observation, three different outcomes
⚠ "this is wrong"
   ⇒ no information, and a defensive author. Nothing improves.

⚠ "why didn't you use a transaction here?"
   ⇒ rhetorical questions read as accusations even when they are
     not meant that way. Text has no tone.

✅ "If the AI call fails after the report row is written, we're
   left with a report that has no predictions. Wrap both in a
   transaction?"
   ⇒ THE FAILURE · THE CONSEQUENCE · A SUGGESTION. The author
     can agree, disagree with a reason, or explain why it is
     already handled.

⭐ LABEL THE SEVERITY — the single best habit in review.
  BLOCKING     must change before merge (correctness, security)
  SUGGESTION   I would do it differently; your call
  QUESTION     I do not understand this yet
  NIT          trivial, take it or leave it
  PRAISE       ⭐ genuinely useful — it teaches the pattern you
               want repeated, and a review with only criticism
               trains people to submit less

  ⇒ without labels, every comment reads as blocking, and a
    twelve-nit review feels like a rejection.

⭐ AND THE RULE THAT KEEPS REVIEWS FROM STALLING: IF IT IS NOT
  BLOCKING, DO NOT BLOCK ON IT. Approve with suggestions. A
  reviewer who blocks on preference becomes a bottleneck people
  route around — which loses you the review entirely.

⚠ THREE HABITS TO AVOID
  · rewriting the change in comments — if you have designed it
    differently, talk rather than type
  · reviewing the author instead of the code
  · the drive-by comment on line 400 of 600 with no verdict —
    say whether you read the rest
Craft 04

Reviewing generated pull requests

A new failure mode, specific to this era

A large, uniformly well-formatted, idiomatic diff that the author has not fully read. Every surface cue you normally use to sense that something is off — inconsistent naming, odd formatting, awkward structure — is absent. It looks like careful work.

So the reviewer becomes the first person to actually read it, while the diff size implies it was already understood. That mismatch is where defects enter.

What to do about it
⭐ ASK THE AUTHOR TO STATE WHAT IT DOES, IN THEIR OWN WORDS.
  not as a challenge — as part of the description. If they
  cannot, the change is not ready, and this single expectation
  changes team behaviour more than any policy.

REQUIRE GENERATED CHANGES IN THEIR OWN COMMITS
  ⇒ then the diff is reviewable in isolation and revert is one
    command. Mixed with hand edits, it is archaeology.

SIZE IS NOW A REVIEW CONCERN, NOT A COURTESY
  a 600-line generated diff gets reviewed at roughly the same
  quality as a 600-line handwritten one — which is to say
  poorly. ⭐ THE FIX IS UPSTREAM: ask for smaller units. A
  reviewer cannot recover attention that the diff size already
  spent.

WHAT TO SEARCH THE DIFF FOR, MECHANICALLY
  □ every `catch` block — is anything swallowed?
  □ every loop containing an `await` — N+1?
  □ every raw query — is anything interpolated?
  □ every new dependency — was it discussed, and does it exist?
  □ every changed default or error case
  □ any identifier you do not recognise — is it real?

⚠ AND THE ONE THAT CATCHES PEOPLE: TESTS THAT ASSERT CURRENT
  BEHAVIOUR. Generated tests are written by reading the code, so
  they encode what the code does — bugs included — rather than
  what it should do. ⭐ A PASSING GENERATED TEST SUITE IS NOT
  EVIDENCE OF CORRECTNESS. Check at least one assertion against
  the requirement.
Craft 05

Review culture

Small PRs, reviewed fast

The two are linked: small changes get reviewed within the hour, which makes people submit small changes. Large ones wait a day, which makes people batch more.

Anyone reviews anyone

Including a junior reviewing a senior. The knowledge flows both ways, and "I don't understand this" is a legitimate and valuable review comment.

Automate the arguments

Formatter, linter, type check, tests in CI. Every preference you automate is a debate you never have again.

Disagreement has an escape hatch

Two rounds and no agreement: talk, then decide, then record it as an ADR if it is architectural. Comment threads are a terrible medium for design disputes.

Part II

Debugging

The most honest skill there is. You cannot memorise your way through a bug, and the method is visible in every sentence you say about it.

Craft 06

The mindset

GuessingHypothesis testing
"Maybe it's the cache." Clears the cache."If it were the cache, a fresh key would work. Let me check one."
Changes three things, it works, shipsChanges one, confirms it explains every symptom, then fixes
Cannot say why it works nowCan trace the mechanism from cause to symptom
The bug returns in a monthThe bug cannot return, and a test says so
The loop
1  REPRODUCE IT
   ⭐ IF YOU CANNOT REPRODUCE IT, YOU ARE SPECULATING, NOT
     DEBUGGING. Getting a reliable reproduction is usually 80% of
     the work — and the moment you have one, the cause is often
     already obvious.

2  STATE WHAT YOU EXPECTED AND WHAT HAPPENED, PRECISELY
   "it's broken" is not an observation. "It returns [] for user
   5309 and 12 rows for 5308" is — and that difference is
   usually the entire investigation.

3  ONE HYPOTHESIS THAT EXPLAINS EVERYTHING
   ⭐ INCLUDING THE STRANGE DETAIL. A theory that explains the
     error but not why it only happens after 6 p.m. is not the
     answer yet — and the strange detail is the most
     informative thing you have.

4  A PREDICTION THAT COULD BE WRONG
   "if this is it, X will be true." Then check X. ⚠ a hypothesis
   you cannot disprove is a belief.

5  CHANGE ONE THING
   change three and the result teaches you nothing.

6  CONFIRM THE MECHANISM BEFORE FIXING
   ⭐ "IT WORKS NOW" IS NOT A DIAGNOSIS. Without cause-to-symptom
     you may have moved the bug rather than removed it — and it
     returns under load, which is when it costs most.

7  ASK WHY IT WAS POSSIBLE
   the fix repairs this instance; the question repairs the class.
   Missing check, loose type, unenforced invariant? ⇒ this is
   where a bug becomes a constraint, a type or a test and stops
   having siblings.
Craft 07

Reproduce and isolate

BISECT IN SPACE — where in the path? browser → network → server → service → database ⭐ THE FASTEST QUESTION IN DEBUGGING: is the data already wrong when it arrives, or does it become wrong here? One look at the payload halves the search, and people skip it constantly. wrong in the response, right in the database ⇒ it is serialisation, mapping, or the permission filter. Three places, not the whole system. BISECT IN TIME — when did it start? a deploy · a config change · a migration · a dependency update · a certificate · a scheduled job · someone else's release · a date boundary ⚠ AND THE ONE PEOPLE FORGET: nothing changed in the code, but the DATA crossed a threshold. The first customer with 10,000 rows. The first name with an apostrophe. The first month-end on a Sunday. BISECT IN SCOPE — who and what is affected? ALL → deploy, config, dependency, infrastructure SOME → data-dependent. ⭐ THE SHARED PROPERTY OF THE FAILING SET *IS* THE BUG. ONE → that record's data, that user's permissions, that timezone INTERMITTENT → ⭐ almost always one of five: a race, a retry, a cache, a clock, or one bad instance in a pool. Find which node served it. ⭐ "WHAT DO THE AFFECTED CASES HAVE IN COMMON?" is the highest-yield question in the discipline, and it is usually answerable before you read any code.
Craft 08

Reading a stack trace

A skill, not a chore
THE METHOD
  1  READ THE ERROR TYPE AND MESSAGE FIRST. Half the time it
     literally says the answer.
  2  ⭐ FIND THE TOPMOST FRAME IN *YOUR* CODE. Twenty frames of
     framework internals are the path, not the cause. Your file
     is where you can act.
  3  READ THE "CAUSED BY" CHAIN TO THE BOTTOM. ⭐ THE ROOT CAUSE
     IS USUALLY THE LAST ONE, not the first — the top of the
     output is the outermost wrapper.
  4  CHECK THE LINE, then check what was passed to it.

⚠ THE TRACES THAT MISLEAD
  · ASYNC BOUNDARIES cut the stack. In Node the trace may start
    inside the event loop with no path back to your handler.
    ⇒ this is exactly what a correlation id and structured
      logging are for.
  · "Cannot read property of undefined" points at the SYMPTOM.
    The bug is wherever that value should have been set — often
    far away. ⭐ ASK "WHY WAS IT UNDEFINED?", not "how do I
    guard this line?"
  · A SWALLOWED-THEN-RETHROWN error shows the rethrow site, not
    the origin. Which is one more reason not to catch and
    rethrow at every level.
  · MINIFIED FRONTEND TRACES are unreadable without source maps
    — upload them, or production errors are unactionable.
Craft 09

Logging that helps at 3 a.m.

Written for the incident you have not had yet
⭐ LOG STRUCTURED, NOT PROSE.
  ⚠ "Processing report for team 5"  → ungreppable at volume
  ✅ { event: 'report.started', teamId: 5, userId: 42,
       requestId: '9f2c…' }
  ⇒ now you can filter by field, count by event, and correlate
    across all three services.

THE LEVELS, USED HONESTLY
  ERROR  something failed and someone must act
  WARN   something unexpected, handled — a retry, a fallback
  INFO   ⭐ significant business events: a report generated, a
         login, a job finished. This is your audit trail.
  DEBUG  detail, off in production

⚠ THE ANTI-PATTERN THAT HIDES REAL FAILURES: catching an
  exception and logging it at info. It is an error. Logging it
  quietly is how a bug survives six months and is discovered by
  a customer.

WHAT TO INCLUDE, EVERY TIME
  the correlation id · who · which entity · the outcome · the
  duration for anything slow
  ⚠ AND WHAT NEVER: passwords, tokens, full request bodies with
    personal data, salaries. ⭐ LOGS ARE A DATA STORE WITH
    WEAKER ACCESS CONTROL THAN YOUR DATABASE — usually readable
    by more people, retained longer, and shipped to a third
    party. Treat a log line as data leaving the system.

⭐ THE TEST FOR YOUR LOGGING: COULD YOU RECONSTRUCT WHAT
  HAPPENED TO ONE USER'S REQUEST FROM THE LOGS ALONE, WITHOUT
  ADDING ANYTHING? If not, add it now — not during the
  incident, when you cannot.
Craft 10

Bug categories

SymptomUsual suspects, in order
Works locally, fails deployedConfig or env var · a data difference (volume, encoding, real names) · timezone or locale · a permission that only exists in production · version drift · a race that needs concurrency to appear.
IntermittentA race · a retry · a cache serving one stale copy · clock skew · one unhealthy instance. Find which instance served the failure — that single fact often ends it.
Slow, then suddenly much slowerA threshold crossed: a query outgrew its index, the pool saturated, memory started swapping, a queue's arrival rate passed its service rate. Nonlinear response means a limit, not load.
Wrong number, no errorThe most dangerous class. A join fanning out · a filter applied after aggregation · a timezone shifting rows across a day boundary · nulls dropped by an aggregate · a unit or currency mismatch.
Memory grows until it diesSomething accumulates: an unbounded cache, listeners added per request, an ever-growing array, a query loading everything to count it.
Fails for some usersFind the shared property — a locale, an apostrophe, an unusually large record, a missing optional relation, a role. The property is the bug.
An AI feature got worseThe prompt changed · the model version changed · retrieved context changed or grew · input distribution changed · a truncation is silently cutting the prompt. Unanswerable without logged prompt versions and token counts.
Craft 11

Incidents and post-mortems

Mitigate first, diagnose second
⭐ THE RULE THAT DEFINES INCIDENT RESPONSE: the instinct — "let
  me just find out why" — is wrong while users are affected.
  ROLL BACK · DISABLE THE FLAG · FAIL OVER · SHED LOAD. Then
  investigate calmly. A rollback you can explain later beats a
  root cause found while the site is down.

THE FIRST FOUR QUESTIONS
  1  WHAT IS THE IMPACT? who, how many, how badly. This decides
     everything else, including whether it is an incident.
  2  WHEN DID IT START? then: what happened at that time.
  3  WHAT CHANGED? deploys, config, migrations, dependencies.
  4  CAN WE UNDO IT? if a change caused it, reversing that
     change is the fastest mitigation available.

WHILE IT IS HAPPENING
  · ONE person coordinates and communicates; everyone else
    investigates. Without this, four people chase one hypothesis
    and nobody talks to the business.
  · WRITE A TIMELINE AS YOU GO. You will not remember it, and
    the review is only as good as the timeline.
  · ⚠ DON'T DESTROY THE EVIDENCE. Before restarting, capture
    logs, metrics and state. A restart that "fixes" it also
    removes your only chance to learn why.
  · say what you know AND what you do not. "Still investigating,
    next update in fifteen minutes" beats a confident wrong
    update.

THE POST-MORTEM
  ⭐ THE QUESTION IS "WHAT MADE THIS POSSIBLE?", NOT "WHO DID
    IT". A culture where the answer is a person produces hidden
    incidents — and hidden incidents are how small failures
    become large ones.
  three outputs or it did not happen:
    · what stops the CLASS of failure
    · what DETECTS it sooner
    · what makes it SMALLER next time
  ⚠ "we'll be more careful" is not an action item. It is a wish.
Part III

Performance

Craft 12

Measure first — and it is not optional

The golden rule, and why it keeps being broken

Intuition about performance is unreliable — including yours, including mine. The bottleneck is almost never where it feels like it is, because the things that feel expensive (a loop, a big function) are usually cheap, and the things that feel free (a round trip, a serialisation) are usually not.

So optimising without measuring produces a week of work, a 2 % gain, and code that is now harder to read. Get one real profile before touching anything.

What to measure, and which number to look at
⭐ LOOK AT PERCENTILES, NOT AVERAGES.
  "average 200 ms" with a p99 of 8 seconds means one user in a
  hundred has a terrible experience, and the average will never
  tell you. ⇒ p50 for the typical case, p95/p99 for the pain.

WHERE THE TIME GOES — four places, in order of likelihood
  ① TOO MANY ROUND TRIPS — ⭐ the N+1, and it is the answer far
    more often than anything exotic
  ② ONE BAD QUERY — missing index, or a scan
  ③ WORK DONE PER ROW THAT SHOULD BE DONE ONCE
  ④ WAITING ON ANOTHER SERVICE

THE FIRST QUESTION, THOUGH: IS THE WORK NECESSARY AT ALL?
  ⭐ THE FASTEST QUERY IS THE ONE YOU DO NOT RUN. Can it be
    cached, precomputed, paginated, or simply not returned?
    Removing work beats optimising it, always.

AND THE ONE THAT DECIDES WHETHER YOU ARE DONE
  DEFINE THE TARGET BEFORE YOU START. "Under 500 ms at p95."
  ⚠ without a target, optimisation has no stopping condition and
    you will keep going until the code is unreadable.

⚠ THE TRAP: MEASURING WITH DEV DATA. Four rows hide every N+1,
  every missing index and every unbounded list. Measure against
  realistic volume or you have measured nothing.

SymptomCauseFix
Slow first loadBundle size — usually one heavy dependency, a chart or date libraryLook at what is actually in the bundle before guessing. Code-split, load on demand, or drop the dependency.
Blank then jumpNo skeleton; layout shifts when data landsA skeleton shaped like the content. Reserve space for images and tables.

Craft 14

Backend and API performance

The five that account for almost everything
①  N+1 QUERIES — ⭐ the champion
   a loop containing an await that hits the database. 200 items
   → 201 queries. Invisible in dev with four rows.
   ⇒ include/join in one query, or one query filtered by
     `id: { in: [...] }` and grouped in memory.

②  MISSING INDEX
   a filter or join on an unindexed column. Fine at 1,000 rows,
   catastrophic at 1,000,000 — ⭐ and the transition is sudden,
   which is why "it was fine last month" is not evidence.

③  SEQUENTIAL AWAITS THAT COULD BE PARALLEL
   two independent calls, one after the other, is double the
   latency for no reason. Promise.all them.

④  SELECTING EVERYTHING
   fetching every column and every relation to display three
   fields. ⭐ `select` RATHER THAN `include` IS BOTH FASTER AND
   THE MECHANISM THAT KEEPS A SALARY OUT OF A PAYLOAD.

⑤  UNBOUNDED WORK IN A REQUEST
   a report, an import, a model call over many records. Move it
   to a job — the request cycle is the wrong place for anything
   whose size you do not control.

CACHING — worth it, with the cost stated
  ⭐ ASK FIRST: HOW WRONG MAY THIS BE, AND FOR HOW LONG? If the
    answer is "not at all", a cache is the wrong tool.
  ⚠ AND A CACHE IN FRONT OF AN N+1 HIDES THE BUG UNTIL THE CACHE
    MISSES — then you have two problems and one of them is
    invisible.

⭐ THE ORDER THAT WORKS: fix the query · add the index · remove
  the round trips · then cache. Caching first buys speed and
  keeps the defect.
Craft 15

Memory

Leaks, and the four things that cause them
A LEAK IS SOMETHING THAT ACCUMULATES AND IS NEVER RELEASED.
The signature: memory climbs steadily, restarts fix it, and the
crash comes hours or days later.

THE FOUR CAUSES
  ① AN UNBOUNDED CACHE. A Map used as a cache with no eviction
    and no size limit is a memory leak with a helpful name.
  ② LISTENERS OR SUBSCRIPTIONS ADDED AND NEVER REMOVED.
    ⭐ THIS IS WHY useEffect CLEANUP IS NOT OPTIONAL — navigate
      twenty times, leave twenty live sockets.
  ③ A CLOSURE HOLDING A LARGE OBJECT. A callback that captures
    a whole request context keeps it alive as long as the
    callback lives.
  ④ LOADING EVERYTHING INTO MEMORY. Reading a million rows to
    count them, or building an array of every record to sum it.
    ⇒ aggregate in the database, or stream.

⭐ THE RULE FOR ANY LONG-RUNNING PROCESS: EVERY COLLECTION NEEDS
  A BOUND, AND EVERY SUBSCRIPTION NEEDS AN UNSUBSCRIBE. Both are
  cheap to add when writing and expensive to find later.

⚠ AND THE ONE PEOPLE MISS IN THIS STACK: a DataFrame is not the
  size of the file that produced it. A 2 GB CSV is routinely
  several times that in memory, so a service that loads one per
  request will fall over under two concurrent requests.
Craft 16

Load testing

What it answers

Where the breaking point is, and which resource breaks. Not "is it fast" — that is a profile. Load tests find the limit and the failure mode.

Ramp, don't spike

Increase gradually and watch for the knee — the point where latency stops rising linearly. That knee is the capacity number worth writing down.

Test realistic mixes

Hammering one cheap endpoint proves nothing. Real traffic is mostly reads with occasional expensive writes, and the interaction is the point.

Watch the dependencies

Under load you usually find the pool limit, the downstream rate limit, or the metered API bill — not CPU. And never load-test against a shared or production service without telling anyone.

Security

Craft 17

Thinking like an attacker

Four questions, asked while designing rather than after
①  WHAT IS WORTH TAKING HERE?
   in this application: salaries, performance reviews, health
   accommodations, disciplinary records, the whole employee
   table. ⭐ NAMING THE ASSET FIRST TELLS YOU HOW MUCH CARE THE
   FEATURE DESERVES.

②  WHAT DOES A VALID REQUEST FROM THE WRONG PERSON LOOK LIKE?
   ⭐ THE VULNERABILITY PEOPLE ACTUALLY SHIP. Not injection — a
     correctly formed request from a logged-in user carrying
     someone else's id, which the code happily serves because
     it authenticated the caller and never asked about the
     resource.

③  WHAT DOES THE UI NOT PROTECT?
   ⚠ THE UI IS NOT A SECURITY BOUNDARY. Hidden buttons, disabled
     fields and client-side role checks are usability. Anything
     the browser can do, a person can do without the browser.

④  WHAT ESCAPES THE SYSTEM?
   exports, downloads, emails, webhooks, logs, error messages,
   analytics, third parties — and text pasted into a model
   prompt.
   ⭐ THE MOMENT DATA LEAVES YOUR PERMISSION SYSTEM, YOUR
     PERMISSION SYSTEM STOPS PROTECTING IT. A file, a link, a
     log line and an email have no idea who may read them.

⭐ AND THE PRINCIPLE UNDER ALL OF IT: MAKE THE MISTAKE
  IMPOSSIBLE, NOT UNLIKELY. A permission check repeated in forty
  handlers will be missing from the forty-first. One path
  everything must traverse, or a database constraint, holds
  forever — including for the migration script and the person
  with a console at 2 a.m.

The risks that actually occur

RiskIn this stackThe real defence
Broken access controlAn endpoint takes an id and does not check ownershipThe most common and most damaging. Enforce in one path every caller traverses. Not in the UI, not by convention.
InjectionRaw SQL with an interpolated value; a shell command built from inputParameterise. Prisma does this by construction — the risk re-enters with $queryRaw and a template literal.
XSSRendering user text as HTML; dangerouslySetInnerHTMLReact escapes by default — so the vulnerability is always an explicit opt-out. Sanitise if you must render HTML at all.
Sensitive data exposureAn endpoint returning the whole record; a salary in a log line; a field the UI hides but the payload containsShape responses per requester. select, not include. Audit what you log.
Auth failuresLong-lived tokens, no revocation path, secrets in the frontend bundleShort expiry, a refresh path, and nothing secret behind NEXT_PUBLIC_.

Craft 19

Input and output

Validate on the way in, escape on the way out
ON THE WAY IN — ⭐ VALIDATE AT THE BOUNDARY, IN CODE
  · a schema per endpoint (DTO + ValidationPipe, or Pydantic)
  · ALLOW-LISTS, NOT DENY-LISTS. You cannot enumerate every bad
    input; you can enumerate the acceptable ones.
  · ⭐ STRIP UNKNOWN FIELDS. `whitelist: true` is a security
    control, not tidiness: without it a caller can post
    `role: 'admin'` and any code that spreads the body into a
    write has just granted it. That is mass assignment.
  · bound every string, array and number. An unbounded array is
    a denial-of-service parameter.
  ⚠ AND THE THREE-LAYER RULE: the browser validates for
    FEEDBACK, the API for CORRECTNESS, the database for
    INVARIANTS. Only the second protects anything — a request
    does not have to come from your form.

ON THE WAY OUT — escape for the destination
  the same string is dangerous differently in HTML, in SQL, in a
  shell, in a URL, in a CSV.
  ⭐ ESCAPE FOR WHERE IT IS GOING, NOT ON THE WAY IN. Escaping at
    input corrupts your stored data and still gets it wrong for
    the next destination.
  ⚠ the one people forget: a CSV export. A cell beginning with
    `=` is a formula when opened in a spreadsheet — a genuine
    remote-code path through an innocuous export feature.

FILE UPLOADS — a boundary with its own rules
  check the actual content type, not the extension · cap the
  size · store outside the web root or in object storage ·
  ⭐ NEVER TRUST THE FILENAME (path traversal) and never serve
  it back from a guessable URL.
Craft 20

Secrets

Rules that are boring and non-negotiable
□  NEVER IN THE REPOSITORY. ⭐ AND GIT HISTORY IS FOREVER — a
   secret committed and then removed in the next commit is
   still published. The only remedy is rotation.
□  NEVER IN THE FRONTEND BUNDLE. Anything with a NEXT_PUBLIC_
   prefix is embedded and readable by every visitor.
□  NEVER IN LOGS, error messages, or an exception payload.
□  NEVER IN A URL or query string — they land in server logs,
   browser history and proxy logs.
□  DIFFERENT SECRETS PER ENVIRONMENT. A shared secret means dev
   can read production.
□  A ROTATION PATH THAT EXISTS AND HAS BEEN TESTED. ⭐ "We
   cannot rotate the database password without downtime" is a
   finding, discovered at the worst moment.
□  LEAST PRIVILEGE. The AI service does not need write access
   to the employee table.

⭐ AND THE ASSUMPTION WORTH MAKING: ASSUME EVERY SECRET WILL
  LEAK EVENTUALLY. Design so that a leak is survivable —
  scoped credentials, short lifetimes, rotation you can perform
  on a Tuesday afternoon. That is a very different posture from
  hoping it does not happen.

⚠ AND ONE SPECIFIC TO THIS ERA: DO NOT PASTE A REAL .env, A
  CONNECTION STRING, A TOKEN OR LIVE EMPLOYEE DATA INTO AN AI
  TOOL. It has left your boundary. Redact first, every time.
Craft 21

Dependencies

You own what you install

Including everything it installs. A dependency is code running with your privileges, chosen by someone you have never met.

Scan and actually update

Automated scanning in CI, plus a habit of merging the updates. Most breaches use a known flaw with a patch available.

Commit the lock file

Reproducible installs are a security property, not just convenience — it is what stops a fresh install pulling a newly compromised version.

Check before adding

Maintained? Reasonable download count? Sensible dependency tree? And is the name spelled correctly — typosquatting is a real and cheap attack.

Craft 22

Security in generated code

The specific hazard

A model produces plausible security code. Plausible authentication looks exactly like correct authentication — same shape, same names, same confident structure — and the difference is invisible without reading it carefully.

Worse, it reproduces patterns from its training data, which includes an enormous amount of tutorial code where the auth check was omitted "for clarity".

What to check, specifically
□  IS THERE AN OWNERSHIP CHECK, or only authentication?
   ⭐ the single most likely omission.
□  IS ANYTHING INTERPOLATED into a query, a command, or a path?
□  DOES THE RESPONSE include fields this caller should not see?
□  IS AN ERROR EXPOSING internals — a stack trace, a SQL
   fragment, whether an email exists?
□  IS VALIDATION PRESENT and does it strip unknown fields?
□  DID IT ADD A DEPENDENCY, and does that package exist and is
   it the one you meant?
□  IS A SECRET HARDCODED, "as a placeholder"?
□  DID IT WEAKEN SOMETHING TO MAKE A TEST PASS —
   ⚠ `allow_origins=["*"]`, a disabled check, a widened type,
   a certificate verification turned off. ⭐ THIS IS THE ONE
   THAT SHIPS: it was a local workaround that nobody removed.

⭐ AND THE GOOD NEWS, WHICH IS REAL: A MODEL IS AN EXCELLENT
  SECURITY *REVIEWER*. "What would an attacker try against this
  endpoint?" and "what does this leak?" are genuinely strong
  prompts — it is fast at enumerating attack surface, and
  enumeration is exactly what humans are bad at.
  ⇒ write the sensitive code yourself; use the model to attack
    it.
Part V

Testing

Craft 23

Why it matters more now

The argument

Tests were always a safety net. When code arrives faster than anyone can fully read it, they become the mechanism by which you can accept change at all — the difference between "this looks fine" and "this does not break what worked".

And there is a second, less obvious payoff: a suite you trust is what makes refactoring possible. Without it, every improvement is a risk, so nobody improves anything, and the codebase ossifies — which is a slower and more expensive failure than any bug.

The pyramid, honestly

╱╲ E2E — few ╱ ╲ a handful of critical user journeys ╱────╲ slow, brittle, and the only thing that ╱ ╲ proves the system actually works ╱────────╲ INTEGRATION — some ╱ ╲ ⭐ THE BEST VALUE PER TEST in a typical ╱────────────╲ web application: a real request through ╱ ╲ guards, validation, service and a real ╱────────────────╲ test database ╱ UNIT — many ╲ ╱ fast, isolated, ╲ ╱ pure logic ╲ ╱──────────────────────────╲ WHY THE SHAPE cost and brittleness rise as you go up; confidence that the whole thing works rises too. Most real defects here are not in pure logic — they are in the seams: a missing permission check, a wrong join, a validation that did not fire. ⭐ A UNIT TEST OF A MOCKED SERVICE CANNOT SEE ANY OF THOSE. THE TEST THAT IS WORTH THE MOST, PER LINE one integration test per endpoint that asserts: the happy path works · an unauthenticated caller gets 401 · a wrong-owner caller gets 403 · invalid input gets 400. ⇒ four assertions that cover the four things most likely to break, and they keep working through refactors.
Craft 25

What to test, and what not to

Worth testingNot worth testing
Business rules — the risk calculation, eligibility, pricing. The things whose wrongness costs money.Framework behaviour. That NestJS routes a GET, that Prisma saves a row. Those are tested upstream.
Permission boundaries — wrong owner, wrong role, no token. Cheap to write, catastrophic to miss.Getters, mappers, trivial pass-throughs. Coverage without confidence.
Edge cases you found once — every bug becomes a test, so the class cannot return.Implementation details. A test asserting how a result was computed breaks on every refactor and blocks improvement.
Data transformations — anything with rounding, timezones, currency, or a join that could fan out.Exact UI markup. Test behaviour ("the error appears"), not structure.
The contract — response shape, status codes, error format. What callers depend on.Third-party libraries. Test your use of them, at the seam.
The rule that keeps a suite valuable

Test behaviour, not implementation. A good test survives a refactor and fails when the behaviour changes. A test that must be rewritten every time you tidy the code is a tax on improvement, and eventually the team stops tidying — which is exactly the outcome tests were supposed to prevent.

Craft 26

Mocking

Mock the boundary, not your own code
✅ WORTH MOCKING
  · third-party APIs — you cannot call a payment provider in CI
  · the LLM provider — non-deterministic, metered, and slow
  · time and randomness — ⭐ freeze the clock, or a test fails
    at midnight, on the 29th of February, or in another timezone
  · email, SMS, webhooks — anything with an outside side effect

⚠ NOT WORTH MOCKING — AND THIS IS THE COMMON MISTAKE
  · YOUR OWN DATABASE. Use a real test database. ⭐ MOCKING
    PRISMA MEANS YOUR TESTS ASSERT THAT YOU CALLED PRISMA THE
    WAY YOU THOUGHT YOU SHOULD — a test of your assumptions,
    not of the query. Wrong joins, constraint violations and
    fan-out are exactly what it cannot see.
  · your own services, in an integration test. The seams between
    them are where the defects live.

⭐ THE FAILURE MODE OF OVER-MOCKING: every test passes and the
  application is broken, because each unit was verified against
  a fake version of its neighbours. This is worse than no tests,
  because it produces confidence.

⭐ AND THE RULE FOR THE MOCKS YOU DO WRITE: A MOCK MUST BEHAVE
  LIKE THE REAL THING WHEN THE REAL THING MISBEHAVES. If the
  provider can time out, return a 429, or return malformed
  output, your mock should be able to do all three — otherwise
  you have only tested the happy path of your error handling.
Craft 27

Coverage, and what it does not mean

A useful signal and a terrible target
WHAT COVERAGE MEASURES: which lines executed during the test
run.
⭐ WHAT IT DOES NOT MEASURE: whether anything was ASSERTED.
  A test that calls a function and asserts nothing produces
  100% coverage of it. Coverage is a measure of execution, not
  of verification.

⚠ SO A COVERAGE TARGET IS A GOODHART PROBLEM: mandate 90% and
  you get tests written to touch lines — trivial getters,
  assertion-free calls — while the branch that actually matters
  stays untested.

⭐ THE USEFUL WAY TO READ IT: AS A MAP OF WHAT IS UNTESTED, NOT
  AS A SCORE. Open the report and look at which files are dark.
  If the risk engine is at 20% and the DTO mappers are at 100%,
  the number is fine and the situation is not.

WHERE COVERAGE GENUINELY MATTERS
  the code whose failure is expensive: money, permissions, the
  risk calculation, anything a decision is made from.
  ⇒ and there, aim at BRANCH coverage rather than line coverage
    — the untested branch is the one with the bug in it.
Craft 28

Testing AI features

You cannot assert equality on a non-deterministic output
⚠ WHAT DOES NOT WORK: expect(output).toBe("...").
  The same prompt can produce different text. A test asserting
  exact output fails randomly, gets marked flaky, and is
  eventually deleted.

WHAT TO ASSERT INSTEAD — in order of preference
  ① THE STRUCTURE. If the output is schema-constrained, assert
    it validates, that the enum is one of the allowed values,
    that required fields are present. ⭐ THIS IS DETERMINISTIC
    AND IT IS WHY STRUCTURED OUTPUT MATTERS FOR TESTABILITY.
  ② THE PROPERTIES. Length within bounds · no forbidden content
    · it cites only chunk ids that were actually in the context
    — that last one is a dozen lines and converts an invisible
    hallucination into a caught one.
  ③ THE BEHAVIOUR AROUND IT. Timeout handled · retry on 429 ·
    the page still renders when the provider is down. ⭐ MOST OF
    WHAT CAN BREAK IN AN AI FEATURE IS ORDINARY ENGINEERING,
    and all of it is deterministically testable.

AND SEPARATELY FROM TESTS: AN EVAL SET
  20–50 graded examples, run on every prompt or model change,
  producing a score.
  ⭐ TESTS ANSWER "IS IT BROKEN?" — EVALS ANSWER "DID IT GET
    BETTER?" You need both, and they are different artefacts.
  ⚠ WITHOUT AN EVAL SET, NOBODY WILL DARE TOUCH THE PROMPT —
    which is how a prompt with a superstition in it stays frozen
    in production for a year.

⭐ AND THE CIRCULARITY WARNING, ONE LAST TIME: do not verify
  generated code with generated tests alone. Both encode the
  same guess, agree with each other, and tell you nothing.

Term bank

Volume III · craft vocabulary
blocking comment
A review comment that must be resolved before merge, as opposed to a suggestion or nit.
silent behaviour change
A refactor that also alters a default, an error case or a response shape. Visible only in the diff.
bisect
Halving the search space — in the request path, in time, or in scope.
correlation id
One id logged by every service handling a request, so the whole path can be reconstructed.
structured logging
Logging fields rather than sentences, so logs are filterable at volume.
post-mortem
A blameless review asking what made the failure possible, with three concrete outputs.
p95 / p99
The latency the slowest 5% or 1% experience. Where the pain lives; averages hide it.
N+1
One query for a list plus one per item. The most common performance defect anywhere.
the knee
The load at which latency stops rising linearly. Your real capacity number.
memory leak
Something that accumulates and is never released. Memory climbs; restarts "fix" it.
mass assignment
Accepting unknown request fields and writing them. Prevented by stripping unknown keys.
allow-list
Enumerate what is acceptable rather than what is forbidden. You cannot enumerate all bad input.
path traversal
A supplied filename containing ../ to escape its directory.
CSV injection
A cell starting with = becoming a formula in a spreadsheet.
least privilege
Every credential has the narrowest access that works.
test double / mock
A stand-in for a real dependency. Mock the boundary, not your own database.
branch coverage
Whether both sides of each condition ran — more meaningful than line coverage.
flaky test
A test that fails intermittently. Usually time, ordering, shared state, or asserting on non-deterministic output.
eval set
Graded examples run on every AI change. Answers "did it get better?", which tests cannot.
