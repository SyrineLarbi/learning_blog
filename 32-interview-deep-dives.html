Why these four

They are the topics where a plausible surface answer exists and is easy to give — everyone can say what an index is, what hashing is, what a unit test is, what a factory is. So interviewers push past the surface, and the second and third questions are where the round is actually decided.

Each section here starts with what they probe — the sequence of questions you should expect — so you can prepare in the order it will arrive.

Dive 02

The N+1

The single most asked ORM question

What is an N+1 query, how do you spot it, and how do you fix it?

Strong

"One query for a list, then one more per item — so 200 employees means 201 round trips. In an ORM it is one line away and reads perfectly: a loop with an await inside that hits the database. I spot it two ways: reading for loops with I/O inside them, and query logging, because the count is obvious the moment you can see it. The fix is either include/select on the first call so it becomes one query, or one findMany filtered by id: { in: ids } and grouped in memory with a Map."

Follow-up

"Why did nobody notice in development?" — four rows. It is invisible until real data, which is why measuring against realistic volume matters more than measuring at all.

Red flag

"I'd cache it." A cache in front of an N+1 hides the defect until it misses, and then you own two problems and one of them is invisible.

Dive 03

Query plans and indexes

Senior · and very few candidates have read a plan

How do you investigate a slow query?

Strong

"EXPLAIN ANALYZE, and I look at four things. A sequential scan on a large table — it read every row. The estimated versus actual row counts, which is the most informative line in the plan: if the planner expected 10 and got 400,000 it chose a strategy for the wrong problem, and everything above that node is consequently wrong. The join strategy — a nested loop is fine for few rows and catastrophic for many. And whether a sort spilled to disk, which means it exceeded working memory."

Follow-up

"There is an index and it is still slow. Three reasons." — a composite index only serves a left-to-right prefix; a function on the column defeats it (LOWER(email)); and a leading wildcard is a scan by definition.

Bonus

Knowing Postgres does not auto-create an index for a foreign key. It surprises people and it is a common cause of slow joins.

Dive 04

Joins and aggregation

A favourite, because wrong answers are confident

Your salary total tripled after adding a join. Explain.

Strong

"Fan-out. Joining to a table with several matching rows multiplies the left-hand rows, so a salary joined to three skills is counted three times. Nothing errors — the number is wrong and plausible, which is the most expensive kind. I would aggregate the many-side first in a CTE, then join the single row. And I would sanity-check the row count before and after any join for exactly this reason."

Follow-up

"What else silently changes a count?" — an inner join dropping rows with no match, which makes orphans invisible; COUNT(column) ignoring nulls; and AVG ignoring nulls rather than treating them as zero.

Then

"Each employee plus their department average, one query?" — a window function: AVG(salary) OVER (PARTITION BY department). And they run after WHERE, so filtering on the result needs a CTE wrapper.

Dive 05

Transactions and races

Senior · the concurrency question that separates people

Two requests both read a balance of 100 and subtract 80, inside transactions. Result?

Strong

"20, and one withdrawal has vanished — a lost update. Postgres defaults to read committed, so both transactions read 100 legitimately; a transaction alone does not prevent this. The best fix is to stop reading: SET balance = balance - 80 is atomic and the race disappears. Otherwise optimistic locking with a version column, where the update fails if the version changed, or SELECT … FOR UPDATE held briefly. Repeatable read also prevents it but then you must handle serialisation failures and retry."

Follow-up

"What is the rule for transaction scope?" — short, and never a network call inside one. Holding locks and a pooled connection while waiting on another service is how one slow dependency becomes a database-wide outage.

Red flag

"I'd wrap it in a transaction" offered as the complete answer. It is the intuitive answer and it does not fix it.

Dive 06

Migrations

The closer, and it tests deployment thinking

Rename a column in production. Walk me through it.

Strong

"Not in one deploy. During a rolling deploy two versions of the code run against one database, so a rename breaks whichever instances have not been replaced. Three deploys — expand, migrate, contract: add the new column and write to both; move reads over and backfill; drop the old column once nothing references it. And I would check whether the migration locks a large table, because an ALTER that takes a long lock is an outage even when the schema change itself is trivial."

Follow-up

"Prisma-specific gotchas?" — migrate reset drops all data and must never touch anything real; the client is generated code, so prisma generate after every schema change; and in v7 the connection URL moved out of the datasource block into prisma.config.ts, and the client needs a driver adapter.

Dive 08

Passwords and tokens

Mid · a competence check with specific expectations

How do you store a password, and why that way?

Strong

"Hashed with bcrypt or argon2, never encrypted — hashing is one-way by design, so a stolen database yields hashes and nobody, including us, can read a user's password. Not a general-purpose hash like SHA-256, because those are fast, and fast means billions of guesses per second; bcrypt is deliberately slow with an adjustable cost so it stays expensive as hardware improves. Salting is per-password and the library handles it, which is what stops two identical passwords producing identical hashes."

Follow-up

"What error do you return for a wrong password versus an unknown email?" — the same one. Distinguishing them tells an attacker which addresses are registered.

Red flag

Any system that can email you your existing password. That is not hashing, and it is a reportable finding.

Senior · the JWT question, and most answers are wrong

What is inside a JWT, and what are its limitations?

Strong

"Three base64 segments: header, payload, signature. And the fact that surprises people — the payload is not encrypted. Base64 is encoding, not secrecy: anyone holding the token can read every claim. So no salary, no personal data, no secrets go in it; just an id, a role and an expiry, and you look the rest up server-side. The signature proves it was issued by us and has not been altered — readable but not forgeable."

"The hard limitation is revocation. The server stores nothing, so there is nothing to delete: a valid token stays valid until it expires even after logout, a disabled account or a demotion. Mitigations are all partial — short expiry, which is the standard answer; refresh tokens that are stored and revocable; or a denylist, which reintroduces the per-request state JWTs existed to avoid."

Follow-up

"You promote someone. Does their token know?" — no. The role was baked in at login, which is a real design consideration rather than a curiosity.

Dive 09

Storage and revocation

WhereThe attack it exposesThe honest verdict
localStorageAny XSS — including one in a dependency — reads itCommon in practice. Acceptable only with short expiry and disciplined output escaping.
httpOnly cookieCSRF, because it is sent automaticallyStronger, with SameSite and a CSRF token. More setup, better default.
Memory onlyNothing — but it is lost on refreshSafest, and needs a refresh-token flow to be usable.
The answer they are actually looking for

That there is no simply-safe option. The question is which attack you are defending against, and the mitigations are what protect you: short expiry, HTTPS everywhere, escaping output, and a revocation path for the long-lived credential.

A candidate who names one location as "the secure choice" with no conditions has not read the trade-off. Saying "there isn't a safe one, here's the trade" is the strong answer.

Dive 10 · the one that decides the round

Authorisation layers

Senior · asked concretely, and it is the real test

Here is an endpoint that returns an employee by id. What is missing?

Strong

"Three layers, and typically two are missing. Authentication is usually there — a guard verifying the token. Ownership is what is missing: the endpoint accepts an id and serves it, so any logged-in user can read any employee by changing a number. A role check does not cover it — 'managers may view employees' is true, but this manager may only view their team. And then field-level: salary, sickness and a disciplinary note have completely different audiences, so returning 'the employee' returns all of it whatever the UI displays."

Follow-up

"Where does the ownership check go?" — in the service, because it needs the resource; and in one path every caller traverses, because a check repeated in forty handlers will be missing from the forty-first.

Then

"How would you make the field-level part hard to get wrong?" — shape the response per requester with select rather than include, and express it in the type: Omit<Employee,'salary'> makes the public shape explicit rather than accidental.

Red flag

"The frontend only sends ids the user can see." That is the vulnerability, stated as the defence.

Dive 11

Input and output

Validate on the way in, escape for the destination on the way out
ON THE WAY IN
  · a schema per endpoint — a DTO with class-validator, or
    Pydantic
  · ALLOW-LISTS, not deny-lists. You cannot enumerate every bad
    input; you can enumerate the acceptable ones.
  · ⭐ STRIP UNKNOWN FIELDS. `whitelist: true` is a SECURITY
    CONTROL, not tidiness — without it a caller can post
    `role: 'admin'`, and any code that spreads the body into a
    write has just granted it. That is MASS ASSIGNMENT, and
    naming it in an interview is a strong signal.
  · bound every string, array and number. An unbounded array is
    a denial-of-service parameter.

⭐ AND THE THREE-LAYER RULE THEY WANT TO HEAR
  the browser validates for FEEDBACK · the API for CORRECTNESS
  · the database for INVARIANTS.
  ⇒ ONLY THE SECOND PROTECTS ANYTHING, because a request does
    not have to come from your form.

ON THE WAY OUT — escape for where it is going
  the same string is dangerous differently in HTML, SQL, a
  shell, a URL and a CSV.
  ⭐ ESCAPE AT OUTPUT, NOT AT INPUT. Escaping on the way in

Dive 12

Secrets

Mid–senior · a hygiene question with one hard fact

A secret was committed and removed in the next commit. Are you safe?

Strong

"No. Git history is forever — the secret is still retrievable from the earlier commit, and if the repository was ever pushed or cloned it is out. The only remedy is rotation. Removing it from the tip is housekeeping, not remediation."

Follow-up

"Where else do secrets leak?" — a build or pipeline log, an error message, a URL or query string (which lands in server logs, browser history and proxy logs), and the frontend bundle via a NEXT_PUBLIC_ prefix. And, now, pasted into an AI tool.

Then

"What is the test of a good secrets setup?" — can you rotate the database password on a Tuesday afternoon without downtime? "We can't" is a finding, and it is discovered at the worst moment.

Dive 14

The pyramid, honestly

Mid–senior · they want an opinion, not the diagram

Describe your testing strategy for an application like ours.

Strong

"Weighted more toward integration tests than the classic pyramid suggests, because in a CRUD-heavy web application most defects live in the seams rather than inside a function — a missing permission check, a wrong join, a validation that did not fire. A unit test of a mocked service cannot see any of those. My highest-value test is one per endpoint asserting four things: the happy path, 401 unauthenticated, 403 wrong owner, 400 invalid input. Four assertions covering what most often breaks, and they survive refactors."

Follow-up

"And E2E?" — a handful, on the critical journeys only. Slow and brittle, and the only thing that proves the system actually works end to end.

Dive 15

Mocking

The filter question in this dive

Do you mock the database?

Strong

"No — a real test database. Mocking Prisma means the test asserts that I called Prisma the way I thought I should, which is a test of my assumptions rather than of the query. Wrong joins, constraint violations and fan-out are exactly what it cannot see. I mock the boundary instead: third-party APIs, the LLM provider because it is non-deterministic and metered, email, and the clock — freeze it, or a test fails at midnight or on 29 February."

Follow-up

"What is the failure mode of over-mocking?" — every test passes and the application is broken, because each unit was verified against a fake version of its neighbours. Worse than no tests, because it produces confidence.

Bonus

"A mock must behave like the real thing when the real thing misbehaves" — if the provider can time out, return 429 or return malformed output, your mock should be able to do all three, or you have only tested the happy path of your error handling.

Dive 16

Coverage and flakes

A trap question — the number is not the answer

What coverage do you aim for?

Strong

"I do not set a target, because coverage measures which lines executed, not whether anything was asserted — a test that calls a function and asserts nothing gives it 100%. Mandate 90% and you get tests written to touch lines while the branch that matters stays untested. I read the report as a map of what is untested: if the risk engine is at 20% and the DTO mappers are at 100%, the number is fine and the situation is not. Where it does matter — money, permissions, the risk calculation — I aim at branch coverage, because the untested branch is the one with the bug."

Follow-up

"Your suite is flaky. What do you do?" — treat it as a bug with a deadline. Once failures are assumed to be noise the team re-runs instead of reading, and at that moment the pipeline has stopped catching anything. Usual causes: shared state, execution order, real clocks, unmocked network, a database not reset.

Dive 17

Testing AI features

Now asked in most loops with an AI feature

How do you test something that gives a different answer every time?

Strong

"Not with equality — that test fails randomly, gets marked flaky and is eventually deleted. Three things instead. The structure: if the output is schema-constrained, assert it validates and the enum is one of the allowed values — deterministic, and it is why structured output matters for testability. The properties: length bounds, no forbidden content, and that it only cites chunk ids that were actually in the context, which is a dozen lines and converts an invisible hallucination into a caught one. And the behaviour around it: timeout handled, retry on 429, the page still renders when the provider is down — most of what can break in an AI feature is ordinary engineering and is deterministically testable."

Follow-up

"So how do you know a prompt change improved things?" — that is an eval set, not a test. Tests answer "is it broken"; evals answer "did it get better". You need both and they are different artefacts.

Dive 20

Already in your stack

The filter question — and the best answer is recognition

Which patterns are already in the code you work on?

Strong

"Most of the framework is patterns with the names hidden. NestJS: dependency injection is inversion of control wholesale, providers are singletons, and guards, interceptors, pipes and filters are decorators arranged as a chain of responsibility — which is exactly why the request lifecycle order is fixed and knowable. React: components are composition over inheritance, props are dependency injection by another name, context is the provider pattern, and custom hooks are the real reuse mechanism. Prisma's generated client is a repository and active-record hybrid."

"Recognising that is what made the framework stop being magic for me — it became a set of decisions I could have made."

Red flag

Listing patterns you have never used, or naming a pattern for something that is plainly a function.

Dive 21

SOLID as diagnostics

Senior · the question that separates recitation from use

Tell me about a time a SOLID principle told you something was wrong.

Strong

"Dependency inversion, on a service that constructed its own Prisma client and its own HTTP client to the AI service. The symptom was that I could not test it without a database and a running AI service — and that difficulty was the design problem announcing itself, not a testing problem. Injecting both made it unit-testable in milliseconds, gave us one connection pool instead of one per service, and meant swapping the AI client for a fake was a constructor argument."

"The other one I use as a diagnostic is single responsibility, phrased usefully: if two different stakeholders can request changes to the same class, it is doing two jobs."

Follow-up

"And Liskov?" — the practical version: if a subclass throws where the parent returned, or narrows what it accepts, the hierarchy is wrong. It is the principle that tells you an inheritance relationship was a mistake.

Red flag

Reciting the five names with no example. Nobody designs by reciting SOLID; they are diagnostic questions for when code is painful to change.

Dive 22

When not to

Senior · a restraint question, and it is scored heavily

When would you not use a pattern? And composition or inheritance?

Strong

"Three tests before adding one. Has the problem actually happened twice — once is a case, twice is a pattern, zero times is a prediction. Does it make the code easier to read for someone new, because if following one request now means opening four files, the indirection cost more than it bought. And could a plain named function do this, which very often it could. Duplication is cheaper than the wrong abstraction — two similar things are often two things, and merging them creates a shared piece that grows flags until nobody dares touch it."

"Composition over inheritance, and the reason is that inheritance is permanent and couples you to the parent's internals — a base-class change can break every subclass subtly and at a distance. The test I use: would 'is a' be true to a domain expert who has never seen code? If I have to explain why it is technically true, it is composition. The exception is implementing an interface, which is inheritance of a contract rather than of implementation and carries almost none of the problems."
