Part I

The three services

Architecture 01

Why split at all

A restaurant has a dining room and a kitchen. Customers never walk into the kitchen; chefs never sit at the tables. Each side has its own job, its own tools, and its own rules — and that separation is not decoration, it is what makes the place work when it is busy.

ServiceRuns whereOwns
Frontend
Next.js · 3001		The user's browser (after the server renders the first pass)Everything visible. Rendering, interaction, calling the API, showing what comes back.
Backend
NestJS · 3010		A server you controlBusiness rules, authentication, authorisation, all database access, and calling out to the AI service.
AI service
FastAPI · 8000		A separate Python processModel inference and LLM calls. Accepts data, returns a prediction or a generated explanation.
The four reasons, and the fourth is not optional
①  SEPARATION OF CONCERNS
    UI logic (layout, animation, form state) is a different kind
    of problem from business logic (who may see what, how a risk
    score is computed). Mixed together they become impossible to
    change safely.

②  INDEPENDENT WORK
    the two sides agree on an API contract and then proceed in
    parallel. The dashboard can be redesigned without touching
    the backend, and a query can be optimised without touching
    the UI.

③  THE RIGHT LANGUAGE FOR EACH JOB
    React for interfaces. NestJS for structured server logic.
    Python for machine learning, because scikit-learn, pandas and
    numpy have no real equivalent in Node.
    ⇒ this is the ONLY reason the AI service exists as a separate
      process, and it is a good one.

④  SECURITY — ⭐ THE NON-NEGOTIABLE ONE
    anything that runs in a browser can be read, modified and
    replayed by the person using it. So:
      · password checks
      · permission decisions
      · database queries
      · API keys and secrets
    all live on the server. THE FRONTEND IS NEVER TRUSTED, not
    because users are hostile but because the code is no longer
    yours once it has been delivered.
    ⚠ a disabled button is a courtesy, not a control.

WHY THE AI SERVICE ALSO GETS ISOLATION
  model inference is memory-hungry and CPU-bound. In a separate
  process, one slow prediction cannot stop the backend from
  serving every other request. Same reasoning as ④, different
  failure mode.
Architecture 02 · the important one

One request, traced end to end

A manager clicks "Generate report". Eleven steps later the screen updates. If you understand this trace, you understand the system.

┌──────────────┐ HTTP + JSON ┌──────────────┐ │ Next.js │ ────────────────────► │ NestJS │ │ frontend │ ◄──────────────────── │ backend │ │ :3001 │ WebSocket push │ :3010 │ └──────────────┘ ◄──────────────────── └──┬────────┬──┘ the browser │ │ HTTP │ │ SQL, via Prisma ▼ ▼ ┌────────────┐ ┌──────────────┐ │ FastAPI │ │ PostgreSQL │ │ :8000 │ │ Neon :5432 │ └────────────┘ └──────────────┘ ⭐ NOTE WHAT IS ABSENT: the frontend never reaches the AI service, and the AI service never reaches the database. Each service talks only to what it must. That restriction is a design decision you should preserve. THE ELEVEN STEPS ① CLICK a React handler fires in the browser. ② REQUEST axios.post('/api/reports', { teamId: 5 }) ③ TOKEN ATTACHED an interceptor adds `Authorization: Bearer …` to every request automatically — see reflex 25. ④ ROUTED NestJS matches POST /api/reports to ReportsController. ⑤ AUTHENTICATED JwtAuthGuard verifies the signature and the expiry. Invalid ⇒ 401 and the journey ends. ⑥ AUTHORISED RolesGuard checks @Roles('manager','admin'). Wrong role ⇒ 403. ⭐ TWO SEPARATE CHECKS, IN THIS ORDER. Who are you, then may you. ⑦ VALIDATED the ValidationPipe turns the raw body into a typed DTO or rejects it with 400 — Volume III. ⑧ BUSINESS LOGIC ReportsService gathers the team's data via Prisma and posts it to the AI service. ⑨ PREDICTION FastAPI returns risk scores; the backend may then ask the LLM for an explanation. ⑩ PERSISTED the report row is written through Prisma. ⑪ PUSHED the backend emits `report:complete` over WebSocket; the frontend's listener updates the UI without polling. ⚠ WHERE THIS TRACE USUALLY BREAKS IN PRACTICE · step ⑤ — an expired token, which looks like "randomly logged out" to the user · step ⑧ — the AI service is not running, so the backend's outbound call times out. Everything else still works, which is exactly why report generation fails alone. · step ⑪ — the socket dropped and reconnected, so the event arrived while nobody was listening. The UI is stale and no error was raised anywhere. ⭐ KNOWING WHICH STEP FAILED IS 80% OF DEBUGGING THIS SYSTEM.
Architecture 03

Monolith, microservices, and what this actually is

MonolithThis projectFull microservices
Services1310+
Languages12 — TypeScript + PythonAny per service
ComplexityLowMediumHigh
DebuggingOne logThree logs, one traceDistributed tracing required
SuitsSmall teams, early stageMid-size projectsLarge organisations with team boundaries to match
The judgement worth taking away

This is not microservices. There is no separate auth service, no email service, no reporting service. It is a monolith backend plus one specialist process, split on a single clear criterion: Python has the ML ecosystem and Node does not.

Splitting for any weaker reason buys you network calls that can fail, transactions that no longer span the operation, and a debugging session across three log streams. Every service boundary is a permanent tax. Pay it where there is a reason you can state in one sentence.

Part II

Authentication & authorisation

Who you are, and what you may do. Two different questions with two different answers, confused constantly.

Auth 04

Authn versus authz

AuthenticationAuthorisation
AsksWho are you?May you do this?
Proves it withA password, then a tokenA role, an ownership check, a policy
HappensOnce, at login — then re-verified per request from the tokenOn every single request, per resource
Failure code401403
In this projectJwtAuthGuardRolesGuard, plus ownership checks in services
The vulnerability people actually ship

Not injection. A correctly formed request from a logged-in user carrying somebody else's id — and the code serves it, because it authenticated the caller and never asked whether this caller may see this record.

A role check does not cover it: "managers may view employees" is true, but this manager may only view their team. Every id that arrives from outside is a claim, not a fact, and the ownership check belongs in code that every path must pass through.

Auth 05

Passwords

Hashing is not encryption, and the difference is the whole point
ENCRYPTION   two-way. With the key you get the original back.
HASHING      ⭐ ONE-WAY. There is no "unhash". Deliberately.

  register:  hash the password, store the hash, discard the
             password
  log in:    hash what they typed, compare the two hashes

⇒ so a stolen database yields hashes, not passwords. And ⭐ NOBODY
  — not you, not an admin, not support — can read a user's
  password. If a system can email you your existing password, it
  is not hashing, and that is a reportable finding.

WHY bcrypt / argon2 AND NOT sha256
  a general-purpose hash is FAST, which is a virtue everywhere
  except here: fast means billions of guesses per second.
  bcrypt is DELIBERATELY SLOW and its cost is adjustable, so the
  same code stays expensive to attack as hardware improves.

SALT — and why it is automatic
  a random value mixed into each hash, stored alongside it.
  ⇒ two users with the same password get different hashes, so
    cracking one does not crack the other, and precomputed
    tables are useless. bcrypt handles this for you; you never
    manage salts by hand.

⚠ THE FIVE RULES
  · never log a password, not even at debug level
  · never return it in an API response — omit it at the type
    level (Omit<User,'password'>) so it cannot leak by accident
  · never put it in a URL or query string
  · compare with the library's compare function, never with ===
  · give the same error for "no such user" and "wrong password":
    ⭐ distinguishing them tells an attacker which emails are
      registered.
Auth 06

What a JWT actually is

THE PROBLEM IT SOLVES HTTP is stateless — the server remembers nothing. So every request must carry proof of identity. A token is that proof. THE SHAPE — three base64 segments joined by dots eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOjQyLCJyb2xlIjoi… . 4pcPyMD0… └──── HEADER ──────┘ └──────── PAYLOAD ───────┘ └─ SIG ─┘ which algorithm the claims: user id, proof it role, issued-at, expiry was signed by us ⭐ THE FACT THAT SURPRISES EVERYONE: THE PAYLOAD IS NOT ENCRYPTED. It is base64, which is encoding, not secrecy. Anyone holding the token can read every claim in it — paste one into a decoder and see. ⇒ SO: never put anything private in a JWT. No salary, no personal data, no secrets. Put an id and a role, and look the rest up server-side. WHAT THE SIGNATURE DOES it proves the token was issued by a holder of the server's secret and has not been altered since. Change one character of the payload and the signature no longer matches. ⇒ readable, but not forgeable. That is the security model. THE HARD PART — ⭐ YOU CANNOT UNDO A JWT the server does not store it, so there is nothing to delete. A valid token stays valid until it expires, even if you "log out", disable the account, or demote the user. the mitigations, all of them partial: SHORT EXPIRY 15 minutes, so the damage window is small — the standard answer REFRESH TOKENS a long-lived token, stored and revocable, used only to mint short access tokens A DENYLIST check every request against revoked ids ⚠ which reintroduces the per-request state JWTs existed to avoid — a real trade-off, not a fix ⇒ and remember the role is baked in: promote someone and their old token still says what it said at login.
Auth 07

The login flow

Seven steps, and where each one can go wrong
1  the user submits email + password over HTTPS
   ⚠ over plain HTTP this is readable in transit. HTTPS is not
     optional for a login form.

2  the backend looks up the user by email
   ⇒ not found? DO NOT say so. Same generic error as a wrong
     password (see reflex 05).

3  bcrypt.compare(submitted, storedHash)
   ⇒ the library re-hashes with the stored salt and compares.

4  on success, sign a JWT: { sub: userId, role, exp }
   ⇒ sub is the subject — the user id. Keep the payload minimal.

5  return the token to the frontend

6  the frontend stores it (reflex 08) and attaches it to every
   subsequent request via an interceptor (reflex 25)

7  on each request the guard verifies signature + expiry, then
   attaches the decoded user to the request object, so controllers
   read `req.user` instead of parsing tokens themselves.

⭐ THE DESIGN POINT: steps 1–5 happen ONCE. Step 7 happens on
  every request forever. That asymmetry is why the token exists
  — verifying a signature is cheap, and hashing a password is
  deliberately not.
Auth 08

Where tokens live

StorageRiskVerdict
localStorageReadable by any JavaScript on the page — so any XSS, including one in a dependency, steals the tokenCommon, and the usual choice in practice. Acceptable only with short expiry and disciplined output escaping.
httpOnly cookieUnreadable by JavaScript, but sent automatically — which enables CSRFStronger, with SameSite and a CSRF token. More setup, better default.
In memory onlyLost on refreshSafest, and needs a refresh-token flow to be usable.
sessionStorageSame XSS exposure as localStorage, cleared per tabMarginal improvement, same class of risk.
The honest summary

There is no storage location that is simply safe. The choice is which attack you are defending against, and the mitigations are what actually protect you: short expiry, HTTPS everywhere, escaping output, and a revocation path for the long-lived credential.

Anyone who tells you one of these four is "the secure option" with no conditions has not read the trade-off.

Auth 09

Roles, RBAC and guards

Three levels of permission, and why you need all three
①  ROLE-BASED (RBAC) — "managers may generate reports"
     @Roles('manager', 'admin')
     coarse, declarative, easy to read on the endpoint.
     ⚠ AND INSUFFICIENT ON ITS OWN: it says a manager may
       generate reports. It does not say WHICH TEAM.

②  OWNERSHIP — "…for their own team"
     lives in the service, because it needs the resource:
       if (team.managerId !== user.id) throw new ForbiddenException()
     ⭐ THIS IS THE CHECK PEOPLE FORGET, and its absence is the
       most common real vulnerability in business software.

③  FIELD-LEVEL — "…and not the salary column"
     an employee record holds a name (everyone), a manager (most),
     a salary (few), and sickness data (fewer still).
     ⚠ ONE ENDPOINT RETURNING "THE EMPLOYEE" RETURNS ALL OF IT.
       Hiding a column in the UI is not access control — the
       network tab shows the whole payload.
     ⇒ shape the response per requester. The type system can
       help: Omit<Employee,'salary'> makes the public shape
       explicit rather than accidental.

HOW A GUARD WORKS (NestJS, detail in Volume III)
  a class that runs BEFORE the controller method and returns
  true or false. Returning false produces a 403.
  ⭐ THE VALUE IS THAT IT IS ONE PLACE. A check repeated in
    forty handlers is a check that will be missing from the
    forty-first, written on a Friday.

⭐ THE PRINCIPLE FOR ALL THREE: enforce it in code every path
  must traverse. Not in the UI, not in documentation, not in a
  convention — those protect the paths that remembered.
Part III

The data layer

Prisma sits between TypeScript objects and SQL rows. Understanding what it generates matters more than memorising its API.

Data 10

What an ORM is

Object–Relational Mapper: the impedance mismatch, solved
THE PROBLEM
  your code thinks in OBJECTS with nested relations.
  the database thinks in ROWS with flat columns and foreign keys.
  translating by hand means writing SQL strings, mapping results
  onto objects, and doing it again in every method.

WITHOUT AN ORM              WITH PRISMA
  string SQL, no checking     const e = await prisma.employee
  manual result mapping         .findUnique({
  ⚠ concatenation invites          where: { id },
    SQL injection                  include: { team: true },
  types unknown                 });
                              ⇒ e.team.name is typed, autocompleted,
                                and the query is parameterised.

⭐ WHAT YOU GAIN
  · types generated FROM THE SCHEMA, so a renamed column becomes
    a compile error across the whole codebase rather than a
    runtime surprise
  · parameterised queries by construction — SQL injection is
    not reachable through the normal API
  · migrations as reviewable, ordered files
  · relations traversed without hand-writing joins

⚠ WHAT YOU LOSE
  · you no longer see the SQL, so an inefficient query is
    invisible until it is slow. ⭐ TURN ON QUERY LOGGING EARLY.
  · the N+1 trap is one line away — a loop of findUnique calls
    reads perfectly and is 200 round trips
  · complex analytical SQL becomes awkward or impossible, which
    is exactly when you drop down (reflex 15)
Data 11

The schema file

schema.prisma is the single source of truth: it generates the client, the types, and the migrations.

One model, and every idea in it
model Employee {
  id         Int      @id @default(autoincrement())
  email      String   @unique
  name       String
  salary     Int?                      // ? = nullable
  hiredAt    DateTime @default(now())
  updatedAt  DateTime @updatedAt       // maintained for you

  teamId     Int?
  team       Team?    @relation(fields: [teamId], references: [id])
  reports    Report[]                  // the other side, virtual

  @@index([teamId])
  @@map("employees")                   // the real table name
}

READING IT
  @id                 primary key
  @unique             a database constraint, not a hope ⭐
  @default(...)       autoincrement(), now(), cuid(), uuid()
  Type?               nullable
  Type[]              the "many" side of a relation
  @relation           declares which column carries the link
  @@index             an index on a column you filter or join on
  @@map               table name in the database differs from the
                      model name in code

⭐ THE TWO SIDES OF A RELATION ARE NOT SYMMETRIC. `teamId` is a
  real column. `team` and `reports` are conveniences Prisma
  resolves with a join or a second query — they do not exist in
  the table.

⭐ AND THE POINT WORTH INTERNALISING: @unique and @relation
  become REAL DATABASE CONSTRAINTS. They hold against every
  writer — your code, a migration, a script, a psql session at
  2 a.m. An application-level check protects only the paths that
  remembered to run it.
Data 12

The generated client

The queries you will write ninety per cent of the time
READ
  findUnique({ where: { id } })          by a unique field
  findFirst({ where: { … } })            first match
  findMany({ where, orderBy, take, skip })  a list

RELATIONS — two different things
  include: { team: true }        ⇒ the whole related object
  select:  { id: true, name: true, team: { select: { name: true } } }
                                 ⇒ only these fields
  ⭐ PREFER select FOR ANYTHING USER-FACING. It is faster, and it
    is how you avoid returning a salary column to someone who
    should not see it — the permission boundary expressed in the
    query itself.

WRITE
  create({ data })
  update({ where, data })
  upsert({ where, create, update })      insert or update
  delete({ where })
  createMany / updateMany / deleteMany   bulk, no relations

⭐ TRANSACTIONS — for anything that must be all-or-nothing
  await prisma.$transaction([ … ])
  ⇒ "write the report AND mark the team processed" must not half
    happen. If step two fails, step one is rolled back.
    Ask reflex 04's question — "what is the state of the world if
    this fails right here?" — and where the answer is "broken",
    that is where a transaction belongs.

⚠ THE N+1 TRAP, WRITTEN IN PRISMA
  for (const t of teams) {                    // 1 query
    t.members = await prisma.employee          // + one per team
      .findMany({ where: { teamId: t.id } });
  }
  ⇒ 1 + N queries. Fix it with include on the first call, or one
    findMany filtered by `teamId: { in: ids }` and grouped in
    memory. ⭐ THIS IS THE SINGLE MOST COMMON PERFORMANCE BUG IN
    ORM CODE, and it never appears in development where there
    are four teams.
Data 13

Migrations

WHAT A MIGRATION IS an ordered, committed file describing a schema change. The schema file says what you WANT; migrations are the recorded history of how the database got there. edit schema.prisma │ ├─ prisma migrate dev --name add_salary │ ⇒ generates SQL, applies it locally, regenerates │ the client │ └─ prisma migrate deploy ← in CI / production ⇒ applies pending migrations only. Never generates. ⭐ WHY NOT JUST EDIT THE DATABASE because the next person's database, the test database and production must all end up identical. A migration file is reviewable, ordered, and repeatable. A manual ALTER TABLE is a fact that exists on exactly one machine. ⚠ THE THREE RULES LEARNED THE HARD WAY · MIGRATIONS ARE FORWARD-ONLY IN PRACTICE. Prisma can reset, and a reset DROPS ALL DATA. Never on anything real. · A DESTRUCTIVE CHANGE NEEDS A PLAN, NOT A MIGRATION. Dropping or renaming a column breaks running code the moment it applies. The safe shape is three deploys: add the new column → move reads and writes over → drop the old one later. · THE ORDER OF DEPLOY MATTERS. Code that requires a column must ship after the migration that adds it, not with it. SEEDING — sample data for a fresh database one script that fills an empty database with enough to work: a few users with known passwords, teams, employees. ⇒ so a new joiner runs one command and has a working app, rather than clicking through forms for an hour. ⚠ seeds are for development. Production data does not come from a seed script.

Data 15

When to drop to SQL

Stay in Prisma for

CRUD, relation traversal, filtered lists, anything a reader should be able to follow without knowing SQL. Which is most of an application.

Drop to SQL for

Window functions, recursive queries, multi-level aggregation, and bulk operations where per-row overhead dominates — the analytics side of this project.

How

$queryRaw with parameterised values. Never build the string by concatenation: that is the one place Prisma stops protecting you from injection.

The rule

Raw SQL returns untyped rows, so declare the shape and validate it. You have stepped outside the generated types and the compiler no longer knows what is coming back.

The library the frontend is built from. Eight ideas; the third and fourth cause most of the confusion.

React 16

Components and JSX

A component is a function that returns markup
function EmployeeCard({ name, department }) {
  return (
    <div className="card">
      <h3>{name}</h3>
      <p>{department}</p>
    </div>
  );
}

JSX IS NOT HTML. It compiles to function calls, and the
differences are real:
  className    not class      (class is a reserved word in JS)
  htmlFor      not for
  onClick      not onclick    and it takes a FUNCTION, not a string
  { }          embeds a JavaScript expression — a value, not a
               statement. No if, no for; use && ?: or .map().
  self-closing every tag: <br />, <img />
  one root      return one element, or wrap in <>…</>

⭐ WHY COMPONENTS: the same reason functions exist. A named,
  reusable, independently testable unit with a declared input.
  The judgement is where to draw the boundary — a component with
  eleven props is usually two components.

THE MENTAL MODEL THAT MAKES REACT CLICK
  ⭐ YOU DO NOT UPDATE THE SCREEN. You describe what the screen
    should look like FOR THE CURRENT STATE, and React works out
    the minimum change to the real DOM.
  ⇒ so you never write "find that row and change its text". You
    change the data and re-describe. Every imperative DOM habit
    you may have is now the wrong instinct.
React 17

Props

Data flows down, events flow up
<EmployeeCard name="A. Chen" department="Engineering"
              onSelect={handleSelect} />

⭐ PROPS ARE READ-ONLY. A component may not modify what it was
  given. If it needs to change something, it calls a function
  the parent passed down — which is why `onSelect` is a prop.

  parent ──── data (props) ────► child
  parent ◄─── events (callbacks) ─── child

THE PATTERNS
  CHILDREN     <Panel><Table /></Panel> — the wrapped content
               arrives as props.children. This is composition,
               and it beats a `content` prop.
  DEFAULTS     function C({ size = 'md' }) — destructure with a
               default.
  SPREAD       <Input {...field} /> — convenient, and it hides
               what is actually being passed. Use sparingly.

⚠ PROP DRILLING — passing something through four components that
  do not use it, just to reach the fifth. The signal that either
  the tree is wrong or this belongs in context (reflex 22).
  ⭐ but three levels of explicit props is clearer than a context
    nobody can trace. Reach for context when the value is
    genuinely global — the current user, the theme — not to avoid
    typing.
React 18 · the one to understand properly

State

const [count, setCount] = useState(0); └─┬─┘ └───┬───┘ └┬┘ current setter initial value ⭐ THE RULE THAT EXPLAINS EVERY STATE BUG: CHANGING STATE IS WHAT CAUSES A RE-RENDER. Mutating a variable does not. employees.push(newOne); // ❌ nothing happens setEmployees([...employees, newOne]); // ✅ new array React compares the OLD value to the NEW one by reference. A mutated array is the same reference, so React concludes nothing changed. This is why Volume I insisted on spread. UPDATING OBJECTS AND NESTED STATE setUser({ ...user, name: 'X' }) one level setForm({ ...form, address: { ...form.address, city } }) ⇒ nested updates get ugly fast. That ugliness is a signal: either flatten the state or keep it in a form library. ⭐ THE STALE-VALUE TRAP setCount(count + 1); setCount(count + 1); // both read the SAME count → +1 use the function form when the new value depends on the old: setCount(c => c + 1); setCount(c => c + 1); // → +2 ✅ WHERE STATE SHOULD LIVE ⭐ AS LOW AS POSSIBLE, AND NO LOWER. Two components need it ⇒ lift it to their nearest common parent. One component needs it ⇒ keep it there. ⚠ AND WHAT SHOULD NOT BE STATE AT ALL: · anything DERIVABLE from other state — compute it during render. A stored total that must be kept in step with the rows it sums is a bug with a schedule. · SERVER DATA copied into local state "so we can edit it" — the copy goes stale and the save overwrites someone else's change. · FILTERS, TABS, PAGE NUMBER — those belong in the URL, so the view can be shared, bookmarked, and reached with the back button.
React 19

Effects

For synchronising with things outside React
useEffect(() => {
  const socket = io(API_URL);        // ① set up
  socket.on('report:complete', onDone);
  return () => socket.disconnect();  // ② clean up  ⭐ NOT OPTIONAL
}, [API_URL]);                       // ③ when to re-run

THE DEPENDENCY ARRAY
  []            run once, after the first render
  [a, b]        re-run whenever a or b changes
  omitted       ⚠ run after EVERY render — usually a bug, and
                sometimes an infinite loop

⭐ THE CLEANUP FUNCTION IS WHERE LEAKS ARE PREVENTED. Every
  subscription, interval, listener and socket opened in an effect
  must be closed in its cleanup. Without it, navigating between
  pages twenty times leaves twenty live sockets — memory grows,
  and events fire on components that no longer exist.

⚠ WHAT DOES NOT BELONG IN AN EFFECT
  · DERIVING VALUES. Computing state from props in an effect
    causes a second render and can loop. Just compute it.
  · EVENT RESPONSES. Work that should happen "when the user
    clicks" belongs in the handler, not in an effect watching a
    state change.
  ⭐ the modern guidance is that most effects people write are
    unnecessary. Effects are for SYNCHRONISING WITH THE OUTSIDE
    WORLD — a socket, a subscription, a browser API, a fetch that
    no framework is handling for you.

DATA FETCHING — and why this project mostly does not do it here
  fetching in an effect means handling loading, errors, races,
  cancellation and refetching by hand. Next.js server components
  (reflex 23) and a data library handle all of that. Use an
  effect for fetching only when nothing else can.
React 20

Lists and keys

The one React rule that silently corrupts a UI
{employees.map(e => <Row key={e.id} employee={e} />)}

⭐ A KEY TELLS REACT WHICH ITEM IS WHICH BETWEEN RENDERS. It must
  be STABLE and UNIQUE — the database id, essentially always.

⚠ key={index} IS A REAL BUG, not a lint nag.
  delete the first row of five: every remaining item's index
  shifts. React concludes that item 0's CONTENT changed rather
  than that item 0 was removed. So it keeps the DOM node and
  swaps the data — and any state inside that node stays where it
  was.
  ⇒ the visible symptom: a checked checkbox, an open dropdown, or
    half-typed text jumps to the wrong row. It looks like a
    haunting, and it is this.

  ⇒ index is acceptable ONLY for a list that never reorders,
    never filters and never has items removed. Rare enough to
    treat as never.

⚠ AND NEVER Math.random() as a key: it changes every render, so
  React discards and rebuilds every node, every time.
React 21

Forms

Controlled inputs, and the three-layer validation rule
CONTROLLED — React state is the single source of truth
  <input value={name} onChange={e => setName(e.target.value)} />
  the input shows what state says; typing updates state; state
  re-renders the input. One truth, one direction.

⚠ THE TWO BEGINNER ERRORS
  · value without onChange ⇒ a field that cannot be typed in
  · value={undefined} ⇒ React silently treats the input as
    uncontrolled, and it starts behaving like plain HTML. Default
    to '' rather than undefined.

⭐ VALIDATION HAPPENS IN THREE PLACES, AND ALL THREE ARE NEEDED
  ① in the browser, for FEEDBACK — fast, helpful, and completely
    bypassable
  ② at the API, for CORRECTNESS — the DTO and ValidationPipe
    (Volume III). ⭐ THIS IS THE ONLY ONE THAT PROTECTS ANYTHING.
    A request does not have to come from your form.
  ③ in the database, for INVARIANTS — unique, not-null, foreign
    keys. Holds against every writer forever.

  ⇒ ①  is UX. ② is security. ③ is truth. Skipping ② because ①
    exists is the mistake, and it is common.

SUBMISSION — the four states again
  disable the button while submitting (prevents the double-click
  that creates two records), show the error inline next to the
  field rather than as a toast, and keep what the user typed on
  failure. Clearing a form on error is a small cruelty.
React 22

Context and custom hooks

Sharing without drilling, and extracting logic
CONTEXT — for genuinely global values
  the current user · the theme · the socket connection · the
  language. Things nearly every component needs and nothing owns.

  create → provide near the root → consume with useContext

  ⚠ EVERY CONSUMER RE-RENDERS WHEN THE VALUE CHANGES. Putting
    frequently-changing state in a wide context re-renders half
    the app on every keystroke. Split contexts by change
    frequency: a rarely-changing user context, and local state
    for the rest.
  ⭐ CONTEXT IS NOT A STATE MANAGER. It is a way to pass a value
    down without threading it through props. It has no
    optimisation of its own.

CUSTOM HOOKS — the real reuse mechanism in React
  a function starting with `use` that calls other hooks:

    function useEmployees(teamId) {
      const [data, setData] = useState(null);
      const [error, setError] = useState(null);
      useEffect(() => { … }, [teamId]);
      return { data, error, loading: !data && !error };
    }

  ⭐ THIS IS HOW YOU SHARE STATEFUL LOGIC WITHOUT SHARING STATE.
    Two components calling useEmployees get their own independent
    state and the same behaviour.

  THE RULES OF HOOKS, and the reason behind them
    · call them only at the TOP LEVEL — never in a condition, a
      loop, or after an early return
    · only in components or other hooks
    ⇒ React identifies hooks BY CALL ORDER, not by name. A
      conditional hook changes the order between renders and
      React starts handing you the wrong state. The lint rule
      that enforces this is protecting you from a bug that is
      very hard to see.
React 23

Server versus client components

Server component (default)Client component 'use client'
RunsOn the server, at request timeIn the browser, after download
CanQuery the database directly, read secrets, await in the bodyUse state, effects, event handlers, browser APIs
CannotUse useState, useEffect, onClickTouch the database or read a secret — anything it holds is public
Ships to the browserOnly the rendered output — no component code, no dependenciesThe component and everything it imports
The pattern that follows

Server by default; 'use client' at the leaves. Fetch and compose on the server, then mark only the interactive pieces — a filter input, a modal, a chart with hover — as client components.

Two consequences worth knowing before your first bug: 'use client' applies to everything a component imports, so one careless directive high in the tree drags the whole subtree into the browser bundle. And a server component may render a client one, but not the reverse — the boundary only goes one way.

Calling the backend

HTTP 24

Axios and the instance

Why not just fetch
fetch is built in and fine. Axios earns its place through four
things, all of which this project uses:

  ① JSON HANDLED — request and response serialised for you.
     ⚠ with fetch you must remember res.json(), and forgetting it
       gives you a Promise where you expected data.
  ② ERRORS THROW ON 4xx AND 5xx.
     ⭐ THE BIG ONE: fetch RESOLVES SUCCESSFULLY on a 500. Your
       .then() runs, res.ok is false, and code that forgets to
       check treats a server error as data. Axios throws, so a
       try/catch actually catches.
  ③ INTERCEPTORS — one place to attach the token and handle 401s.
  ④ ONE CONFIGURED INSTANCE — base URL, timeout, headers, set once.

THE INSTANCE — create it once, import it everywhere
  const api = axios.create({
    baseURL: process.env.NEXT_PUBLIC_API_URL,   // http://localhost:3010/api
    timeout: 10000,
    headers: { 'Content-Type': 'application/json' },
  });

⭐ WHY THIS MATTERS MORE THAN IT LOOKS
  · the API location lives in ONE place, so moving from port
    3000 to 3010 — which this project did — is one variable
  · ⭐ ALWAYS SET A TIMEOUT. Without one, a request can hang
    indefinitely and the user sees a spinner forever with no
    error anywhere. The default is no timeout.
  · every call goes through the same configured object, which is
    what makes the interceptors in reflex 25 universal rather
    than per-call.
HTTP 25

Interceptors

Two functions that run around every request in the app
REQUEST INTERCEPTOR — attach identity
  api.interceptors.request.use(config => {
    const token = getToken();
    if (token) config.headers.Authorization = `Bearer ${token}`;
    return config;
  });

  ⭐ THIS IS STEP ③ OF THE TRACE IN REFLEX 02. Written once, it
    authenticates every request in the application — and, more
    importantly, it CANNOT BE FORGOTTEN on a new endpoint written
    next month. Compare "remember to add the header", which is
    the weakest rung of the prevention ladder.

RESPONSE INTERCEPTOR — handle failure once
  api.interceptors.response.use(
    res => res,
    error => {
      if (error.response?.status === 401) {
        clearToken();
        redirectToLogin();          // the token expired
      }
      return Promise.reject(error); // ⭐ RE-THROW
    },
  );

  ⚠ THE MISTAKE: swallowing the error here. If the interceptor
    does not re-reject, every caller's catch block stops running
    and failures become silent — the loud-failure-into-silent-
    wrong-state problem, installed globally.

  ⚠ AND THE INFINITE LOOP: if the interceptor retries a refresh
    through the SAME instance and the refresh also 401s, it
    intercepts its own retry forever. Guard with a flag, or use a
    separate bare client for the refresh call.

Handling failure in the browser

What happenedHow to tellWhat the user should see

The one that will confuse you first

CORS. A browser refuses to let JavaScript on localhost:3001 read a response from localhost:3010 unless the server explicitly permits that origin. The request is often sent and answered — the browser hides the answer from your code.

So it looks like the backend failed while the backend's log shows a clean 200. The fix is always on the server (enable CORS for the frontend's origin), never in the frontend, and never by disabling browser security.

Real time 27

Why WebSockets

THE LIMIT OF HTTP the client asks; the server answers. The server cannot start a conversation. So "your report is ready" has no way home. THE THREE WORKAROUNDS, AND WHY THE THIRD WON POLLING ask every 5 seconds. Simple. Wasteful — 719 of every 720 requests find nothing, and the news is still up to 5 seconds late. LONG POLLING ask, and the server holds the request open until it has something. Better, awkward. WEBSOCKET ⭐ ONE PERSISTENT CONNECTION, EITHER SIDE MAY SEND AT ANY TIME. A phone call instead of letters. WHEN IT IS WORTH IT ✅ server-initiated notifications ("report ready") ✅ live dashboards, presence, collaborative editing, chat ❌ ordinary request/response — ⚠ using a socket for a normal query throws away every HTTP convenience: status codes, caching, retries, and the fact that a request obviously belongs to its response. ⭐ THE COST NOBODY MENTIONS: A CONNECTION IS STATE. · it drops — trains, tunnels, laptop lids, load balancer timeouts — and must reconnect · reconnecting means EVENTS MISSED WHILE DISCONNECTED ARE GONE. The UI is silently stale and nothing errored. · in this project, Socket.io handles reconnection for you; it does NOT handle the gap. ⇒ on reconnect, RE-FETCH the current state over HTTP rather than trusting your cache. · and a server holding thousands of open connections is holding thousands of pieces of memory, which is why scaling sockets is harder than scaling requests.
Real time 28

The event pattern

Named events, both directions
SERVER (NestJS gateway)
  @WebSocketGateway()
  export class EventsGateway {
    @WebSocketServer() server: Server;

    notifyReportDone(userId: number, reportId: number) {
      this.server.to(`user:${userId}`)
                 .emit('report:complete', { reportId });
    }
  }

CLIENT (React, inside an effect)
  useEffect(() => {
    const socket = io(URL, { auth: { token } });
    socket.on('report:complete', ({ reportId }) => refresh());
    return () => socket.disconnect();      // ⭐ cleanup
  }, [token]);

CONVENTIONS THAT PAY OFF
  · NAMESPACE THE EVENT NAMES — `report:complete`,
    `employee:updated`. A flat name like `update` becomes
    ambiguous the moment there are two of them.
  · ⭐ SEND AN ID, NOT THE WHOLE OBJECT. Then the client fetches
    the current state over HTTP, where permissions are checked
    normally. Pushing full records through a socket bypasses the
    response-shaping that keeps a salary out of the payload.
  · EVENTS ARE NOT GUARANTEED AND MAY ARRIVE TWICE. Design the
    handler to be idempotent — "refresh this" always is;
    "increment a counter" is not.

⚠ AND THE ORDERING TRAP: an event can arrive BEFORE the HTTP
  response that caused it. If the handler refreshes a record the
  frontend does not know exists yet, handle the not-found case
  rather than crashing.
Real time 29

Authentication and rooms

A socket needs the same permission model as an endpoint
⭐ THE MISTAKE THAT MATTERS: TREATING THE SOCKET AS TRUSTED.
  A WebSocket connection is opened by a client you do not
  control, the same as an HTTP request. It needs authentication
  at handshake and authorisation per event.

AUTHENTICATE AT THE HANDSHAKE
  io(URL, { auth: { token } })
  the server verifies the token before accepting the connection,
  and attaches the user to the socket.
  ⇒ an unauthenticated socket is refused, so no event handler
    ever has to wonder who is on the other end.

⚠ AND THE EXPIRY PROBLEM PEOPLE MISS: the token is checked ONCE,
  at connection. A long-lived socket outlives a 15-minute token.
  ⇒ either re-verify periodically, or accept that the connection
    has its own lifetime and keep it short.

ROOMS — how you avoid broadcasting to everyone
  socket.join(`user:${user.id}`);
  socket.join(`team:${user.teamId}`);

  then emit to a room rather than to all:
    server.to(`user:42`).emit(…)     one person
    server.to(`team:5`).emit(…)      one team

  ⭐ ROOMS ARE THE AUTHORISATION BOUNDARY FOR SOCKETS. The room a
    socket may join is decided by the SERVER from the verified
    identity — never from something the client asked for.
  ⚠ letting the client choose its room ("subscribe me to team 9")
    without checking is the socket version of the wrong-id
    vulnerability in reflex 04: a valid request from someone with
    no right to that data.

  ⇒ and `server.emit()` with no room sends to EVERY connected
    client. In an HR application that is a data breach one
    keyword long.
