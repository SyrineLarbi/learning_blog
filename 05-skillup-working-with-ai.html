Skill upgrading handbook · Volume I of VIII

Working with AI. The tier everyone reads first.

The model can write the code. It cannot tell you whether the code is right, whether the problem was worth solving, or what it quietly broke. This volume is the six skills that decide whether an AI assistant makes you faster or makes you slower with more confidence.

The premise of this whole handbook

The onboarding handbook taught this stack. This one is about becoming senior — and the measure of senior has shifted. When generating a plausible implementation is nearly free, the scarce skills are judging, deciding and explaining: whether the output is correct, which approach fits the situation, and why.

So the order is deliberate. Every later volume assumes you can read code critically and evaluate what a model hands you, because without those two, more output is a liability rather than leverage.

Part I

The tools

AI skills 01

What they are, mechanically

Why knowing the mechanism changes how you use it
AN AI CODING ASSISTANT IS A LANGUAGE MODEL WITH YOUR CODE IN ITS
CONTEXT. That is the whole thing. It predicts the next token,
conditioned on whatever it was shown.

⭐ SO EVERY BEHAVIOUR YOU WILL EVER SEE FOLLOWS FROM TWO FACTS:

  ① IT ONLY KNOWS WHAT IS IN THE CONTEXT.
    not your whole repository. not the ticket. not the decision
    your team made in a meeting last March. not the constraint
    that lives in someone's head.
    ⇒ SO "IT WROTE THE WRONG THING" IS USUALLY "IT COULD NOT SEE
      THE RIGHT THING". The fix is context, not a better prompt.

  ② IT PRODUCES WHAT IS PLAUSIBLE, NOT WHAT IS TRUE.
    plausible code is code that LOOKS like the code it has seen.
    ⚠ which means the output is confident, idiomatic, well-named,
      correctly formatted — AND POSSIBLY WRONG. There is no
      correlation between how right it looks and how right it is.
    ⭐ THIS IS THE SINGLE MOST IMPORTANT THING IN THIS VOLUME.
      Bad code that looks bad is harmless; you rewrite it. Wrong
      code that looks excellent gets merged.

THE THREE SHAPES YOU WILL USE
  INLINE COMPLETION   suggests as you type. Best for boilerplate
                      and the obvious next line. ⚠ and it is
                      quietly the most dangerous, because you
                      accept it without a decision.
  CHAT                you describe, it produces, you discuss.
                      Best for a contained unit you can review.
  AGENTIC             it reads files, edits several, runs
                      commands. Best for mechanical changes at
                      scale. ⚠ requires the most review, and a
                      way to see exactly what it changed.

⚠ THE KNOWLEDGE CUTOFF, WHICH BITES CONSTANTLY IN THIS PROJECT:
  the model's training has a date. Prisma 7 moved the connection
  URL out of the datasource block; Next.js changed its caching
  defaults. ⭐ A MODEL CONFIDENTLY WRITES THE OLD API, because
  the old API is what most of its training data contains. When a
  suggestion looks right and fails, VERSION DRIFT IS THE FIRST
  SUSPECT.
AI skills 02

Genuinely good at, genuinely bad at

Reach for itDon't
Boilerplate with a clear shape — a DTO, a controller matching five others, a migration, test scaffolding.Anything security-critical. Auth flows, permission checks, token handling, crypto. Plausible-looking security code is the worst possible output.
Translation — SQL to Prisma, JavaScript to TypeScript, a curl command to Axios. Mechanical and verifiable.Decisions with business context it cannot see. Which metric definition is correct, whether this feature should exist.
Explaining unfamiliar code — "what does this regex do", "why would this function exist". Fast orientation.Novel algorithms where correctness is subtle. It will produce something confident and subtly wrong.
The blank page — a first draft to react to. Often faster to fix a wrong draft than to start cold.Anything where you cannot check the answer. If you can't verify it, you're not using a tool — you're trusting one.
Mechanical refactors across many files — renames, signature changes, adding a parameter everywhere.Architecture. It will happily produce a plausible structure with no knowledge of your constraints or team.
Tests for code that exists — enumerating cases you'd forget. Review them: it writes tests that assert current behaviour, bugs included.Anything with a hard version dependency you haven't confirmed. See the cutoff warning above.
The productivity trap, stated honestly

AI makes producing code faster. It does not make understanding, reviewing, integrating, debugging or maintaining code faster — and those are most of the work. Generate a 300-line module in four seconds and you have created a 300-line review task for someone, possibly future you.

So the honest measure is not lines per hour. It is working, understood, maintainable changes per week — and by that measure, unreviewed generation can put the number down.

AI skills 03

Configuring it for your codebase

The highest-leverage hour you can spend
⭐ THE SETUP THAT ACTUALLY CHANGES OUTPUT QUALITY: give the tool
  a persistent project instruction file. Most assistants read one
  automatically, and it removes the need to re-explain your stack
  in every conversation.

WHAT BELONGS IN IT
  THE STACK, WITH VERSIONS
    "NestJS 11, Next.js 16 App Router, Prisma 7, PostgreSQL on
    Neon, FastAPI, Ant Design (NOT Tailwind), Claude API."
    ⭐ VERSIONS ARE THE HIGHEST-VALUE LINE IN THE FILE. They are
      what stops the model writing the pre-7 Prisma client
      constructor forever.

  THE CONVENTIONS
    thin controllers, fat services · DTOs validate every input ·
    services never touch the response object · never
    `new PrismaClient()` in a service · errors are thrown, not
    returned · Ant Design components, never utility CSS.

  THE STRUCTURE
    one folder per feature, six predictable files. Point at an
    existing module as the canonical example.

  ⭐ AND THE MOST UNDERRATED SECTION — WHAT NOT TO DO
    "do not add a caching layer unless asked · do not introduce a
    new dependency without flagging it · do not write comments
    that restate the code · do not put business logic in a
    controller."
    ⇒ a model will not infer your prohibitions. Written down,
      they hold on every future conversation without you
      repeating yourself.

⭐ THE PATTERN THAT BEATS ALL PROSE: POINT AT A FILE.
  "Follow the shape of employees.service.ts." One reference to
  real code in your repository conveys naming, error handling,
  layering and style more accurately than a page of description
  — and it cannot drift out of date, because it IS the code.
Part II

Prompting for code

Not incantations. Supplying enough information that a competent stranger could do the task — because that is exactly what you are talking to.

Prompting 04

The anatomy of a code prompt

THE FOUR PARTS, IN ORDER OF HOW MUCH THEY MATTER ① CONTEXT — ⭐ 70% OF THE OUTCOME the code it must fit alongside · the types and interfaces involved · the versions · the constraint that is not visible in the code ⇒ "here is the service, here is the DTO, here is the Prisma model" beats every clever phrasing. ② TASK — what, specifically ⚠ "improve this" gives you an opinion. ✅ "extract the ownership check into a reusable guard so the other three endpoints can use it" gives you a change you can review. ③ CONSTRAINTS — the boundaries "no new dependencies · keep the public signature · must work on Node 20 · follow the error handling in this file" ⭐ AN UNSTATED CONSTRAINT WILL BE VIOLATED. Not from malice — it simply is not in the context. ④ OUTPUT SHAPE — what you want back "just the changed function" · "explain the approach before writing code" · "give me two options with trade-offs" ⭐ ASKING FOR THE PLAN FIRST IS THE SINGLE BEST HABIT IN THIS PART. A wrong plan costs one paragraph to reject; a wrong implementation costs a review. THE WEAK VERSION vs THE STRONG VERSION ⚠ "write a function to get employees by team" ⇒ invents a data layer, invents types, ignores your permission model, probably N+1s. ✅ "In employees.service.ts (shown below), add a method findByTeam(teamId, user). It must: reuse the ownership check pattern from create() · select only id, name, riskScore — not salary · return [] rather than throwing when the team is empty. Prisma 7. Show me the method only." ⇒ reviewable, correct-by-construction, and it took fifteen seconds longer to write.
Prompting 05

Supplying context

TechniqueWhen and why
Point at real filesThe default. Existing code carries conventions no description can. "Match this file" is the most efficient instruction available.
Paste the typesThe Prisma model, the DTO, the interface. Most wrong output is guessed field names — this eliminates the whole category.
Paste the actual errorThe full message and stack, not your summary of it. Your paraphrase has already discarded the diagnostic detail.
State the version explicitlyWhenever a library's API has moved. Cheaper than debugging a confidently-wrong Prisma 6 pattern.
Give a counter-example"Not like this — this is the old pattern we moved away from." Negative examples are unusually effective and rarely used.
Start a fresh conversationWhen the thread has gone wrong twice. A context full of failed attempts biases everything after it — the model is now conditioned on its own mistakes.
The test that saves the most time

Before sending: could a competent engineer who has never seen this codebase complete this task with only what I have written?

If no, you are about to receive a guess — and no amount of rephrasing substitutes for the missing information. This single question resolves most "the AI is useless at our codebase" complaints.

Prompting 06

Iterating

Steering, not re-rolling
⚠ THE LOSING LOOP
  ask → wrong → "no, try again" → wrong differently → "still
  wrong" → …
  each round adds a failed attempt to the context, and you are
  now asking a model that has been conditioned on three of its
  own mistakes.

⭐ THE WINNING MOVE: SAY WHAT IS WRONG, SPECIFICALLY.
  "This queries in a loop — one per team. Rewrite it as a single
  query filtered by teamId: { in: ids } and group in memory."
  ⇒ a diagnosis, not a verdict. That is a steer; "try again" is
    a coin flip.

THE FOUR USEFUL FOLLOW-UPS
  ① "WHAT DID YOU ASSUME?"
     ⭐ exposes the invented field name, the guessed default, the
       version it targeted. Frequently the whole bug.
  ② "WHAT BREAKS IF THE LIST IS EMPTY / THE USER LACKS
     PERMISSION / THIS RUNS TWICE?"
     ⇒ the edge catalogue, delegated.
  ③ "GIVE ME A SIMPLER VERSION."
     ⚠ models over-engineer by default — abstractions with one
       caller, configuration nobody asked for, a factory for two
       cases. Asking for simpler almost always improves it.
  ④ "WHAT WOULD A REVIEWER OBJECT TO?"
     ⇒ surprisingly effective at surfacing the thing you would
       otherwise find in review.

⭐ AND KNOW WHEN TO STOP. If two well-specified attempts have
  failed, the task is probably one of: underspecified (fix the
  context), genuinely subtle (write it yourself), or wrong
  (rethink the approach). A third attempt at the same prompt is
  a bet against evidence.
Prompting 07

Anti-patterns

The mega-prompt

Five features in one request. You get five half-implementations that must all be reviewed together. Ask for one reviewable unit.

Politeness as specification

"Please write clean, professional, production-ready code." Every adjective is unfalsifiable. Say which constraint you mean.

Accepting the first answer

Especially when it looks good. Looking good is exactly what the model optimises for and is uncorrelated with being right.

Prompting instead of reading

Asking the model to explain its own output rather than reading it. Its explanation is generated too — it can confidently describe code that does something else.

Letting it name things

Names encode domain meaning it cannot see. data, result, handleData — rename them yourself; it is the cheapest quality gain in the diff.

Pasting secrets

A real .env, a connection string, a token, live employee data. It has left your boundary. Redact before pasting, every time.

Part III

Reading code

The skill whose value went up when writing became cheap — because now the volume of code you must understand and did not write has multiplied.

Reading 08

Why it matters more now

The arithmetic

Engineers have always read far more code than they wrote. Generation shifts that ratio further: more code enters your codebase that nobody on your team composed line by line.

Which makes reading the bottleneck. If you cannot read fluently, you cannot review, so you cannot safely accept — and an assistant becomes a machine for manufacturing code you do not understand. Reading speed is now a throughput constraint on the whole team.

Reading 09

Entering an unfamiliar codebase

The order that works, and why
1  THE README AND THE PACKAGE MANIFEST
   what it claims to be, and what it depends on. ⭐ THE
   DEPENDENCY LIST IS THE FASTEST ARCHITECTURE SUMMARY THERE IS
   — socket.io means real-time, prisma means an ORM, xgboost
   means a model. Two minutes, most of the shape.

2  THE ENTRY POINT
   main.ts, app.module.ts, page.tsx. ⭐ In NestJS the root
   module lists every feature — that single file is the map.

3  THE FOLDER STRUCTURE, AS A SENTENCE
   "one folder per feature, six files each." Once you can say
   it, you can predict where anything lives, which is most of
   what "knowing a codebase" means.

4  THE DATA MODEL
   schema.prisma, the migrations, the types. ⭐ THE SCHEMA IS
   THE MOST STABLE AND MOST INFORMATIVE FILE IN AN APPLICATION.
   Code churns; the nouns and their relationships persist.

5  ONE FEATURE, ALL THE WAY THROUGH
   pick something small and trace it end to end: route → guard →
   controller → service → database → response.
   ⭐ ONE VERTICAL SLICE TEACHES MORE THAN SKIMMING FIFTY FILES,
     because it shows you the seams — where the layers actually
     meet, which is where bugs live.

6  THE TESTS
   ⭐ tests are executable documentation of intent. They tell you
     what the authors believed mattered and which edge cases
     they had been bitten by.

⚠ WHAT NOT TO DO: read alphabetically, or read everything before
  touching anything. You will spend a week and retain a fog.
  ⭐ READ WITH A QUESTION. "Where does the risk score come from?"
    gives every file you open a purpose, and you stop when you
    have the answer.
Reading 10

Tracing execution

TOP-DOWN — start at the entry point, follow the call good for: "what happens when the user clicks this?" the risk: you descend into a helper, then its helper, and lose the thread six levels down. ⭐ THE FIX: KEEP A STACK ON PAPER. Write the chain as you descend, and note what you skipped to come back to. BOTTOM-UP — start at the thing you care about, find callers good for: "who uses this function, and can I change it?" ⭐ THE MOST USEFUL SINGLE ACTION IN CODE READING IS "FIND ALL REFERENCES". It answers "is this safe to change?" faster than any amount of reading, and it is the first thing to run before any refactor. THE PRACTICAL METHOD — MEET IN THE MIDDLE go top-down until you are lost, then bottom-up from the thing you actually need, and join the two. ⭐ AND THE TECHNIQUE PEOPLE UNDERUSE: RUN IT. put a breakpoint, or a log line, and look at the real values. Five minutes of watching actual data beats an hour of reasoning about what the code probably does — especially with framework magic, dependency injection or decorators in the path, where the call chain is not visible in the source at all. READING FRAMEWORK CODE — the shortcut you do not need to understand how NestJS resolves a provider. You need to know THE ORDER: middleware → guards → interceptors → pipes → handler → interceptors → filters. ⭐ WITH FRAMEWORKS, LEARN THE LIFECYCLE, NOT THE INTERNALS. The lifecycle tells you where your code runs and what has already happened; the internals rarely change your day.
Reading 11

Building a mental model

What "knowing a codebase" actually consists of
YOU UNDERSTAND A SYSTEM WHEN YOU CAN ANSWER, WITHOUT LOOKING:

  □ what are the main NOUNS, and how do they relate?
  □ where does a request ENTER, and what does it pass through?
  □ where does TRUTH live — which store is authoritative for
    each fact?
  □ what are the BOUNDARIES — the network calls, the queues, the
    third parties? ⭐ these are where failures and latency come
    from, and where your assumptions stop holding.
  □ what is the CONVENTION — where would a new feature go?
  □ what is DANGEROUS — which files does everyone touch
    nervously, and why?

⭐ THE FASTEST WAY TO FIND OUT WHETHER YOUR MODEL IS RIGHT:
  EXPLAIN IT TO SOMEONE, OR WRITE IT DOWN. Every gap becomes
  audible the moment you try to say it out loud. Nothing else
  exposes a fuzzy understanding as quickly.

⚠ AND THE HABIT WORTH KEEPING: WRITE DOWN WHAT SURPRISED YOU.
  Surprises are where your model was wrong, and they are the
  highest-value notes you will make in your first month —
  they are also exactly what the next new joiner needs.

⭐ READING GENERATED CODE CRITICALLY — the specific version of
  this skill that this volume exists for. Ask of any suggestion:
    · does it use OUR patterns, or generic ones?
    · did it invent a field, a method or a config key?
    · does it handle the empty case, the permission case, the
      twice case?
    · is there an abstraction here with exactly one caller?
    · did it silently change a behaviour something depends on?
  ⚠ FLUENCY IS NOT CORRECTNESS. Generated code is uniformly
    well-formatted and idiomatic, which removes every surface
    cue you normally use to sense that something is off. You
    have to read it deliberately, because it will never look
    suspicious.
Part IV

Pair programming with a model

Pairing 12

Who leads, and when

SituationWho leadsWhy
Boilerplate matching an existing patternLet it leadThe shape is known, the review is quick, the risk is low.
An unfamiliar libraryLet it leadFaster than the docs for a first draft — then check the docs, because of version drift.
A mechanical change across many filesLet it leadTedious, uniform, and easy to verify by reading the diff.
You know exactly what you wantYou leadDescribing it precisely often costs more than typing it. Not everything is a prompt.
Security, permissions, moneyYou leadThe failure mode is severe and the output looks correct either way.
An architectural decisionYou leadIt cannot see your constraints, team or history. Use it to explore options, not to choose.
You do not understand the problem yetYou leadThe most important row. Generating code to avoid thinking produces a plausible answer to a question you have not framed.
Pairing 13

The workflow that works

Five steps, and the order is the point
1  UNDERSTAND THE TASK YOURSELF FIRST
   what is being asked, what the unknowns are, what "done"
   means. ⭐ NEVER OUTSOURCE THIS STEP. If you cannot state the
   task in one sentence, the model has no chance and you will
   not be able to review what it produces.

2  DECIDE THE APPROACH — with it, not by it
   "here are two options, what are the trade-offs?" is a good
   use. "Pick one for me" is not — you own this.

3  ASK FOR ONE UNIT AT A TIME
   one function, one endpoint, one migration. Small enough to
   review properly, which is the actual constraint.

4  REVIEW BEFORE ACCEPTING
   the pass in reflex 17. ⭐ EVERY TIME, INCLUDING WHEN IT LOOKS
   OBVIOUSLY FINE. That is when it slips through.

5  RUN IT
   ⭐ AND THE COMMON FAILURE: TRUSTING THE TESTS IT WROTE FOR THE
     CODE IT WROTE. If both came from the same guess, they agree
     with each other and with nothing else. Write at least one
     assertion yourself, from the requirement.

⭐ THE COMMIT DISCIPLINE THAT MAKES ALL OF THIS SAFE:
  COMMIT BEFORE A LARGE GENERATED CHANGE, AND KEEP GENERATED
  CHANGES IN THEIR OWN COMMITS. Then the diff is reviewable in
  isolation and reverting is one command rather than an
  archaeology exercise. With agentic tools that edit many files,
  this is not optional.
Pairing 14

Managing context

THE CONTEXT WINDOW IS A BUDGET, AND EVERYTHING SHARES IT your instructions · the files you attached · the whole conversation so far · the output being generated ⭐ THREE CONSEQUENCES YOU WILL FEEL ① MORE CONTEXT IS NOT BETTER CONTEXT. attach twelve files and the three relevant ones compete with nine irrelevant ones. ⇒ ATTACH WHAT IS NEEDED, and say why each is there. ② LONG CONVERSATIONS DEGRADE. ⚠ material in the MIDDLE of a long context gets less attention than material at the start or the end. So the constraint you stated twenty messages ago is the one quietly dropped. ⇒ RESTATE CRITICAL CONSTRAINTS in the message that matters. Do not assume the thread remembers. ③ A POISONED THREAD STAYS POISONED. once the conversation contains two wrong approaches, they are part of what the next answer is conditioned on. ⭐ START FRESH, and bring forward only what was correct. This feels wasteful and is almost always faster. ⭐ THE HABIT: TREAT A CONVERSATION AS DISPOSABLE AND THE PROJECT INSTRUCTION FILE AS PERMANENT. Anything you find yourself explaining a second time belongs in the file (reflex 03), not in another message.
Pairing 15

Collaboration traps

The four that do real damage

Accepting code you could not have written. Not "would not have" — could not. If you cannot explain why it works, you cannot maintain it, review it, or debug it at 3 a.m. And you are now the owner.

Skill atrophy by delegation. Delegating the thinking, not just the typing. The judgement in every other volume of this handbook is built by exercising it.

Scope creep by suggestion. It adds a caching layer, a retry, an abstraction you did not ask for. Each is plausible; together they are a diff nobody asked for and everybody must now maintain.

Silent behaviour changes. A refactor that also changes an error case, a default, or a return shape. The diff looks like a tidy-up; something downstream depended on the old behaviour.

Part V · the core skill

Evaluating what it produces

Evaluating 16

Why this is the skill

The whole argument in one paragraph

When generating an implementation is nearly free, the value moves entirely to judging it. Two engineers with the same tool produce wildly different outcomes: one merges plausible code, the other catches the invented field, the missing permission check and the query in a loop.

That difference is not knowledge of the tool. It is the review pass. It is also the most transferable skill in this handbook — it is the same pass you run on a colleague's pull request, and on your own.

Evaluating 17 · print this

The review pass

Six questions, in order of what they catch
①  DOES IT DO WHAT I ASKED?
   read the code against the requirement, not against its own
   explanation. ⭐ THE MOST COMMON FAILURE IS A CORRECT SOLUTION
   TO A SLIGHTLY DIFFERENT PROBLEM — and it is invisible if you
   only check that the code is good code.

②  IS EVERYTHING IT REFERENCES REAL?
   ⚠ HALLUCINATED IDENTIFIERS ARE THE #1 DEFECT: a method that
     does not exist, a config key that was never a key, a
     package that does not exist, a Prisma field spelled almost
     right. ⭐ THE COMPILER CATCHES SOME OF THIS. It does not
     catch a real method used with wrong semantics.

③  THE EDGE CASES
   zero · one · many · null · twice · order · race · lie ·
   halfway.
   ⭐ MODELS WRITE THE HAPPY PATH BY DEFAULT, because that is
     what most training code looks like. Assume the empty list
     and the second click are unhandled until you see otherwise.

④  SECURITY
   is every id from outside checked against the caller? does
   this leak a field the caller may not see? is a permission
   enforced in code or merely in the shape of the request?
   ⚠ AND: DID IT INTERPOLATE ANYTHING INTO A QUERY STRING?
     Generated raw SQL with a template literal in it is the
     classic injection reintroduced.

⑤  DOES IT FIT OUR CODEBASE?
   our layering, our error handling, our naming. ⚠ generic
   correct code that ignores your conventions is a slow tax —
   it is the second pattern in a codebase that had one.

⑥  IS IT MORE COMPLICATED THAN NECESSARY?
   ⭐ ASK FOR SIMPLER ROUTINELY. Models produce abstractions with
     one caller, options nobody will set, and defensive
     try/catch around code that cannot throw. Deleting is part
     of the review.

⭐ THE ONE-QUESTION VERSION, IF YOU ONLY DO ONE:
  "WHAT WOULD I HAVE TO BELIEVE FOR THIS TO BE CORRECT?"
  then check whether you actually believe it. That question
  surfaces the invented field, the unstated assumption and the
  unhandled empty list in a single pass.

Evaluating 19

Verifying, not trusting

In ascending order of strength
WEAKEST
  it looks right                    ⚠ this is not verification
  the model says it is correct       ⚠ nor is this
  it compiles                        catches invented names only
  it runs on the happy path          catches obvious breakage
  it runs on YOUR edge cases         ⭐ now you are testing
  a test YOU wrote from the
    requirement passes               ⭐ independent of its guess
  it behaves correctly against
    real data volume                 catches N+1 and timeouts
  a colleague reviewed it            catches what you cannot see
STRONGEST

⭐ THE PRINCIPLE: VERIFY WITH SOMETHING THAT DID NOT COME FROM
  THE SAME SOURCE. Code and tests generated in one breath agree
  with each other by construction — they encode the same
  misunderstanding twice and give you two confirmations of one
  guess.

FOR ANYTHING NUMERIC — the rule from the analytics side
  ⇒ compute it a second way and compare. A total from a query
    and a total from a spreadsheet agreeing is real evidence; a
    total that "looks about right" is not.

⚠ AND THE ONE PEOPLE SKIP: CHECK IT AGAINST REALISTIC VOLUME.
  Generated code is routinely correct and unusably slow. Four
  test rows hide every N+1, every missing index, and every
  unbounded list endpoint in existence.
Evaluating 20

When to rewrite instead

You have iterated three times

The task is underspecified, genuinely subtle, or wrong. A fourth attempt is a bet against evidence.

You cannot follow it

Unreviewable code is unmergeable code, regardless of whether it works today. You will own it.

It is 80% right in a tangled way

Fixing someone else's near-miss is often slower than writing it cleanly, and leaves a hybrid nobody understands.

It is security or money

Write it yourself, then use the model as a reviewer — "what would an attacker try here?" is a genuinely good prompt.

Part VI

The mindset

Mindset 21

The shift

Was valuableIs valuable now
Knowing the syntaxKnowing what to build, and what not to
Writing it quicklyJudging it correctly
Memorised APIsSystems thinking — how the parts interact and where they fail
Producing volumeProducing understood, maintainable change
Solving the ticketQuestioning the ticket — half of them are a proposed solution in disguise
Individual outputExplaining, deciding, and raising the team's standard
What has not changed at all

Every column on the right was valuable before too — it is the left column that depreciated. Debugging, trade-off reasoning, knowing the domain, communicating clearly and owning what you ship were always the senior skills. The tooling change did not create a new career ladder; it removed some of the busywork that used to disguise where you were on it.

Mindset 22

What the model cannot do

Not "yet" — structurally, from where it sits
①  KNOW YOUR CONTEXT
   the business, the customer, last quarter's incident, the
   constraint somebody agreed to in a meeting, why the previous
   attempt failed. ⭐ IT ONLY KNOWS WHAT IS IN THE WINDOW.

②  DECIDE WHAT MATTERS
   which of the nine things on the board is worth doing, and
   which feature should not exist. That is a judgement about
   consequences it cannot observe.

③  OWN THE OUTCOME
   ⭐ THE ONE THAT ACTUALLY MATTERS. When it is wrong at 3 a.m.,
     a person is accountable — for the decision, the review, and
     the fix. Accountability does not delegate.

④  BE TRUSTED BY PEOPLE
   colleagues rely on your judgement because it has been right
   before. That is a relationship, and it accrues to you.

⑤  KNOW WHAT IT DOES NOT KNOW
   no reliable uncertainty signal. It cannot tell you "I am
   guessing about this field name" — it produces the guess with
   the same fluency as a fact. ⇒ WHICH IS WHY EVALUATION HAS TO
   BE YOURS.

⑥  SAY NO
   "this should be three rules in the database, not a model" ·
   "this feature will create a support burden nobody has costed"
   · "we should not build this."

  Judgement, systems thinking and trust do not depreciate, and

Term bank

Volume I · used without explanation later
context window
Everything the model can see for one request — instructions, files, conversation, output. One shared budget.
knowledge cutoff
The date its training data stops. The reason it writes last year's API confidently.
hallucination
A confident, plausible, false output. Here: an invented method, field or package.
version drift
Generated code that was correct for an older release of a library.
agentic tool
An assistant that reads and edits multiple files and runs commands on its own.
project instructions
A persistent file the tool reads every session — stack, versions, conventions, prohibitions.
poisoned thread
A conversation whose context contains failed attempts, biasing everything after them.
plausible-but-wrong
Output that is idiomatic, well-formatted and incorrect. The defining risk of the era.
the review pass
The six questions in reflex 17, run on every accepted change.
N+1
One query for a list plus one per item. The most common generated performance defect.
independent verification
Checking output with something that did not come from the same guess.
skill atrophy
Delegating the thinking rather than the typing, and losing the judgement.
