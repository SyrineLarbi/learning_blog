Topic 09 · four prior lines of coverage

BullMQ and background jobs

The layer this adds

"We use a queue" is the claim. The layer underneath is what the queue actually guarantees, and what it makes you responsible for — because a queue does not remove failure, it relocates it.

The mechanism
  • Redis is the store. A job is a hash; the queue is a set of lists — waiting, active, delayed, completed, failed. Understanding that explains everything else: why jobs survive a restart, why a crashed worker leaves a job in active, and why the stalled-job check exists to recover it.
  • Concurrency is per worker process. Set it to 5 and run three replicas and you have fifteen concurrent jobs hitting your database — which is how a queue drain becomes a self-inflicted outage. The database connection pool, not the worker, is the real limit.
  • Retries need backoff and a cap. Exponential, capped, with jitter. Without jitter every retry from a burst fires simultaneously and you have built a thundering herd.
  • The dead-letter path. A job that has exhausted its attempts must land somewhere a human sees. A failed queue nobody watches is a silent data-loss mechanism — so alert on its depth, not just on errors.
  • Rate limiting and flow control. A limiter on the queue is how you protect a metered API — and for this project's LLM calls that is a cost control as much as a reliability one.
  • Repeatable jobs for scheduled work, with the important caveat below.
Where it goes wrong
  • A non-idempotent consumer. BullMQ is at-least-once: a job can run twice after a worker crash or a stall. If the handler charges a card, sends an email or appends a row, it will do it twice. This is the single most important thing to get right.
  • Storing large payloads in the job. The whole payload lives in Redis. Pass an id; let the worker fetch.
  • Repeatable jobs with several replicas, so the scheduled job runs three times — unless you use the built-in scheduler correctly or elect a single leader.
  • No visibility. The user clicked a button and got "accepted", and now there is no way to tell them it finished — or failed.
  • Unbounded completed/failed retention, so Redis memory grows until it does not.
The question you must be able to answer

"Your worker crashes halfway through generating a report. What happens?" — the job returns to the queue and runs again, so the answer must cover whether the half-written state is safe, whether the retry duplicates anything, and how the user finds out. "It retries" alone is not an answer.

Socket.io horizontal scaling

THE PROBLEM, STATED PRECISELY ONE INSTANCE — works perfectly client ──ws──► server ──► emit to room ──► every member (all sockets are in this process's memory) TWO INSTANCES — silently broken client A ──ws──► server 1 client B ──ws──► server 2 │ │ emit to `team:5` ─────► only A gets it. B does not, because server 1 has never heard of B's socket. ⭐ AND IT FAILS SILENTLY AND INTERMITTENTLY, depending on which instance each client happened to connect to. Which is why it is fine in development and mysterious in production. THE FIX: AN ADAPTER a Redis (or equivalent) adapter makes every emit a pub/sub message that all instances receive and fan out to their own local sockets. ⇒ one line of configuration, and the whole class of bug disappears. ⚠ BUT THREE THINGS THE ADAPTER DOES NOT FIX ① THE HANDSHAKE AND FALLBACK. Socket.io may start on HTTP long-polling before upgrading to WebSocket, and polling requires the SAME instance for consecutive requests. ⇒ SO YOU NEED STICKY SESSIONS AT THE LOAD BALANCER, or you must force the WebSocket transport only. ⭐ THIS IS THE DETAIL PEOPLE MISS, and it produces random handshake failures. ② THE GAP AFTER A RECONNECT. A dropped connection — trains, tunnels, laptop lids, load-balancer timeouts — reconnects automatically, and EVENTS EMITTED WHILE DISCONNECTED ARE GONE. The UI is silently stale and nothing errored. ⇒ ⭐ ON RECONNECT, RE-FETCH CURRENT STATE OVER HTTP. Do not trust your cache. This is the correctness fix, and the adapter has nothing to do with it. ③ MEMORY AND CONNECTION LIMITS. Each open connection is state on a server. Thousands of them is a capacity question, and file-descriptor limits bite before CPU does. AND THE SECURITY LAYER, WHICH IS SEPARATE AGAIN · authenticate AT THE HANDSHAKE, so no handler ever wonders who is connected · ⚠ the token is checked ONCE — a long-lived socket outlives a fifteen-minute token · ⭐ ROOMS ARE THE AUTHORISATION BOUNDARY, and the server decides membership from the verified identity. Letting a client ask to join `team:9` without a check is the socket version of the wrong-id vulnerability. · `server.emit()` with no room sends to EVERY connected client — in an HR application that is a breach one keyword long.
Topic 11

Realtime progress pipelines

The layer this adds

This is the six-stage report pipeline on the CV, and the claim invites a specific question: how does a multi-stage job report progress honestly, and what happens when stage four of six fails?

The shape that works
  1. The request accepts and returns a handle. A job id, immediately, with status queued. Nothing long-running happens inside the request.
  2. State lives in the database, not in memory. One row per job with a stage, a percentage, a message and a timestamp. Memory does not survive a restart and cannot be read by another instance — and the status endpoint must work even if every worker is down.
  3. Each stage updates the row, then emits. The database write is the source of truth; the socket event is an optimisation. In that order, so a missed event costs nothing.
  4. The client has two paths. Subscribe to events for immediacy, and poll the status endpoint on reconnect or as a fallback. Realtime is the fast path, not the only path.
  5. Stages are checkpointed. Record which stages completed, so a retry resumes rather than restarting — which matters when stage three called a metered API.
  6. Failure is a state, not silence. failed with the stage, a human message and a correlation id. The user should never be left watching a spinner.
Where it goes wrong
  • Progress that lies. Six stages reported as even sixteens when stage four takes 80% of the time. Weight the stages, or report the stage name rather than a fake percentage — a stalled bar at 66% destroys trust faster than no bar.
  • Progress only in memory, so a restart loses it and the user's job appears to vanish.
  • The event as the only channel, so a reconnect leaves a permanently stale UI.
  • An event arriving before the HTTP response that caused it. The client is told about a record it does not yet know exists — handle the not-found case rather than crashing.
  • No terminal state. Jobs that are neither finished nor failed, forever, with nothing reaping them.
  • Emitting the full record over the socket, bypassing the response shaping that keeps a salary out of the payload.
The question you must be able to answer

"Stage four of six fails and the user is watching. Walk me through exactly what they see and what the system does." A strong answer covers the row update, the emitted failure event, the message shown, whether the retry resumes or restarts, whether stage three's side effects are duplicated, and how you would find the cause afterwards.
