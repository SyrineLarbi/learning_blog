Part I

NestJS

The backend framework. Its whole proposition is structure — it decides where code goes so that a team does not have to argue about it.

NestJS 01

The mental model

Four building blocks, and one rule for each
MODULE       a feature's boundary. What it owns, what it needs
             from elsewhere, what it lets others use.
CONTROLLER   ⭐ HTTP ONLY. Reads the request, calls a service,
             returns the result. NO BUSINESS LOGIC.
SERVICE      the business logic. Knows nothing about HTTP — no
             request, no response, no status codes.
             ⇒ so the same service can be called by a controller,
               a scheduled job, a socket gateway or a test.
DTO          the declared, validated shape of incoming data.

⭐ THE ONE-SENTENCE VERSION: THIN CONTROLLERS, FAT SERVICES.
  When you find business rules in a controller, the rule has
  become unreachable from anywhere else and untestable without
  faking a request.

WHY NESTJS RATHER THAN BARE EXPRESS
  Express gives you a router and nothing else, so every team
  invents its own structure — and every codebase is different.
  Nest imposes one:
    · one module per feature, always the same internal shape
    · dependency injection, so units are swappable and testable
    · decorators that put routing and validation next to the code
      they describe
    · cross-cutting concerns (auth, logging, errors) expressed
      once as guards, interceptors and filters
  ⇒ the cost is more ceremony for a two-endpoint service. The
    return is that a codebase of forty modules stays navigable,
    and a new joiner can guess where anything lives.
NestJS 02

Modules

The four keys, and what each one actually does
@Module({
  imports:     [PrismaModule, AuthModule],   // what I need
  controllers: [ReportsController],          // my HTTP surface
  providers:   [ReportsService],             // my injectables
  exports:     [ReportsService],             // what others may use
})
export class ReportsModule {}

⭐ THE PART THAT CONFUSES EVERYONE FIRST WEEK:
  A PROVIDER IS ONLY AVAILABLE WHERE IT IS EXPORTED AND IMPORTED.
  "Nest can't resolve dependencies of ReportsService (?)" almost
  always means: the module holding that dependency did not
  EXPORT it, or this module did not IMPORT that module. The `?`
  in the error marks which constructor position failed.

  ⇒ read the error as a two-part checklist and it stops being
    mysterious.

THE ROOT MODULE
  app.module.ts imports every feature module. That file is the
  fastest map of the application you will find — read it first
  on any unfamiliar Nest codebase.

GLOBAL MODULES
  @Global() makes a provider available everywhere without
  importing. ⚠ convenient, and it hides the dependency graph.
  Justified for a few genuinely universal things — the Prisma
  client, configuration — and a bad habit beyond that.

THIS PROJECT'S MODULES
  auth · users · teams · employees · analytics · reports · audit
  · prisma
  ⭐ one per noun, matching the API surface from Volume I.
    A new feature means a new folder with the same six files —
    copying a pattern rather than inventing one.
NestJS 03

Controllers

Decorators map HTTP onto methods
@Controller('reports')                    // → /api/reports
export class ReportsController {
  constructor(private reports: ReportsService) {}   // injected

  @Get()                                  // GET /api/reports
  findAll(@Query() q: ListReportsDto) {
    return this.reports.findAll(q);
  }

  @Get(':id')                             // GET /api/reports/42
  findOne(@Param('id', ParseIntPipe) id: number) {
    return this.reports.findOne(id);
  }

  @Post()
  @Roles('manager', 'admin')
  @HttpCode(201)
  create(@Body() dto: CreateReportDto, @CurrentUser() user: User) {
    return this.reports.create(dto, user);
  }
}

READING THE PARAMETER DECORATORS
  @Param('id')   from the path
  @Query()       from the query string
  @Body()        from the request body
  @CurrentUser() ⭐ a CUSTOM decorator in this project: it reads
                 the user the JwtAuthGuard attached to the
                 request. Cleaner than @Req() and it keeps
                 controllers free of framework plumbing.

⭐ ParseIntPipe IS NOT COSMETIC. A path parameter arrives as a
  STRING, always. Typing it `: number` does not convert it —
  Volume I, reflex 16: types are erased. Without the pipe you
  have a string labelled as a number, and the comparison against
  a database id silently fails.

⚠ AND THE ONE THAT LOOKS FINE AND IS WRONG:
  return this.prisma.employee.findMany();   // in a CONTROLLER
  it works, and it has put a database query where no job, test or
  socket handler can reuse it. Controllers call services.
NestJS 04

Services

Where the actual application lives
@Injectable()
export class ReportsService {
  constructor(
    private prisma: PrismaService,
    private ai: AiClientService,
  ) {}

  async create(dto: CreateReportDto, user: User) {
    const team = await this.prisma.team.findUnique({
      where: { id: dto.teamId },
    });
    if (!team) throw new NotFoundException('Team not found');

    // ⭐ THE OWNERSHIP CHECK — Volume II, reflex 09.
    // A role said "managers may create reports". This says
    // "…for their own team", and nothing else in the stack
    // enforces it.
    if (team.managerId !== user.id && user.role !== 'admin') {
      throw new ForbiddenException();
    }

    const predictions = await this.ai.predict(team.id);
    return this.prisma.report.create({ data: { … } });
  }
}

⭐ @Injectable() IS WHAT MAKES IT AVAILABLE FOR INJECTION. Omit it
  and Nest cannot construct the class — a confusing startup error
  for a one-line cause.

WHAT BELONGS HERE
  · business rules and ownership checks
  · database access, through Prisma
  · calls to other services, including the AI service
  · throwing the right exception, which the framework turns into
    the right status code (reflex 25)

WHAT DOES NOT
  · reading headers or building responses — that is HTTP, and it
    belongs in the controller or an interceptor
  · anything that makes the service impossible to call from a
    scheduled job

⭐ THE TEST THAT TELLS YOU IT IS RIGHT: could this method be
  called from a cron job with no HTTP request in sight? If not,
  HTTP has leaked into your business logic.
NestJS 05 · print this

The request lifecycle

Six stages, in a fixed order. Knowing it tells you exactly where to put a cross-cutting concern — and where a bug can and cannot be.

INCOMING REQUEST │ ▼ ① MIDDLEWARE runs first, knows nothing about routes │ ⇒ logging, request ids, raw body needs ▼ ② GUARDS may I proceed? → false gives 403 │ ⇒ JwtAuthGuard, then RolesGuard │ ⭐ AUTH BELONGS HERE, before anything │ has touched the payload ▼ ③ INTERCEPTORS (pre) wrap the handler │ ⇒ timing, audit logging, transforms ▼ ④ PIPES transform + validate the arguments │ ⇒ ValidationPipe turns the body into a │ typed DTO, or throws 400 ▼ ⑤ THE HANDLER your controller method → the service │ ▼ ⑥ INTERCEPTORS (post) shape the response on the way out │ ⇒ envelope, serialisation, cache ▼ ⑦ EXCEPTION FILTERS anything thrown anywhere above lands │ here and becomes an HTTP response ▼ RESPONSE ⭐ THE TWO CONSEQUENCES WORTH INTERNALISING GUARDS RUN BEFORE PIPES. So authorisation is decided before the body has been validated. That is deliberate — an unauthenticated caller should never reach your validation logic, let alone your service. It also means a guard cannot rely on a parsed DTO. EVERY THROW ENDS IN ⑦. So a service can throw NotFoundException and simply not think about HTTP. One filter turns the whole application's failures into consistent responses, and no controller needs a try/catch for the ordinary cases. WHERE TO PUT A NEW CONCERN "who is allowed?" → a guard "log every call" → an interceptor "coerce and check input" → a pipe (or the DTO) "make every error look the same" → the exception filter ⇒ if you are writing the same three lines at the top of eleven handlers, one of the four above is the right home.
NestJS 06

Swagger

Documentation that cannot drift

NestJS generates browsable API docs from the code itself — the routes from the decorators, the request and response shapes from the DTO classes. Visit it, and every endpoint is listed with its fields and their validation rules, ready to try.

The point is not convenience, it is truth. A hand-written API document is accurate on the day it is written and wrong within a month. Generated documentation is wrong only when the code is. So the DTOs are simultaneously the validation, the types and the docs — one definition, three jobs, no drift.

Next.js

React plus routing, rendering and a server. The App Router changed the defaults, and most confusion comes from following older guides.

Next.js 07

The App Router

The folder is the URL
app/
├── layout.tsx              wraps EVERYTHING (required, root)
├── page.tsx                        →  /
├── globals.css
├── dashboard/
│   ├── layout.tsx          wraps only this subtree
│   ├── page.tsx                    →  /dashboard
│   ├── loading.tsx         shown while this segment loads
│   └── error.tsx           shown if this segment throws
├── employees/
│   ├── page.tsx                    →  /employees
│   └── [id]/
│       └── page.tsx                →  /employees/42
└── (auth)/                 ⭐ ROUTE GROUP — parentheses mean
    ├── login/page.tsx        this folder does NOT appear in the
    └── register/page.tsx     URL. /login, not /(auth)/login.
                              For sharing a layout across pages
                              that are not nested in the URL.

⭐ ROUTING IS THE FILE SYSTEM. There is no route configuration
  file to keep in step — a folder with a page.tsx in it is a URL,
  and that is the whole mechanism.

DYNAMIC SEGMENTS
  [id]        one segment      → /employees/42
  [...slug]   catch-all        → /docs/a/b/c
  ⇒ the value arrives as a prop, and ⚠ it is a STRING even when
    it looks like a number.

Next.js 09

Rendering modes

THE FOUR, AND HOW TO CHOOSE STATIC (default where possible) rendered at BUILD time, served as a file. ⇒ fastest possible, cacheable at the edge. for: marketing pages, docs — anything identical for everyone. DYNAMIC (server-rendered per request) rendered on the server, per request, with that user's data. ⇒ ⭐ WHAT ALMOST EVERY PAGE IN THIS PROJECT IS, because a dashboard is different for every viewer and must not be cached across them. ISR (static, revalidated on a timer) static, rebuilt every N seconds. ⇒ for content that changes but not per-user. A public league table, not an HR record. CLIENT-RENDERED an empty shell that fetches after load. ⇒ for genuinely interactive surfaces. ⚠ the trade is a blank first paint and no server-side data. ⭐ HOW NEXT DECIDES — AND THE TRAP IN IT it is INFERRED, not declared. Reading cookies, headers or the current user makes a route dynamic automatically. So a page can silently become dynamic — or silently stay static and serve one user's data to another. ⇒ ⚠ ON ANY AUTHENTICATED PAGE, BE EXPLICIT. Do not leave per-user rendering to inference; state it, and know which mode each route is in. THE HYDRATION ERROR YOU WILL EVENTUALLY HIT "Text content did not match server-rendered HTML." the server rendered one thing and the browser rendered another. Nearly always one of: · new Date() or Math.random() in render — different on each side, by definition · reading localStorage or window during the first render — they do not exist on the server · a timezone or locale difference between server and browser ⭐ THE FIX IS NOT TO SUPPRESS THE WARNING. Move the browser-only value into an effect so the first render matches on both sides.
Next.js 10

Data fetching

In a server component, fetching is just await
// app/employees/page.tsx  — a SERVER component
export default async function EmployeesPage() {
  const employees = await api.get('/employees');   // ⭐ no effect,
  return <EmployeeTable rows={employees} />;       //   no useState,
}                                                   //   no loading
                                                    //   flag

⭐ THIS IS THE BIGGEST PRACTICAL CHANGE THE APP ROUTER BROUGHT.
  No useEffect, no loading state, no race conditions, no
  cancellation, no "fetch on mount" — and the data never reaches
  the browser as an intermediate JSON blob. loading.tsx covers
  the wait automatically.

WHERE TO FETCH
  ⭐ AS CLOSE TO WHERE IT IS USED AS POSSIBLE, and in parallel.
  two independent awaits in sequence are two round trips for no
  reason — Promise.all them (Volume I, reflex 14). This matters
  more on a server, where each call may cross a network.

MUTATIONS — SERVER ACTIONS
  a function marked 'use server' that a form or a handler can
  call directly, running on the server. It replaces the
  hand-written POST-then-refetch dance.
  ⚠ AND THE SECURITY POINT PEOPLE MISS: a server action is a
    PUBLIC ENDPOINT. It is reachable by anyone who can craft the
    request, exactly like a REST route.
    ⇒ so it needs the same authentication and authorisation
      checks in its body. "It is only called from that form" is
      not a control.

CACHING
  Next caches aggressively by default, and the defaults have
  changed between major versions. ⭐ FOR PER-USER DATA, BE
  EXPLICIT ABOUT NO-CACHE rather than trusting a default —
  the failure mode is serving one user's data to another, which
  is the worst bug in the catalogue.
Next.js 11

Loading and error states

loading.tsx

Automatic. Drop it into a segment and it appears while that segment resolves — a skeleton that matches the eventual layout beats a spinner, because the page does not jump when data arrives.

error.tsx

Catches throws in its segment. Must be a client component; gets a reset() to retry. Scope matters — one at the root means any error blanks the whole app.

Suspense boundaries

Wrap a slow part so the rest of the page renders immediately. The right answer for "the AI summary panel is slow" — Volume IV's problem, solved here.

The empty state

No framework gives you this. A new tenant sees it before any other state, and it is the best onboarding surface you will get — design it deliberately.

Next.js 12

Environment variables and metadata

The one that leaks secrets

NEXT_PUBLIC_ means "embed this in the browser bundle". The value is baked into the JavaScript at build time and is readable by anyone who opens the page. Not hidden, not obfuscated — published.

So NEXT_PUBLIC_API_URL is correct, and NEXT_PUBLIC_ANTHROPIC_API_KEY would be a disclosed credential. Anything secret has no prefix, is read on the server only, and if the browser needs the result of using it, that call goes through a route handler.

Metadata
export const metadata = {
  title: 'Employees · HR Insight',
  description: 'Team roster and attrition risk',
};

· static export for a fixed page; generateMetadata() when the
  title depends on the data (an employee's name)
· sets the tab title, and what a shared link shows in Slack
⚠ an internal tool still needs this: "localhost:3001" as every
  tab's title makes eleven open tabs unusable, which is a real
  daily cost rather than a polish item.
Part III

FastAPI

The AI service. Small surface, and it will feel familiar — the decorator idea is the same as NestJS.

FastAPI 13

Why it exists here

A whole service in fifteen lines
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="HR Insight AI Service")

class PredictRequest(BaseModel):
    tenure_years: float = Field(ge=0, le=60)
    satisfaction: float = Field(ge=0, le=1)

class PredictResponse(BaseModel):
    risk_score: float
    risk_level: str

@app.post("/predict", response_model=PredictResponse)
def predict(body: PredictRequest) -> PredictResponse:
    score = model.score(body)
    return PredictResponse(risk_score=score,
                           risk_level="high" if score > .5 else "low")

⭐ WHAT YOU GOT FOR FREE FROM THE TYPE HINTS
  · the body PARSED AND VALIDATED — a satisfaction of 1.4 is
    rejected with a 422 and a message naming the field, before
    your function runs
  · the response shape enforced on the way out
  · OpenAPI docs generated and browsable at /docs
  ⇒ the same "one definition, three jobs" property as NestJS
    DTOs, arrived at from the other direction.

⭐ AND THE KEY DIFFERENCE FROM TYPESCRIPT: PYDANTIC VALIDATES AT
  RUNTIME. A TypeScript interface is a compile-time hope
  (Volume I, reflex 16); a Pydantic model actually inspects the
  incoming data. This is why FastAPI is a good choice for a
  service whose input arrives over a network.

FastAPI 15

Async, sync and CORS

The choice that decides whether your service stalls
async def  — for work that WAITS on something (a network call,
             another API). Frees the loop to serve other requests
             while waiting.
def        — for work that COMPUTES. FastAPI runs it in a thread
             pool so it does not block the event loop.

⭐ THE MISTAKE THAT MATTERS, AND IT IS SPECIFIC:
  putting BLOCKING work inside an `async def`.

    @app.post("/predict")
    async def predict(body):
        score = model.predict(...)   # ⚠ CPU-bound, blocking

  a model inference in an async handler blocks the ENTIRE event
  loop. Every other request waits — the service appears to hang
  under any concurrency at all, and the symptom is dramatic.
  ⇒ for CPU-bound inference, use a plain `def` and let FastAPI
    put it on a thread. This one decision is the difference
    between a service that scales and one that stalls.

CORS — same rule as Volume II, other side of the wire
  the browser blocks cross-origin reads unless the server
  permits the origin. In this project the FRONTEND does not call
  the AI service at all, so its CORS list should be narrow or
  empty — only the backend calls it, and backend-to-backend
  calls are not subject to CORS.
  ⚠ allow_origins=["*"] is a development shortcut that keeps
    shipping to production. Name the origins.

ERRORS
  raise HTTPException(status_code=422, detail="…")
  the same discipline as NestJS: raise, and let the framework
  turn it into a response. And the same rule as everywhere — a
  4xx for the caller's fault, a 5xx for yours.

Why this comparison is worth reading

The two frameworks are the same ideas in two languages: declare the route next to the handler, declare the input shape as a class, validate at runtime, generate the docs from both, inject what the handler needs.

Which means the concepts transfer completely and only the spelling changes. That is the fastest route into the AI service for someone who has learned the backend.

Part IV

Ant Design

The component library the interface is built from. This project uses antd, not Tailwind — components, not utility classes.

antd 17

Why a component library

What you are actually buying
NOT "buttons you did not have to style". What you are buying is
the part that takes months to get right:

  · KEYBOARD NAVIGATION and focus management in a modal, a
    dropdown, a date picker
  · ARIA roles and screen-reader behaviour
  · form state, validation display and error association
  · a table with sorting, filtering, pagination and fixed columns
  · consistent spacing and type across sixty screens by default
  · every one of the above tested across browsers

⭐ THE HONEST TRADE
  ✅ enormous head start; internal tools look coherent for free;
     accessibility you would not otherwise ship
  ⚠ a large bundle; a distinctive visual identity that is
     recognisable as antd; and fighting a component that is 90%
     what you want is genuinely worse than building the last 10%
     yourself.

  ⇒ for an internal HR dashboard this trade is clearly right.
    For a public marketing site it clearly is not. Knowing which
    kind of product you are on is the whole decision.

⚠ AND ONE PROJECT-SPECIFIC RULE: THIS PROJECT USES antd, NOT
  TAILWIND. Mixing a utility-CSS system into a component library
  produces two competing sources of spacing and colour, and the
  result is inconsistent in a way nobody can fix later. Use
  antd's tokens and its layout components.
antd 18

Layout and navigation

THE STANDARD ADMIN SHELL — and it is standard for a reason ┌─────────────────────────────────────────────────┐ │ Layout.Header logo · user menu │ ├──────────┬──────────────────────────────────────┤ │ │ Breadcrumb │ │ Sider │ ┌────────────────────────────────┐ │ │ + Menu │ │ Layout.Content │ │ │ │ │ Card / Table / Form │ │ │ │ └────────────────────────────────┘ │ └──────────┴──────────────────────────────────────┘ Layout · Header · Sider · Content · Footer the frame. Put it in a Next.js layout.tsx so it does not re-render on navigation (Volume III, reflex 08) — that is what keeps the sidebar's scroll position and open sections. Menu ⚠ THE MISTAKE: not syncing selectedKeys with the current route. The sidebar then highlights the wrong item after a browser back or a direct link — a small bug that makes an app feel broken. Drive it from the pathname, always. Grid — Row and Col, on a 24-column grid <Col xs={24} md={12} xl={8}> — 24 means full width on phones, 12 means half on tablets. ⭐ 24, not 12, which surprises people coming from Bootstrap. Space and Flex ⭐ USE THESE INSTEAD OF MARGINS. Consistent gaps from one system, and no collapsing-margin surprises — the same "let layout do the spacing" rule that applies anywhere.
antd 19

Tables

The component you will spend the most time in
<Table
  rowKey="id"                    ⭐ NOT optional. Volume II,
  columns={columns}                 reflex 20 — without a stable
  dataSource={employees}            key, selection and expansion
  loading={isLoading}               attach to the wrong rows
  pagination={{ current, pageSize, total, onChange }}
/>

COLUMNS ARE DATA, NOT MARKUP
  { title: 'Name', dataIndex: 'name', key: 'name', sorter: true }
  { title: 'Risk', dataIndex: 'risk',
    render: (v) => <Tag color={v > .5 ? 'red' : 'green'}>{v}</Tag> }

  ⇒ so columns can be built from configuration — which is how you
    show a salary column to HR and omit it for a team lead. ⭐ AND
    THE SERVER MUST STILL OMIT THE FIELD: a column you did not
    render is still in the payload (Volume II, reflex 09).

⭐ CLIENT-SIDE VS SERVER-SIDE — THE DECISION THAT BITES LATER
  antd will sort, filter and paginate in the browser, on whatever
  array you passed. Delightful for 200 rows. For 50,000 it means
  downloading 50,000 rows to show ten.
  ⇒ past a few hundred rows, move sorting, filtering and paging
    to the API and pass `total` in explicitly. Retrofitting this
    means changing every call site, so decide at the start.

⚠ AND THE ONE THAT LOOKS LIKE A FRAMEWORK BUG: rebuilding the
  columns array on every render re-renders the whole table.
  Define it outside the component, or memoise it.
antd 20

Forms

Form.Item does more than it looks
<Form form={form} layout="vertical" onFinish={submit}>
  <Form.Item name="email" label="Email"
             rules={[{ required: true }, { type: 'email' }]}>
    <Input />
  </Form.Item>
  <Button type="primary" htmlType="submit" loading={saving}>
    Save
  </Button>
</Form>

⭐ Form.Item OWNS THE FIELD'S STATE. You do not write value and
  onChange (Volume II, reflex 21) — antd wires the child input
  and manages the value, the touched state and the error display,
  including associating the error text with the input for screen
  readers.

  ⇒ so ⚠ DO NOT put your own value/onChange on an Input inside a
    Form.Item. You then have two owners of one value and the
    field behaves erratically.

VALIDATION — and the rule from Volume II, restated because it is
the one people skip
  ⭐ THESE RULES ARE FEEDBACK, NOT SECURITY. They run in a browser
    the user controls. The DTO on the backend is what actually
    protects the system, and it must repeat every rule that
    matters. A request does not have to come from your form.

  ⇒ where a rule exists in both places, that duplication is
    deliberate and correct: one for the human, one for the
    system.

SUBMISSION
  · `loading` on the button while saving — prevents the
    double-click that creates two records
  · show the server's field errors back on the fields with
    form.setFields, rather than as a toast that loses the
    connection to the input
  · keep what the user typed on failure

Theming

Tokens, not overrides
<ConfigProvider theme={{
  token: { colorPrimary: '#0E6A6A', borderRadius: 4 },
  components: { Table: { headerBg: '…' } },
}}>

⭐ CHANGE THE TOKEN, NOT THE COMPONENT'S CSS. A token propagates
  to every component that derives from it — hover states, focus
  rings, disabled variants, the shades antd computes from your
  primary colour. Overriding one component's class fixes one
  place and leaves eleven derived states inconsistent.

⚠ AND OVERRIDES BREAK ON UPGRADE. Internal class names are not a
  public API; a minor version can rename them, and your styling
  silently stops applying.

DARK MODE
  antd ships an algorithm — theme.darkAlgorithm — rather than
  asking you to redefine every colour. Set it from the user's
  preference and let the tokens cascade.

⭐ THE PRINCIPLE, WHICH IS THE SAME ONE AS EVERYWHERE IN THIS
  HANDBOOK: one definition, derived everywhere. A colour written
  in two places is a promise to update both, and that promise is
  always broken.
Part V

The four patterns

These repeat in every module. Learn them once and every unfamiliar file becomes predictable.

Pattern 23

Dependency injection

THE PROBLEM — TIGHT COUPLING class ReportsService { constructor() { this.prisma = new PrismaClient(); // ⚠ built its own this.ai = new AiClient('http://…:8000'); // ⚠ and its own } } what this costs you: · you CANNOT TEST IT without a real database and a running AI service · the URL is buried in a class that should not know it · every service builds its own connection, so you have twenty database clients instead of one · swapping the AI client for a fake, or for a different provider, means editing this file THE FIX — ASK FOR WHAT YOU NEED @Injectable() class ReportsService { constructor( private prisma: PrismaService, private ai: AiClientService, ) {} } ⭐ THE CLASS NO LONGER DECIDES WHERE ITS DEPENDENCIES COME FROM. It declares what it needs; something else supplies them. That inversion is the entire idea, and the "IoC container" is just the thing doing the supplying. WHAT YOU GET TESTABILITY pass fakes in the constructor. No database, no network, no framework — a unit test that runs in milliseconds. ONE INSTANCE ⭐ providers are SINGLETONS by default. One Prisma client, one connection pool, shared. This is why you never call `new PrismaClient()` in a service. SWAPPABILITY the module decides the implementation, so changing it is one line in one place. HOW NEST KNOWS WHAT TO INJECT from the TypeScript types on the constructor parameters, via decorator metadata. ⭐ WHICH IS WHY @Injectable() IS REQUIRED — it is what makes that metadata get emitted. ⇒ and it is why a missing @Injectable() or a not-exported provider produces "cannot resolve dependencies (?)" — the container has nothing to look up. FASTAPI DOES THE SAME THING DIFFERENTLY def endpoint(db = Depends(get_db)) — declared in the signature rather than the constructor. Same principle: the function asks, the framework provides.
Pattern 24

DTOs and validation

Never trust incoming data
export class CreateEmployeeDto {
  @IsString() @Length(2, 100)
  name: string;

  @IsEmail()
  email: string;

  @IsInt() @Min(0) @Max(60)
  tenureYears: number;

  @IsOptional() @IsInt()
  managerId?: number;
}

⭐ WHY A CLASS AND NOT AN INTERFACE: an interface is erased at
  compile time (Volume I, reflex 16) and cannot validate
  anything. A class exists at runtime and can carry decorators
  that actually inspect the incoming object.

THE PIPE MAKES IT AUTOMATIC
  registered once, globally:
    app.useGlobalPipes(new ValidationPipe({
      whitelist: true,             ⭐ STRIP unknown properties
      forbidNonWhitelisted: true,  ⭐ or reject them outright
      transform: true,             turn the plain object into the
                                   DTO class instance
    }));

  ⭐ `whitelist` IS A SECURITY CONTROL, not tidiness. Without it,
    a caller can post extra fields — `role: 'admin'`,
    `isApproved: true` — and if any code later spreads that body
    into a database write, they have escalated their own
    privileges. This is called mass assignment, and stripping
    unknown keys removes the whole class of it.

UPDATE DTOs
  export class UpdateEmployeeDto extends PartialType(CreateEmployeeDto) {}
  ⇒ every field optional, every rule preserved. One definition
    (Volume I, reflex 20 — derive types, do not duplicate them).

⭐ THE THREE JOBS ONE DTO DOES
  ① validates the request at runtime
  ② provides the TypeScript type for the controller and service
  ③ generates the Swagger documentation
  ⇒ which is why a DTO is worth writing even for two fields, and
    why the three can never disagree.

⚠ AND THE BOUNDARY RULE: a DTO is for data ENTERING the system.
  Do not reuse it as a response type — a response needs the
  opposite shaping (omitting fields the caller may not see), and
  conflating the two is how a salary ends up in a payload.
Pattern 25

Error handling

Throw the right thing; let one place turn it into a response
IN A SERVICE — throw a semantic exception
  throw new NotFoundException('Employee not found');   → 404
  throw new ForbiddenException();                      → 403
  throw new ConflictException('Email already exists');  → 409
  throw new BadRequestException('…');                   → 400

⭐ THE SERVICE NEVER TOUCHES A RESPONSE OBJECT. It throws a
  meaning; the framework maps it to a status. That is what keeps
  the service callable from a job or a socket handler.

THE FOUR CLASSES, AND THE RIGHT RESPONSE TO EACH
  THE CALLER'S FAULT   4xx. Reject and explain precisely. Never
                       retry — it will fail identically forever.
  TEMPORARY            retry with backoff, a cap and jitter.
                       ⚠ retrying instantly and forever is how
                       one slow service takes down four.
  PERMANENT, OURS      fail loudly. ⭐ AN ERROR CAUGHT AND LOGGED
                       AT `info` IS A BUG YOU WILL FIND IN SIX
                       MONTHS VIA A CUSTOMER.
  DEGRADED             continue without the optional part, and
                       tell the user what is missing. The AI
                       service being down should not blank a page.

THE GLOBAL FILTER — one shape for every failure
  · a machine-readable code, a human message, the field at fault
  · a correlation id, logged with the full detail
  ⭐ RETURN THE ID, LOG THE STACK. A stack trace or SQL fragment
    in a user-facing message is a security finding, not a
    debugging convenience. "Error ref 8f2c1a" lets support find
    everything without disclosing anything.

⚠ THE THREE HABITS THAT CAUSE REAL DAMAGE
  · catching everything and continuing — turns a loud failure
    into silent wrong data, the most expensive kind
  · swallowing an error in an interceptor without re-throwing —
    every caller's catch stops running (Volume II, reflex 25)
  · logging and re-throwing at every level, so one failure
    produces nine log entries and nobody can find the cause

Volume III · the vocabulary of this codebase
module
A feature's boundary in NestJS: what it owns, imports and exports.
controller
The HTTP surface. Reads the request, calls a service, returns. No logic.
service
The business logic, with no knowledge of HTTP.
provider
Anything injectable. A singleton by default.
pipe
Transforms and validates a handler's arguments — where the DTO is enforced.
interceptor
Wraps the handler, before and after. Logging, audit, response shaping.
exception filter
The one place every thrown error becomes an HTTP response.
DTO
A class declaring and validating the shape of incoming data.
mass assignment
Accepting unknown fields from a request body — the reason whitelist exists.

The thing that constructs your classes and supplies their dependencies.

Next.js routing where the folder structure is the URL.

A (folder) that shares a layout without appearing in the URL.
server action
A server-side function callable from the client. A public endpoint — it needs its own auth checks.

Static rendering revalidated on a timer.
hydration error
Server-rendered HTML disagreeing with the browser's first render.

Python models that validate at runtime — FastAPI's DTO equivalent.

FastAPI's dependency injection, declared in the signature.
token (antd)

Where antd's theme tokens are set, once, near the root.
