Topic 23 · SAML at zero, Okta at one line

OIDC, SAML and Okta SSO

⭐ THE DISTINCTION TO GET RIGHT FIRST OAuth 2.0 is AUTHORISATION — "this app may act on your behalf". It says nothing about who you are. OIDC is AUTHENTICATION built on top of OAuth — it adds the ID TOKEN, which is a JWT describing the user. SAML is authentication too, but older: XML assertions, browser POST redirects, no JSON. ⇒ SO "WE USE OAUTH TO LOG IN" IS IMPRECISE, and being precise here is a small, reliable senior signal. THE OIDC AUTHORISATION-CODE FLOW, WHICH IS THE ONE YOU USE browser ──1──► your app: "log in" ◄─2─── redirect to Okta with client_id, scope, redirect_uri, state, PKCE challenge browser ──3──► Okta: authenticates the user ◄─4─── redirect back with a CODE (not a token) your app ─5──► Okta token endpoint: code + client_secret + PKCE verifier ◄─6─── ID token + access token (+ refresh token) your app ──7─► VALIDATE the ID token, then issue YOUR OWN session ⭐ THE FIVE VALIDATIONS PEOPLE SKIP AT STEP 7 · the SIGNATURE, against the provider's published keys (fetched from JWKS and cached, not hardcoded) · `iss` — the issuer is who you expect · `aud` — the token was issued FOR your client · `exp` / `iat` — not expired, not from the future · `nonce` — matches the one you sent ⚠ AND `state` IS CHECKED AT STEP 4, BEFORE ANY OF THIS — it is the CSRF defence for the flow itself. ⇒ A LIBRARY DOES ALL OF THIS. Writing it yourself is where people introduce real vulnerabilities. WHY PKCE, AND WHY IT IS NOW UNIVERSAL it binds the code to the client that requested it, so an intercepted code is useless. Originally for mobile apps with no secret; ⭐ NOW RECOMMENDED EVERYWHERE. SAML, IN THE DETAIL THAT MATTERS · XML assertions signed by the identity provider, delivered by a browser POST to your ACS endpoint · you validate the signature, the audience, the recipient, and the NotBefore/NotOnOrAfter window · ⭐ XML SIGNATURE WRAPPING IS A REAL ATTACK CLASS — which is the strongest possible argument for using a maintained library rather than parsing it yourself · ⇒ WHY IT STILL EXISTS: large enterprises standardised on it, and enterprise HR buyers will ask for it. That is the honest reason to know it. ⚠ AND THE THREE THINGS SSO DOES NOT GIVE YOU ① AUTHORISATION. The provider says who they are; your app still decides what they may do. ⭐ Group claims are a convenience, not a permission model. ② DEPROVISIONING. Someone removed in Okta still holds your session until it expires — unless you check status, use short sessions, or implement SCIM. ③ A SESSION MODEL. You still issue and manage your own.
Topic 24

Authorisation beyond roles

The layer this adds

Four-role RBAC is the CV claim. The layer underneath is that roles cannot express the rules an HR system actually needs — and the interesting engineering is where you put the rules that roles cannot hold.

The three layers, and why all three are needed
  • Role (RBAC). "Managers may generate reports." Coarse, declarative, readable on the endpoint. And insufficient alone — it does not say whose reports.
  • Relationship / ownership (ReBAC). "…for their own team." This needs the resource, so it lives in the service. This is the check people forget, and its absence is the most common real vulnerability in business software.
  • Attribute (ABAC) and field-level. "…and not the salary column, unless they are HR." Salary, sickness and a disciplinary note have completely different audiences on one record.

Where to enforce it — in ascending strength: a repeated if in each handler (drifts) → a guard (one place, but no resource) → a service-layer check (has the resource) → a query-level filter every read passes through → a database policy. The fourth is the sweet spot for this stack: a Prisma extension or a scoped helper that injects the tenant and scope filter, so forgetting becomes impossible rather than merely discouraged.

Where it goes wrong
  • Trusting a group claim from the identity provider as the permission decision, so changing a group in Okta silently changes what your app permits.
  • Authorising in the controller only, so a job, a socket handler or a script bypasses it entirely.
  • Filtering in the UI — the payload still contains the field, and the network tab does not respect your table configuration.
  • Row filters without the aggregate case: a scoped list is filtered, but a COUNT or an average silently includes rows the caller cannot see, leaking information through a number.
  • No deny path or delegation model, so covering leave and temporary access get done by sharing accounts.
The question you must be able to answer

"A manager requests /employees/4821, who is not on their team. Walk me through every layer that stops it — and tell me which layer would still stop it if a new endpoint were written on a Friday afternoon." Only the query-level filter survives that second question.

Topic 25 · asserted but never designed

Audit logging by design

The layer this adds

The existing docs assert that audit logging exists and never design it. In an HR system it is a compliance requirement, an incident-response tool, and the answer to "who looked at my record?" — and it has to be designed, because bolting it on later produces gaps you cannot fill retrospectively.

The design
  • Log reads, not just writes. The unusual and essential part. "Who viewed this employee's record" is the question an employee is entitled to ask, and most systems cannot answer it because they only logged mutations.
  • One row per event, and the fields that make it useful: who (the authenticated user, not the display name), what action, which resource and id, when, from where, the outcome, and a correlation id so an audit entry joins to the request trace.
  • Append-only. No updates, no deletes, enforced by permissions rather than convention — an audit log a compromised application account can rewrite is not an audit log.
  • Separate from application logs. Different retention, different access, different purpose. Application logs are debugging; the audit log is evidence.
  • Write it in the same transaction as the action where the action is a write, so you cannot have one without the other. For reads, write it on the read path — which is why an interceptor is the right home.
  • Make it queryable by subject — by the employee whose data it was, not only by the actor. That is the shape a subject-access request needs.
Where it goes wrong
  • Logging the payload. An audit entry containing the salary it recorded becomes a second copy of the sensitive data, with weaker access control. Log the fields that changed, not the values — or store values separately with the same protection as the source.
  • Best-effort writes that fail silently, so the gaps are invisible.
  • Unbounded retention with no policy, which is both a cost and a liability — and it collides with erasure obligations.
  • An audit log nobody ever reads or tests. Query it during development, or you will discover at the worst moment that the field you need was never captured.
  • Forgetting that erasure must reach it — or deciding deliberately that it must not, and being able to justify that.
The question you must be able to answer

"An employee asks who has viewed their record in the last year. Can you answer, and how long would it take?" — if the answer is no, that is a designed limitation you should be able to state rather than a surprise.

Topic 26

Document storage and uploads

Both directions, and the one that gets people
UPLOADS — the checks, in order
  □  SIZE CAP, enforced before you buffer anything
  □  CONTENT TYPE FROM THE BYTES, not the extension and not
     the client-supplied header
  □  ⭐ NEVER TRUST THE FILENAME. `../../etc/passwd` is path
     traversal; generate your own storage key and keep the
     original name as metadata only.
  □  STORE OUTSIDE THE WEB ROOT — object storage, not a served
     directory
  □  SCAN, or at minimum never serve it back with a content
     type that lets a browser execute it
  □  ⭐ PRESIGNED DIRECT UPLOAD keeps large files out of your
     application entirely — your backend authorises and issues
     a short-lived URL, the browser uploads straight to
     storage. Fewer bytes through your server, and no memory
     spike.
  □  STREAM, never buffer. Ignoring backpressure on a large
     upload is an out-of-memory crash under concurrency.

DOWNLOADS — ⭐ AND THIS IS THE ONE THAT MATTERS
  A LINK IS A CREDENTIAL.
  a URL carries no identity. Whoever holds the string holds the
  file — and it will be pasted into chat, forwarded, and left
  in a browser history, an email thread and a proxy log. If the
  key is predictable, the other records are reachable by
  editing it.
  ⚠ AND YOUR PERMISSION SYSTEM IS NO LONGER INVOLVED IN ANY OF
    THIS.

  ⇒ IN ORDER OF PREFERENCE
    ①  ⭐ DON'T PRODUCE A FILE. Render it in the app, behind the
       session, where the check runs on every view. The
       strongest answer, and the one nobody proposes.
    ②  SERVE THROUGH AN AUTHENTICATED ENDPOINT — the request is
       checked against the caller every time, and the object is
       never publicly addressable.
    ③  A PRESIGNED URL with a SHORT expiry, an UNGUESSABLE key,
       single-use where the storage supports it, and delivered
       to the verified account rather than returned in the page.

  AND REGARDLESS
    · the generated file has a LIFETIME and gets deleted. ⚠ A
      bucket of HR PDFs with no expiry is a breach waiting for
      an audit.
    · every generation is AUDITED: who, which employee, which
      fields, when.
    · ⭐ THE FILE ITSELF SAYS WHO IT WAS GENERATED FOR AND WHEN,
      so a copy found later is traceable.

⚠ AND THE SIZE PROBLEM: a twenty-year employee record with
  attachments is not a new joiner's. ⭐ BUILD IT AS A JOB FROM
  THE START — not because it is slow today, but because what
  decides its size is outside your control and only grows.

Fourteen one-sentence answers to have ready
□  OAuth is authorisation; OIDC adds authentication via an ID
   token; SAML is the XML predecessor
□  the authorisation-code flow returns a CODE, not a token
□  `state` defends the flow; `nonce` binds the ID token
□  PKCE binds the code to the requesting client — use it
   everywhere
□  validate signature, iss, aud, exp and nonce — via a library
□  ⭐ SSO gives you identity, not authorisation, and not
   deprovisioning
□  a role says what; ownership says whose; attributes say
   which fields
□  ⭐ only a query-level filter survives a new endpoint written
   on a Friday

□  audit logs must cover READS in an HR system

   subject
