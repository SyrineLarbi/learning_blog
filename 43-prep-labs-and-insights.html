The labs

How to run one

The rule that makes labs worth doing

Produce the artefact. A lab you read and imagined solving has taught you nothing you can defend — and the whole point of this curriculum is defensibility. The artefact is the query plan, the running service, the passing suite, the memo.

And for each one, write down the same four things: what the before number was, what you changed, what the after number was, and what you tried that did not work. That is the narrative structure every deep-dive question wants, and it only exists if you record it while doing the work.

Lab 01 · foundational

Reproduce and fix a 50-second query

The task

Build a dataset large enough for a naive report query to take tens of seconds, then fix it — and record the investigation properly, because this lab is what turns the CV's headline number into a method you can narrate.

The order that teaches the most
  1. Count the queries first. Query logging with a count, before reading any SQL. If one request issues 1,400 queries, that is the finding and no plan analysis is needed.
  2. Then EXPLAIN ANALYZE the worst single query — sequential scan, estimated versus actual rows, join strategy, whether a sort spilled to disk.
  3. Fix one thing. Re-measure under identical conditions. Repeat.
  4. Add an index that is not used, deliberately, so you learn why: a function on the column, or a non-leftmost prefix.
The artefact

The before and after plans, saved. A committed benchmark script with its conditions in a comment. And four sentences: the bottleneck, the method, the failed attempt, and how a regression would be noticed.

Lab 02 · intermediate

Build a six-stage realtime pipeline

The task

A long job that reports progress across six stages, survives a restart, and fails informatively at stage four.

What it must demonstrate
  • Progress state in the database, not in memory — the status endpoint must work with every worker down.
  • The database write first, the socket event second, so a missed event costs nothing.
  • Two client paths: subscribe for immediacy, poll on reconnect.
  • Checkpointed stages, so a retry resumes rather than restarting a metered call.
  • Weighted progress, or stage names instead of a percentage — a bar stuck at 66% destroys trust faster than no bar.
The test that proves it

Kill the worker mid-run. The user should see a clear state, the job should resume or fail honestly, and stage three's side effects must not duplicate.

Lab 03 · advanced

Query-level RBAC with Prisma extensions

The task

Move the scope filter from "every service remembers it" to a layer every read passes through, so a new endpoint written on a Friday is safe by construction.

What it must demonstrate
  • A client extension or scoped helper that injects the tenant and scope filter from the verified session.
  • The aggregate case: a scoped list is easy; a COUNT or an average that silently includes invisible rows leaks information through a number.
  • Field-level shaping — the response type omits salary for callers who may not see it.
  • A test that writes a new endpoint without any explicit check and proves it is still scoped.
The artefact

That last test. It is the one that demonstrates the difference between a convention and a mechanism, and it is the thing worth showing.

Lab 04 · intermediate

Okta OIDC integration

The task

A full authorisation-code flow with PKCE against a real identity provider, ending in your own session rather than the provider's token.

What it must demonstrate
  • The state check before anything else, and the nonce bound to the ID token.
  • All five validations on the ID token — signature against fetched JWKS, issuer, audience, expiry, nonce — via a library.
  • Your own session issued afterwards, because SSO gives identity and not a session model.
  • The deprovisioning gap made concrete: disable the user in Okta and observe that your session still works. Then decide what to do about it, and write down the decision.
The artefact

A working flow, plus a one-paragraph note on the deprovisioning window and which mitigation you chose. That note is worth more in an interview than the working flow.

Lab 05 · intermediate

A BullMQ pipeline with retries and a dead-letter queue

The task

A job pipeline that handles transient failure correctly and permanent failure visibly.

What it must demonstrate
  • Exponential backoff with a cap and jitter, and a distinction between retryable and non-retryable failures.
  • An idempotent handler, proven by running the same job twice and asserting the effect happened once.
  • A dead-letter path with an alert on its depth.
  • A concurrency cap chosen from the database pool size, not from a default — and the arithmetic written down.
  • An id in the payload rather than the payload itself.
The test that proves it

Force a stall, let the job be redelivered, and assert no duplicate side effect. That is the only proof of idempotency that counts.

Lab 06 · advanced

Deploy three services to Kubernetes

The task

The full topology on a local cluster: manifests, ingress, TLS, config and secrets, probes and a rolling update.

What it must demonstrate
  • Resource requests and limits on every deployment, with a stated reason.
  • Liveness and readiness as separate probes — and readiness that checks the model is loaded for the AI service, but does not check the AI service from the backend.
  • A rolling update performed while a request is in flight, and a graceful shutdown that does not drop it.
  • Ingress with path routing, TLS, and a WebSocket upgrade that survives longer than sixty seconds.
  • An HPA that does nothing useful on CPU, deliberately, then a note on what metric would work.
The artefact

The manifests, and a paragraph on why this project does not need Kubernetes in production. Being able to argue against the tool you just demonstrated is the senior half.

Lab 07 · intermediate

A Playwright and Cucumber suite from zero

The task

An end-to-end suite covering one real journey, with the flakiness engineered out rather than tolerated.

What it must demonstrate
  • Role- and text-based locators, auto-waiting, and no explicit sleeps anywhere.
  • Storage state reused so login happens once.
  • Network interception to force the provider-down path — the otherwise untestable case.
  • State set up through the API, asserted through the UI.
  • Gherkin scenarios written in domain language, not UI language — and an honest note on whether anyone outside the team will read them.
  • A frozen clock and per-test data isolation, then the suite run in parallel to prove it.
The artefact

A trace from a deliberately failed run. Being able to show that you can diagnose a CI-only failure is the point of the tool.

Lab 08 · advanced

Server-side PDF rendering

The task

Generate a document server-side and deliver it safely — which is the export design problem made concrete.

What it must demonstrate
  • Headless rendering in a job, not in a request, because the size is outside your control.
  • Streaming, not buffering — then test it with a large record and watch memory.
  • Content assembled per requester, so a caller who may not see salary gets a document without it.
  • Delivery through an authenticated endpoint, or a short-expiry presigned URL with an unguessable key delivered to the verified account.
  • A lifetime on the file, an audit row per generation, and provenance printed in the document itself.
The artefact

The delivery decision, written down with its alternatives. "A link is a credential" is the sentence this lab exists to earn you.

Lab 09 · advanced

An XGBoost attrition model end to end

The task

From raw data to a served prediction, with the four things that actually get asked about done properly.

What it must demonstrate
  • A baseline first — a rule — measured, so the model has something to beat.
  • The point-in-time test applied to every feature, and at least one deliberate leak introduced and then caught by noticing absurd feature importance.
  • Split before fitting any transformation, and a time-based split rather than random.
  • PR-AUC and precision at k, not accuracy — and per-subgroup evaluation.
  • A threshold derived from a cost matrix, with the resulting numbers expressed in people.
  • The whole fitted pipeline saved with its data version, library versions and metrics; served from a plain def with the model loaded once.
The artefact

A one-page memo: the decision it changes, the baseline, the metric, the threshold reasoning, the false-positive reality, and what could make it wrong.

Lab 10 · advanced

An LLM report generator with caching and evals

The task

Generate a report where every number is computed elsewhere, with caching for cost and an eval set for change safety.

What it must demonstrate
  • Numbers computed in SQL, passed into the prompt as data. The model narrates and never calculates.
  • Prompt caching verified by reading the cache-read token count, not assumed — with a frozen system prompt and per-request values at the end.
  • Streaming, and a short-output instruction as a measured latency control.
  • A twenty-case eval set with programmatic checks, run before and after a prompt change so the score moves visibly.
  • An adapter interface, and a pinned model version.
  • A cost figure per report, and the monthly total at ten times current volume.
The artefact

The eval score before and after one prompt change, plus the cost number. Almost nobody brings either to an interview.

Lab 11 · advanced

An analytics layer from OLTP to dashboard

The task

Take the application database and build a reporting layer on top, without the reporting queries hurting the application.

What it must demonstrate
  • A layered shape — raw, staged, marts — with each layer having one job and the raw layer never modified.
  • A metric defined once in the intermediate layer: numerator, denominator, window, timezone, inclusions, grain. Then two dashboards built from it that cannot disagree.
  • A cohort and a funnel query, with the incomplete-period trap handled explicitly.
  • Row-level security in the dashboard, and a minimum cell size on every aggregate.
  • An idempotent refresh, so re-running it changes nothing the second time.
  • A reconciliation against the application database, by count and by value.
The artefact

The metric definition document. It is the deliverable that prevents the most common analytics failure — two numbers, no arbiter.

Lab 12 · the capstone

Rebuild the whole system from a blank folder

The one that consolidates everything

Three services, a database, auth, realtime, a model, a report generator, tests and a deployment — from nothing. Not to produce a better version of the product, but to find out which of the previous nine volumes you actually absorbed, because every decision you cannot make quickly is a gap.

Do it in thin vertical slices: one login, one employee list, one prediction, one report. Ship each slice end to end before starting the next — the same discipline the design volumes argue for, applied to yourself.

The decision log to keep while doing it — this is the real output

Part II

Field insights

Ten practitioners, each compressed to the one idea that changes how you work — and the specific place it applies in this stack.

F01 · Rich Hickey

Simple made easy

The idea

Simple and easy are different words. Simple means not intertwined — one concept, one role. Easy means familiar and near to hand. Most complexity is chosen because it was easy, and then it is permanent.

Where it applies here
  • A service that handles HTTP and business rules and data access is complected — easy to write, hard to change. The three cuts in the reasoning volumes are un-complecting moves.
  • An ORM is easy. Understanding what SQL it emits keeps it simple.
  • The test: can you change one thing without understanding the others? If not, they are intertwined regardless of how tidy the code looks.
F02 · Martin Kleppmann

Data-intensive thinking

The idea

Every data system is a set of trade-offs between reliability, scalability and maintainability — and the interesting engineering is naming which one you traded.

Where it applies here
  • A read replica buys read capacity and costs read-your-writes. A cache buys speed and costs staleness. Neither is free, and saying so is the skill.
  • "Exactly once" is not a thing you get; at-least-once plus idempotency is what you build. That single reframing fixes most queue designs.
  • Derived data — a search index, a cache, a mart — is a second copy with its own consistency problem, and it must be treated as such.
F03 · Markus Winand

Indexes are not a magic switch

The idea

An index is a sorted structure, and everything about its behaviour follows from that. "We added an index and it did not help" is nearly always a consequence of sorted order rather than a mystery.

Where it applies here
  • A composite index serves a left-to-right prefix — like a phone book sorted by surname then first name, which cannot find everyone called Alice.
  • A function on the column, or a leading wildcard, defeats it entirely.
  • An index can also serve ORDER BY, which is what turns a paged query from a sort of the whole table into a read of twenty rows.
  • And the cost side: every write updates every index, so an unused index is pure overhead.
F04 · Charity Majors

Observability, not monitoring

The idea

Monitoring answers questions you knew to ask. Observability is being able to answer questions you did not anticipate — which is what a real incident consists of.

Where it applies here
  • High-cardinality context is the point: log the user id, the tenant, the request id, the version — so you can ask "what was different about the failures?" rather than only "how many were there?"
  • "Is it up?" is the least interesting question. "Which users are having a bad time, and what do they have in common?" is the one that resolves incidents.
  • And the discipline point: you cannot add this during an incident. The answer to "what happened at 02:14" exists only if it was being recorded at 02:14.
F05 · Kent Beck

Tidy first

The idea

Separate structural change from behavioural change, and do the small tidying first — in its own commit — so the behavioural change that follows is reviewable.

Where it applies here
  • A pull request mixing a rename with a bug fix is neither reviewable nor revertable. Two commits, and both become both.
  • Tidy the area you are about to work in, not the whole codebase — which is also the only debt-repayment strategy that reliably works.
  • And the economic framing: tidying is an investment in the next change, so it is justified by how often that area changes — which is a measurable argument rather than an aesthetic one.
F06 · Kelsey Hightower

Kubernetes pragmatism

The idea

Most teams do not need Kubernetes, and the person best placed to say so is someone who understands it. It is a platform you operate, and its real cost is ongoing expertise.

Where it applies here
  • Three services and one database do not justify it. A managed container platform gives you rolling deploys, TLS and scaling without a cluster to run.
  • Learn the manifests anyway, because enterprises run it and you will be asked — and because being able to argue against a tool you understand is a stronger position than never having learned it.
  • The general form: adopt the property you need, not the platform's name.
F07 · Dan Abramov

The server–client boundary

The idea

The boundary is a first-class design decision, not an implementation detail. Deciding what runs where determines what ships to the browser, what can be trusted, and what the user waits for.

Where it applies here
  • Server by default, 'use client' at the leaves — and the directive applies to everything a component imports, so its placement is an architectural choice.
  • A server action is a public endpoint. The boundary being invisible in the code does not make it absent.
  • Data fetched on the server never travels as an intermediate JSON payload, which is a security property as much as a performance one.
F08 · Tianqi Chen

Why XGBoost is designed the way it is

The idea

Its success is systems engineering as much as statistics — regularisation in the objective, cache-aware layout, sparsity-aware splitting, and a default direction learned for missing values.

Where it applies here
  • It handles missing values natively — which does not mean you should ignore missingness, because if it is MNAR the model learns the bias faithfully.
  • It needs no feature scaling, so the absence of a scaler in the pipeline is correct rather than an oversight.
  • Early stopping is the single most effective control against overfitting, and it is a design affordance rather than an afterthought.
F09 · Addy Osmani

Performance is a distribution

The idea

There is no single "performance" number. Your users are a distribution of devices, networks and data sizes, and the average describes none of them.

Where it applies here
  • Measure on a throttled CPU and connection. An internal HR dashboard is used all day on five-year-old office machines, not on a developer laptop.
  • The tail is where the causes are — a p99 ten times the p50 usually means a distinct mechanism, often one customer with far more data.
  • And the corollary from the measurement volume: a percentile is per-request, so per-user experience is worse than it suggests, because a user makes many requests.
F10 · Camille Fournier

Management and engineering are different crafts

The idea

Management is a career change, not a promotion — a different craft whose daily work has little overlap with engineering. And the tracks are parallel, so moving between them in either direction is normal.

Where it applies here
  • A prior management role transfers judgement, communication and decision discipline — and not authority, because a tech lead argues rather than announces.
  • What has to be rebuilt is hands-on depth, which is the reason the other nine volumes exist and the reason the labs matter more than the reading.
  • And the framing to use: not "I managed people and now I want to code", but where you want your judgement applied — with the technical evidence to make it credible.
