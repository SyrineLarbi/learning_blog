The senior full-stack standard. What a senior knows, what a junior does instead.

Twelve areas of this stack, each in the same four bands: what a senior actually knows, the anti-patterns that mark a junior, the patterns worth copying, and a checklist you can run before opening a pull request. Opinionated on purpose — this is a standard, not a survey.

The mindset shift

A junior asksA senior asks
Does it work?What happens when it doesn't?
How do I build this?Should this be built, and is this the smallest version that helps?
Is the code clean?Can the next person change it safely, without asking me?
Did the tests pass?Do the tests test anything that matters?
Is it fast?Fast for whom — the median request, or the customer with 40,000 rows?
Is it secure?What does a valid request from the wrong person look like?
Did it deploy?Can I tell it is healthy, and can I undo it in one step?
The one-sentence version

A senior optimises for the second year, not the first week. Almost every standard in this document is a consequence of that: structure that survives new people, failures that are loud rather than silent, and changes that can be reversed.

Part I

Structure

Topic 01

Architecture principles

What a senior knows
  • Dependencies point one way. Controller → service → data access, and never back. A service that knows about HTTP has stopped being reusable from a job or a script.
  • Boundaries are where change is contained. The measure of a good boundary is how many files you must open to make one conceptual change.
  • The data model is the most permanent decision in the system. Code churns weekly; the nouns and their relationships persist for years, and changing them is a migration under load.
  • Every service boundary is a permanent tax — network failures, no shared transactions, distributed debugging. Pay it only for a reason you can state in one sentence.
  • Boring is a feature. The best compliment a codebase can receive is that it is unsurprising.
Anti-patterns
  • Business logic in controllers, so it cannot be called from anywhere else and cannot be tested without faking a request.
  • Shared "utils" folders that become a dumping ground nobody owns.
  • Splitting into services for architectural fashion, before there is a scaling or team reason.
  • Abstractions with a single caller, added "for flexibility" — complexity paid today for an option that expires unused.
The patterns

One folder per feature, the same six files every time. A new feature becomes a copy of an existing pattern rather than a design decision, and nobody has to ask where anything lives.

Modular monolith before microservices. Strong internal boundaries give you most of the organisational benefit with none of the network.

Before you open the PR
  • Could this service method be called from a cron job with no HTTP request in sight?
  • How many files did one conceptual change touch?
  • Is there a new abstraction with exactly one caller?
Topic 02

NestJS

What a senior knows
  • Thin controllers, fat services. The controller reads the request, calls a service, returns. Nothing else.
  • The request lifecycle order is fixed and knowable: middleware → guards → interceptors → pipes → handler → interceptors → filters. It tells you exactly where a cross-cutting concern belongs.
  • Guards run before pipes — so authorisation is decided before the body is validated. That is deliberate, and it means a guard cannot rely on a parsed DTO.
  • Every throw ends in the exception filter, which is why a service can throw NotFoundException and never think about HTTP.
  • Providers are singletons. Which is why you never write new PrismaClient() in a service — you would get twenty connection pools.
Anti-patterns
  • Querying Prisma directly from a controller. It works, and it puts a database call where no job, test or socket handler can reuse it.
  • Forgetting ParseIntPipe on a path parameter: it arrives as a string, typing it : number does not convert it, and the id comparison silently fails.
  • Repeating the same permission check in forty handlers instead of writing one guard.
  • Reaching for @Global() to avoid thinking about module imports, hiding the dependency graph.
The patterns

A custom @CurrentUser() decorator so controllers read the authenticated user without touching the request object.

A global ValidationPipe with whitelist: true — which strips unknown properties, and is a security control rather than tidiness: it removes mass assignment entirely.

One exception filter so every failure in the application has the same response shape, a correlation id, and no stack trace for the caller.

Before you open the PR
  • Is there any business logic in a controller?
  • Does every path parameter that should be a number have a pipe?
  • Is the new endpoint's permission enforced by a guard, or by a copied if?
Topic 03

Next.js

What a senior knows
  • Server by default, 'use client' at the leaves. The directive applies to everything a component imports, so one careless placement drags a whole subtree into the browser bundle.
  • Rendering mode is inferred, not declared. Reading cookies or the current user makes a route dynamic automatically — which means a page can silently stay static and serve one user's data to another.
  • A server action is a public endpoint. It is reachable by anyone who can craft the request; "it's only called from that form" is not a control.
  • Caching defaults change between major versions. For per-user data, be explicit about no-cache rather than trusting one.
  • A layout does not re-render on navigation within its subtree — which is what keeps a sidebar's scroll position, and is the reason the app shell belongs there.
Anti-patterns
  • 'use client' at the top of the tree, so the whole app ships to the browser.
  • Fetching in a useEffect when a server component could just await — reinventing loading states, races and cancellation by hand.
  • A secret behind NEXT_PUBLIC_. That value is embedded in the bundle and readable by every visitor: it is published, not hidden.
  • Suppressing a hydration warning instead of fixing the cause — new Date(), Math.random() or localStorage in a first render.
The patterns

Fetch on the server, pass data down, mark only the interactive leaf as a client component. No effect, no loading flag, and the data never travels as an intermediate JSON blob.

loading.tsx and error.tsx per segment, scoped narrowly — one at the root means any error blanks the whole app.

Filters, tabs and page number in the URL, so a view can be shared, bookmarked and reached with the back button.

Before you open the PR
  • Which components did 'use client' actually pull into the bundle?
  • Is this authenticated route explicitly not cached?
  • Does every new server action check authentication and ownership in its own body?
Topic 04

Prisma and the database

What a senior knows
  • The ORM hides the SQL, so an inefficient query is invisible until it is slow. Query logging goes on early, not during the incident.
  • select beats include for anything user-facing: faster, and it is the mechanism that keeps a salary out of a payload.
  • @unique and relations become real database constraints — they hold against every writer, including a migration script and a console at 2 a.m. An application-level check protects only the paths that remembered.
  • A destructive migration needs three deploys, not one: add the column, move reads and writes, drop the old one later. During a rolling deploy two versions of your code are running against one database.
  • Transactions exist for the "what if it fails right here" question — and must never contain a network call, or one slow dependency holds locks and pooled connections for seconds.
Anti-patterns
  • The N+1: a loop containing an await that hits the database. Invisible in development with four rows; 201 queries in production.
  • Read-modify-write for a counter or a balance, inside a transaction, believing that makes it safe. It does not — two transactions both read the old value.
  • $queryRaw with an interpolated template literal, reintroducing SQL injection in the one place Prisma stopped protecting you.
  • Running migrate reset against anything real. It drops all data.
  • Forgetting prisma generate after a schema change, then debugging a "missing module" that is generated code.
The patterns

Let the database do the arithmetic: SET balance = balance - 80 is atomic, needs no read, and removes the race entirely. This is the fix people skip because the ORM encourages fetch-then-save.

Index what you filter, join and order by — and note that Postgres does not create an index for a foreign key automatically, which is a common cause of slow joins.

Store the value that was true at the time when history must not change. Joining to the current department means last quarter's report silently rewrites itself after a reorganisation.

Before you open the PR
  • Is there a loop with a database call inside it?
  • Does this migration drop or rename anything that running code still uses?
  • Is any raw SQL built by string concatenation?
  • Does this response include a field the caller should not see?
Topic 05

API design

What a senior knows
  • Is it safe to call twice? The most important API question. Networks retry whether or not you designed for it, users double-click, and phones re-send.
  • The response shape is a contract. An endpoint returning a bare array cannot later gain a pagination wrapper without breaking every caller — so paginate from the first commit, even with nine rows.
  • Which changes are breaking: removing a field, renaming one, narrowing a type, making an optional field required. Adding an optional field is not. Know which category you are in before shipping.
  • Errors are part of the interface. Changing an error code breaks clients as surely as removing a field.
  • 401 means unauthenticated; 403 means known and not permitted. And for "exists but not yours", 404 is often correct — a 403 confirms the record exists, which is itself a leak.
Anti-patterns
  • Returning 200 with {"error": "..."} in the body. Every retry policy, monitor and load balancer believes the status code, so your failures are invisible to all of them.
  • Verbs in paths — /getEmployees, /createReport. The method is already the verb.
  • An unpaginated list endpoint. A future incident with a scheduled date.
  • Nesting four levels deep, so the URL encodes a hierarchy that will change.
  • A bulk endpoint that cannot express partial success — 40 of 50 updated, and the response says nothing.
The patterns

A caller-supplied idempotency key on anything that moves money, sends a message or starts a job, so the second attempt returns the first result.

Cursor pagination for large or growing lists — stable under writes and fast at any depth, unlike offset.

Generated documentation from the DTOs, so the contract cannot drift from the code.

Before you open the PR
  • What happens if this endpoint is called twice with the same payload?
  • Is this change breaking for any existing caller?
  • Does the list endpoint return an envelope with a cursor?

Topic 06

Security

What a senior knows
  • The vulnerability people actually ship is broken access control — a correctly formed request from a logged-in user carrying someone else's id, which the code happily serves.
  • Authentication is not authorisation, and a role is not ownership. "Managers may view employees" is true; this manager may only view their team.
  • The UI is not a security boundary. Anything the browser can do, a person can do without the browser.
  • Per-field permissions, not per-page. One endpoint returning "the employee" returns the salary and the sickness record too, whatever the UI displays.
  • A JWT's payload is readable — base64 is encoding, not secrecy. And it cannot be revoked, which is why expiry is short.
  • Git history is forever. A secret committed and removed in the next commit is still published; the only remedy is rotation.
Anti-patterns
  • Trusting an id from the client because the UI only ever sends the right one.
  • allow_origins=["*"] or a disabled certificate check, added locally to make an error go away, shipped to production.
  • Distinguishing "no such user" from "wrong password" — which tells an attacker which emails are registered.
  • Returning a stack trace or SQL fragment to the caller as a debugging convenience.
  • Personal data in log lines, which are readable by more people and retained longer than your database.
The patterns

One path everything traverses. A check repeated in forty handlers will be missing from the forty-first, written on a Friday. A guard, a single query helper, or a database constraint holds forever.

Type the boundary: Omit<Employee, 'salary'> makes the public shape explicit rather than accidental.

Log the detail, return an identifier. "Error ref 8f2c1a" lets support find everything and discloses nothing.

Before you open the PR
  • Every id from outside — is it checked against the caller, on this path?
  • Does anything new escape the system: a log line, an export, an email, a prompt?
  • Was anything weakened to make a test or a local run pass?
Topic 07

Testing strategy

What a senior knows
  • Integration tests are the best value per test in a web application. Most defects live in the seams — a missing permission check, a wrong join, a validation that did not fire — and a unit test of a mocked service cannot see any of them.
  • Test behaviour, not implementation. A test that must be rewritten every time you tidy the code is a tax on improvement, and eventually the team stops improving.
  • Coverage measures execution, not verification. A test that calls a function and asserts nothing gives 100% coverage of it.
  • A flaky test destroys the suite's value — once failures are assumed to be noise, nothing is being caught.
  • Mock the boundary, not your own database. Mocking Prisma tests that you called Prisma the way you thought you should.
Anti-patterns
  • Chasing a coverage number, producing tests for getters and mappers while the risk engine stays untested.
  • Tests that depend on execution order or on state left by a previous test — fine locally, broken when the runner parallelises.
  • Trusting generated tests for generated code: both encode the same guess and agree with each other.
  • Asserting on exact UI markup, so every restyle breaks the suite.
  • Real clocks and real timers, so a test fails at midnight or on 29 February.
The patterns

One integration test per endpoint with four assertions: the happy path works, an unauthenticated caller gets 401, a wrong-owner caller gets 403, invalid input gets 400. Those four cover what most often breaks and survive refactors.

Every bug becomes a test, so the class cannot return.

Freeze the clock and seed randomness in anything time- or chance-dependent.

Before you open the PR
  • Would these tests fail if the behaviour were wrong — or only if the code were restructured?
  • Is the permission boundary covered?
  • Did I write at least one assertion from the requirement rather than from the code?
Topic 08

Performance

What a senior knows
  • Measure first. Intuition about performance is unreliable — the things that feel expensive are usually cheap, and round trips that feel free are usually not.
  • Percentiles, not averages. "Average 200 ms" with a p99 of 8 seconds means one user in a hundred has a terrible time, and the average will never say so.
  • Round trips, not CPU, make ordinary business software slow. Fifty sequential 5 ms queries is 250 ms of pure waiting.
  • The fastest query is the one you don't run. Removing work beats optimising it.
  • Define the target before starting, or optimisation has no stopping condition and the code gets worse.
  • Dev data hides everything. Four rows conceal every N+1, every missing index and every unbounded list.
Anti-patterns
  • Adding a cache in front of an N+1 — which hides the defect until the cache misses, and then you have two problems.
  • Sequential awaits for independent calls, doubling latency for no reason.
  • Fetching 50,000 rows to sort and take ten in application code, instead of ORDER BY … LIMIT with an index.
  • useMemo everywhere without measuring — memoisation has its own cost.
  • Lifting form state high enough that every keystroke re-renders half the page.
The patterns

The order that works: fix the query → add the index → remove the round trips → then cache. Caching first buys speed and keeps the defect.

Move unbounded work out of the request — a report, an import, a model call over many records. Accept, enqueue, notify.

Before adding a cache, answer: how wrong may this be, and for how long? If the answer is "not at all", a cache is the wrong tool.

Before you open the PR
  • Did I measure, or guess?
  • How does this behave at realistic data volume?
  • Is there anything unbounded — a list, a loop, an upload — whose size I do not control?

Topic 09

Observability and debugging

What a senior knows
  • You cannot add observability during an incident. "What happened at 02:14?" is answerable only if the answer was being recorded at 02:14.
  • Metrics say something is wrong; traces say where; logs say why. A team with only logs finds out late and greps blindly.
  • A correlation id is the cheapest win available — twenty lines of middleware, and one grep reconstructs a request across all three services.
  • Mitigate first, diagnose second. While users are affected: roll back, disable the flag, fail over. A rollback you can explain later beats a root cause found while the site is down.
  • Structured logs, not prose. Sentences are ungreppable at volume.
  • An error logged at info is a bug you will find in six months via a customer.
Anti-patterns
  • Catching everything and continuing, turning a loud failure into silent wrong data — the most expensive kind, because nobody knows to look.
  • Restarting the box before capturing logs, metrics and state, removing the only chance to know why.
  • Alerting on CPU rather than on user-visible failure, then ignoring the channel.
  • Debugging by changing three things at once, so the result teaches nothing.
  • Stopping at "it works now" without tracing cause to symptom — the bug returns under load.
The patterns

Bisect in space, time and scope. Is the data already wrong when it arrives? What changed at that time? What do the affected cases have in common? The third question usually ends the investigation.

Four metrics per service: request rate, error rate split 4xx/5xx, latency percentiles, and saturation — the pool, the queue depth, memory. Saturation is the leading indicator.

Close the class, not the instance. After every bug ask what made it possible, and move the fix one rung up: a comment → a test → a type → a constraint.

Before you open the PR
  • Could I reconstruct one user's request from the logs alone, without adding anything?
  • Does any new catch block swallow an error?
  • Is there a log line containing personal data or a token?
Topic 10

Deployment and CI/CD

What a senior knows
  • The pipeline is the only way code reaches production. The moment someone can deploy from a laptop, the state of production becomes unknowable.
  • Build once, promote the same artefact. Rebuilding per environment means you tested something you did not ship.
  • Tag images with the commit SHA, never latest — otherwise "which code is in production?" and "what do I roll back to?" have no answer, which is exactly what you need during an incident.
  • During any zero-downtime deploy, two versions run against one database. Every migration must be compatible with the version still running.
  • A deploy that completes is not a deploy that worked. Check the error rate automatically for a few minutes afterwards.
  • Deploy when the people who can roll it back are available. Not superstition — the fix window matters as much as the deploy.
Anti-patterns
  • A migration that drops or renames a column in the same deploy as the code change.
  • Secrets echoed into a pipeline log, which is widely readable and retained.
  • Ordering pipeline stages by importance rather than by speed, so a type error surfaces after eight minutes of tests.
  • Re-running a flaky suite until it passes, which is how a real regression reaches production.
  • No way to disable a feature without a deploy.
The patterns

Expand → migrate → contract for any destructive schema change: add the new column, move reads and writes over, drop the old one in a later deploy.

Feature flags separate deploy from release — ship the code disabled, enable it when ready, disable it instantly if wrong.

Cheap checks first — lint, types and unit tests in parallel before the slow suite. Target under ten minutes to a merge decision.

Before you open the PR
  • Is this migration safe with the previous version of the code still running?
  • Can this change be turned off without a deploy?
  • Can it be undone in one step — and if not, is that stated in the description?

Topic 11

The mistakes list, by area

The consolidated version — the things that most reliably mark work as junior, grouped the way the source file groups them.

Architecture

Logic in controllers · a utils dumping ground · services that know about HTTP · abstractions with one caller · splitting into services with no stated reason.

TypeScript

any to silence an error · as instead of a check · ! to dismiss a possible undefined · types duplicated instead of derived · trusting an annotation on data that arrived over a network.

Frontend

key={index} on a list that reorders · mutating state instead of replacing it · deriving values into state instead of computing them · effects with no cleanup · filters kept in memory instead of the URL.

Backend

Missing ownership checks · no DTO or no whitelist · swallowed errors · unbounded list endpoints · long work inside a request.

Database

N+1 queries · read-modify-write races · missing indexes on foreign keys · destructive migrations in one deploy · select * returning fields the caller may not see.

Security

Trusting client-supplied ids · secrets in the repo or the bundle · stack traces returned to callers · * CORS in production · personal data in logs.

Testing

Coverage as a target · order-dependent tests · mocking your own database · asserting on markup · no test for the permission boundary.

Performance

Optimising without measuring · caching over a defect · sequential independent awaits · sorting in application code · testing against four rows.

Operations

No correlation id · alerting on CPU · latest tags · no rollback path · no way to turn a feature off.

Code hygiene

Commented-out code left in · commit messages that say "fix" · a PR mixing a refactor with a fix · names that need a comment · dead configuration nobody sets.

Process

Silence when an estimate slips · accepting a request at face value · changing code you do not understand · merging something you could not have written.

The meta-rule

Almost every entry above is the same mistake: optimising for this week instead of the second year — and making a failure quiet instead of loud.

Topic 12

Code review standards

What a senior looks for, in order
  1. Does it do the right thing? Read the description, then the code, and check they match. The most expensive defect is a correct solution to the wrong problem.
  2. Authorisation. Every id from outside, checked against the caller, on this path.
  3. The edge cases — zero, one, many, null, twice, order, race, hostile input, halfway.
  4. What else does this change? A changed default, error case or response shape — visible only in the diff, not in the new file.
  5. Migrations and anything irreversible, which deserve disproportionate attention.
  6. Complexity — a one-caller abstraction, config nobody sets, a clever line a tired person would misread.
  7. Names and clarity. Suggesting a rename is the highest value per second in review.
How reviews go wrong
  • Spending the review on formatting and import order — attention taken from points 1–4. Automate all of it.
  • Unlabelled comments, so twelve nits read as a rejection.
  • Rhetorical questions: "why didn't you use a transaction?" reads as an accusation. Text has no tone.
  • Blocking on preference, which makes the reviewer a bottleneck people route around.
  • Rewriting the change in comments instead of talking.
  • Approving a large generated diff nobody has read, because it looks tidy.
The PR description that makes review fast

What changed · why · how to test · risks · rollback — plus what you deliberately did not do, and what a reviewer should look at hardest. Four or five sentences that make a review twice as good and half as long.

Label every comment: blocking · suggestion · question · nit · praise. And if it is not blocking, do not block on it — approve with suggestions.

Say the failure, the consequence, then a suggestion. "If the AI call fails after the report row is written, we're left with a report that has no predictions. Wrap both in a transaction?"

What a senior-level PR looks like
  • Small enough to review properly, and one logical change.
  • A description that answers why, and names the risk.
  • Tests that would fail if the behaviour were wrong.
  • Migrations separated and reversible, or explicitly flagged as not.
  • Nothing in it the author could not explain.

The operating principles

The whole document, compressed to twelve lines
①  DEPENDENCIES POINT ONE WAY. Controller → service → data.
②  THE DATA MODEL IS THE MOST PERMANENT DECISION. Design it
   before creating it.
③  ENFORCE IT WHERE EVERY PATH MUST PASS. A guard, a single
   query helper, or a database constraint — never a convention.
④  ⭐ EVERY ID FROM OUTSIDE IS A CLAIM, NOT A FACT.
⑤  SHAPE THE RESPONSE PER REQUESTER. `select`, not `include`.
⑥  ASSUME EVERY WRITE WILL BE RETRIED. Make it idempotent.
⑦  TWO VERSIONS RUN AT ONCE. Expand, migrate, contract.
⑧  MEASURE BEFORE OPTIMISING, AND AT REALISTIC VOLUME.
⑨  FAIL LOUDLY. A swallowed error is a silent wrong number.
⑩  LOG A CORRELATION ID, RETURN AN IDENTIFIER.
⑪  ⭐ CAN IT BE TURNED OFF, AND CAN IT BE UNDONE? If not, say so
   in the description.
⑫  CLOSE THE CLASS, NOT THE INSTANCE. Move every fix one rung
   up: comment → test → type → constraint.
