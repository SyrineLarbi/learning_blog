Topic 17 · three prior lines of coverage

MariaDB and InnoDB internals

⭐ THE ONE FACT THAT EXPLAINS MOST INNODB BEHAVIOUR: THE PRIMARY KEY *IS* THE TABLE. InnoDB uses a CLUSTERED INDEX — rows are stored inside the primary key's B-tree, in key order. There is no separate heap. PRIMARY KEY B-TREE ┌──────────────────────────────────────┐ │ leaf pages contain THE ENTIRE ROW │ └──────────────────────────────────────┘ SECONDARY INDEX B-TREE ┌──────────────────────────────────────┐ │ leaf pages contain the indexed value │ │ + THE PRIMARY KEY │ └──────────────────┬───────────────────┘ │ ⭐ then a second lookup into the ▼ primary key tree to get the row the row ⇒ FOUR CONSEQUENCES YOU CAN BE ASKED ABOUT ① SECONDARY-INDEX LOOKUPS COST TWO TRAVERSALS unless the index covers every column the query needs. ⭐ THAT IS WHY A COVERING INDEX IS SO MUCH FASTER HERE — it skips the second lookup entirely. ② A LARGE PRIMARY KEY BLOATS EVERY SECONDARY INDEX, because each one stores a copy of it. A UUID primary key is measurably worse than an integer for this reason. ③ RANDOM PRIMARY KEYS CAUSE PAGE SPLITS. Sequential inserts append to the end of the tree; random ones insert into the middle, splitting pages and fragmenting storage. ⇒ AND THIS IS THE REAL ARGUMENT AGAINST RANDOM UUIDs AS PRIMARY KEYS in MySQL/MariaDB — not aesthetics. ④ RANGE QUERIES ON THE PRIMARY KEY ARE FAST because the rows are physically adjacent. THE OTHER INTERNALS WORTH KNOWING BUFFER POOL the in-memory cache of pages. ⭐ THE SINGLE MOST IMPORTANT CONFIGURATION VALUE — if the working set does not fit, everything is disk-bound and no query tuning saves you. REDO LOG writes go to the log first, then to pages lazily. Which is why a commit is fast and why a crash recovers. UNDO LOG / MVCC readers see a consistent snapshot without blocking writers. GAP LOCKS ⚠ MariaDB/MySQL at REPEATABLE READ locks RANGES, not just rows — so two inserts into the same gap can deadlock where you would not expect it. This is a genuine difference from Postgres and a good senior question. ⚠ AND THE MIGRATION TRAP: an `ALTER TABLE` on a large table can hold a lock long enough to be an outage, even when the change itself is trivial. ⭐ CHECK WHETHER IT IS AN ONLINE OPERATION BEFORE RUNNING IT IN PRODUCTION.
Topic 18 · the CV claim

The optimisation case study

What this topic is for

This is the "50 seconds to 6 seconds" claim, worked end to end so it becomes a method you can narrate rather than an outcome you assert. Volume 01 covered what a number must carry; this is the shape of the investigation itself.

The investigation, in order
  1. Reproduce it with a real trace. Not a memory. And record the conditions — data volume, concurrency, cache state — because the before number is worthless without them.
  2. Count the queries first. Query logging with a count, before reading any SQL. If one request issues 1,400 queries, that is the answer and no plan analysis is needed.
  3. Then read the plan for the worst single query. Sequential scan on a large table; estimated versus actual rows; the join strategy; whether a sort spilled to disk.
  4. Fix one thing. Measure again under the same conditions. Repeat.
  5. Stop when it is fast enough — against a target defined before starting, not when it stops improving.
  6. Leave something behind that would notice a regression: a logged duration, an alert, or at minimum a committed benchmark script.
The four wrong turns worth admitting to
  • Adding a cache first. It hid the N+1 until the cache missed, and then there were two problems and one was invisible. Volunteering this is a positive signal — clean narratives sound rehearsed, and nobody's debugging is clean.
  • Adding an index that was not used, because the query had a function on the column or the filter was not a left-most prefix.
  • Optimising the wrong query — the one that felt expensive rather than the one the trace named.
  • Measuring on development data, where the whole table fits in memory and no N+1 is visible.
The four questions this claim invites

What was the actual bottleneck · how did you find it · what did you try that failed · how do you know it stayed fixed. Answer all four and the claim is your strongest asset; answer two and it damages you more than its absence would.

Topic 19

Prisma transactions and migrations

The semantics behind the convenient API
TRANSACTIONS — two forms, different guarantees
  SEQUENTIAL ARRAY   `$transaction([...])`
                     runs the operations in one transaction.
                     Simple, and you cannot branch on an
                     intermediate result.
  INTERACTIVE        `$transaction(async tx => { ... })`
                     you get a client scoped to the transaction
                     and can make decisions inside it.
                     ⚠ AND IT HOLDS A CONNECTION AND LOCKS FOR
                       AS LONG AS THE CALLBACK RUNS.

⭐ SO THE RULE: NEVER PUT A NETWORK CALL INSIDE AN INTERACTIVE
  TRANSACTION. Waiting on the AI service while holding locks and
  a pooled connection is how one slow dependency becomes a
  database-wide outage. Compute first, then transact.

⚠ AND WHAT A TRANSACTION DOES *NOT* FIX: the read-modify-write
  race. Two transactions both read 100, both write 20, and one
  update is lost — at Postgres's default isolation this is
  permitted. ⭐ LET THE DATABASE DO THE ARITHMETIC
  (`balance = balance - 80`), or use a version column, or
  `SELECT … FOR UPDATE` briefly.

MIGRATIONS — what the commands actually do
  `migrate dev`     generates SQL from the schema diff, applies
                    it locally, regenerates the client.
                    ⚠ CAN PROMPT TO RESET, WHICH DROPS ALL DATA.
  `migrate deploy`  applies pending migrations only. Never
                    generates. ⭐ THIS IS THE ONLY ONE THAT
                    TOUCHES PRODUCTION.
  `migrate diff`    generates SQL without applying — useful for
                    review, and for hand-editing a destructive
                    change.
  `db push`         syncs schema with no migration file.
                    Prototyping only; it leaves no history.

⭐ THE PRODUCTION SEQUENCE FOR ANYTHING DESTRUCTIVE:
  EXPAND → MIGRATE → CONTRACT, across three deploys. During a
  rolling deploy two code versions run against one database, so
  a rename in one step breaks the instances not yet replaced.

⚠ PRISMA 7 SPECIFICS THIS PROJECT HIT
  · the connection `url` moved OUT of the datasource block into
    `prisma.config.ts`
  · the client requires a DRIVER ADAPTER — `new PrismaClient({
    adapter })` with `@prisma/adapter-pg`
  · seed config lives inside `migrations` as a string
  · `dotenv` is a separate install for the config file
  · ⭐ THE CLIENT IS GENERATED CODE — `prisma generate` after
    every schema change and every fresh install

AND THE PERFORMANCE FACTS
  · `select` beats `include` — faster, and it is the mechanism
    that keeps a salary out of a payload
  · relation loading is often a second query, not a join —
    which is why query logging matters more than reading the API
  · `createMany` skips relations and returns a count, not rows
Topic 20

Redis beyond caching

The layer this adds

Most people describe Redis as a cache. It is a single-threaded server of data structures, and that framing explains both what it is excellent at and where it hurts you.

What it is actually for, in this stack
  • The queue's backing store — BullMQ's lists and hashes, from Volume 03.
  • The Socket.io adapter's pub/sub channel, which is what makes multi-instance realtime work at all.
  • Rate-limit counters — INCR with an expiry is the canonical implementation, and it is atomic without a transaction because the server is single-threaded.
  • Distributed locks, with the important caveat: a lock needs an expiry so a crashed holder releases it, and a token so you only delete your own. Getting this subtly wrong is common, which is why the safest use is "prevent duplicate work" rather than "guarantee mutual exclusion for correctness".
  • Idempotency keys — store the key with the first result, return it on a repeat.
  • Sessions and short-lived state, where losing it is inconvenient rather than incorrect.
Where it goes wrong
  • Single-threaded means one slow command blocks everything. KEYS * on a large database is a stall for every other client — use SCAN. So is a big Lua script or a huge DEL.
  • No eviction policy and no memory limit, so it fills and then fails. A cache with unbounded growth is a memory leak with a helpful name.
  • Treating it as durable. Persistence is configurable and asynchronous; a crash can lose recent writes. Never make it the system of record.
  • A cache key that omits the user or scope — the dangerous one. One user's filtered data served to another, and in an HR system that is an incident rather than a bug.
  • No stampede protection. A popular key expires and a thousand requests all miss and all recompute. Lock one refresh, or stagger expiries with jitter.
The question you must be able to answer

"Redis restarts. What breaks, and what recovers?" — queued jobs may survive depending on persistence, sockets reconnect but lose their gap, rate-limit counters reset, caches simply refill. Naming which of those is a correctness problem and which is only a performance one is the answer.

Topic 21 · zero prior coverage

MongoDB for the relational developer

The layer this adds

Zero prior coverage of driver-level MongoDB. The shift that matters: you model for the queries you will run, not for normalised truth — and "schemaless" means the schema lives in your application code, unenforced.

The mechanism
  • Embed versus reference. Embed when the data is read together and bounded — an address inside a person. Reference when it is large, unbounded, or shared. The unbounded array is the classic mistake: a document grows until it hits the size limit, and it cannot be paged internally.
  • Indexes work the same way as elsewhere, including compound-prefix rules. And the same trap: a query that cannot use an index does a collection scan.
  • The aggregation pipeline is the real query language — $match early to reduce documents, then $group, $lookup for a join-like step, $project to shape. $match before $lookup is the performance rule, and it is the same instinct as filtering before joining in SQL.
  • Transactions exist across documents, and they are more expensive than a single-document write — which is atomic by default, and is the reason embedding can remove the need for one.
  • Write concern and read preference are the durability and consistency dials: acknowledging from the primary only versus a majority, and reading from a secondary at the cost of staleness.
Where it goes wrong
  • Modelling relationally — many small collections joined with $lookup — which gives you the costs of both models and the benefits of neither.
  • No schema validation at all, so three shapes of the same document accumulate and every reader must handle all three.
  • An unbounded embedded array.
  • Assuming a secondary read is current.
The question you must be able to answer

"When would you choose Mongo over Postgres for this project?" — the honest answer is rarely: the data is relational, permissions are per-field, and reporting is SQL-shaped. It earns a place for genuinely document-shaped, schema-varying data where you can name the query pattern in advance.

Topic 22 · zero prior coverage

Typesense and search engineering

The layer this adds

The concept that matters is not the product: search is a second copy of your data with its own consistency, ranking and permission problems. Adopting a search engine means taking all three on.

The mechanism
  • Why not LIKE '%term%': a leading wildcard cannot use a B-tree index, so it is a full scan. And it cannot do typo tolerance, relevance ranking, stemming or field weighting — which is what people actually mean by "search".
  • An inverted index maps each token to the documents containing it, which is why a term lookup is fast and why the index must be built and maintained separately.
  • Typo tolerance is edit-distance matching, and it is the feature that makes internal search feel usable — people misspell colleagues' names constantly.
  • Ranking is configuration, not magic. Field weights, tie-breakers, and explicit rules. Relevance is a product decision, and "search is bad" almost always means the weights are wrong rather than the engine is.
  • Faceting gives you the counts-per-category that make a filter UI usable.
  • Indexing strategy: a full reindex is simple and idempotent; incremental is fast and has the same four failure modes as any incremental load — boundary, clock skew, silent updates, and deletes, which do not appear in "what changed" and so linger in the index forever.
Where it goes wrong
  • Permissions. The index is a second copy, so it must be filtered per requester too — otherwise search becomes the way to discover records you cannot open. In an HR system this is the whole risk of adopting search.
  • Indexing sensitive fields that then appear in a highlighted snippet.
  • No reconciliation, so the index and the database silently diverge and nobody knows which is right.
  • Adopting a search engine for a dataset a well-indexed WHERE clause would serve.
The question you must be able to answer

"How do you stop search returning employees the searcher may not see?" — a scoped filter applied server-side on every query, derived from the verified session, plus care about which fields are indexed at all. If the answer is "we filter the results afterwards", the counts and the paging are already wrong.
