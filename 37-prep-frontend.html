Topic 12 · zero prior coverage

App Router: the missing half

The layer this adds

The onboarding handbook covers routing, layouts and server versus client components. The missing half is the cache and mutation model — revalidation, server actions, and streaming — which is where the App Router's real behaviour lives and where its security surface is.

The mechanism
  • Server actions are public endpoints. A function marked 'use server' gets an id and is reachable by anyone who can craft the request. "It is only called from that form" is not a control — it needs authentication and an ownership check in its own body, exactly like a REST route.
  • Revalidation is how the cache is invalidated after a mutation. By path, or by tag when several routes derive from the same data. The tag approach is what stops a mutation needing to know every page that displays it.
  • ISR is static plus a timer. Rendered at build or first request, rebuilt after N seconds. Right for content that changes but is not per-user — wrong for anything showing one person's data.
  • Rendering mode is inferred, not declared. Reading cookies, headers or the current user makes a route dynamic automatically. So an authenticated page can silently stay static, which is how one user's data gets served to another.
  • Streaming and Suspense let the shell render while a slow part resolves — the correct answer to "the AI summary panel is slow", rather than blocking the page.
  • Route handlers exist for the cases a server action does not fit: webhooks, file responses, and anything a non-browser client calls.
Where it goes wrong
  • A server action with no auth check, because the form is behind a login.
  • Relying on a caching default that changed between major versions. For per-user data, be explicit about no-cache rather than trusting inference.
  • Mutating and not revalidating, so the UI shows stale data until a hard refresh.
  • 'use client' placed high, dragging a whole subtree — and anything it imports — into the browser bundle.
  • Suppressing a hydration warning instead of fixing the cause: new Date(), Math.random(), localStorage, or a timezone difference in the first render.
The question you must be able to answer

"What stops someone calling your server action directly with a different employee id?" — only a check inside the action. If your answer is the form, that is the vulnerability.

Topic 13

Rendering and memoisation decisions

When memoisation helps, and when it is cost with no benefit
⭐ THE MODEL: A COMPONENT RE-RENDERS WHEN ITS STATE CHANGES, ITS
  PARENT RE-RENDERS, OR ITS CONTEXT VALUE CHANGES. Re-rendering
  is not itself expensive — it is cheap for most components. The
  expense is a large subtree, or real work inside render.

SO THE ORDER OF FIXES IS:
  ①  MOVE STATE DOWN. If only one input cares about a value,
     it should not live three levels up. ⭐ THIS FIXES MOST
     "TYPING IS LAGGY" PROBLEMS AND COSTS NOTHING.
  ②  SPLIT THE COMPONENT so the changing part is small.
  ③  STABILISE VALUES that are recreated inline each render —
     an object or array literal passed as a prop is a new
     reference every time, which defeats any memoisation below
     it.
  ④  SPLIT WIDE CONTEXTS by change frequency. A rarely-changing
     user context and a frequently-changing UI context should
     not be the same provider, or every consumer re-renders on
     every keystroke.
  ⑤  ⭐ ONLY THEN MEMOISE, AND ONLY AFTER MEASURING.

⚠ WHY `useMemo` EVERYWHERE IS A REAL COST
  · it allocates and compares dependencies on every render
  · a wrong dependency array produces a STALE VALUE — a
    correctness bug traded for imagined speed
  · it makes the code harder to read for no measured gain
  ⇒ AND IT IS NOT FREE: the comparison itself runs every time.

WHERE MEMOISATION GENUINELY PAYS
  · a large list where each row would otherwise re-render
  · an expensive derived computation over a big array
  · a callback passed into a memoised child, where a new
    function identity would defeat the memo
  ⇒ ⭐ IN THIS PROJECT: THE TABLE. Rebuilding the columns array
    inline on every render re-renders the whole table — define
    it outside the component or memoise it. That one is real.

⭐ AND THE MEASUREMENT POINT: PROFILE FIRST. React's profiler
  tells you what re-rendered and why. Guessing produces
  memoisation in the wrong places and leaves the actual cause.
Topic 14 · three prior lines of coverage

TanStack Query

The layer this adds

It is usually described as "data fetching". It is not — it is a cache with a lifecycle, and every question about it is really a question about that cache.

The mechanism
  • The query key is the cache identity. Include every variable the result depends on — the filters, the page, the scope. A key that omits a filter serves one filter's data for another, which in an HR app can be a permissions leak rather than a cosmetic bug.
  • staleTime versus gcTime. Stale time is how long the data is considered fresh — while fresh, no refetch happens at all. Garbage-collection time is how long an unused cache entry is kept. Confusing these two is the most common source of "why is it refetching constantly".
  • Stale-while-revalidate is the default behaviour. You get cached data immediately and a background refetch — which is why the UI feels instant and why a "loading" flag is often the wrong thing to show.
  • Invalidation after a mutation is the counterpart to revalidation on the server: mark the affected keys stale and let them refetch.
  • Optimistic updates need a rollback path. Write the expected result, keep the previous value, restore it on error. Skipping the rollback is how a failed save leaves a UI claiming success.
  • Deduplication. Three components asking for the same key produce one request — which is why it removes a class of waterfall without any coordination.
Where it goes wrong
  • An incomplete query key. The defect of record.
  • Copying query data into local state to edit it — the copy goes stale and the save overwrites someone else's change.
  • Using it in a server-component world where a plain await would do. It earns its place for client-side interactive data, not for the initial render of a server-rendered page.
  • No staleTime at all, so every mount refetches and the network tab looks alarming.
The question you must be able to answer

"A user changes the department filter and briefly sees the previous department's employees. What happened?" — the query key did not include the filter, so both requests share a cache entry.

Topic 15 · zero prior coverage

React Hook Form and Zod

The layer this adds

Both were at literal zero in the existing docs. The idea worth understanding: RHF minimises re-renders by keeping form state out of React where it can, and Zod lets one schema produce both the validation and the TypeScript type.

The mechanism
  • Uncontrolled by default. RHF registers inputs and reads their values on submit rather than re-rendering on every keystroke — which is why a large form stays responsive. watch and useWatch opt into subscriptions where you actually need live values, and useWatch is the narrower one.
  • One schema, two outputs. A Zod schema validates at runtime and infers the TypeScript type. That is the fix for the erased-types problem: instead of an annotation you hope is true, you have a validator and a type derived from the same definition.
  • The resolver connects them, so field errors come from the schema rather than from hand-written rules — which means the rules exist in one place.
  • Server errors mapped back onto fields. setError per field, so a 400 from the API appears next to the input rather than as a toast that has lost its context.
  • Coercion and transformation belong in the schema — a date string to a Date, a numeric string to a number — so the parsed output is the shape your code expects.
Where it goes wrong
  • Believing client validation protects anything. It is feedback. The API's DTO is what protects the system, and it must repeat every rule that matters — a request does not have to come from your form.
  • Mixing a controlled value/onChange onto an input inside a form library, giving two owners of one value.
  • watch() on the whole form, which reintroduces the re-render-per-keystroke problem the library exists to avoid.
  • Clearing the form on a failed submit, which is a small cruelty and loses the user's work.
  • No disabled state while submitting, so a double-click creates two records.
The question you must be able to answer

"Where does validation happen in your app, and why in more than one place?" — the browser for feedback, the API for correctness, the database for invariants. Three layers, and only the middle one is a control. That duplication is deliberate and correct.

Topic 16

antd tables at scale, and accessibility

The layer this adds

The onboarding handbook covers the component. The layer underneath is the decision that bites later — whether sorting, filtering and paging happen in the browser or in the database — plus the accessibility obligations of an internal tool.

The mechanism
  • Client-side is the default and it is a trap past a few hundred rows. antd will sort and filter whatever array you passed — delightful for 200 rows, and for 50,000 it means downloading 50,000 rows to display ten. Retrofitting server-side paging changes every call site, so decide at the start.
  • Server-side means passing total explicitly and handling sort and filter parameters in the API — which then needs a stable ORDER BY with a unique tie-breaker, or rows repeat and vanish between pages.
  • rowKey is not optional. Same rule as a React key: without a stable id, selection and expansion attach to the wrong rows after a sort or a delete.
  • Columns are data, not markup — which is how you show a salary column to HR and omit it for a team lead. And the server must still omit the field: a column you did not render is still in the payload.
  • Virtualisation for genuinely long lists, and the honest prior question: does anyone need 5,000 rows on one screen, or do they need a better filter?
  • Accessibility is a real obligation here. Internal tools are used all day by people who may rely on keyboard navigation or a screen reader. antd gives you a great deal for free — but custom cell renderers, icon-only buttons and colour-only status indicators break it. Colour alone is never the signal; pair it with text or a shape.
Where it goes wrong
  • Rebuilding the columns array inline every render, re-rendering the entire table.
  • Client-side paging over a growing dataset, discovered when a customer grows.
  • Icon-only action buttons with no accessible label.
  • A red/green risk indicator with no text, unreadable for a colour-blind user — and this is an HR risk score, so it matters.
The question you must be able to answer

"This table works for 200 employees. What changes at 50,000?" — server-side sort, filter and paging with a stable tie-breaker, a considered page size, and the recognition that the payload shape is a contract you are now committed to.
